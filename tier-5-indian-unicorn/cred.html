1 Number of Islands
dfsbfsunion-find
Medium 92%
Approach
DFS or BFS. When land cell found, increment count and DFS to mark all connected land as visited.
Solution
def numIslands(grid):
    if not grid: return 0
    count = 0
    def dfs(r, c):
        if r < 0 or r >= len(grid) or c < 0 or c >= len(grid[0]): return
        if grid[r][c] != '1': return
        grid[r][c] = '0'  # mark visited
        for dr, dc in [(0,1),(0,-1),(1,0),(-1,0)]:
            dfs(r+dr, c+dc)
    for r in range(len(grid)):
        for c in range(len(grid[0])):
            if grid[r][c] == '1':
                count += 1; dfs(r, c)
    return count
Union-Find alternative
find with path compression + union by rank. O(α(n)) per operation. Good for streaming updates.
Complexity
Time: O(m×n) | Space: O(m×n) recursion stack

def lengthOfLongestSubstring(s):
    seen = {}; l = res = 0
    for r, c in enumerate(s):
        if c in seen and seen[c] >= l:

1 Design Twitter/X timeline — fan-out on write vs fan-out on read

Approaches
  • Fan-out on Write (Push): When user tweets, push tweet ID to all followers' home timeline caches (Redis sorted sets). Read is fast (O(1) from cache). Write is expensive for users with millions of followers (celebrities).
  • Fan-out on Read (Pull): On timeline load, fetch tweets from all followed users, merge, sort. Write is O(1). Read is expensive (100 follows = 100 DB queries).

Storage Architecture
Tweet Service:
  - MySQL: tweet metadata (id, user_id, text, created_at)
  - Blob store (S3): media files
  - Redis: home timeline cache per user (sorted set by tweet_id)

Timeline Service:
  - Read from Redis cache
  - For celebrities: merge from DB query on read
  - Ranked feed: ML model scores tweets, inserted in order
Key Design Decisions
  • Tweet ID as Snowflake (time-sortable → no ORDER BY timestamp needed)
  • Timeline cache: Redis ZSET with tweet_id as score, cap at 800 entries

1 REST vs GraphQL vs gRPC — when to use each?
restgraphqlgrpc
Medium 90%
REST vs GraphQL vs gRPC
  • REST: Stateless, resource-based (nouns), HTTP verbs. Cacheable, universally supported. Over-fetching (get entire user object for just the name) / under-fetching (need 3 calls for related data).
  • GraphQL: Single endpoint. Client specifies exact fields. Eliminates over/under-fetching. Schema as contract. N+1 problem (use DataLoader). Good for complex UIs, mobile (save bandwidth).
  • gRPC: HTTP/2 + Protocol Buffers. Binary, strongly typed, 5-10x smaller than JSON. Bidirectional streaming. Generated client/server stubs. Best for internal microservices.
Decision Matrix
  • Public API / browser-to-server → REST
  • Complex UI with diverse data needs → GraphQL
  • Internal microservice-to-microservice → gRPC
  • Real-time bidirectional → WebSocket
Follow-ups

Kafka Architecture
  • Topic: Named category. Divided into partitions (immutable ordered log).
  • Producer: Writes to partition (by key hash or round-robin). Acks: 0/1/all.
  • Consumer Group: Each partition consumed by exactly 1 consumer in group. Multiple groups = independent reads.

Internals
  • Messages appended to segment files. Retention by time or size.
  • Consumer tracks offset in __consumer_offsets topic.
  • Exactly-once: idempotent producer + transactional API.
  • Page cache: Kafka relies on OS page cache for near-disk-speed throughput.

1 Goroutines vs OS threads
goroutinesthreadsgmp
Medium 92%
Goroutines vs OS Threads
  • Goroutine: ~2KB initial stack (grows dynamically to hundreds of MB if needed). M:N threading — N goroutines multiplexed onto M OS threads. Scheduled by Go runtime.
  • OS Thread: ~1MB stack (fixed at creation). 1:1 with kernel thread. Expensive context switch (μs).
  • Can run millions of goroutines. Thousands of OS threads = OOM.
GMP Model (brief)
  • G: Goroutine (the task)
  • M: OS thread (the runner)
  • P: Processor/scheduler context (GOMAXPROCS Ps). Each P has local run queue.
  • When G blocks on syscall → M + G detach from P → P gets another M to continue work
Follow-ups
• What is goroutine stack growth mechanism? (segmented stacks → copying stacks since Go 1.4)
• What is GOMAXPROCS and when would you change it?
• How do goroutines avoid the 10K thread problem?

2 Channels: buffered vs unbuffered
channelsbufferedsynchronous
Medium 90%
Buffered vs Unbuffered Channels
  • Unbuffered make(chan T): Sender blocks until receiver is ready. Receiver blocks until sender sends. Strict synchronization point (rendezvous).
  • Buffered make(chan T, n): Sender blocks only when buffer full. Receiver blocks only when buffer empty. Decouples send and receive timing.
Usage Patterns
// Semaphore (limit concurrency to 5):
sem := make(chan struct{}, 5)
for _, job := range jobs {
    sem <- struct{}{}  // acquire
    go func(j Job) {
        defer func() { <-sem }()  // release
        process(j)
    }(job)
}

// Signal (done channel):
done := make(chan struct{})
go func() { defer close(done); doWork() }()
<-done  // wait for completion
Closing Channels
Only sender should close. Closing a closed channel panics. Reading from closed channel returns zero value + false: v, ok := <-ch; if !ok { // closed }

6 defer, panic, recover — full semantics and patterns
deferpanicrecover
Medium 88%
defer
Deferred call runs when surrounding function returns (normal or panic). Arguments evaluated immediately; call deferred. LIFO order.
func processFile(path string) (err error) {
    f, err := os.Open(path)
    if err != nil { return }
    defer f.Close()           // runs even on early return/panic
    defer func() {            // named return: modify err on cleanup failure
        if cerr := f.Close(); cerr != nil && err == nil {
            err = cerr
        }
    }()
    // ... process f
    return
}
panic / recover
func safeDiv(a, b int) (result int, err error) {
    defer func() {
        if r := recover(); r != nil {     // recover() catches panic
            err = fmt.Errorf("panic: %v", r)
        }
    }()
    return a / b, nil  // panics if b==0
}

// recover() returns nil if no panic, or the panic value
// ONLY works inside a deferred function
Rules
  • recover() only stops a panic if called directly from a deferred function
  • Panic unwinds stack, running deferred functions
  • Use panic for truly unrecoverable states (programming errors), not business logic
  • HTTP handlers should recover panics to avoid crashing the whole server

What is a goroutine leak
Goroutines that are started but never terminate. They consume memory (~2KB initial stack, can grow), CPU for scheduling, and keep referenced objects alive.
Common Causes
  • Blocked channel read/write with no one to unblock
  • Not passing/checking context.Context
  • Infinite loops without exit condition
  • Forgotten goroutines in tests
Prevention Pattern
func worker(ctx context.Context, jobs <-chan Job) {
    for {
        select {
        case <-ctx.Done():
            return  // clean exit
        case job, ok := <-jobs:
            if !ok { return }  // channel closed
            process(job)
        }
    }
}

28 Go GMP scheduler — deep dive (G, M, P, work stealing)
gmpschedulergoroutine
Hard 74%
GMP Model
  • G (Goroutine): Lightweight coroutine. ~2KB initial stack, grows dynamically. Millions possible.
  • M (Machine/Thread): OS thread. One M executes one G at a time. Limited by GOMAXPROCS for Go code; more Ms created for blocking syscalls.
  • P (Processor): Scheduling context. GOMAXPROCS Ps (default = CPU cores). Each P has a local run queue (LRQ) of Gs.
Scheduling Flow
1. goroutine created → added to P's LRQ
2. P pops G from LRQ, assigns to M → runs
3. G blocks on syscall → M + G detached from P
   → P finds idle M (or creates new) → continues running other Gs
4. Syscall completes → G goes back to global run queue (GRQ)
5. Work stealing: idle P steals half of busy P's LRQ → balanced load
Preemption
Go uses cooperative preemption (yield at function calls) + async preemption (sysmon thread sends SIGURG after 10ms to interrupt G). Long CPU-bound goroutines preempted automatically.
GOMAXPROCS
Number of OS threads for Go code = number of Ps. runtime.GOMAXPROCS(n) or GOMAXPROCS=n env var.

Replication Mechanics (MySQL binlog / PostgreSQL WAL)
Primary records every write as binary log events. Replica connects, streams binlog, applies changes. Replication can be:
  • Async (default): Primary doesn't wait for replica. Replica may lag.
  • Semi-sync: Primary waits for at least 1 replica to acknowledge before committing.

  • High write throughput on primary
  • Network latency between primary and replica
  • Single-threaded replay (older MySQL — use parallel replication)
Handling Lag in Applications
  • Read-your-own-writes: route reads after writes to primary for 1s, or use session stickiness

7 PostgreSQL MVCC — how it achieves non-blocking reads
mvccpostgresqlsnapshot
Hard 82%
MVCC = Multi-Version Concurrency Control
Each row has hidden columns:
  • xmin: transaction ID that inserted this version
  • xmax: transaction ID that deleted/updated this version (0 = still live)
Reads see a snapshot: only versions where xmin ≤ snapshot_xid < xmax.
How it works
T1 (xid=100): UPDATE users SET name='Bob' WHERE id=1
→ Old row: xmin=50, xmax=100  (now dead to T1)
→ New row: xmin=100, xmax=0   (live)

T2 (xid=99, started before T1):
→ Sees old row (xmin=50 <= 99 < xmax=100) ✓
→ Sees 'Alice' — no blocking!

T3 (xid=101, started after T1 commits):
→ Old row: xmax=100 <= 101 → dead, skip
→ New row: xmin=100 <= 101, xmax=0 → live, sees 'Bob' ✓
VACUUM
Dead rows (old versions) accumulate. VACUUM reclaims space. AUTOVACUUM runs automatically. Transaction ID wraparound prevented by freezing old rows.

8 Database deadlocks — detection, prevention, resolution
deadlocklockwait-for-graph
Hard 82%
What is a Deadlock
Two or more transactions each hold a lock the other needs.
T1: LOCK A → wait for B
T2: LOCK B → wait for A
→ Circular wait = deadlock
Deadlock Detection
Most DBs run a background detector (PostgreSQL, MySQL InnoDB).
Builds a wait-for graph: node = transaction, edge = T1 waits for lock held by T2. Cycle = deadlock → kill victim transaction (least expensive to rollback).
Prevention Strategies
  • Lock ordering: Always acquire locks in the same global order (e.g., lower ID first)
  • Timeout: SET lock_timeout = '1s' — transaction aborts if wait too long
  • SELECT FOR UPDATE SKIP LOCKED: Skip locked rows instead of waiting (job queues)
  • Reduce transaction scope: Short transactions hold locks briefly
Application-Level Fix
-- Instead of long transaction:
BEGIN;
  UPDATE account SET bal = bal - 100 WHERE id = 1;  -- locks row
  -- ... complex computation (seconds) ...
  UPDATE account SET bal = bal + 100 WHERE id = 2;  -- deadlock risk!
COMMIT;

-- Better: do computation outside transaction, then short UPDATE

9 Eventual consistency models — BASE, read-your-writes, monotonic reads
eventual-consistencybasecausal
Hard 82%
CAP Theorem Recap
In presence of network partition (P), choose between Consistency (C) or Availability (A). Most distributed systems choose AP → eventual consistency.
BASE (Basically Available, Soft state, Eventually consistent)
Contrast to ACID.
  • Basically Available: System works, even during partial failure (stale data OK)
  • Soft State: State may change without input (replication catching up)
  • Eventually Consistent: Given no new updates, all replicas converge to same state
Consistency Models (weakest to strongest)
  • Eventual: Converges eventually. DNS, S3.
  • Monotonic Read: Once you read version V, you never see older version. (client stickiness)
  • Read-Your-Writes: You always see your own writes immediately. (session token pinning)
  • Causal: If A caused B, everyone sees A before B. (vector clocks)
  • Sequential: All operations appear in a global order consistent with program order.
  • Linearizable (Strict): Strongest. Operations appear instantaneous. ZooKeeper, etcd.

5 I/O Models
  • Blocking I/O: Thread blocks until data ready. Simple. Scales poorly (1 thread/connection).
  • Non-blocking I/O: Returns EAGAIN immediately if no data. Polling loop wastes CPU.
  • I/O Multiplexing (select/poll/epoll): One thread watches many fds. Blocks on select, wakes when any fd ready. Efficient for many connections.
  • Signal-driven I/O (SIGIO): Signal when data ready. Complex, rarely used.
  • Async I/O (AIO, io_uring): Kernel does I/O, notifies completion. True async. io_uring (Linux 5.1+): submission/completion queues in shared memory, no syscall overhead.
epoll vs select vs poll
  • select: fd_set bitmap, max 1024 fds, O(n) scan, copies fd_set each call
  • poll: array of pollfd, no 1024 limit, still O(n) scan
  • epoll: O(1) event notification. Register fds once (epoll_ctl), wait (epoll_wait) returns only ready fds. Kernel red-black tree for O(log n) add/remove. Level-triggered or edge-triggered modes.
io_uring (Modern Linux)
Fully async: app submits I/O requests to SQ ring, kernel processes, posts completions to CQ ring. Zero syscall on fast path. Used in: Tokio (Rust), QEMU, PostgreSQL, Nginx.

2 Virtual memory — paging, page tables, TLB

Hard 88%
Virtual Memory
Each process has its own virtual address space (e.g., 0 to 2^48 on 64-bit). OS maps virtual pages → physical frames via page table. Allows: isolation between processes, overcommit memory, memory-mapped files, copy-on-write.
Multi-level Page Tables
64-bit systems use 4-level (x86-64) or 5-level page tables to reduce space. Each level is a 4KB page of 512 8-byte entries. Virtual address split:
[sign ext | L4 (9) | L3 (9) | L2 (9) | L1 (9) | Offset (12)]
TLB (Translation Lookaside Buffer)
Hardware cache for recent virtual→physical translations. TLB hit: 1 cycle. TLB miss: walk page table (several cycles + memory accesses). TLB flushed on context switch (unless ASID used). Huge pages (2MB/1GB) reduce TLB misses.
Page Fault
  • Minor: Page in memory but not mapped (memory-mapped file, copy-on-write) → map it
  • Major: Page not in memory → read from disk (swap). Expensive (~ms)
  • Invalid: Access to unmapped address → SIGSEGV

3 Deadlock — conditions, prevention, avoidance, detection
deadlockcoffmanbanker
Hard 88%
Coffman's Four Necessary Conditions
  • Mutual Exclusion: Resources not sharable
  • Hold and Wait: Process holds resource while waiting for another
  • No Preemption: Resources can't be forcibly taken
  • Circular Wait: T1→waits for T2→waits for T3→waits for T1
Breaking any one prevents deadlock.
Prevention
  • Eliminate Hold and Wait: Request all resources at once before starting
  • Allow Preemption: If waiting, release held resources (costly)
  • Eliminate Circular Wait: Global ordering of resources (always lock in same order)
Avoidance — Banker's Algorithm
Each process declares max resource claim. System checks if granting a request leaves system in safe state (all processes can complete). If unsafe → deny and wait. Used in theory; impractical for dynamic systems.
Detection and Recovery
Allow deadlocks to occur. Periodically run deadlock detector (wait-for graph cycle detection). Recovery: kill one victim process, or preempt + rollback resources.

class SlidingWindowRateLimiter {
    private final int maxRequests;
    private final long windowMs;
    private final Map<String, Deque<Long>> windows = new ConcurrentHashMap<>();

    boolean allow(String clientId) {
        long now = System.currentTimeMillis();
        long cutoff = now - windowMs;

        Deque<Long> timestamps = windows.computeIfAbsent(clientId, k -> new ArrayDeque<>());

        synchronized (timestamps) {
            // Remove expired
            while (!timestamps.isEmpty() && timestamps.peekFirst() <= cutoff)
                timestamps.pollFirst();
            if (timestamps.size() >= maxRequests) return false;
            timestamps.addLast(now);
            return true;
        }
    }
}

class TokenBucketRateLimiter {

    }

class SnowflakeIdGenerator {
    private final long EPOCH = 1288834974657L;  // Nov 4, 2010
    private final long MACHINE_ID;              // 0-1023
    private long sequence = 0;
    private long lastTs = -1;

    synchronized long nextId() {
        long ts = System.currentTimeMillis();
        if (ts == lastTs) {
            sequence = (sequence + 1) & 0xFFF;  // 12-bit mask
            if (sequence == 0) ts = waitNextMs(lastTs);  // sequence exhausted
        } else { sequence = 0; }
        lastTs = ts;
        return ((ts - EPOCH) << 22) | (MACHINE_ID << 12) | sequence;
    }

    private long waitNextMs(long ts) {
        long now = System.currentTimeMillis();
        while (now <= ts) now = System.currentTimeMillis();
        return now;
    }
}

6 Design a Circuit Breaker

Hard 86%
States
CLOSED → calls go through. OPEN → calls fail-fast (no downstream). HALF_OPEN → probe call, if succeeds → CLOSED, else → OPEN.
Full Implementation
enum State { CLOSED, OPEN, HALF_OPEN }

class CircuitBreaker {
    State state = CLOSED;
    int failCount = 0, successCount = 0;
    final int failThreshold = 5;
    final int successThreshold = 2;
    Instant openedAt;
    final Duration timeout = Duration.ofSeconds(30);
    final ReentrantLock lock = new ReentrantLock();

    <T> T call(Supplier<T> fn) {
        lock.lock(); try {
            if (state == OPEN) {
                if (Duration.between(openedAt, Instant.now()).compareTo(timeout) > 0)
                    state = HALF_OPEN;
                else throw new CircuitOpenException();
            }
        } finally { lock.unlock(); }

        try {
            T result = fn.get();
            onSuccess(); return result;
        } catch (Exception e) { onFailure(); throw e; }
    }

    void onSuccess() {
        lock.lock(); try {
            if (state == HALF_OPEN && ++successCount >= successThreshold) {
                state = CLOSED; failCount = 0; successCount = 0;
            }
        } finally { lock.unlock(); }
    }

    void onFailure() {
        lock.lock(); try {
            if (++failCount >= failThreshold || state == HALF_OPEN) {
                state = OPEN; openedAt = Instant.now(); successCount = 0;
            }
        } finally { lock.unlock(); }
    }
}

class Scheduler {

                  .thenComparing(j -> -j.priority));
    ScheduledExecutorService executor = Executors.newScheduledThreadPool(4);

JWT Structure

Header: {"alg": "RS256", "typ": "JWT"}

  • Sensitive data in payload: JWT is base64 NOT encrypted. Anyone can decode it.

2 Cache strategies — cache-aside, read-through, write-through, write-back
cachingrediscache-aside
Medium 88%
Cache Strategies
  • Cache-Aside (Lazy loading): App checks cache first; on miss, reads DB, populates cache. Cache only stores what's actually requested. Risk: thundering herd on cold start.
  • Read-Through: Cache reads from DB automatically on miss (library handles it). App always reads from cache. DB not directly accessed by app.
  • Write-Through: Write to cache AND DB synchronously. Cache never stale. High write latency (must wait for both). Good for read-heavy.
  • Write-Back (Write-Behind): Write to cache, return immediately. Write to DB asynchronously. Fast writes. Risk: data loss if cache crashes before flush.
Cache-Aside Pattern (most common)
def get_user(user_id):

    # Populate cache with TTL
    redis.setex(f"user:{user_id}", ttl=3600, value=serialize(user))

def update_user(user_id, data):

CDN Architecture
Points of Presence (PoPs): Edge servers distributed globally (Cloudflare: 300+ PoPs, Akamai: 4000+). User request routed to nearest PoP via Anycast (same IP, BGP routes to nearest datacenter) or GeoDNS.
Cache Flow
User → CDN Edge (PoP)
  → Cache HIT: return immediately (<5ms)
  → Cache MISS: fetch from origin (100-300ms), cache response, serve

Subsequent users at same PoP → cache HIT
Users at different PoP → may still be cache MISS (PoP-local cache)
Cache Control Headers
Cache-Control: max-age=31536000, immutable     # 1 year, static assets
Cache-Control: max-age=60, stale-while-revalidate=30  # 1min fresh, serve stale while revalidating
Cache-Control: no-store                         # never cache (auth pages)
Surrogate-Control: max-age=3600                 # CDN-only hint (Varnish/Fastly)
Vary: Accept-Encoding                           # different cache per encoding
Dynamic Content
Not all content is cacheable. Edge computing (Cloudflare Workers, Lambda@Edge) runs logic at edge. For personalized content: cache fragment (Edge Side Includes) or stream-stitch.
