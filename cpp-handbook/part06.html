Chapter 1 — CAP Theorem

In a distributed system, you can guarantee at most 2 of 3: Consistency (every read returns latest write), Availability (every request gets a response), Partition Tolerance (system works despite network partition). Since partitions are unavoidable in real networks, choose CP or AP.

ModelGuaranteeExamplesWhen to Use
Linearizable (CP)Every read sees the latest write globallyetcd, ZookeeperLeader election, distributed locks
Sequential (CP)All operations in some sequential orderMost RDBMSTransactions requiring ordering
Causal (AP-ish)Causally related ops orderedAmazon DynamoDB (w/ transactions)Shopping cart, collaborative editing
Eventual (AP)Converges if no new writesCassandra, DynamoDB (default)DNS, user profile, analytics
Read-your-writesClient always sees own writesSession consistency in DBUser profile updates
✅ DO THIS
// Choosing consistency model for a distributed inference cache:
// Requirement: cache inference results by input hash
// Tolerance: stale result served for up to 30s is acceptable (saves compute)
// Choice: Eventual consistency with TTL = 30s

// Redis with TTL — eventual consistency acceptable here:
// If two nodes briefly have different cached values, no harm done
// (worst case: two slightly different results for same input during sync)
redis_client.setex(input_hash, 30, result_json);   // 30s TTL

// For critical path (model weight version used for inference):
// Choice: strong consistency — wrong model version = wrong results
// Use etcd or Zookeeper for model version metadata
etcd_client.put("/models/resnet50/version", "v1.2.3",
                etcd::PutOptions().with_lease(60));  // leader-elected
✅ Why this works: Match your consistency model to your correctness requirements. Inference result caches can tolerate eventual consistency. Model version metadata requires strong consistency — serving with wrong weights is a correctness bug.
❌ AVOID THIS
// BAD: using eventual consistency for financial transactions
// Cassandra with eventual consistency:
cassandra.write("account:alice:balance", 1000);   // node A sees 1000
// Network partition — node B still has old value
cassandra.read("account:alice:balance");   // might return 900 (stale!)
// User double-spends because read saw stale balance

// BAD: using strong consistency for everything even when not needed
// Zookeeper for every read in a high-QPS system:
// Zookeeper can handle ~50K reads/sec
// Your inference cache needs 500K reads/sec → Zookeeper is the bottleneck
// Redis with TTL would serve the same purpose at 10x the throughput
❌ Why this fails: Over-engineering with strong consistency where eventual would do causes unnecessary bottlenecks. Under-engineering with eventual consistency for financial data causes correctness bugs.

Chapter 2 — Raft Consensus: Step by Step

Raft States and Transitions: Follower ──timeout──► Candidate ──majority votes──► Leader ▲ │ │ └──────────────────────┘ │ (receives AppendEntries ◄──────────────────┘ or RequestVote) (sends heartbeat/AppendEntries) Leader Election: 1. Follower doesn't hear from leader for election_timeout (150-300ms) 2. Increments term, votes for itself, sends RequestVote to all 3. Candidate wins if it gets (n/2 + 1) votes 4. Vote granted only if candidate's log is at least as up-to-date as voter's Log Replication: Client → Leader: entry appended to leader's log Leader → Followers: AppendEntries RPC (also serves as heartbeat) Majority ACK → Leader marks entry committed Leader responds to client Followers learn of commit on next AppendEntries
✅ DO THIS
// Raft in practice — what this means for your code:

// 1. All writes go to the leader
// Use a Raft client that does leader routing automatically:
etcd_client.put("key", "value");   // client retries on wrong node
// etcd's clientv3 does leader forwarding transparently

// 2. Reads can be from followers (stale) or leader (linearizable)
etcd_client.get("key");                         // stale — follower ok
etcd_client.get("key", {.leader_endpoint = true}); // linearizable — leader

// 3. Membership changes are Raft log entries — not instant
// Adding a node: new node joins as learner → catches up → becomes voter
// Safe: cluster remains available during membership change

// 4. Leader leases for low-latency reads (no round-trip needed)
// Leader knows it's leader for lease duration → serve reads locally
// Used by etcd, CockroachDB for fast reads without consensus round-trip
✅ Why this works: etcd's lease-based reads (linearizable default) add one network round-trip. For hot read paths, use stale reads from followers and accept bounded staleness.

Chapter 3 — Apache Kafka Deep Dive

Kafka Cluster Architecture: Producer ──────────► [Topic: 3 Partitions × 3 Replicas] ┌─────────┬─────────┬─────────┐ │ Part 0 │ Part 1 │ Part 2 │ ← Leader replicas │ Broker1 │ Broker2 │ Broker3 │ └─────────┴─────────┴─────────┘ │ │ │ Follower Follower Follower ← ISR replicas Consumer Group A: Consumer 1 ← Partition 0 (each partition to ONE consumer in group) Consumer 2 ← Partition 1 (parallelism = min(consumers, partitions)) Consumer 3 ← Partition 2 Consumer Group B (independent offset tracking): Consumer 4 ← all partitions (single consumer, full replay)
✅ DO THIS
// Kafka producer with key for ordering guarantee
Properties props;
props["bootstrap.servers"] = "kafka1:9092,kafka2:9092";
props["acks"] = "all";          // wait for all ISR replicas to ACK
props["retries"] = "10";
props["enable.idempotence"] = "true";  // exactly-once per partition
props["compression.type"] = "lz4";    // compress batches

KafkaProducer producer(props);
// Key determines partition: same key → same partition → ordered
producer.send({
    .topic     = "inference-requests",
    .key       = user_id,         // all requests for user go to same partition
    .value     = request.to_json(),
    .callback  = [](RecordMetadata md, KafkaException* e) {
        if (e) log_error(e->what());
        else   metrics.record("kafka.produce.latency", md.latency());
    }
});

// Consumer: commit after processing (at-least-once delivery)
while (true) {
    auto records = consumer.poll(std::chrono::milliseconds(100));
    for (auto& record : records) {
        process(record.value());     // process first
        consumer.commitSync({record.topic(), record.partition(),
                             record.offset() + 1});  // then commit offset
    }
}
✅ Why this works: acks=all + enable.idempotence gives you exactly-once per partition. Commit offset AFTER processing (not before) ensures at-least-once — if processing fails, the message is reprocessed.
❌ AVOID THIS
// BAD: auto-commit offset before processing
consumer.enable_auto_commit(true);   // commits offset automatically
auto records = consumer.poll(100ms);
for (auto& record : records) {
    // auto-commit fires here in background — offset committed!
    process(record.value());   // if this crashes → message LOST (committed but not processed)
}
// Use manual commit + process first for at-least-once

// BAD: all data in one partition → no parallelism
producer.send({.topic="events", .key=nullptr, .value=data});
// Without a key: messages go to random partitions (round-robin)
// But if you always use key=nullptr: all in default partition → 1 consumer only

// BAD: consumer group larger than partition count
// 4 partitions, 8 consumers in same group
// → 4 consumers are idle (each partition has at most 1 active consumer)
// → wasted resources. Scale consumers to match partition count
❌ Why this fails: Kafka parallelism is bounded by partition count. Design partition count based on max needed consumer parallelism — you can increase partitions later, but you can't decrease them without creating a new topic.

✅ DO THIS
// Pattern 1: Rate limiting with sliding window (sorted set)
def check_rate_limit(user_id: str, limit: int, window_s: int) -> bool:
    key = f"ratelimit:{user_id}"
    now = time.time()
    pipe = redis.pipeline()
    pipe.zremrangebyscore(key, 0, now - window_s)  # remove old entries
    pipe.zcard(key)                                 # count recent requests
    pipe.zadd(key, {str(now): now})                 # add this request
    pipe.expire(key, window_s)                      # auto-expire key
    _, count, *_ = pipe.execute()
    return count < limit   # True if allowed

// Pattern 2: Distributed lock with expiry
bool acquire_lock(const std::string& key, const std::string& token, int ttl_s) {
    // SET key token NX EX ttl — atomic, only sets if key doesn't exist
    auto result = redis.set(key, token,
                            nx=true,     // NX: only set if Not eXists
                            ex=ttl_s);   // EX: expire after ttl_s seconds
    return result.has_value();   // true = lock acquired
}
void release_lock(const std::string& key, const std::string& token) {
    // Lua script: only delete if value matches (we own the lock)
    const char* lua = "if redis.call('get',KEYS[1])==ARGV[1] "
                      "then return redis.call('del',KEYS[1]) "
                      "else return 0 end";
    redis.eval(lua, {key}, {token});   // atomic: check + delete
}
✅ Why this works: Lua scripts in Redis execute atomically — the entire script runs without interruption. This is how you implement check-and-modify operations (compare-and-delete for locks, check-and-increment for rate limits) without TOCTOU races.

Interview Q&A — Distributed Systems

❓ Explain Raft leader election. What prevents split-brain?
Raft prevents split-brain through two mechanisms: (1) Majority quorum: any operation (election or log commit) requires votes from n/2+1 nodes. With n=5, you need 3 votes. If the cluster splits into groups of 2 and 3, only the group of 3 can form a quorum — the group of 2 is inactive. (2) Term numbers: each election increments the term. Old leaders with lower term number immediately step down when they hear a higher term. So there can never be two leaders in the same term. A candidate can only win if its log is at least as up-to-date as the majority — prevents stale leaders from winning.
Follow-up questions interviewers ask:
  • What happens to a Raft leader that gets network partitioned?
  • How does Raft handle a follower that missed many log entries?
  • What is the difference between committed and applied in Raft?
Common mistakes in answers:
  • Saying 'Raft prevents split-brain entirely' — it prevents two active leaders in the same term, but a partitioned old leader may continue operating (with stale data) until it sees a higher term.
  • Confusing leader election timeout with heartbeat interval — timeout must be much larger than heartbeat interval.
❓ How does Kafka guarantee ordering? What are the tradeoffs?
Kafka guarantees ordering WITHIN a partition. Messages with the same key go to the same partition via consistent hashing (Kafka uses murmur2 hash of key). All messages in that partition are ordered by offset. Consumer reads partitions sequentially — within a partition, you see messages in write order. Tradeoff: ordering per partition means your parallelism is limited by partition count. If you need global ordering across all messages: use one partition (no parallelism). If you need per-user ordering: use user_id as key (parallel processing, ordered per user). Common mistake: using no key (random partition) when you need ordering — guaranteed to break ordering.
Follow-up questions interviewers ask:
  • How does Kafka handle duplicate messages after a consumer crash?
  • What is the difference between at-least-once and exactly-once in Kafka?
  • When would you use compacted topics?
