Chapter 1 — Thread Basics

A thread is the smallest unit of CPU scheduling. Threads in the same process share address space, heap, file descriptors, and global data — but each has its own stack (~1-8MB), registers, and thread-local storage.

Process address space (shared by all threads): ┌───────────────────────────────────────────────────────┐ │ .text (code) │ .data / .bss (globals) │ Heap │ └───────────────────────────────────────────────────────┘ Thread 1 stack Thread 2 stack Thread 3 stack │ │ │ (separate, private) (separate, private) (separate, private) Thread lifecycle: Created ──► Runnable ◄──► Running ──► Blocked (wait/sleep/I/O) └──► Terminated
✅ DO THIS
#include <thread>
#include <iostream>

// Worker function: accepts data by value — safe across threads
void compute(int id, std::vector<int> data) {   // own copy of data
    int sum = 0;
    for (int x : data) sum += x;
    std::cout << "Thread " << id << " sum: " << sum << "\n";
}

int main() {
    std::vector<int> big_data(1000, 1);

    std::thread t1(compute, 1, big_data);          // copy of big_data to t1
    std::thread t2(compute, 2, std::vector<int>(500, 2)); // temp moved in

    t1.join();   // wait for t1 to finish — REQUIRED before main exits
    t2.join();   // wait for t2 to finish

    return 0;
}
// Thread destructor calls std::terminate() if thread is joinable but not joined!
✅ Why this works: Always join (or detach) every thread before it goes out of scope. std::thread destructor calls terminate() on a joinable thread — a hard crash.
❌ AVOID THIS
// BAD 1: Thread not joined — std::terminate() at destructor
void bad_no_join() {
    std::thread t([]{ do_work(); });
    if (some_condition()) return;   // t not joined! → std::terminate() crash
    t.join();
}

// BAD 2: Passing local by reference — dangling reference
void bad_dangling() {
    int local = 42;
    std::thread t([&local]() {   // captures local by reference
        std::this_thread::sleep_for(std::chrono::seconds(1));
        std::cout << local;   // local is GONE! UB — stack frame was freed
    });
    t.detach();   // bad_dangling() returns → local destroyed → thread reads garbage
}

// FIX for BAD 2: capture by value
std::thread t([local]() { std::cout << local; });   // own copy — safe
❌ Why this fails: Dangling reference in a thread lambda is the #1 beginner threading bug. The thread captures a reference to a local variable, the function returns, and the thread runs with freed stack memory.

Chapter 2 — Mutexes: Theory to Practice

A mutex (mutual exclusion) ensures only one thread at a time executes the critical section. Without mutex: two threads writing the same variable simultaneously produce data races — undefined behavior in C++.

Without mutex (data race): Thread 1: reads count=5 Thread 2: reads count=5 (before Thread 1 writes) Thread 1: writes count=6 ← lost update! Thread 2: writes count=6 ← both wrote 6 instead of 7 With mutex: Thread 1: lock → reads 5 → writes 6 → unlock Thread 2: ........waits.......................... lock → reads 6 → writes 7 → unlock Final: count = 7 ✓
✅ DO THIS
#include <mutex>
#include <shared_mutex>

class ThreadSafeCounter {
    mutable std::mutex mtx_;   // mutable: allow locking in const methods
    int value_ = 0;
public:
    void increment() {
        std::lock_guard<std::mutex> lk(mtx_);  // locked; released at }
        ++value_;
    }

    // Atomic increment and return new value
    int add(int delta) {
        std::lock_guard<std::mutex> lk(mtx_);
        value_ += delta;
        return value_;
    }

    int get() const {
        std::lock_guard<std::mutex> lk(mtx_);  // const method also needs lock
        return value_;
    }
};

// Reader-Writer Lock: many readers OR one writer
class Config {
    mutable std::shared_mutex rw_;
    std::map<std::string, std::string> data_;
public:
    std::string get(const std::string& key) const {
        std::shared_lock lk(rw_);   // multiple readers can hold this simultaneously
        auto it = data_.find(key);
        return it != data_.end() ? it->second : "";
    }
    void set(const std::string& key, std::string val) {
        std::unique_lock lk(rw_);  // exclusive: no readers or writers while held
        data_[key] = std::move(val);
    }
};
✅ Why this works: shared_mutex is the right tool when reads heavily outnumber writes (e.g., config data, caches). Multiple readers run in parallel; writers get exclusive access.
❌ AVOID THIS
// BAD 1: Raw lock/unlock — easy to miss on every exit path
class BadCounter {
    std::mutex mtx_;
    int v_ = 0;
public:
    int increment() {
        mtx_.lock();
        if (v_ >= MAX) {
            mtx_.unlock();   // must manually unlock on every path
            return -1;
        }
        ++v_;
        return v_;
        // FORGOT mtx_.unlock() before return! → DEADLOCK
    }
};

// BAD 2: Locking same non-recursive mutex twice → DEADLOCK
class Bad2 {
    std::mutex mtx_;
    void inner() {
        std::lock_guard lk(mtx_);   // locks mtx_
        // ...
    }
    void outer() {
        std::lock_guard lk(mtx_);   // locks mtx_ again from same thread
        inner();   // tries to lock mtx_ AGAIN → DEADLOCK (mutex is not recursive)
    }
};
// Fix: use std::recursive_mutex, or refactor inner() to not lock
❌ Why this fails: Double-locking (locking a non-recursive mutex you already hold) causes an instant deadlock in the same thread. This is why large critical sections that call other locking methods are dangerous.

2.1 Deadlock — Four Conditions and Prevention

Deadlock (all four conditions present simultaneously): 1. Mutual exclusion: at least one resource is non-shareable 2. Hold and wait: thread holds resource while waiting for another 3. No preemption: resources released only voluntarily 4. Circular wait: T1 waits for T2's lock; T2 waits for T1's lock Thread 1: Lock(A) ──waiting──► Lock(B) ─locked by Thread 2─►◄ Thread 2: Lock(B) ──waiting──► Lock(A) ─locked by Thread 1─►◄ Both wait forever.
✅ DO THIS
// Fix 1: Always acquire locks in the same global order
// Define: A must be locked before B — always
void transfer(Account& from, Account& to, double amount) {
    // Ensure consistent order by comparing addresses
    auto* first  = (&from < &to) ? &from : &to;
    auto* second = (&from < &to) ? &to : &from;
    std::lock_guard lk1(first->mtx_);
    std::lock_guard lk2(second->mtx_);
    from.balance -= amount;
    to.balance   += amount;
}

// Fix 2: std::scoped_lock — atomically locks BOTH, deadlock-free (C++17)
void transfer_safe(Account& from, Account& to, double amount) {
    std::scoped_lock lk(from.mtx_, to.mtx_);  // locks both atomically
    from.balance -= amount;
    to.balance   += amount;
}
// scoped_lock uses a deadlock-avoidance algorithm internally
✅ Why this works: std::scoped_lock is the cleanest solution for multi-mutex locking. It uses std::lock internally which tries lock/backoff/retry to avoid deadlock.

Chapter 3 — Condition Variables

Condition variables allow threads to sleep until a condition is true. Used with a mutex — the thread releases the mutex while sleeping, so others can update the condition.

✅ DO THIS
#include <condition_variable>

class BoundedQueue {
    std::mutex              mtx_;
    std::condition_variable not_full_, not_empty_;
    std::queue<int>         q_;
    const size_t            capacity_;
public:
    explicit BoundedQueue(size_t cap) : capacity_(cap) {}

    void push(int val) {
        std::unique_lock lk(mtx_);
        not_full_.wait(lk, [this]{ return q_.size() < capacity_; });
        //          ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^
        //  wait(): release lock, sleep until woken, reacquire lock, CHECK predicate
        //  If predicate is false (spurious wakeup), go back to sleep
        q_.push(val);
        not_empty_.notify_one();   // wake one consumer
    }

    int pop() {
        std::unique_lock lk(mtx_);
        not_empty_.wait(lk, [this]{ return !q_.empty(); });
        int val = q_.front(); q_.pop();
        not_full_.notify_one();   // wake one producer
        return val;
    }
};
✅ Why this works: The predicate lambda in wait() handles spurious wakeups — the OS may wake a thread even when not notified. The predicate re-checks the condition and goes back to sleep if needed.
❌ AVOID THIS
// BAD: no predicate → spurious wakeup bug
void bad_consumer(std::queue<int>& q, std::mutex& m, std::condition_variable& cv) {
    std::unique_lock lk(m);
    cv.wait(lk);          // ← no predicate!
    // Spurious wakeup: OS wakes thread even when queue is empty
    int val = q.front();  // q is empty → CRASH or undefined behavior
    q.pop();
}

// BAD: signaling outside lock
void bad_producer(std::queue<int>& q, std::mutex& m, std::condition_variable& cv) {
    {
        std::lock_guard lk(m);
        q.push(42);
    }   // lock released here
    // Consumer might run here, see queue, go back to sleep
    cv.notify_one();   // notify AFTER lock released: consumer misses it!
    // (In practice this specific ordering is technically fine per C++ standard,
    //  but it's fragile and confusing. Better: notify while holding lock or just after)
}
❌ Why this fails: Always use the predicate form of wait(). Spurious wakeups are real — the Linux kernel can wake waiting threads without notification (e.g., signal delivery). The predicate protects against them.

Chapter 4 — Atomics and Memory Ordering

Atomics provide lock-free, thread-safe operations. Memory ordering controls what other memory operations become visible relative to the atomic operation.

Memory ordering visualized: relaxed: No ordering guarantee — just atomicity Thread A: x=1; cnt.store(1, relaxed) Thread B: cnt.load(relaxed); // might see 1 but x might still see 0! release/acquire: Synchronization point Thread A: x=1; flag.store(true, release) // x must be written BEFORE flag Thread B: while(!flag.load(acquire)); x // once flag seen, x is also visible seq_cst: Total order — all threads see operations in the same order Most expensive but easiest to reason about
✅ DO THIS
#include <atomic>

// Pattern 1: Simple counter (no ordering needed between threads)
std::atomic<int> request_count{0};
void on_request() {
    request_count.fetch_add(1, std::memory_order_relaxed);  // just count
}
int get_count() {
    return request_count.load(std::memory_order_relaxed);
}

// Pattern 2: Publish-Subscribe (release/acquire pair)
struct Data { int value; std::string name; };
Data shared_data;
std::atomic<bool> data_ready{false};

// Publisher thread:
void publish(int v, const std::string& n) {
    shared_data.value = v;     // write data
    shared_data.name  = n;     // write data
    data_ready.store(true, std::memory_order_release);
    //                       ^^^^^^^ all writes above are visible to matching acquire
}
// Subscriber thread:
void subscribe() {
    while (!data_ready.load(std::memory_order_acquire));
    //                       ^^^^^^^ once true, shared_data writes are visible
    use(shared_data.value, shared_data.name);  // guaranteed correct
}

// Pattern 3: CAS (Compare-And-Swap) — the lock-free building block
bool push_if_empty(std::atomic<int>& slot, int val) {
    int expected = 0;
    return slot.compare_exchange_strong(expected, val);
    // If slot==0: set slot=val, return true
    // If slot!=0: set expected=slot's value, return false
}
✅ Why this works: Release/acquire is the minimum ordering needed for producer-consumer patterns. It's cheaper than seq_cst (no global memory fence) while still providing the synchronization guarantee you need.
❌ AVOID THIS
// BAD: data race — two threads write same int with no protection
int shared = 0;
void thread1() { ++shared; }   // NOT ATOMIC: read-modify-write is 3 ops
void thread2() { ++shared; }   // interleaving possible → lost updates

// Expected: shared == 2. Actual: might be 1 (lost update)
// This is UNDEFINED BEHAVIOR in C++ — compiler may assume no data races

// BAD: wrong memory ordering for publish-subscribe
std::atomic<bool> ready{false};
int data = 0;
// Thread A:
data = 42;
ready.store(true, std::memory_order_relaxed);   // WRONG: relaxed doesn't sync data

// Thread B:
while (!ready.load(std::memory_order_relaxed)); // WRONG: relaxed doesn't sync
assert(data == 42);   // FAILS: data=42 write may not be visible to Thread B!
❌ Why this fails: Using relaxed ordering for a publish-subscribe pattern gives you atomicity but no synchronization guarantee. Thread B may see the flag as true but still see data as 0.

Chapter 5 — Lock-Free Programming

5.1 CAS Loop — The Fundamental Lock-Free Pattern

✅ DO THIS
// Lock-free stack using CAS
template<typename T>
class LockFreeStack {
    struct Node { T data; Node* next; };
    std::atomic<Node*> head_{nullptr};
public:
    void push(T val) {
        Node* new_node = new Node{std::move(val), nullptr};
        // CAS loop: retry until we successfully update head_
        do {
            new_node->next = head_.load(std::memory_order_relaxed);
        } while (!head_.compare_exchange_weak(
                new_node->next,   // expected (updated on failure)
                new_node,         // desired
                std::memory_order_release,   // success: publish new node
                std::memory_order_relaxed)); // failure: just retry
    }

    std::optional<T> pop() {
        Node* old_head = head_.load(std::memory_order_acquire);
        while (old_head) {
            if (head_.compare_exchange_weak(old_head, old_head->next,
                    std::memory_order_acquire,
                    std::memory_order_relaxed)) {
                T val = std::move(old_head->data);
                delete old_head;   // NOTE: hazard pointers needed for safe reclaim
                return val;
            }
            // old_head was updated to current head_ on failure — retry
        }
        return std::nullopt;   // empty stack
    }
};
✅ Why this works: compare_exchange_weak is used in loops — it may fail spuriously (cheaper on some architectures). compare_exchange_strong never fails spuriously but costs more. Use weak in loops, strong for single-attempt.
❌ AVOID THIS
// BAD: ABA problem — CAS succeeds incorrectly
// Thread 1: reads head_ = NodeA
// Thread 2: pops NodeA, pops NodeB, pushes NodeA back (same address)
// Thread 1: CAS(head_, NodeA, NodeA->next) — succeeds!
//           But NodeA->next now points to freed memory!

// This is the ABA problem: address A → B → A looks like "nothing changed"
// to a CAS, but the state DID change.

// Real consequences in lock-free stacks:
// - Nodes freed and reused: dangling pointers
// - Corrupted linked list structure

// Solutions:
// 1. Tagged pointer: pack a version counter into the pointer
//    (use low/high bits on 64-bit systems)
// 2. Hazard pointers: thread registers the pointer before use
// 3. Epoch-based reclamation: defer free until no thread could use it
❌ Why this fails: ABA is the most subtle lock-free bug. It doesn't crash immediately — it corrupts data structure integrity, causing occasional hangs or wrong results under load. Use established libraries (folly::hazptr, libatomic_ops) for production lock-free code.

Chapter 6 — Thread Pool Design

✅ DO THIS
class ThreadPool {
    std::vector<std::thread>          workers_;
    std::queue<std::function<void()>> tasks_;
    std::mutex                        mtx_;
    std::condition_variable           cv_;
    std::atomic<bool>                 stop_{false};
public:
    explicit ThreadPool(size_t n) {
        workers_.reserve(n);
        for (size_t i = 0; i < n; ++i)
            workers_.emplace_back([this] {
                while (true) {
                    std::function<void()> task;
                    {
                        std::unique_lock lk(mtx_);
                        cv_.wait(lk, [this] {
                            return stop_.load() || !tasks_.empty();
                        });
                        if (stop_.load() && tasks_.empty()) return;
                        task = std::move(tasks_.front());
                        tasks_.pop();
                    }   // unlock before running task — important for throughput
                    task();
                }
            });
    }

    // Submit any callable — returns future for the result
    template<typename F, typename... Args>
    auto submit(F&& f, Args&&... args) {
        using R = std::invoke_result_t<F, Args...>;
        auto pkg = std::make_shared<std::packaged_task<R()>>(
            [f=std::forward<F>(f), ...args=std::forward<Args>(args)]() mutable {
                return f(args...);
            });
        std::future<R> fut = pkg->get_future();
        {
            std::lock_guard lk(mtx_);
            tasks_.emplace([pkg]{ (*pkg)(); });
        }
        cv_.notify_one();
        return fut;
    }

    ~ThreadPool() {
        stop_.store(true);
        cv_.notify_all();        // wake all sleeping workers
        for (auto& t : workers_) t.join();   // wait for completion
    }
};

// Usage:
ThreadPool pool(std::thread::hardware_concurrency());
auto fut1 = pool.submit(compute_hash, data1);
auto fut2 = pool.submit(compute_hash, data2);
auto h1 = fut1.get();   // blocks until result ready
auto h2 = fut2.get();
✅ Why this works: Unlock the mutex before running the task — otherwise the lock is held for the entire duration of the task, serializing all workers.

Chapter 7 — False Sharing and Cache Coherency

Cache line = 64 bytes (typical on x86) False sharing: Thread 1: reads/writes counter1 (offset 0) Thread 2: reads/writes counter2 (offset 4) ┌────────────────────────────────────────────────────────────────┐ │ counter1 (4B) │ counter2 (4B) │ padding (56B) │ └────────────────────────────────────────────────────────────────┘ ↑─────────────same cache line (64 bytes)───────────────────────↑ → Each write by either thread invalidates the other's L1 cache! → Cache line bounces between cores: 100-300 cycle penalty per access Fix: align each to a separate cache line:
✅ DO THIS
// Pad each counter to its own 64-byte cache line
struct alignas(64) PaddedCounter {
    std::atomic<long> value{0};
    // char padding[64 - sizeof(value)];  // implicit via alignas(64)
};

// Per-thread counters (no sharing at all)
class ShardedCounter {
    static constexpr size_t SHARDS = 16;
    PaddedCounter shards_[SHARDS];
public:
    void increment() {
        // Each thread hits its own shard — no cache contention
        size_t idx = std::hash<std::thread::id>{}(std::this_thread::get_id()) % SHARDS;
        shards_[idx].value.fetch_add(1, std::memory_order_relaxed);
    }
    long total() const {
        long sum = 0;
        for (auto& s : shards_) sum += s.value.load(std::memory_order_relaxed);
        return sum;
    }
};
// ~8x faster than a single atomic<long> under 8-thread contention
✅ Why this works: ShardedCounter trades slightly stale reads (total()) for dramatically better write throughput. This pattern is used in Linux kernel's percpu counters, Java's LongAdder, and high-performance event counters.
❌ AVOID THIS
// BAD: naive struct — counter1 and counter2 share cache line
struct NaiveCounters {
    std::atomic<long> counter1{0};   // bytes 0-7
    std::atomic<long> counter2{0};   // bytes 8-15
};
// Both fit in one 64-byte cache line
// Thread1 writes counter1 → invalidates cache line on Thread2's core
// Thread2 writes counter2 → invalidates cache line on Thread1's core
// Performance: ~300 cycles per operation instead of ~1 cycle
// Detected by: perf c2c record ./app && perf c2c report
❌ Why this fails: False sharing looks like a data race in profilers (high cache miss rate, low IPC) but has no correctness issue — just catastrophic performance. The fix is alignment.

Interview Q&A — Multithreading

❓ What is priority inversion? How does an RTOS solve it?
Priority inversion: High-priority task H waits on a mutex held by low-priority task L. Medium-priority task M preempts L (L has lower priority than M), so M runs instead of L. L can't release the mutex, H can't proceed — H is effectively blocked by M, a lower-priority task. This violates priority-based scheduling. Solution — Priority Inheritance: when H blocks on a mutex held by L, L's priority is temporarily raised to H's level. L runs preempting M, finishes critical section, releases mutex, H can proceed, L's priority reverts. POSIX: pthread_mutexattr_setprotocol(PTHREAD_PRIO_INHERIT). FreeRTOS: xSemaphoreCreateMutex() has this built-in.
Follow-up questions interviewers ask:
  • What is priority ceiling protocol?
  • How is priority inversion different from deadlock?
  • Give a real-world example of priority inversion.
Common mistakes in answers:
  • Saying 'just use a higher-priority mutex' — priority ceiling is a specific protocol, not just raising priority.
  • Confusing priority inversion with deadlock — H isn't deadlocked, it's just delayed incorrectly.
❓ Explain the difference between mutex, semaphore, and condition variable.
Mutex: binary lock with ownership semantics. Only the thread that locked it can unlock it. Used for: mutual exclusion of a critical section. Semaphore: signaling primitive with a counter. Any thread can signal (post) or wait. No ownership. Use for: producer-consumer signaling (binary semaphore), resource pools (counting semaphore — allows N concurrent accesses). Condition variable: used WITH a mutex. Allows a thread to atomically release the mutex and sleep until a condition becomes true. Use for: waiting for a complex condition (queue not empty, data ready). Key difference: mutex is about exclusion; condition variable is about waiting for a state change.
Follow-up questions interviewers ask:
  • When would you use a counting semaphore?
  • Why does condition variable require a mutex?
  • What is a monitor? How does it relate to condition variables?
Common mistakes in answers:
  • Saying semaphore = mutex — semaphore has no ownership, is broader in use.
  • Saying you'd use condition variable without a predicate — spurious wakeups require a predicate.
