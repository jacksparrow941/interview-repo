System Design Interview Framework

System design interviews evaluate your ability to build large-scale systems. The interviewer is looking for structured thinking, awareness of tradeoffs, and real-world engineering judgment — not a perfect answer.

  1. Clarify requirements (5 min): What does it DO? What are non-functional requirements? Scale?
  2. Estimate scale (5 min): QPS, DAU, storage size, bandwidth. Determines architecture.
  3. High-level design (10 min): Key components, data flow, main APIs.
  4. Deep dive (15 min): Critical component. Interviewer usually steers this.
  5. Tradeoffs (5 min): What did you choose and why? What alternatives exist?

Case Study 1 — Design an AI Inference Service

Requirements: Serve ResNet-50 image classification. 10K QPS, p99 < 100ms, 99.9% availability. Support multiple models.

Client (mobile app / API consumer) │ HTTPS REST or gRPC ▼ API Gateway (authentication, rate limiting, routing) │ ▼ Inference Service Cluster (N GPU servers) ┌────────────────────────────────────────┐ │ Request Handler (async epoll loop) │ │ │ │ │ Dynamic Batcher (5ms window, 32 max)│ │ │ │ │ TensorRT Engine (GPU inference) │ │ │ │ │ Result Cache (Redis, 30s TTL) │ └────────────────────────────────────────┘ │ Model Registry (S3 / object store) Metrics (Prometheus + Grafana) Tracing (OpenTelemetry)
✅ DO THIS
// Dynamic batching — key for GPU throughput
class DynamicBatcher {
    struct PendingRequest {
        cv::Mat image;
        std::promise<std::vector<float>> promise;
    };
    std::queue<PendingRequest>    pending_;
    std::mutex                    mtx_;
    std::condition_variable       cv_;
    const size_t MAX_BATCH = 32;
    const std::chrono::milliseconds TIMEOUT{5};   // 5ms batch window

    void batch_loop() {
        while (running_) {
            std::vector<PendingRequest> batch;
            {
                std::unique_lock lk(mtx_);
                // Wait up to 5ms or until batch is full
                cv_.wait_for(lk, TIMEOUT, [this]{
                    return pending_.size() >= MAX_BATCH || stop_;
                });
                while (!pending_.empty() && batch.size() < MAX_BATCH) {
                    batch.push_back(std::move(pending_.front()));
                    pending_.pop();
                }
            }
            if (batch.empty()) continue;

            // Run GPU inference on batch of images
            auto results = engine_->run_batch(batch);
            for (size_t i = 0; i < batch.size(); ++i)
                batch[i].promise.set_value(std::move(results[i]));
        }
    }
public:
    std::future<std::vector<float>> infer(cv::Mat image) {
        std::promise<std::vector<float>> p;
        auto fut = p.get_future();
        {std::lock_guard lk(mtx_); pending_.push({image, std::move(p)});}
        cv_.notify_one();
        return fut;
    }
};
✅ Why this works: Dynamic batching is the single biggest throughput improvement for GPU inference. A GPU is designed for batch parallelism — 32 images at once is often only 2-3x slower than 1 image, giving 10x throughput improvement.
❌ AVOID THIS
// BAD: one-image-at-a-time inference
std::vector<float> infer(cv::Mat image) {
    return engine_->run(image);   // one image → full GPU round-trip overhead
}
// GPU utilization: ~5-10% (kernel launch overhead dominates)
// Throughput: limited by kernel launch latency (~50µs)
// With dynamic batching: 32 images for ~2x the GPU time = 16x better throughput

// BAD: synchronous inference on request thread
void handle_request(HttpRequest& req, HttpResponse& resp) {
    auto result = infer(req.image());   // BLOCKS request thread during inference!
    resp.write(result);
}
// With 100ms inference time: thread pool of 100 handles 1000 QPS maximum
// Better: async submit to GPU, release thread to handle other requests
❌ Why this fails: Synchronous per-request inference blocks a thread for each request duration. With async + batching: threads are only blocked for the HTTP parsing overhead, not the GPU inference time.

Case Study 2 — Design a Distributed Rate Limiter

Requirements: Rate limit 100K users at 100 req/min each. Consistent limit across all nodes. <100ms added latency.

Request → API Server N │ ├──► Redis Cluster (check+increment) │ (sharded by user_id hash) │ Lua script: atomic check and increment │ ├── Allowed → forward to backend └── Denied → 429 Too Many Requests Redis Cluster: 6 shards × 2 replicas Shard key: hash(user_id) % 6 Data: sorted_set(user_id) with TTL Lua atomicity: no race condition between check and increment
✅ DO THIS
-- Redis Lua script for sliding window rate limiting (atomic!)
local key = KEYS[1]              -- e.g., "ratelimit:user:12345"
local now = tonumber(ARGV[1])    -- current timestamp (microseconds)
local window = tonumber(ARGV[2]) -- window size in microseconds
local limit = tonumber(ARGV[3])  -- max requests per window
local req_id = ARGV[4]           -- unique request ID

-- Remove entries older than window
redis.call('ZREMRANGEBYSCORE', key, 0, now - window)
-- Count remaining entries
local count = redis.call('ZCARD', key)

if count < limit then
    -- Add this request's timestamp
    redis.call('ZADD', key, now, req_id)
    redis.call('EXPIRE', key, math.ceil(window / 1000000))
    return 1   -- allowed
else
    return 0   -- rate limited
end
-- Entire script runs atomically — no TOCTOU race between check and add
✅ Why this works: The Lua script is atomic — no other Redis command can execute between ZCARD and ZADD. Without atomicity, two concurrent requests could both pass the check and both increment, exceeding the limit by 2x.
❌ AVOID THIS
// BAD: non-atomic rate limiting — race condition
bool check_rate_limit(const std::string& user_id) {
    int count = redis.zcard("rl:" + user_id);   // check
    if (count >= LIMIT) return false;
    // RACE CONDITION: another request can pass check here
    redis.zadd("rl:" + user_id, now(), request_id);  // increment
    return true;
}
// Under concurrent load: two requests both read count=99 (limit=100)
// Both see count < limit, both zadd → count becomes 101
// Rate limit exceeded by concurrent requests

// BAD: in-memory rate limiting without Redis
// Each API server has its own counter
// 10 API servers: each allows 100 req/min → total 1000 req/min allowed
// User exploits by spreading requests across servers
❌ Why this fails: Always use Redis with Lua or Redis atomic commands (SET NX, INCR+EXPIRE) for distributed rate limiting. In-memory rate limiting is incorrect in a multi-server deployment.

Case Study 3 — Design a URL Shortener

Write path (POST /shorten): Client → API Server → ID Generator (Snowflake) → Base62 encode → PostgreSQL → return short URL Read path (GET /:code): Client → API Server → Redis cache lookup → hit: 301 redirect immediately → miss: PostgreSQL lookup → cache it → 301 redirect Scale numbers: Writes: 100 URLs/sec → 100M URLs/year → ~50GB storage (5 years) Reads: 10K redirects/sec → 95% Redis hit → 500 DB queries/sec
✅ DO THIS
// Snowflake ID for globally unique, roughly sortable IDs
// Format: [41 bits timestamp][10 bits machine_id][12 bits sequence]
// Generates 4096 IDs per millisecond per machine — no coordination needed

uint64_t generate_id() {
    auto now_ms = duration_cast<milliseconds>(steady_clock::now()
                                              .time_since_epoch()).count();
    auto seq = sequence_.fetch_add(1) & 0xFFF;   // 12-bit sequence
    return (now_ms << 22) | (machine_id_ << 12) | seq;
}

// Base62 encode the ID to get short code
std::string to_base62(uint64_t id) {
    const char* chars = "0123456789ABCDEFGHIJKLMNOPQRSTUVWXYZabcdefghijklmnopqrstuvwxyz";
    std::string result;
    while (id > 0) {
        result = chars[id % 62] + result;
        id /= 62;
    }
    return result;   // 7 chars handles 62^7 = 3.5 trillion URLs
}

// Postgres schema
// CREATE TABLE urls (
//     id BIGINT PRIMARY KEY,        -- Snowflake ID
//     short_code VARCHAR(10) NOT NULL UNIQUE,
//     long_url TEXT NOT NULL,
//     created_at TIMESTAMPTZ DEFAULT NOW(),
//     user_id BIGINT,
//     click_count BIGINT DEFAULT 0
// );
// CREATE INDEX ON urls(short_code);
✅ Why this works: Snowflake IDs are sortable by creation time (timestamp in high bits) — good for database indexing. No coordination needed between servers — machine_id makes IDs unique.

Interview Q&A — System Design

❓ How do you design for 99.9% availability (the 'three nines')?
99.9% = 8.76 hours downtime/year = 43.8 minutes/month = 1.44 minutes/day. Key techniques: (1) Eliminate single points of failure: every component has at least 2 replicas. Load balancer in front of all services. (2) Health checks + automatic failover: load balancer probes /health every 10s, removes unhealthy instances automatically. (3) Circuit breakers: if downstream service fails, fail fast instead of waiting (prevents cascading failures). (4) Graceful degradation: if recommendation service is down, serve default recommendations rather than error. (5) Rolling deployments: deploy new version to 10% of instances first, watch error rate, then roll out. (6) Database: primary-replica replication, automatic failover (Patroni for Postgres). (7) Multi-AZ/multi-region for higher availability. Calculate availability: two independent instances with 99.9% each = 1-(0.001^2) = 99.9999% (if both must fail to have downtime).
Follow-up questions interviewers ask:
  • What is the difference between 99.9% and 99.99% availability?
  • How does a circuit breaker work?
  • What is blue-green deployment?
Common mistakes in answers:
  • Saying 'just add more servers' — availability requires removing SPOFs, not just adding capacity.
  • Forgetting that deployment itself is a source of downtime without careful strategies.
❓ Design the data model for a distributed key-value store.
Storage engine: LSM-tree (Log-Structured Merge-tree) like RocksDB — optimized for writes. Writes go to in-memory memtable + WAL (Write-Ahead Log for durability). Memtable flushed to SSTable on disk when full. Background compaction merges SSTables and removes deleted keys. Keys partitioned across nodes using consistent hashing — each node owns a range. Replication: each key replicated to N=3 nodes (configurable). Consistency: quorum reads/writes (R=2, W=2, R+W>N guarantees reads see latest write). Operations: GET(key): route to any of N replicas for read, quorum vote on version. PUT(key,val): route to all N replicas, wait for W=2 ACKs. Version vectors for conflict detection (last-write-wins or application-level merge). MVCC for concurrent reads without blocking writes.
Follow-up questions interviewers ask:
  • How does consistent hashing handle node failure?
  • What is the difference between LSM-tree and B-tree storage?
  • How do you handle hot spots (one key getting all traffic)?
