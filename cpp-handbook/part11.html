Chapter 1 — Git: Internals and Best Practices

Git stores everything as content-addressed objects. Understanding the object model helps you resolve complex merges, recover 'lost' commits, and use git as a tool rather than a black box.

Git Object Model (.git/objects/): blob — raw file content. SHA1 = hash(content). No filename stored in blob — filename stored in tree. tree — directory listing: [(mode, name, sha1)...] References blobs (files) and other trees (subdirectories) commit — tree (root snapshot) + parent(s) + author + message Two commits with same tree SHA1 are identical snapshots tag — points to another object (usually commit) + message Every commit is a SNAPSHOT, not a diff. Diffs are computed on-demand by comparing two snapshots. DAG (Directed Acyclic Graph) of commits: A ← B ← C ← D (main) ↑ E ← F (feature branch) HEAD: pointer to current branch. Branch: pointer to a commit.
✅ DO THIS
# Essential git commands with explanation

# Interactive staging — commit only specific changes in a file
git add -p                        # review each hunk, stage selectively

# Fix last commit without creating a new one
git commit --amend --no-edit      # add staged changes to last commit silently
git commit --amend -m "better msg" # just fix the message

# Clean up local history before PR (rebase interactively)
git rebase -i HEAD~4              # squash, reorder, edit last 4 commits
# In editor: pick=keep, squash=merge into prev, fixup=squash+drop msg, reword=edit msg

# Binary search for the commit that introduced a bug
git bisect start
git bisect bad HEAD               # current commit is broken
git bisect good v1.0.0            # this tag was fine
# Git checks out middle commit. Test. Then:
git bisect good  # or bad — git narrows down. O(log n) attempts!
git bisect reset # done

# Recover "deleted" commits (reflog keeps all HEAD movements for 90 days)
git reflog                        # shows all HEAD positions with timestamps
git checkout HEAD@{3}             # go back to where HEAD was 3 moves ago
git branch recovery HEAD@{3}      # create branch to save it

# Work on two branches simultaneously
git worktree add ../hotfix hotfix-v1.2  # second checkout in ../hotfix/
# Now you can run two terminals: one in main, one in hotfix
# No stashing needed!
✅ Why this works: git bisect is underutilised. For a regression that appeared in a 500-commit range: bisect does ~9 tests (log2(500)) instead of manually testing each commit. Essential for performance regressions.
❌ AVOID THIS
# BAD: force-pushing to shared branches — overwrites others' work
git push --force origin main     # DO NOT do this on shared branches!
# Teammates who have fetched will have diverged history
# They must do: git pull --rebase — potentially losing work

# Fix: use --force-with-lease which fails if someone else pushed
git push --force-with-lease      # safe force: fails if remote was updated

# BAD: committing large binaries to git
git add model_weights.h5         # 2GB model weights committed to history
# Git stores full copy in every clone — 2GB per developer
# Impossible to remove from history without git filter-branch/BFG

# Fix: Git LFS (Large File Storage) for binary assets
git lfs track "*.bin" "*.h5" "*.onnx"  # track large files separately
git add .gitattributes && git commit -m "chore: track large files in LFS"

# BAD: committing secrets (API keys, passwords)
git add config.h  # contains: #define AWS_SECRET_KEY "AKIAIOSFODNN7..."
# Secret is in git history forever — even after deletion in next commit
# git log -S 'AKIAIOSFODNN7' will find it

# Fix: use environment variables, never commit secrets
# Add to .gitignore: *.env, config/secrets.h, credentials.json
❌ Why this fails: Force-pushing rewrites history — teammates' local branches become diverged. Always use --force-with-lease as a safety net. Secrets in git history must be treated as compromised — rotation required.

Chapter 2 — Docker: Containers for C++ and AI

Docker packages your application with all dependencies into a reproducible, isolated container. Essential for: reproducible CI builds, GPU inference deployment, multi-version testing.

✅ DO THIS
# Multi-stage Dockerfile for C++ AI runtime
# Stage 1: Builder — full build environment (large)
FROM ubuntu:22.04 AS builder

# Install build tools — combine into one RUN to minimize layers
RUN apt-get update && apt-get install -y --no-install-recommends     cmake=3.22*     ninja-build     g++-12     libssl-dev     && rm -rf /var/lib/apt/lists/*   # clean up — reduces image size

WORKDIR /src
# Copy dependency files first — enables layer caching
# If CMakeLists.txt doesn't change, this layer is cached even if source changes
COPY CMakeLists.txt .
COPY cmake/ cmake/
RUN cmake -B build -G Ninja     -DCMAKE_BUILD_TYPE=Release     -DCMAKE_CXX_COMPILER=g++-12     -DCMAKE_CXX_FLAGS="-O3 -march=native"
COPY src/ src/
COPY include/ include/
RUN cmake --build build --target inference_server -j$(nproc)

# Stage 2: Runtime — minimal image (small, deployed)
FROM ubuntu:22.04 AS runtime
RUN apt-get update && apt-get install -y --no-install-recommends     libgomp1     && rm -rf /var/lib/apt/lists/*

# Non-root user for security
RUN useradd -m -u 1001 appuser

# Copy ONLY the binary and required assets
COPY --from=builder /src/build/inference_server /usr/local/bin/
COPY models/ /models/

USER appuser
EXPOSE 8080
HEALTHCHECK --interval=30s --timeout=5s     CMD curl -f http://localhost:8080/health || exit 1
ENTRYPOINT ["/usr/local/bin/inference_server"]
CMD ["--port=8080", "--model-dir=/models"]
✅ Why this works: Multi-stage builds are essential for C++. Builder stage can be 2GB+ (compilers, headers). Runtime stage can be 50MB. NEVER ship the build tools in production images — they're attack surface.
❌ AVOID THIS
# BAD: single-stage Dockerfile — ships build tools in production
FROM ubuntu:22.04
RUN apt-get install -y cmake g++ libssl-dev ninja-build python3
COPY . .
RUN cmake -B build && cmake --build build
# Result: 2.5GB image with:
# - gcc (400MB), cmake, ninja, Python, all dev headers
# - These are attack surface — unnecessary in production
# - CVE in development tools = vulnerability in your production image

# BAD: running as root
USER root  # default — most base images run as root
ENTRYPOINT ["./server"]
# If server has a vulnerability → attacker has root in container
# Root in container can often escape to host (depends on container config)

# BAD: not specifying package versions — non-reproducible builds
RUN apt-get install -y cmake  # installs "latest" cmake
# CI builds today may use cmake 3.22; next month uses 3.28
# Build breaks silently when cmake API changes between versions
❌ Why this fails: Always pin package versions in Dockerfiles for reproducibility. Run as non-root. Use multi-stage builds. Scan images with trivy or snyk for CVEs before deployment.

Chapter 3 — Kubernetes: Running AI Inference at Scale

✅ DO THIS
# Complete deployment for GPU inference server
# deployment.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: inference-server
  namespace: production
spec:
  replicas: 3
  selector:
    matchLabels: {app: inference}
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxUnavailable: 1    # at most 1 pod unavailable during update
      maxSurge: 1          # at most 1 extra pod during update
  template:
    metadata:
      labels: {app: inference}
      annotations:
        prometheus.io/scrape: "true"
        prometheus.io/port: "9090"
    spec:
      containers:
      - name: server
        image: myrepo/inference:v1.2.3   # always pin to specific version, not 'latest'
        ports:
        - containerPort: 8080
        resources:
          requests:
            memory: "2Gi"
            cpu: "1000m"
            nvidia.com/gpu: "1"
          limits:
            memory: "4Gi"
            cpu: "2000m"
            nvidia.com/gpu: "1"
        # Readiness: is pod ready to serve traffic?
        readinessProbe:
          httpGet: {path: /ready, port: 8080}
          initialDelaySeconds: 30   # wait for model loading
          periodSeconds: 5
          failureThreshold: 3
        # Liveness: is pod still alive?
        livenessProbe:
          httpGet: {path: /health, port: 8080}
          initialDelaySeconds: 60
          periodSeconds: 15
          failureThreshold: 4
        env:
        - name: MODEL_PATH
          value: /models/resnet50
        - name: MAX_BATCH_SIZE
          value: "32"
        volumeMounts:
        - name: model-storage
          mountPath: /models
          readOnly: true
      volumes:
      - name: model-storage
        persistentVolumeClaim:
          claimName: model-pvc
---
# HorizontalPodAutoscaler — scale based on GPU utilization or custom metric
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: inference-hpa
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: inference-server
  minReplicas: 2
  maxReplicas: 10
  metrics:
  - type: Resource
    resource:
      name: cpu
      target:
        type: Utilization
        averageUtilization: 70
✅ Why this works: Pin image versions — 'latest' in production means unpredictable deployments when the image changes. Always use specific SHA or semantic version tags.

Chapter 4 — CI/CD Pipeline for C++

✅ DO THIS
# .github/workflows/ci.yml — production-grade CI for C++ AI runtime
name: CI
on:
  push:
    branches: [main, release/*]
  pull_request:
    branches: [main]

jobs:
  # Job 1: Static analysis (fast, catches issues before compile)
  lint:
    runs-on: ubuntu-22.04
    steps:
    - uses: actions/checkout@v4
    - name: clang-format check
      run: find src include -name "*.cpp" -o -name "*.h" |
             xargs clang-format --dry-run --Werror
    - name: clang-tidy
      run: cmake -B build -DCMAKE_EXPORT_COMPILE_COMMANDS=ON &&
           run-clang-tidy -p build src/

  # Job 2: Build matrix (multiple compilers and build types)
  build-test:
    runs-on: ubuntu-22.04
    needs: lint
    strategy:
      fail-fast: false   # run all combinations even if one fails
      matrix:
        compiler: [g++-11, g++-12, clang-14, clang-15]
        build_type: [Debug, Release]
        exclude:
        - compiler: g++-11   # skip Debug+g++-11 (too slow)
          build_type: Debug
    steps:
    - uses: actions/checkout@v4
      with: {submodules: recursive}
    - name: Install dependencies
      run: sudo apt-get install -y ${{ matrix.compiler }} cmake ninja-build
    - name: Configure
      run: cmake -B build -G Ninja
             -DCMAKE_CXX_COMPILER=${{ matrix.compiler }}
             -DCMAKE_BUILD_TYPE=${{ matrix.build_type }}
    - name: Build
      run: cmake --build build --parallel $(nproc)
    - name: Test
      run: cd build && ctest --output-on-failure --parallel $(nproc)

  # Job 3: Sanitizers (debug build with ASan + TSan)
  sanitizers:
    runs-on: ubuntu-22.04
    needs: lint
    steps:
    - uses: actions/checkout@v4
    - name: ASan + UBSan
      run: |
        cmake -B build_asan -DCMAKE_BUILD_TYPE=Debug
          -DCMAKE_CXX_FLAGS="-fsanitize=address,undefined -fno-sanitize-recover=all"
        cmake --build build_asan --parallel $(nproc)
        cd build_asan && ctest --output-on-failure
    - name: TSan (separate build — incompatible with ASan)
      run: |
        cmake -B build_tsan -DCMAKE_BUILD_TYPE=Debug
          -DCMAKE_CXX_FLAGS="-fsanitize=thread"
        cmake --build build_tsan --parallel $(nproc)
        cd build_tsan && ctest --output-on-failure

  # Job 4: Performance benchmark regression
  benchmark:
    runs-on: [self-hosted, linux, gpu]   # needs actual GPU
    needs: build-test
    steps:
    - uses: actions/checkout@v4
    - name: Build Release
      run: cmake -B build -DCMAKE_BUILD_TYPE=Release && cmake --build build -j4
    - name: Run benchmarks
      run: ./build/benchmarks --benchmark-out=results.json
    - name: Compare vs baseline
      run: python3 compare_benchmarks.py baseline.json results.json
           --fail-threshold 0.05  # fail if any benchmark regresses >5%
✅ Why this works: The benchmark regression job is what keeps performance from slowly degrading over many commits. A 5% threshold prevents alarm fatigue while catching real regressions.

Interview Q&A — DevOps

❓ What is the difference between Docker and a VM? When would you use each?
VM (Virtual Machine): virtualizes hardware. Each VM has its own OS kernel, device drivers, and full userspace. Hypervisor (VMware, KVM, VirtualBox) manages VMs. Overhead: ~1-2% CPU, ~1GB+ image, 30-60s startup. Strong isolation — separate kernels means a kernel exploit in one VM doesn't affect others. Container: virtualizes userspace only. All containers share the host kernel — different processes with different filesystem namespaces (using Linux namespaces: PID, net, mnt, uts, ipc) and resource limits (cgroups). Overhead: ~0.1% CPU, ~10-100MB image, <1s startup. Weaker isolation — a kernel vulnerability affects all containers. Use containers: microservices, CI/CD pipelines, consistent environments, fast scaling. Use VMs: strong security isolation requirements, different OS kernels (Windows workloads on Linux host), hardware-level isolation for multi-tenant environments.
Follow-up questions interviewers ask:
  • What is containerd? What is the OCI specification?
  • How do Docker namespaces work?
  • What is a container escape and how is it prevented?
Common mistakes in answers:
  • Saying containers are as secure as VMs — they share the kernel, which is a significant difference.
  • Saying Docker IS a container — Docker is a tool for building/running containers. containerd is the runtime. runc creates the actual container.
❓ How would you set up a CI/CD pipeline for a C++ inference runtime?
Stages: (1) Lint (fast, catch early): clang-format --dry-run, clang-tidy, cmake --check. (2) Build matrix: all combinations of compiler (GCC/Clang) × build type (Debug/Release) × platform (x86/ARM). Fail fast on any. (3) Unit tests: ctest with parallel execution. Minimum 80% coverage. (4) Sanitizers: separate ASan+UBSan and TSan builds and test runs. (5) Integration tests: run inference on reference inputs, compare outputs vs golden files (cosine similarity > 0.999, max error < 1e-4). (6) Performance benchmarks: compare vs baseline, fail if p99 latency regresses >5%. (7) Docker build: multi-stage, tag with git SHA. Push to registry. (8) Deploy to staging: kubectl rollout. (9) Smoke tests on staging: end-to-end request with expected output verification. (10) Manual approval gate. (11) Rollout to production: 10% → 50% → 100% canary.
Follow-up questions interviewers ask:
  • How do you handle flaky tests in CI?
  • What is a canary deployment?
  • How do you roll back quickly if production deployment fails?
