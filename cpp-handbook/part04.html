Chapter 1 — TCP/IP Stack

Application (HTTP, gRPC, DNS) │ creates message ▼ Transport (TCP/UDP) — adds port numbers, seq numbers, checksum │ ▼ Network (IP) — adds src/dst IP, TTL, routing │ ▼ Link (Ethernet) — adds MAC addresses, CRC │ ▼ Physical — bits on wire

TCP Connection Lifecycle

3-Way Handshake: Client Server ──SYN(seq=x)──────► SYN_RCVD ◄──SYN-ACK(seq=y,ack=x+1)── ──ACK(ack=y+1)────► ESTABLISHED 4-Way Teardown (active close by client): Client Server ──FIN──────────────► (server enters CLOSE_WAIT) ◄──ACK─────────────── ◄──FIN─────────────── (server closes its side) ──ACK──────────────► Client: TIME_WAIT (waits 2×MSL ≈ 60s) Server: CLOSED
✅ DO THIS
// TCP server with non-blocking I/O + epoll (scales to 100K+ connections)
#include <sys/epoll.h>

int server_fd = socket(AF_INET, SOCK_STREAM | SOCK_NONBLOCK, 0);

// Critical socket options
int opt = 1;
setsockopt(server_fd, SOL_SOCKET, SO_REUSEADDR, &opt, sizeof(opt));
// SO_REUSEADDR: reuse port in TIME_WAIT state — essential for fast server restart

setsockopt(server_fd, IPPROTO_TCP, TCP_NODELAY, &opt, sizeof(opt));
// TCP_NODELAY: disable Nagle algorithm — send small packets immediately
// Essential for low-latency RPC (gRPC disables Nagle by default)

// Large socket buffers for high throughput
int buf_size = 4 * 1024 * 1024;   // 4MB
setsockopt(server_fd, SOL_SOCKET, SO_RCVBUF, &buf_size, sizeof(buf_size));
setsockopt(server_fd, SOL_SOCKET, SO_SNDBUF, &buf_size, sizeof(buf_size));

sockaddr_in addr{};
addr.sin_family = AF_INET;
addr.sin_port   = htons(8080);
addr.sin_addr.s_addr = INADDR_ANY;
bind(server_fd, (sockaddr*)&addr, sizeof(addr));
listen(server_fd, SOMAXCONN);   // SOMAXCONN: max backlog

// epoll event loop
int epfd = epoll_create1(0);
epoll_event ev{EPOLLIN | EPOLLET, {.fd = server_fd}};  // edge-triggered
epoll_ctl(epfd, EPOLL_CTL_ADD, server_fd, &ev);

epoll_event events[256];
while (true) {
    int n = epoll_wait(epfd, events, 256, -1);
    for (int i = 0; i < n; ++i) {
        if (events[i].data.fd == server_fd) {
            int conn = accept4(server_fd, nullptr, nullptr, SOCK_NONBLOCK);
            epoll_event ce{EPOLLIN | EPOLLET, {.fd = conn}};
            epoll_ctl(epfd, EPOLL_CTL_ADD, conn, &ce);
        } else {
            handle_connection(events[i].data.fd);
        }
    }
}
✅ Why this works: epoll is O(active events) — scales to 100K connections without performance degradation. select() and poll() are O(total fds) — fail at high connection counts.
❌ AVOID THIS
// BAD: select() or poll() for high-connection servers
// select() has two problems:
// 1. FD_SETSIZE limit: typically 1024 file descriptors max
// 2. O(n) scan: copies and scans entire fd_set on every call
// At 10K connections: 10K fds scanned per wake → unusable

// BAD: fork() per connection (Apache pre-fork model)
// One process per connection: 10K connections = 10K processes
// Each process: ~8MB stack + page tables → 80GB for 10K connections
// Context switch: ~10µs × 10K = 100ms just in scheduling overhead

// BAD: thread per connection
// One thread per connection: 10K connections = 10K threads
// Default 8MB stack per thread: 80GB for stacks alone
// Context switches: expensive for idle threads
// Threshold: thread-per-connection works up to ~100-1000 connections

// GOOD alternatives:
// - epoll + event loop + thread pool (nginx model)
// - io_uring for even lower overhead (Linux 5.1+)
❌ Why this fails: Thread/process per connection doesn't scale. A modern inference server might have 10K concurrent HTTP/2 connections — only epoll or io_uring handles this efficiently.

HTTP/2 HOL blocking explained: HTTP/2 multiplexes multiple streams over one TCP connection. If a TCP segment is lost, ALL streams wait for retransmission — TCP-level HOL blocking. HTTP/3 uses QUIC (UDP-based) where each stream is independent — one stream's loss doesn't block others.

Chapter 3 — gRPC & Protocol Buffers

✅ DO THIS
// model.proto
syntax = "proto3";
package inference;

service ModelService {
    rpc Predict (PredictRequest)  returns (PredictResponse);
    rpc PredictStream (PredictRequest) returns (stream PredictResponse);
    rpc BatchPredict  (stream PredictRequest) returns (stream PredictResponse);
}

message PredictRequest {
    bytes  image_data  = 1;   // field number 1: encoded as 0x0A in wire format
    string model_name  = 2;
    float  confidence_threshold = 3;
    map<string, string> metadata = 4;
}
message PredictResponse {
    repeated float   scores  = 1;   // packed encoding for numeric arrays
    repeated string  labels  = 2;
    float            latency_ms = 3;
}

// C++ client:
auto channel = grpc::CreateChannel("inference:50051",
    grpc::InsecureChannelCredentials());
auto stub = ModelService::NewStub(channel);

grpc::ClientContext ctx;
ctx.set_deadline(std::chrono::system_clock::now()
                 + std::chrono::milliseconds(500));  // 500ms timeout

PredictRequest req;
req.set_model_name("resnet50");
req.set_image_data(image_bytes);

PredictResponse resp;
auto status = stub->Predict(&ctx, req, &resp);
if (!status.ok())
    throw std::runtime_error("gRPC error: " + status.error_message());

for (int i = 0; i < resp.scores_size(); ++i)
    std::cout << resp.labels(i) << ": " << resp.scores(i) << "\n";
✅ Why this works: Always set a deadline on gRPC calls — without it, a slow server will block the client indefinitely. gRPC's deadline propagates through the call chain automatically.
❌ AVOID THIS
// BAD: gRPC without deadline — hangs indefinitely on server issues
auto status = stub->Predict(&ctx, req, &resp);  // ctx has no deadline
// If server is slow, overloaded, or hung: client waits forever

// BAD: creating a new channel per request — extremely expensive
void handle_request(Request& req) {
    auto channel = grpc::CreateChannel(...);   // TCP + TLS handshake every time!
    auto stub = Service::NewStub(channel);
    // This adds ~50-200ms latency per request!
}
// FIX: create channel once, reuse stub for all requests
// gRPC channels maintain a connection pool internally

// BAD: ignoring metadata size limits
ctx.AddMetadata("user-data", huge_string);  // gRPC has 4MB default limit
// Headers too large → server rejects with RESOURCE_EXHAUSTED
❌ Why this fails: Channel creation involves DNS resolution + TCP handshake + TLS handshake — ~100ms. Creating a new channel per RPC adds unacceptable latency. Create once, reuse the stub.

Chapter 4 — TLS 1.3 Handshake

TLS 1.3 Handshake (1-RTT, compared to TLS 1.2's 2-RTT): Client Server ──ClientHello──────────────────► (supported ciphers, key shares for multiple groups) ◄──ServerHello────────────────── (chosen cipher, server's key share) ◄──{EncryptedExtensions}───────── (encrypted with handshake key) ◄──{Certificate}───────────────── (server's X.509 cert) ◄──{CertificateVerify}─────────── (signature over transcript hash) ◄──{Finished}──────────────────── (MAC over transcript) ──{Finished}───────────────────► (MAC over transcript) ══ Application Data (encrypted) ══ 0-RTT (for reconnecting clients): ──ClientHello + EarlyData──────► (reuse pre-shared key from previous session) ══ Application Data immediately ══ (before server responds!) Risk: replay attacks — don't use 0-RTT for non-idempotent requests

Chapter 5 — Zero-Copy Networking

✅ DO THIS
// Method 1: sendfile() — kernel copies file to socket without user-space copy
// Traditional: file → page cache → user buffer → kernel socket buffer → NIC
// sendfile:   file → page cache ──────────────→ NIC (2 copies instead of 4)

#include <sys/sendfile.h>
ssize_t sent = sendfile(sock_fd,    // destination socket
                        file_fd,    // source file
                        &offset,    // file offset (updated by sendfile)
                        file_size); // bytes to send
// Used by: nginx static file serving, Kafka log shipping

// Method 2: splice() — pipe between two fds without user-space copy
#include <fcntl.h>
int pipefd[2];
pipe(pipefd);
splice(file_fd, nullptr, pipefd[1], nullptr, chunk, SPLICE_F_MOVE);
splice(pipefd[0], nullptr, sock_fd, nullptr, chunk, SPLICE_F_MOVE | SPLICE_F_MORE);

// Method 3: io_uring (Linux 5.1+) — async I/O with submission ring buffer
// Batches I/O operations to reduce syscall overhead
struct io_uring ring;
io_uring_queue_init(256, &ring, 0);
io_uring_sqe* sqe = io_uring_get_sqe(&ring);
io_uring_prep_send(sqe, sock_fd, buf, len, 0);
io_uring_sqe_set_data(sqe, &context);
io_uring_submit(&ring);
// ... later ...
io_uring_cqe* cqe;
io_uring_wait_cqe(&ring, &cqe);
int result = cqe->res;   // bytes sent or error
✅ Why this works: sendfile is used by nginx for all static file serving. At 10Gbps network speeds, the difference between copying through user-space and zero-copy is the bottleneck.

Interview Q&A — Networks

❓ Why does TCP have TIME_WAIT? How do you mitigate the port exhaustion problem?
TIME_WAIT lasts 2×MSL (Maximum Segment Lifetime, typically 60s) after the active closer sends the final ACK. Two reasons: (1) Ensure any delayed packets from the old connection don't corrupt a new connection with the same 4-tuple (src_ip, src_port, dst_ip, dst_port). (2) Guarantee the remote side received the final ACK — if the ACK is lost, the remote retransmits FIN, and the TIME_WAIT side re-ACKs. Problem: high-QPS servers making many outgoing connections exhaust ephemeral ports (~28K-60K). Each TIME_WAIT ties up a port for 60s. Fix: SO_REUSEADDR (allows reusing TIME_WAIT ports for new connections with different remote addr), increase net.ipv4.ip_local_port_range to 1024-65535, SO_LINGER(0) sends RST instead (risky — may lose data), connection pools (reuse existing connections instead of creating new ones), HTTP/2 (multiplexes 1000s of requests on one connection).
Follow-up questions interviewers ask:
  • What is the difference between TIME_WAIT and CLOSE_WAIT?
  • What is TCP FIN_WAIT_2 state?
  • How does HTTP/2 help with port exhaustion?
Common mistakes in answers:
  • Confusing TIME_WAIT (client side) with CLOSE_WAIT (server side — means server hasn't called close() yet).
  • Saying SO_REUSEADDR allows multiple connections with same 4-tuple — it doesn't.
❓ Explain TCP congestion control — how does the kernel decide how fast to send?
TCP congestion control maintains cwnd (congestion window): max bytes in flight. Phases: Slow Start: cwnd starts at ~10 MSS, doubles every RTT (exponential growth until ssthresh). Congestion Avoidance: cwnd grows by 1 MSS per RTT (linear) once cwnd >= ssthresh. Loss detection: 3 duplicate ACKs → packet loss → reduce cwnd. Timeout → severe congestion → reset cwnd to 1. Algorithms: Reno: cut cwnd in half on 3 dup ACKs. CUBIC (Linux default): cubic function of time since last loss — recovers faster on high-bandwidth-delay-product links. BBR (Google): model-based, measures actual bottleneck bandwidth and RTT — doesn't wait for loss to detect congestion. BBR achieves higher throughput on satellite links and is used in YouTube.
Follow-up questions interviewers ask:
  • Why does BBR sometimes cause unfairness with CUBIC flows?
  • What is the bandwidth-delay product?
  • How does QUIC handle congestion differently than TCP?
