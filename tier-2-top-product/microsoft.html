2 Number of Islands

Medium 92%
Approach
DFS or BFS. When land cell found, increment count and DFS to mark all connected land as visited.
Solution
def numIslands(grid):
    if not grid: return 0
    count = 0
    def dfs(r, c):
        if r < 0 or r >= len(grid) or c < 0 or c >= len(grid[0]): return
        if grid[r][c] != '1': return
        grid[r][c] = '0'  # mark visited
        for dr, dc in [(0,1),(0,-1),(1,0),(-1,0)]:
            dfs(r+dr, c+dc)
    for r in range(len(grid)):
        for c in range(len(grid[0])):
            if grid[r][c] == '1':
                count += 1; dfs(r, c)
    return count

Complexity
Time: O(m×n) | Space: O(m×n) recursion stack

from collections import deque
def levelOrder(root):
    if not root: return []
    res, q = [], deque([root])
    while q:
        level = []

12 Meeting Rooms II
heapgreedyintervals
Medium 82%
Approach
DP with memoization. dp[i][j] = LCS length of s1[i:] and s2[j:]. If chars match: 1 + dp[i+1][j+1]. Else max(dp[i+1][j], dp[i][j+1]).
Solution
def longestCommonSubsequence(text1, text2):
    m, n = len(text1), len(text2)
    dp = [[0]*(n+1) for _ in range(m+1)]
    for i in range(m-1,-1,-1):
        for j in range(n-1,-1,-1):
            if text1[i]==text2[j]:
                dp[i][j] = 1 + dp[i+1][j+1]
            else:
                dp[i][j] = max(dp[i+1][j], dp[i][j+1])
    return dp[0][0]

17 Trapping Rain Water

Hard 78%
Approach
Two pointer from both ends. Track left_max and right_max. Water at index i = min(left_max, right_max) - height[i]. Move the shorter side inward.
Solution
def trap(height):
    l, r = 0, len(height)-1
    lmax = rmax = water = 0
    while l < r:
        if height[l] <= height[r]:
            if height[l] >= lmax: lmax = height[l]
            else: water += lmax - height[l]
            l += 1
        else:
            if height[r] >= rmax: rmax = height[r]

            r -= 1
    return water

5 Design a distributed key-value store (like Redis/DynamoDB)
distributed-kvconsistent-hashingreplication
Hard 88%
Architecture
Client → Load Balancer → Coordinator Node
                            ↓ (consistent hash ring)
                        Partition 0 → Replica A, B, C
                        Partition 1 → Replica D, E, F
                        ...
Data Distribution
Consistent hashing: keys mapped to ring. Each node owns a range. Virtual nodes (vnodes): each physical node = 100-200 vnodes for even distribution. Adding/removing node: only adjacent vnodes affected.
Replication
Each key replicated to N nodes (typically N=3, DynamoDB style). Coordinator writes to all N. Quorum: W=2 (write), R=2 (read) → W+R>N = strong consistency. W=1, R=1 → eventual consistency, highest availability.
Conflict Resolution
Vector clocks track causality. On divergent versions (network partition): return both to client (DynamoDB shopping cart), or last-write-wins (LWW) for simpler cases.
Storage Engine
LSM Tree (write-optimized): MemTable → immutable SSTable → compaction. B+Tree (read-optimized): InnoDB, LMDB. LSM preferred for KV stores: fast sequential writes, compaction amortizes cost.

3 How do Docker image layers work? (Union filesystem)

Answer
Docker images are built as read-only layers stacked using a Union Filesystem (OverlayFS/AUFS). Each RUN, COPY, ADD instruction in a Dockerfile creates a new layer.

When a container runs, Docker adds a thin read-write layer on top (Copy-on-Write). Writes go to the container layer; reads search layers bottom-up.

12 Kubernetes HPA — Horizontal Pod Autoscaler, how does it work?
kuberneteshpaautoscaling
Medium 85%
How HPA works
HPA watches metrics (CPU, memory, custom) via the Metrics API and adjusts pod replica count.

Control loop (every 15s):
desiredReplicas = ceil(currentReplicas × currentMetric / targetMetric)
e.g., 3 pods at 90% CPU, target 50% → ceil(3 × 90/50) = 6 pods
Setup
kubectl autoscale deployment app \
  --cpu-percent=50 --min=2 --max=20

# Or declarative:
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
spec:
  scaleTargetRef:
    kind: Deployment
    name: app
  minReplicas: 2
  maxReplicas: 20
  metrics:
  - type: Resource
    resource:
      name: cpu
      target:
        type: Utilization
        averageUtilization: 50
VPA vs HPA vs KEDA

  • VPA: adjusts CPU/memory requests per pod (vertical) — requires restart

Requests vs Limits
Requests: Minimum guaranteed resources. Used by scheduler to find a node with enough capacity.
Limits: Maximum allowed. CPU is throttled if exceeded. Memory: container is OOMKilled if exceeded.
QoS Classes
  • Guaranteed: requests == limits for all containers. Highest priority, last to be evicted.

Input: sequence of tokens → embeddings (d_model=768 for BERT-base)

10 PostgreSQL MVCC — how it achieves non-blocking reads

MVCC = Multi-Version Concurrency Control
Each row has hidden columns:
  • xmin: transaction ID that inserted this version
  • xmax: transaction ID that deleted/updated this version (0 = still live)
Reads see a snapshot: only versions where xmin ≤ snapshot_xid < xmax.
How it works
T1 (xid=100): UPDATE users SET name='Bob' WHERE id=1
→ Old row: xmin=50, xmax=100  (now dead to T1)
→ New row: xmin=100, xmax=0   (live)

T2 (xid=99, started before T1):
→ Sees old row (xmin=50 <= 99 < xmax=100) ✓
→ Sees 'Alice' — no blocking!

T3 (xid=101, started after T1 commits):
→ Old row: xmax=100 <= 101 → dead, skip
→ New row: xmin=100 <= 101, xmax=0 → live, sees 'Bob' ✓
VACUUM
Dead rows (old versions) accumulate. VACUUM reclaims space. AUTOVACUUM runs automatically. Transaction ID wraparound prevented by freezing old rows.

What is WAL
Before modifying data pages in memory (buffer pool), the change is written to the WAL log first. On crash: replay WAL from last checkpoint to recover committed transactions. Guarantee: committed data never lost, even on sudden crash.

1. Transaction modifies data in buffer pool (in-memory dirty page)
2. WAL record written to WAL buffer → flushed to disk (fsync)

Virtual Memory
Each process has its own virtual address space (e.g., 0 to 2^48 on 64-bit). OS maps virtual pages → physical frames via page table. Allows: isolation between processes, overcommit memory, memory-mapped files, copy-on-write.
Multi-level Page Tables
64-bit systems use 4-level (x86-64) or 5-level page tables to reduce space. Each level is a 4KB page of 512 8-byte entries. Virtual address split:
[sign ext | L4 (9) | L3 (9) | L2 (9) | L1 (9) | Offset (12)]

Hardware cache for recent virtual→physical translations. TLB hit: 1 cycle. TLB miss: walk page table (several cycles + memory accesses). TLB flushed on context switch (unless ASID used). Huge pages (2MB/1GB) reduce TLB misses.

  • Major: Page not in memory → read from disk (swap). Expensive (~ms)
  • Invalid: Access to unmapped address → SIGSEGV

4 Deadlock — conditions, prevention, avoidance, detection

Coffman's Four Necessary Conditions
  • Mutual Exclusion: Resources not sharable
  • Hold and Wait: Process holds resource while waiting for another
  • No Preemption: Resources can't be forcibly taken
  • Circular Wait: T1→waits for T2→waits for T3→waits for T1
Breaking any one prevents deadlock.
Prevention
  • Eliminate Hold and Wait: Request all resources at once before starting
  • Allow Preemption: If waiting, release held resources (costly)
  • Eliminate Circular Wait: Global ordering of resources (always lock in same order)
Avoidance — Banker's Algorithm
Each process declares max resource claim. System checks if granting a request leaves system in safe state (all processes can complete). If unsafe → deny and wait. Used in theory; impractical for dynamic systems.
Detection and Recovery
Allow deadlocks to occur. Periodically run deadlock detector (wait-for graph cycle detection). Recovery: kill one victim process, or preempt + rollback resources.

8 Spinlock vs Mutex vs Semaphore — detailed comparison
spinlockmutexsemaphore
Hard 84%
Spinlock
Thread loops (busy-waits) until lock is free. No OS involvement for uncontended case.
Pros: Near-zero overhead for very short critical sections, no context switch.
Cons: Wastes CPU if lock held long, terrible on uniprocessor, can cause priority inversion.
Use when: Critical section <~100ns (kernel code, interrupt handlers, lock-free structures).
Mutex
Thread puts itself to sleep if lock unavailable. OS wakes it when lock released.
Pros: No CPU waste while waiting, works with long critical sections.
Cons: Context switch overhead (~1-10μs), kernel involvement.
Adaptive Mutex (Linux futex): Spin briefly, then sleep. Best of both worlds.
Semaphore
Generalized mutex: can allow N concurrent holders (counting semaphore). Binary semaphore = mutex but can be released by different thread (unlike mutex, which must be released by owner). Use for: resource pools, producer-consumer signaling.
futex (Linux fast userspace mutex)
Check lock in userspace (atomic). Only make syscall when contended (wait/wake). Foundation of pthread_mutex, Java synchronized.

CFS Algorithm
CFS maintains a virtual runtime (vruntime) per process — time the process has run, weighted by priority (nice value). Always picks the process with minimum vruntime (leftmost node in red-black tree).
vruntime Update
vruntime += actual_runtime × (NICE_0_WEIGHT / task_weight)
# Low-priority (high nice) tasks: vruntime increases faster → scheduled less
# High-priority (low nice): vruntime increases slower → scheduled more
Time Slice
No fixed time slice in CFS. Scheduling period (default 6ms) divided proportionally by weights. Minimum granularity: 0.75ms. Prevents starvation.
Priority Inheritance
When high-priority task blocks on mutex held by low-priority task → boost low-priority task's priority temporarily to prevent priority inversion (critical in RT systems).

class SnowflakeIdGenerator {
    private final long EPOCH = 1288834974657L;  // Nov 4, 2010
    private final long MACHINE_ID;              // 0-1023
    private long sequence = 0;
    private long lastTs = -1;

    synchronized long nextId() {
        long ts = System.currentTimeMillis();
        if (ts == lastTs) {
            sequence = (sequence + 1) & 0xFFF;  // 12-bit mask
            if (sequence == 0) ts = waitNextMs(lastTs);  // sequence exhausted
        } else { sequence = 0; }
        lastTs = ts;
        return ((ts - EPOCH) << 22) | (MACHINE_ID << 12) | sequence;
    }

    private long waitNextMs(long ts) {
        long now = System.currentTimeMillis();
        while (now <= ts) now = System.currentTimeMillis();
        return now;
    }
}

6 Design a Circuit Breaker

Hard 86%
States
CLOSED → calls go through. OPEN → calls fail-fast (no downstream). HALF_OPEN → probe call, if succeeds → CLOSED, else → OPEN.
Full Implementation
enum State { CLOSED, OPEN, HALF_OPEN }

class CircuitBreaker {
    State state = CLOSED;
    int failCount = 0, successCount = 0;
    final int failThreshold = 5;
    final int successThreshold = 2;
    Instant openedAt;
    final Duration timeout = Duration.ofSeconds(30);
    final ReentrantLock lock = new ReentrantLock();

    <T> T call(Supplier<T> fn) {
        lock.lock(); try {
            if (state == OPEN) {
                if (Duration.between(openedAt, Instant.now()).compareTo(timeout) > 0)
                    state = HALF_OPEN;
                else throw new CircuitOpenException();
            }
        } finally { lock.unlock(); }

        try {
            T result = fn.get();
            onSuccess(); return result;
        } catch (Exception e) { onFailure(); throw e; }
    }

    void onSuccess() {
        lock.lock(); try {
            if (state == HALF_OPEN && ++successCount >= successThreshold) {
                state = CLOSED; failCount = 0; successCount = 0;
            }
        } finally { lock.unlock(); }
    }

    void onFailure() {
        lock.lock(); try {
            if (++failCount >= failThreshold || state == HALF_OPEN) {
                state = OPEN; openedAt = Instant.now(); successCount = 0;
            }
        } finally { lock.unlock(); }
    }
}

class Scheduler {
    // Min-heap by scheduledAt
    PriorityQueue<Job> queue = new PriorityQueue<>(
        Comparator.comparingLong((Job j) -> j.scheduledAt)
                  .thenComparing(j -> -j.priority));
    ScheduledExecutorService executor = Executors.newScheduledThreadPool(4);
    Map<String, ScheduledFuture<?>> running = new ConcurrentHashMap<>();

    String schedule(Runnable task, long delayMs, int priority) {
        Job job = new Job(UUID.randomUUID().toString(), task, 
                          System.currentTimeMillis() + delayMs, priority);
        queue.offer(job);
        return job.id;
    }

    void processJobs() {
        while (!Thread.currentThread().isInterrupted()) {
            Job job = queue.peek();
            if (job == null || job.scheduledAt > System.currentTimeMillis()) {
                Thread.sleep(10); continue;
            }
            queue.poll();
            executor.submit(() -> executeWithRetry(job));
        }
    }

    void executeWithRetry(Job job) {
        try { job.task.run(); job.status = COMPLETED; }
        catch (Exception e) {
            if (job.retryCount++ < job.maxRetries) {
                job.scheduledAt = System.currentTimeMillis() + backoff(job.retryCount);
                queue.offer(job);
            } else { job.status = FAILED; }
        }
    }
}

What is a Bloom Filter
Space-efficient probabilistic data structure. Answers: 'definitely not in set' OR 'probably in set'. No false negatives, configurable false positive rate.
Implementation
class BloomFilter {
    private final BitSet bits;
    private final int numBits;
    private final int numHashFunctions;

    BloomFilter(int expectedItems, double falsePositiveRate) {
        // Optimal bit count: -n*ln(p) / (ln2)^2
        numBits = (int)(-expectedItems * Math.log(falsePositiveRate) / (Math.log(2)*Math.log(2)));
        // Optimal hash count: (m/n) * ln2
        numHashFunctions = (int)(numBits * 1.0 / expectedItems * Math.log(2));
        bits = new BitSet(numBits);
    }

    void add(String item) {
        for (int i = 0; i < numHashFunctions; i++)
            bits.set(Math.abs(hash(item, i)) % numBits);
    }

    boolean mightContain(String item) {
        for (int i = 0; i < numHashFunctions; i++)
            if (!bits.get(Math.abs(hash(item, i)) % numBits)) return false;  // Definitely not
        return true;  // Probably yes
    }

    private int hash(String s, int seed) {
        return Objects.hash(s, seed);
    }
}

How CSRF works
1. User logs into bank.com (session cookie stored)
2. User visits malicious.com
3. malicious.com has hidden form:
   <form action="https://bank.com/transfer" method="POST">
     <input name="to" value="attacker"/>

  • Custom Request Header: X-Requested-With: XMLHttpRequest. Cross-origin forms can't set custom headers.

2 Cache strategies — cache-aside, read-through, write-through, write-back
cachingrediscache-aside
Medium 88%
Cache Strategies
  • Cache-Aside (Lazy loading): App checks cache first; on miss, reads DB, populates cache. Cache only stores what's actually requested. Risk: thundering herd on cold start.
  • Read-Through: Cache reads from DB automatically on miss (library handles it). App always reads from cache. DB not directly accessed by app.
  • Write-Through: Write to cache AND DB synchronously. Cache never stale. High write latency (must wait for both). Good for read-heavy.
  • Write-Back (Write-Behind): Write to cache, return immediately. Write to DB asynchronously. Fast writes. Risk: data loss if cache crashes before flush.
Cache-Aside Pattern (most common)
def get_user(user_id):
    # Try cache first
    user = redis.get(f"user:{user_id}")
    if user:
        return deserialize(user)  # cache hit
    
    # Cache miss — read from DB
    user = db.query("SELECT * FROM users WHERE id=%s", user_id)
    
    # Populate cache with TTL
    redis.setex(f"user:{user_id}", ttl=3600, value=serialize(user))
    return user

def update_user(user_id, data):
    db.execute("UPDATE users SET ... WHERE id=%s", user_id)
    redis.delete(f"user:{user_id}")  # invalidate — don't update!
Cache Eviction Policies
  • LRU: Evict least recently used. Good general-purpose.
  • LFU: Evict least frequently used. Better for skewed access patterns.
  • TTL: Time-based expiry. Always stale by at most TTL seconds.
  • Allkeys-lru (Redis): Apply LRU across all keys when memory full.

Ensures delayed packets from old connection don't confuse new connection on same 4-tuple. 2×MSL (Maximum Segment Lifetime). Can cause port exhaustion on high-traffic servers. Fix: SO_REUSEADDR, SO_REUSEPORT, or increase local port range.
SYN Flood
Attacker sends many SYN packets, never completes handshake. Server holds half-open connections (SYN_RCVD state). Defense: SYN cookies — encode state in ISN, allocate resources only after ACK.

6 HTTP/2 vs HTTP/3 (QUIC) — feature comparison
http2http3quic
Hard 88%
HTTP/2 Features
  • Multiplexing: Multiple streams over one TCP connection. No request queuing.
  • Header compression (HPACK): Reduce redundant headers (cookies, user-agent)
  • Server push: Server proactively sends resources before client requests
  • Binary framing: Efficient parsing vs text-based HTTP/1.1
  • Stream priority: Weighted dependency tree
  • Problem: TCP head-of-line blocking — one lost packet blocks ALL streams
HTTP/3 / QUIC
  • Runs over UDP, not TCP. Implements reliable delivery in userspace.
  • Stream-level reliability: Lost packet blocks only affected stream, not all
  • 0-RTT connection setup: QUIC + TLS 1.3 combined handshake (1-RTT new, 0-RTT resume)
  • Connection migration: Connection ID-based, survives IP change (WiFi → 4G)
  • QPACK: Header compression without HOL blocking (vs HPACK)
When HTTP/3 helps
High latency (mobile), packet loss, many parallel requests, clients switching networks. Major adopters: Google, Meta, Cloudflare, YouTube.

8 TLS 1.3 handshake — 1-RTT and 0-RTT
tlstls1.3handshake
Hard 86%
TLS 1.3 Full Handshake (1-RTT)
Client → Server: ClientHello + key_share (ECDHE public key) + supported ciphers
Server → Client: ServerHello + key_share (server ECDHE public key)
                  + Certificate + CertificateVerify + Finished
[Both derive session keys immediately from shared ECDHE secret]
Client → Server: Finished + HTTP request
[TLS 1.2 needed 2-RTT; TLS 1.3 = 1-RTT]
0-RTT Session Resumption
Client stores session ticket from previous connection. On reconnect, sends early data in first packet — zero round trips before HTTP request. Risk: replay attacks (early data not protected against replay). Mitigate: use only for idempotent requests.
Key Improvements over TLS 1.2
  • 1-RTT instead of 2-RTT for new connections
  • Forward secrecy mandatory: ECDHE always used (ephemeral keys)
  • Removed weak algorithms: RSA key exchange, RC4, SHA-1, MD5
  • Encrypted handshake: Certificate encrypted (hidden from observers)
Certificate Verification
Client verifies server cert chain up to trusted CA root. CT (Certificate Transparency) logs prevent mis-issuance. OCSP stapling for revocation.

13 CDN architecture — how content is cached and served
cdnedgepop
Medium 84%
CDN Architecture
Points of Presence (PoPs): Edge servers distributed globally (Cloudflare: 300+ PoPs, Akamai: 4000+). User request routed to nearest PoP via Anycast (same IP, BGP routes to nearest datacenter) or GeoDNS.
Cache Flow
User → CDN Edge (PoP)
  → Cache HIT: return immediately (<5ms)
  → Cache MISS: fetch from origin (100-300ms), cache response, serve

Subsequent users at same PoP → cache HIT
Users at different PoP → may still be cache MISS (PoP-local cache)
Cache Control Headers
Cache-Control: max-age=31536000, immutable     # 1 year, static assets
Cache-Control: max-age=60, stale-while-revalidate=30  # 1min fresh, serve stale while revalidating
Cache-Control: no-store                         # never cache (auth pages)
Surrogate-Control: max-age=3600                 # CDN-only hint (Varnish/Fastly)
Vary: Accept-Encoding                           # different cache per encoding
Dynamic Content
Not all content is cacheable. Edge computing (Cloudflare Workers, Lambda@Edge) runs logic at edge. For personalized content: cache fragment (Edge Side Includes) or stream-stitch.

14 TCP flow control (receive window) vs congestion control (CWND)
tcpflow-controlcongestion
Hard 82%
Flow Control (Receiver-side)
Prevents sender from overwhelming receiver's buffer.
Receiver advertises receive window (rwnd) in ACK headers. Sender must not have more than rwnd unacknowledged bytes in flight.
Congestion Control (Network-side)
Prevents sender from overwhelming the network (routers/links).
Sender maintains congestion window (cwnd). Effective window = min(cwnd, rwnd).
Congestion Control Phases
  • Slow Start: cwnd=1 MSS → doubles each RTT until ssthresh or packet loss
  • Congestion Avoidance: cwnd grows +1 MSS per RTT (linear)
  • Fast Retransmit: 3 duplicate ACKs → retransmit lost segment immediately (don't wait for timeout)
  • Fast Recovery (CUBIC, BBR): On loss: ssthresh = cwnd/2, cwnd = ssthresh (not back to 1)
BBR (Google)
Model-based congestion control. Estimates bottleneck bandwidth and RTT. Less reactive to loss, better for high-bandwidth long-distance links. Used in YouTube, cloud networking.
