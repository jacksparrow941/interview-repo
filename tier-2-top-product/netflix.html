1 Explain the circuit breaker pattern
circuit-breakerhystrix
Medium 78%
Circuit Breaker States
  • CLOSED: Normal operation. Failure counter tracks errors. If failures > threshold → OPEN.
  • OPEN: All calls fail immediately (fail-fast). No downstream load. After timeout → HALF_OPEN.
  • HALF_OPEN: Allow one probe request. If succeeds → CLOSED. If fails → OPEN again.
Why it matters
Without circuit breaker: one slow service causes thread pool exhaustion in caller → cascading failure across the system. Circuit breaker prevents this by failing fast and giving downstream service recovery time.
Libraries
  • Resilience4j (Java): sliding window (count/time based), bulkhead pattern
  • Hystrix (deprecated): used at Netflix, pioneered the pattern
  • Go: sony/gobreaker, mercadolibre/go-breakers
Follow-ups
• What is the bulkhead pattern and how does it complement circuit breaker?
• How do you set the right failure threshold to avoid flapping?
• What is the difference between circuit breaker and retry with exponential backoff?

2 Blue-green vs Canary vs Rolling deployments
deploymentcanaryzero-downtime
Medium 74%
Deployment Strategies
  • Blue-Green: Two identical environments. New version deployed to 'green'. Switch traffic instantly. Easy rollback: flip back to 'blue'. Requires 2x infrastructure.
  • Canary: Route small % of traffic (1-5%) to new version. Monitor error rates / latency. Gradually increase if healthy. Slow, but minimizes blast radius.
  • Rolling: Replace instances one at a time (or in batches). Both versions run simultaneously. No extra infrastructure. Standard Kubernetes Deployment behavior.
  • Feature Flags: Deploy code disabled; enable per-user/segment at runtime. Decouple deploy from release.
In Kubernetes
# Canary with Argo Rollouts:
apiVersion: argoproj.io/v1alpha1
kind: Rollout
spec:
  strategy:
    canary:
      steps:
      - setWeight: 5    # 5% traffic to new
      - pause: {duration: 10m}
      - setWeight: 50
      - pause: {duration: 10m}
      - setWeight: 100

1 Docker container vs Virtual Machine — key differences?
dockervmcontainer
Easy 93%
Answer
Virtual Machine: Full OS per VM, hardware emulation via hypervisor (Type-1: bare metal, Type-2: hosted). Heavy: ~GBs, slow boot (~minutes), strong isolation.
Docker Container: Shares host OS kernel, isolates via Linux namespaces (PID, NET, MNT, UTS, IPC) + cgroups for resource limits. Lightweight: ~MBs, starts in milliseconds, process-level isolation.
Key Differences
  • Boot time: VM ~1-2 min | Container ~100ms
  • Size: VM ~GBs | Container ~MBs (shared layers)
  • Isolation: VM = full kernel isolation | Container = namespace isolation (kernel shared)
  • Use case: VM for multi-OS, strong isolation | Container for microservices, CI/CD
Follow-ups
• What Linux namespaces does Docker use? (PID, NET, MNT, IPC, UTS, USER)
• How do cgroups limit CPU/memory in containers?
• What is a container runtime? (runc, containerd, CRI-O)

2 How do Docker image layers work? (Union filesystem)
dockerlayersoverlay2
Medium 90%
Answer
Docker images are built as read-only layers stacked using a Union Filesystem (OverlayFS/AUFS). Each RUN, COPY, ADD instruction in a Dockerfile creates a new layer.

When a container runs, Docker adds a thin read-write layer on top (Copy-on-Write). Writes go to the container layer; reads search layers bottom-up.
Dockerfile Layer Example
FROM ubuntu:22.04          # Layer 1: base OS
RUN apt-get install -y java # Layer 2: java install
COPY app.jar /app/          # Layer 3: app binary
CMD ["java", "-jar", "/app/app.jar"]  # metadata only
Optimization Tips
  • Order layers from least to most frequently changing
  • Combine RUN commands to reduce layer count
  • Use .dockerignore to exclude build artifacts
  • Use multi-stage builds to discard build-time layers
Follow-ups
• What is docker build --cache-from?

4 ConfigMaps vs Secrets in Kubernetes
kubernetesconfigmapsecrets
Easy 88%
ConfigMap
Stores non-sensitive configuration as key-value pairs. Mounted as environment variables or volume files. Plain text in etcd.
Secret
Stores sensitive data (passwords, tokens, TLS certs). Base64-encoded in etcd (NOT encrypted by default). Enable encryption at rest with EncryptionConfiguration. Types: Opaque, kubernetes.io/tls, kubernetes.io/dockerconfigjson, etc.
Usage
# Mount as env
env:
- name: DB_PASSWORD
  valueFrom:
    secretKeyRef:
      name: db-secret
      key: password

# Mount as volume
volumeMounts:
- name: config
  mountPath: /etc/config
volumes:
- name: config
  configMap:
    name: app-config
Best Practices
  • Use external secret managers: HashiCorp Vault, AWS Secrets Manager with External Secrets Operator
  • Never bake secrets into Docker images
  • RBAC: restrict Secret read access to specific ServiceAccounts

5 Git internals — rebase vs merge, when to use each
gitrebasemerge
Medium 88%
Merge
Creates a merge commit that ties two branches together. Preserves full history including branch structure. Safe for shared branches — never rewrites history.
git checkout main
git merge feature/login
# Creates commit: Merge branch 'feature/login'
Rebase
Replays commits from one branch onto another. Creates linear history. Rewrites commit SHAs — never rebase shared/public branches.
git checkout feature/login
git rebase main
# Moves feature commits on top of latest main
When to use
  • Merge: Merging feature into main (preserves context). Shared branches.
  • Rebase: Keeping feature branch up-to-date with main. Clean PR history. git pull --rebase.
  • Squash merge: Combine all feature commits into 1 clean commit on main.
Interactive Rebase
git rebase -i HEAD~3
# Options: pick, squash, fixup, reword, drop

1 Design a recommendation system (Netflix/YouTube)
recommendationcollaborative-filteringembedding
Hard 88%
Architecture Layers
Request → Candidate Generation → Scoring → Re-ranking → Response
           (retrieval)            (ML model)   (business rules)
           millions→hundreds      hundreds→50  50→10 (diversity, freshness, ads)
Candidate Generation
  • Collaborative Filtering: Users who watched A also watched B. Matrix factorization (SVD). Doesn't require item features. Cold-start problem for new items.
  • Content-Based: Item embeddings from metadata (genre, actors, tags). Works for new items.
  • Two-Tower Model: Separate user-tower + item-tower → embeddings → ANN search (FAISS). Pre-compute item embeddings, compute user embedding at request time. YouTube's approach.
Scoring & Ranking
Input: [user_embedding, item_embedding, context_features]
Model: Deep neural network → predicted CTR / watch_time
ANN Search: FAISS HNSW index → top-K candidates in <10ms for 100M items
A/B Testing
Split traffic by user ID hash. Primary metric: engagement (watch time, CTR). Guard metrics: don't harm diversity, churn rate. Run for statistical significance.

2 Design an A/B testing platform
ab-testingexperimentationstatistics
Hard 85%
Core Components
Experiment Config Service → stores experiment definition
  (variants, allocation %, targeting rules, metrics)

Assignment Service → deterministic bucketing by user_id
  hash(user_id + experiment_id) % 100 < allocation%
  → same user always in same bucket (sticky assignment)
  → results cached in Redis

Event Tracking → user actions logged with experiment_id + variant
  → Kafka → Data Warehouse (Clickhouse/BigQuery)

Analysis Service → daily/real-time stats computation
  → t-test / z-test for significance
  → dashboard with p-value, confidence interval, lift %
Statistical Concepts
  • p-value < 0.05: Less than 5% chance result is due to random variation
  • Statistical power: Probability of detecting a real effect. Usually target 80%.
  • MDE (Minimum Detectable Effect): Smallest effect worth detecting → determines sample size
  • Sample size calculator: n = 16σ²/δ² (for 80% power, 5% significance)
  • Multiple testing problem: 20 experiments at 5% significance → 1 false positive on average. Fix: Bonferroni correction or FDR.
Common Pitfalls
  • Novelty effect: New feature gets engagement just because it's new — run longer
  • Network effect: Treating control and treatment users who interact with each other — cluster randomization
  • Peeking: Stopping early when p < 0.05 inflates false positive rate — use sequential testing

3 Design a ML feature store — what is it and why?
feature-storemlfeast
Hard 82%
What is a Feature Store?
Centralized repository for ML features. Solves two problems:
  • Training-serving skew: Feature computed differently at training vs inference → model underperforms in production
  • Feature reuse: Team A computes user_30d_spend, Team B recomputes it separately → wasted effort
Architecture
Data Sources (events, DB, streams)
    ↓
Feature Engineering (Spark/Flink job)
    ↓ write
┌────────────────────────────────────┐
│ Feature Store (Feast / Tecton)     │
│  Offline Store: S3/BigQuery/Hive   │ ← batch training data
│  Online Store:  Redis/DynamoDB     │ ← low-latency serving
└────────────────────────────────────┘
    ↑ read at training time          ↑ read at inference time (<10ms)
    Training Job                     Inference Service
Key Concepts
  • Point-in-time correct joins: Feature store returns the feature value as it was at prediction time (prevents data leakage)
  • Feature versioning: Rollback features if model performance degrades
  • Feature monitoring: Drift detection — alert if feature distribution changes significantly

5 How do you detect and handle model drift?
model-driftdata-driftmonitoring
Hard 78%
Types of Drift
  • Data drift (covariate shift): Input feature distribution changes. User behavior changed, new user segment, seasonality. Model predictions become unreliable.
  • Concept drift: Relationship between features and label changes. E.g., 'fraud' patterns evolve.
  • Label drift: Output distribution changes. E.g., more fraudulent transactions in new season.
Detection Methods
  • Statistical tests: KS-test, PSI (Population Stability Index), Chi-squared for categorical features
  • Model performance metrics: Track AUC, precision, recall on labeled samples in production
  • Shadow deployment: Run new model in shadow, compare predictions vs current model
  • Outlier detection: Flag inputs far from training distribution (z-score, isolation forest)
Response Strategy
  • Auto-retrain trigger: PSI > 0.2 → trigger retraining pipeline in MLflow/SageMaker
  • Continuous training: Retrain on rolling window of recent data (online learning for fast-moving data)
  • Canary deployment: New model serves 5% traffic, compare metrics before full rollout
Follow-ups
• What is PSI (Population Stability Index) and what thresholds indicate drift?
• How do you maintain a training data pipeline that is always fresh?
• What is the difference between online and batch retraining?

1 How do you diagnose and fix high API latency?
latencyprofilingp99
Hard 92%
Systematic Approach
1. MEASURE: Where is the time going?
   - Add distributed tracing (Jaeger/Zipkin): see each span's duration
   - p50/p95/p99 latency (NOT just average — outliers matter)
   - Breakdown: network + serialization + DB queries + external API + CPU

2. IDENTIFY bottleneck:
   Common causes:
   - N+1 queries (add JOIN FETCH or batch)
   - Missing DB index (check EXPLAIN ANALYZE → seq scan)
   - Synchronous external API call in critical path (make async / cache)
   - Lock contention (connection pool exhausted, mutex hotspot)
   - GC pauses (Java: -XX:+PrintGCDetails, G1/ZGC tuning)
   - Memory pressure (swap, cache thrashing)

3. FIX:
   - Caching: Redis in front of slow DB queries
   - Async: move non-critical work off request path (Kafka)
   - Parallelism: concurrent DB queries (CompletableFuture/goroutines)
   - Index: add composite index for slow query
   - Connection pooling: tune min/max pool size
Key Metrics
  • Latency percentiles: p50=100ms is fine; p99=5s means 1% users wait 5 seconds
  • Throughput: RPS the service can handle without degrading
  • Error rate: 5xx rate as % of total requests
  • Saturation: CPU%, memory%, connection pool utilization, queue depth
USE Method
For every resource: Utilization (how busy), Saturation (how much queuing), Errors (error count). Invented by Brendan Gregg.

2 Cache strategies — cache-aside, read-through, write-through, write-back
cachingrediscache-aside
Medium 88%
Cache Strategies
  • Cache-Aside (Lazy loading): App checks cache first; on miss, reads DB, populates cache. Cache only stores what's actually requested. Risk: thundering herd on cold start.
  • Read-Through: Cache reads from DB automatically on miss (library handles it). App always reads from cache. DB not directly accessed by app.
  • Write-Through: Write to cache AND DB synchronously. Cache never stale. High write latency (must wait for both). Good for read-heavy.
  • Write-Back (Write-Behind): Write to cache, return immediately. Write to DB asynchronously. Fast writes. Risk: data loss if cache crashes before flush.
Cache-Aside Pattern (most common)
def get_user(user_id):
    # Try cache first
    user = redis.get(f"user:{user_id}")
    if user:
        return deserialize(user)  # cache hit
    
    # Cache miss — read from DB
    user = db.query("SELECT * FROM users WHERE id=%s", user_id)
    
    # Populate cache with TTL
    redis.setex(f"user:{user_id}", ttl=3600, value=serialize(user))
    return user

def update_user(user_id, data):
    db.execute("UPDATE users SET ... WHERE id=%s", user_id)
    redis.delete(f"user:{user_id}")  # invalidate — don't update!
Cache Eviction Policies
  • LRU: Evict least recently used. Good general-purpose.
  • LFU: Evict least frequently used. Better for skewed access patterns.
  • TTL: Time-based expiry. Always stale by at most TTL seconds.
  • Allkeys-lru (Redis): Apply LRU across all keys when memory full.
Follow-ups
• What is the thundering herd problem and how do you prevent it? (mutex/lock on cache miss, staggered TTLs)
• How do you handle cache warming after a cold restart?
• What is probabilistic early expiration (PER) and how does it prevent dogpile?

3 Observability — metrics, logs, traces — the three pillars
observabilityprometheusgrafana
Medium 86%
Three Pillars
  • Metrics: Numeric aggregations over time. Low cardinality. Cheap to store. Tool: Prometheus (pull-based scraping) + Grafana. Counter, Gauge, Histogram, Summary.
  • Logs: Discrete events with context. High volume. Searchable. Tool: ELK stack (Elasticsearch+Logstash+Kibana) or Loki+Grafana. Structured JSON logs with trace_id for correlation.
  • Traces: Request journey across services. Tool: Jaeger, Zipkin, Tempo. Essential for microservices debugging.
SLI / SLO / SLA / Error Budget
SLI (Service Level Indicator): the metric you measure
  e.g., "% of requests with latency < 200ms"

SLO (Service Level Objective): your internal target
  e.g., "99.9% of requests < 200ms over rolling 30 days"

SLA (Service Level Agreement): contractual with customer
  e.g., "99.5% uptime or credit applied"

Error Budget: 1 - SLO = allowed unreliability
  99.9% SLO = 0.1% error budget = 43.8 min downtime/month
  If budget exhausted: freeze feature work, focus on reliability
RED Method (for services)
Rate (requests/sec), Error rate (errors/sec), Duration (latency). Apply to every microservice for quick health check.

4 Explain distributed tracing — how it works
distributed-tracingopentelemetryjaeger
Medium 84%
How it works
Request enters Service A → Tracer generates trace_id (128-bit)
Service A calls Service B → propagates trace_id + span_id in HTTP header:
  traceparent: 00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01
               version  traceId                    parentSpanId   flags

Each service creates a span:
  span = {traceId, spanId, parentSpanId, name, startTime, duration,
          tags: {"db.type":"postgresql", "http.status":200},
          logs: [{"event":"query", "sql":"..."}]}

Spans sent async to collector (Jaeger/Zipkin) → assembled into trace tree
OpenTelemetry (OTel)
  • Vendor-neutral standard for traces, metrics, logs
  • SDK instruments your code (auto-instrumentation for popular frameworks)
  • Exporter sends to Jaeger, Zipkin, Tempo, AWS X-Ray, Datadog
  • OTEL_TRACES_EXPORTER=jaeger OTEL_EXPORTER_JAEGER_ENDPOINT=http://jaeger:14268/api/traces
Sampling
  • Head sampling: Decision at trace start (before outcome known). Simple. Loses tail errors.
  • Tail sampling: Buffer traces, decide after seeing all spans. Can keep errored/slow traces.
  • Rate: 1% for healthy services, 100% for errors, 10% for slow (p99 > 1s)

5 Load testing — how to approach and what tools to use
load-testingk6gatling
Medium 78%
Test Types
  • Load test: Expected normal + peak load. Validate SLAs. Measure p99 latency, throughput, error rate.
  • Stress test: Push beyond expected load until system breaks. Find breaking point. Test recovery.
  • Soak/endurance test: Normal load for extended time (hours/days). Find memory leaks, connection exhaustion, log rotation issues.
  • Spike test: Sudden large traffic burst. Test autoscaling, circuit breakers.
  • Chaos test: Kill instances, inject latency, corrupt network. Test resilience.
k6 Example
import http from 'k6/http';
import { check, sleep } from 'k6';

export const options = {
  stages: [
    { duration: '2m', target: 100 },   // ramp up to 100 VUs
    { duration: '5m', target: 100 },   // hold at 100 VUs
    { duration: '2m', target: 0 },     // ramp down
  ],
  thresholds: {
    'http_req_duration': ['p(99)<500'],  // 99% requests < 500ms
    'http_req_failed': ['rate<0.01'],   // <1% error rate
  },
};

export default function() {
  const r = http.get('https://api.example.com/users');
  check(r, { 'status 200': (r) => r.status === 200 });
  sleep(1);
}
What to measure
  • Throughput: requests/sec at saturation
  • Latency: p50, p95, p99, p999 as load increases
  • Error rate: 5xx rate, timeout rate
  • Resource utilization: CPU, memory, disk I/O, network on each tier
  • Database: connection pool saturation, query latency at load
