1 Goroutines vs OS threads
goroutinesthreadsgmp
Medium 92%
Goroutines vs OS Threads
  • Goroutine: ~2KB initial stack (grows dynamically to hundreds of MB if needed). M:N threading — N goroutines multiplexed onto M OS threads. Scheduled by Go runtime.
  • OS Thread: ~1MB stack (fixed at creation). 1:1 with kernel thread. Expensive context switch (μs).
  • Can run millions of goroutines. Thousands of OS threads = OOM.
GMP Model (brief)
  • G: Goroutine (the task)
  • M: OS thread (the runner)
  • P: Processor/scheduler context (GOMAXPROCS Ps). Each P has local run queue.
  • When G blocks on syscall → M + G detach from P → P gets another M to continue work
Follow-ups
• What is goroutine stack growth mechanism? (segmented stacks → copying stacks since Go 1.4)
• What is GOMAXPROCS and when would you change it?
• How do goroutines avoid the 10K thread problem?

2 Go context package — propagation, timeout, cancellation

Medium 90%
Context Tree
// Root
ctx := context.Background()

// Cancellable
ctx, cancel := context.WithCancel(ctx)
defer cancel()  // always call cancel to free resources

// With timeout
ctx, cancel = context.WithTimeout(ctx, 5*time.Second)
defer cancel()

// With deadline
ctx, cancel = context.WithDeadline(ctx, time.Now().Add(5*time.Second))

// With value (carry request-scoped data)
ctx = context.WithValue(ctx, userKey{}, user)
Checking cancellation
func doWork(ctx context.Context) error {
    for {
        select {
        case <-ctx.Done():
            return ctx.Err()  // context.Canceled or DeadlineExceeded
        case result := <-workChan:
            process(result)
        }
    }
}
Propagation
Always pass context as first parameter. Context propagates cancellation to all child contexts automatically.
context.Value best practices
  • Use only for request-scoped data: traceID, userID, auth token
  • Use unexported key types to avoid collisions: type ctxKey struct{}
  • Never store mutable data in context values

3 Go error handling — errors.Is, errors.As, wrapping
errorswrappingsentinel
Medium 88%
Error Wrapping (Go 1.13+)
Wrap errors with context using fmt.Errorf("%w", err). This creates an error chain. The original error is retrievable.
errors.Is and errors.As
var ErrNotFound = errors.New("not found")  // sentinel

// Wrapping
func getUser(id int) error {
    return fmt.Errorf("getUser %d: %w", id, ErrNotFound)
}

err := getUser(42)
// errors.Is: checks entire chain
if errors.Is(err, ErrNotFound) {
    // handles wrapped ErrNotFound
}

// errors.As: extract concrete type from chain
var dbErr *DBError
if errors.As(err, &dbErr) {
    fmt.Println(dbErr.Code)
}
Custom Error Types
type ValidationError struct {
    Field   string
    Message string
}
func (e *ValidationError) Error() string {
    return fmt.Sprintf("validation error: %s — %s", e.Field, e.Message)
}

// Callers use errors.As to get the typed error
Best Practices
  • Always wrap with context: fmt.Errorf("operation X: %w", err)
  • Use sentinel errors for known conditions (io.EOF, sql.ErrNoRows)
  • Use typed errors when callers need to inspect fields
  • At service boundary: log + translate to user-facing error
Follow-ups
• When would you use panic vs return error?
• How does errors.Join (Go 1.20) work?
• How does the errors package handle multiple wrapped errors?

4 defer, panic, recover — full semantics and patterns
deferpanicrecover
Medium 88%
defer
Deferred call runs when surrounding function returns (normal or panic). Arguments evaluated immediately; call deferred. LIFO order.
func processFile(path string) (err error) {
    f, err := os.Open(path)
    if err != nil { return }
    defer f.Close()           // runs even on early return/panic
    defer func() {            // named return: modify err on cleanup failure
        if cerr := f.Close(); cerr != nil && err == nil {
            err = cerr
        }
    }()
    // ... process f
    return
}
panic / recover
func safeDiv(a, b int) (result int, err error) {
    defer func() {
        if r := recover(); r != nil {     // recover() catches panic
            err = fmt.Errorf("panic: %v", r)
        }
    }()
    return a / b, nil  // panics if b==0
}

// recover() returns nil if no panic, or the panic value
// ONLY works inside a deferred function
Rules
  • recover() only stops a panic if called directly from a deferred function
  • Panic unwinds stack, running deferred functions
  • Use panic for truly unrecoverable states (programming errors), not business logic
  • HTTP handlers should recover panics to avoid crashing the whole server
Follow-ups
• What is the difference between os.Exit and panic?
• Can you defer a method call? (yes)
• What is the defer overhead? (small but measurable in hot loops)

5 goroutine leak — how to detect and prevent
goroutine-leakcontextdone-channel
Medium 86%
What is a goroutine leak
Goroutines that are started but never terminate. They consume memory (~2KB initial stack, can grow), CPU for scheduling, and keep referenced objects alive.
Common Causes
  • Blocked channel read/write with no one to unblock
  • Not passing/checking context.Context
  • Infinite loops without exit condition
  • Forgotten goroutines in tests
Prevention Pattern
func worker(ctx context.Context, jobs <-chan Job) {
    for {
        select {
        case <-ctx.Done():
            return  // clean exit
        case job, ok := <-jobs:
            if !ok { return }  // channel closed
            process(job)
        }
    }
}
Detection with pprof
import _ "net/http/pprof"
// curl http://localhost:6060/debug/pprof/goroutine?debug=2
// Lists all goroutine stacks — look for blocked goroutines

// In tests: goleak
func TestWorker(t *testing.T) {
    defer goleak.VerifyNone(t)  // fails if goroutines leak
    ...
}

• What happens to a goroutine blocked on a closed channel?

6 Go interfaces — nil interface trap, empty interface
interfacenilempty-interface
Medium 84%
Interface internals
A Go interface value has two words: (type, pointer). An interface is nil only when both type and pointer are nil.
The Nil Trap
type MyError struct{ msg string }
func (e *MyError) Error() string { return e.msg }

func getError() error {
    var err *MyError = nil
    return err  // TRAP: returns (type=*MyError, ptr=nil) — NOT nil interface!
}

if err := getError(); err != nil {
    fmt.Println("This prints!")  // Bug!
}

// Fix: return nil explicitly
func getError() error {
    var err *MyError
    if conditionFailed { return err }  // still buggy
    return nil  // correct
}
Type Assertions & Switches
var i interface{} = "hello"

// Type assertion
s, ok := i.(string)  // ok=true, s="hello"

// Type switch
switch v := i.(type) {
case string:  fmt.Println("string:", v)
case int:     fmt.Println("int:", v)
default:      fmt.Println("other")
}
any (Go 1.18)
any is an alias for interface{}. Prefer any in new code.

7 Channel patterns — fan-out, fan-in, pipeline, done channel
channelspipelinefan-out
Hard 84%
Pipeline
func gen(nums ...int) <-chan int {
    out := make(chan int)
    go func() {
        defer close(out)
        for _, n := range nums { out <- n }
    }()
    return out
}
func sq(in <-chan int) <-chan int {
    out := make(chan int)
    go func() { defer close(out); for n := range in { out <- n*n } }()
    return out
}
// Usage: for v := range sq(sq(gen(2,3,4))) { fmt.Println(v) }
Fan-Out
func fanOut(in <-chan int, workers int) []<-chan int {
    outs := make([]<-chan int, workers)
    for i := range outs {
        outs[i] = sq(in)  // each worker reads from same input
    }
    return outs
}
Fan-In (Merge)
func merge(cs ...<-chan int) <-chan int {
    var wg sync.WaitGroup
    out := make(chan int)
    output := func(c <-chan int) {
        defer wg.Done()
        for v := range c { out <- v }
    }
    wg.Add(len(cs))
    for _, c := range cs { go output(c) }
    go func() { wg.Wait(); close(out) }()
    return out
}
Done Channel (Cancellation)
func sq(done <-chan struct{}, in <-chan int) <-chan int {
    out := make(chan int)
    go func() {
        defer close(out)
        for n := range in {
            select {
            case out <- n*n:
            case <-done: return  // cancelled
            }
        }
    }()
    return out
}
// Use context.Context in production instead of done channel

• How do you implement a timeout with select?

Table-Driven Tests
func TestAdd(t *testing.T) {
    tests := []struct {
        name string; a, b, want int
    }{
        {"positive", 2, 3, 5},
        {"negative", -1, 1, 0},
        {"zeros", 0, 0, 0},
    }
    for _, tc := range tests {
        t.Run(tc.name, func(t *testing.T) {
            if got := Add(tc.a, tc.b); got != tc.want {
                t.Errorf("Add(%d,%d)=%d, want %d", tc.a, tc.b, got, tc.want)
            }
        })
    }
}
Benchmarks
func BenchmarkAdd(b *testing.B) {
    for i := 0; i < b.N; i++ {
        Add(42, 58)
    }
}
// go test -bench=. -benchmem -count=5
Fuzz Testing (Go 1.18+)
func FuzzReverse(f *testing.F) {
    f.Add("hello")  // seed corpus
    f.Fuzz(func(t *testing.T, s string) {
        rev := Reverse(s)
        if Reverse(rev) != s {
            t.Errorf("double reverse != original")
        }
    })
}
// go test -fuzz=FuzzReverse -fuzztime=30s

func Logger(next http.Handler) http.Handler {

10 Functional options pattern in Go
functional-optionsdesign-patternconfiguration
Medium 80%
Problem
How to provide optional configuration to a constructor without breaking API as options grow? Config structs are verbose; many parameters are messy.
Functional Options Pattern
type Server struct {
    host    string
    port    int
    timeout time.Duration
    maxConn int
}

type Option func(*Server)

func WithPort(p int) Option      { return func(s *Server) { s.port = p } }
func WithTimeout(d time.Duration) Option { return func(s *Server) { s.timeout = d } }
func WithMaxConn(n int) Option   { return func(s *Server) { s.maxConn = n } }

func NewServer(host string, opts ...Option) *Server {
    s := &Server{host: host, port: 8080, timeout: 30*time.Second, maxConn: 100}  // defaults
    for _, opt := range opts { opt(s) }
    return s
}

// Usage (clean, readable, extensible):
srv := NewServer("localhost",
    WithPort(9090),
    WithTimeout(5*time.Second),
)
Advantages
  • Backward compatible — add new options without changing signature
  • Self-documenting call sites
  • Easy to set sensible defaults
  • Options are first-class values — can be composed, stored, passed around

11 Go interface composition and embedding
interfaceembeddingcomposition
Medium 80%
Interface Composition
type Reader interface { Read(p []byte) (n int, err error) }
type Writer interface { Write(p []byte) (n int, err error) }
type Closer interface { Close() error }

// Compose interfaces:
type ReadWriter interface { Reader; Writer }  // embeds both
type ReadWriteCloser interface { ReadWriter; Closer }

// io.ReadWriteCloser = standard library example
// os.File implements ReadWriteCloser
Struct Embedding
type Animal struct { Name string }
func (a Animal) Speak() string { return a.Name + " speaks" }

type Dog struct {
    Animal          // embedded — promotes fields and methods
    Breed string
}

d := Dog{Animal{"Rex"}, "Labrador"}
fmt.Println(d.Speak())  // promoted method: Dog.Speak() = Animal.Speak()
fmt.Println(d.Name)     // promoted field
Override via Shadowing
func (d Dog) Speak() string { return d.Name + " barks" }  // shadows Animal.Speak
d.Speak()         // calls Dog.Speak
d.Animal.Speak()  // explicitly call embedded method
Interface Satisfaction
A type satisfies an interface if it implements all its methods. Embedding helps: if Dog embeds Animal, Dog gets Animal's methods → may satisfy interfaces automatically.

12 sync.Once, sync.Map — when and how to use
sync-oncesync-mapconcurrent
Medium 78%
sync.Once
Guarantees a function runs exactly once, even if called concurrently. Perfect for lazy initialization.
sync.Once Example
var (
    instance *DB
    once     sync.Once
)

func GetDB() *DB {
    once.Do(func() {
        instance = connectDB()  // runs exactly once
    })
    return instance
}
// Thread-safe singleton. Once completes, all goroutines see instance.
sync.Map
Concurrent map without external locking. Optimized for two use cases: (1) write once, read many; (2) different goroutines write different keys.
sync.Map Example
var m sync.Map
m.Store("key", "value")
v, ok := m.Load("key")
m.Delete("key")
m.Range(func(k, v any) bool {
    fmt.Println(k, v)
    return true  // continue iteration
})
sync.Map vs map+RWMutex
  • sync.Map: better for high-read, diverse-keys workloads
  • map+RWMutex: better for small maps or when you need atomic multi-op
Follow-ups
• Why is sync.Once better than an atomic boolean flag?
• What happens if the function passed to Once panics?
• How is sync.Map implemented internally? (dirty + read maps)
