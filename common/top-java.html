1 JVM memory model: heap, stack, metaspace
jvmmemorygc
Medium 92%
JVM Memory Areas
  • Heap: All objects (new). Divided into Young (Eden + 2 Survivors) + Old/Tenured. GC managed.
  • Stack: Per-thread. Holds stack frames: local variables, operand stack, method calls. Fixed size (typically 512KB-1MB). StackOverflowError if exceeded.
  • Metaspace (Java 8+): Class metadata (class bytecode, method data). Native memory, grows dynamically. Replaced PermGen which had fixed max size.
  • Code Cache: JIT-compiled native code.
  • Direct Memory: Off-heap via NIO ByteBuffer.allocateDirect(). Not GC'd, must be freed explicitly.
Tuning Flags
-Xms512m -Xmx4g       # initial and max heap
-XX:MetaspaceSize=256m # initial metaspace
-XX:MaxMetaspaceSize=512m
-Xss512k               # thread stack size
Follow-ups
• What causes OutOfMemoryError in heap vs metaspace vs direct memory?
• What is object header size in JVM? (12-16 bytes: mark word + klass pointer)
• How does compressed OOPs affect memory usage?

3 HashMap internals in Java 8+
hashmaptreeifycollision
Medium 90%
HashMap Internals
// Java 8+ structure:
// Node<K,V>[] table  (array of buckets, power of 2 size)
// Each bucket: null | Node (linked list) | TreeNode (red-black tree)

// Hash calculation:
static int hash(Object key) {
    int h;
    return (key == null) ? 0 : (h = key.hashCode()) ^ (h >>> 16);
    // XOR high bits into low bits — better distribution
}
// Bucket index: (n-1) & hash  (n = table length, power of 2)
Thresholds
  • TREEIFY_THRESHOLD = 8: Bucket with >8 nodes → convert to red-black tree (O(log n) per op)
  • UNTREEIFY_THRESHOLD = 6: Tree shrinks back to list on removal
  • LOAD_FACTOR = 0.75: Resize (double) when size/capacity > 0.75
Thread Safety
HashMap is NOT thread-safe. Use ConcurrentHashMap (lock-striping, CAS) or Collections.synchronizedMap() (coarse lock).

8 HashMap vs LinkedHashMap vs TreeMap internals
hashmaplinkedhashmaptreemap
Medium 84%
HashMap
Array of Node<K,V> buckets. Hash → index via (n-1) & hash. Collision: linked list, then treeify at threshold 8 (TREEIFY_THRESHOLD). Resize (double) at 75% load factor. Java 8: balanced BST (TreeNode) for long chains.
LinkedHashMap
Extends HashMap. Adds doubly-linked list through all entries maintaining insertion order. Can be configured for access order (LRU behaviour) with constructor parameter.
// LRU Cache using LinkedHashMap
Map<K,V> lru = new LinkedHashMap<>(16, 0.75f, true) {  // accessOrder=true
    protected boolean removeEldestEntry(Map.Entry<K,V> e) {
        return size() > capacity;
    }
};
TreeMap
Red-Black tree. Keys always sorted (natural order or Comparator). O(log n) get/put/remove. Extra operations: floorKey, ceilingKey, headMap, tailMap, subMap.
Quick Comparison
  • HashMap: O(1) avg, unordered, null key/values allowed
  • LinkedHashMap: O(1) avg, insertion/access ordered, LRU capable
  • TreeMap: O(log n), sorted, no null key

9 Java Memory Model and happens-before
jmmhappens-beforevolatile
Hard 82%
Java Memory Model (JMM) Happens-Before
If action A happens-before B, then A's writes are visible to B. Established by:
  • Monitor unlock happens-before lock by any thread
  • volatile write happens-before volatile read of same field
  • Thread.start() happens-before all actions in started thread
  • Thread.join() happens-before all actions after join returns
  • Program order within single thread
volatile vs synchronized
  • volatile: Visibility + ordering for single variable. No atomicity for compound ops (i++ is not atomic).
  • synchronized: Mutual exclusion + full memory visibility. Heavier.
  • Atomic classes: CAS-based, lock-free, best for single variable atomic operations.
Follow-ups
• Why does double-checked locking need volatile? (prevents reordering of new T() allocation vs pointer assignment)
• What is a publication failure and how does final field guarantee prevent it?

12 CountDownLatch vs CyclicBarrier vs Semaphore vs Phaser
countdown-latchbarriersemaphore
Medium 82%
CountDownLatch
One-time gate. Threads await() until count reaches 0 via countDown(). Cannot be reset.
CountDownLatch latch = new CountDownLatch(3);
// 3 workers call latch.countDown() when done
latch.await();  // main thread blocks until all 3 done
CyclicBarrier
Reusable rendezvous point. All N threads call await() and block until all arrive. Then all proceed.
CyclicBarrier barrier = new CyclicBarrier(3, () -> System.out.println("phase done"));
// Each thread calls barrier.await() — blocked until 3 threads reach barrier
Semaphore
Controls access to N permits. acquire() blocks if 0 permits. release() returns one.
Semaphore sem = new Semaphore(5);  // max 5 concurrent threads
sem.acquire();  // blocks if 5 already running
try { doWork(); } finally { sem.release(); }
Phaser (Java 7+)
Most flexible: dynamic party count, multiple phases, tree structure for scaling.
phaser.arriveAndAwaitAdvance() — arrive + wait for next phase.
When to use
  • CountDownLatch: wait for N events (startup, test setup)
  • CyclicBarrier: parallel computation phases (map-reduce stages)
  • Semaphore: connection pool, rate limiting, bounded resource access
  • Phaser: complex multi-phase parallel algorithms
Follow-ups

JWT Flow
1. POST /login {username, password}
2. Server validates credentials
3. Server signs JWT: header.payload.signature (HMAC-SHA256 or RS256)
4. Client stores JWT (HttpOnly cookie or memory — NOT localStorage)
5. Client sends: Authorization: Bearer <token>
6. Server: JwtFilter extracts token → validate signature + expiry
          → set SecurityContextHolder with authentication
7. Request proceeds to controller
JWT Filter
@Component
class JwtAuthFilter extends OncePerRequestFilter {
    @Override
    protected void doFilterInternal(HttpServletRequest req, ...) {
        String token = extractToken(req);
        if (token != null && jwtUtil.validate(token)) {
            UsernamePasswordAuthenticationToken auth =
                new UsernamePasswordAuthenticationToken(
                    jwtUtil.getUser(token), null,
                    jwtUtil.getAuthorities(token));
            SecurityContextHolder.getContext().setAuthentication(auth);
        }
        filterChain.doFilter(req, res);
    }
}
JWT vs Sessions
  • JWT: Stateless, scalable, no server-side storage. Con: can't invalidate before expiry.
  • Session: Server stores state, easy to invalidate. Con: sticky sessions or distributed session store needed.
Refresh Tokens
Short-lived access token (15min) + long-lived refresh token (7d) stored in HttpOnly cookie. Refresh endpoint issues new access token without re-login.

Common Causes
  • Static references: Static fields holding large objects or collections never GC'd
  • ThreadLocal leak: In thread pools, ThreadLocal not removed → memory leak per thread

19 Java Virtual Threads (Project Loom, Java 21)
virtual-threadsloomproject-loom
Hard 78%
Problem with Platform Threads
Java platform thread = OS thread. Creating 10,000 threads = 10,000 OS threads. Each uses ~1MB stack. I/O blocking wastes the OS thread.
Virtual Threads
Java 21 GA. Virtual threads are JVM-managed, lightweight. Mounted on platform threads (carrier threads) from a pool. On blocking I/O: JVM unmounts virtual thread, frees the carrier for others. Millions of VTs are feasible.
Usage
// Simple
Thread.ofVirtual().start(() -> handleRequest());

// With ExecutorService
try (var exec = Executors.newVirtualThreadPerTaskExecutor()) {
    for (int i = 0; i < 1_000_000; i++) {
        exec.submit(this::handleRequest);
    }
}
When to use
I/O-bound workloads (HTTP servers, DB queries). CPU-bound: still use platform threads or ForkJoinPool. Don't use synchronized blocks (causes carrier pinning) — use ReentrantLock.

22 Java Memory Model — happens-before, volatile, final
java-memory-modelhappens-beforevolatile
Hard 78%
Happens-Before Rules
If A happens-before B, A's writes are visible to B.
  • Program order: actions in a thread
  • Monitor unlock HB lock by any thread
  • volatile write HB volatile read of same field
  • Thread.start() HB all actions in started thread
  • Thread.join() HB actions after join returns
  • Static initializer HB first use of class
volatile
Guarantees: (1) reads/writes are atomic for long/double, (2) no caching in registers, (3) volatile write HB volatile read. Does NOT guarantee atomicity of compound operations (i++ is not atomic even on volatile).
volatile boolean running = true;
void stop() { running = false; }  // immediately visible to reader thread
Double-Checked Locking — Safe with volatile
class Singleton {
    private volatile static Singleton instance;
    public static Singleton get() {
        if (instance == null) {           // first check (no lock)
            synchronized (Singleton.class) {
                if (instance == null)     // second check (locked)
                    instance = new Singleton();
            }
        }
        return instance;
    }
}  // volatile prevents reordering of: alloc → init → assign
Follow-ups

• What is the difference between volatile and synchronized?

26 Java ClassLoader hierarchy and how class loading works
classloaderbootstrapdelegation
Hard 76%
ClassLoader Hierarchy
  • Bootstrap ClassLoader: Loads JDK core classes (java.lang, java.util) from rt.jar/modules. C++ code, no Java object.
  • Platform ClassLoader (was Extension): Loads java.se, java.xml etc.
  • Application ClassLoader: Loads from classpath (your app + third-party JARs).
  • Custom ClassLoaders: hot-deploy, OSGi, isolation (one classloader per plugin).
Delegation Model
When loading class X: check cache → delegate to parent → parent delegates to its parent → reach Bootstrap → if not found, child tries to load itself → ClassNotFoundException if all fail.
Class Identity
Same class name loaded by different ClassLoaders = different classes. ClassCastException when assigning across loaders. Root of hot-deploy complexity.
Custom ClassLoader
class HotLoader extends ClassLoader {
    @Override
    protected Class<?> findClass(String name) throws ClassNotFoundException {
        byte[] bytes = readBytesFromFile(name);
        return defineClass(name, bytes, 0, bytes.length);
    }
}

27 Java GC algorithms — Mark-Sweep, Mark-Compact, Copying, Generational
gc-algorithmsmark-sweepgenerational
Hard 76%
Mark-Sweep
Mark: traverse GC roots, mark all reachable objects. Sweep: scan heap, free unmarked objects. Problem: fragmentation — free spaces scattered.
Mark-Compact
Mark phase same. Compact phase: slide all live objects to one end. No fragmentation. Slower than sweep (extra copy). G1GC uses this for selected regions.
Copying Collection
Divide heap into From/To spaces. Copy live objects to To, flip spaces. No fragmentation, fast allocation (bump pointer). Wastes 50% of heap. Used for young generation.
Generational Hypothesis
Most objects die young. Java heap split:
  • Young (Eden + 2 Survivors): Minor GC — fast, copying collector
  • Old (Tenured): Major/Full GC — mark-compact or concurrent marking
Promotion: object surviving N minor GCs (default 15) moves to Old gen.
G1GC
Divides heap into equal regions (~1-32MB). Marks concurrently. Selects regions with most garbage (Garbage-First) for collection. Pause target: -XX:MaxGCPauseMillis=200.
Follow-ups

What is Reactive Programming
Non-blocking, event-driven programming with backpressure. Publisher emits data only as fast as subscriber can consume.
Project Reactor Types
  • Mono<T> — 0 or 1 element (like CompletableFuture)
  • Flux<T> — 0 to N elements (stream)
Example
// Blocking (Spring MVC)
@GetMapping("/user/{id}")
public User getUser(@PathVariable Long id) {
    return userService.findById(id);  // blocks thread!
}

// Reactive (Spring WebFlux)
@GetMapping("/user/{id}")
public Mono<User> getUser(@PathVariable Long id) {
    return userService.findById(id)  // non-blocking Mono
        .map(UserDto::from)
        .switchIfEmpty(Mono.error(new NotFoundException()));
}
When to use WebFlux
  • High-concurrency I/O bound workloads (thousands of concurrent connections)
  • Streaming data (SSE, WebSocket)
  • Avoid: CPU-bound work, blocking libraries (use bounded elastic scheduler)

G1GC (Default Java 9+)
Region-based collector. Divides heap into equal regions (~1-32MB). Concurrent marking + stop-the-world compaction of selected regions. Target: balance throughput with pause goals.

-XX:G1NewSizePercent=20    # young gen min %

-Xlog:gc*:file=gc.log      # GC logging

Concurrent, scalable, <1ms pauses regardless of heap size (even TBs). Uses colored pointers + load barriers. Ideal for latency-sensitive workloads.

30 Java NIO — Channels, Buffers, Selectors (non-blocking I/O)
niochannelbuffer
Hard 74%
NIO vs Old IO
  • Old IO (java.io): Stream-based, blocking, thread-per-connection
  • NIO (java.nio): Buffer-based, non-blocking, multiplexed via Selector
Key Components
  • Buffer: Fixed-size data container (ByteBuffer, IntBuffer). Has position, limit, capacity.
  • Channel: Bidirectional, non-blocking I/O endpoint (SocketChannel, FileChannel, ServerSocketChannel)
  • Selector: Monitors multiple channels on one thread. OS epoll/kqueue underneath.
Non-blocking Server Skeleton
Selector selector = Selector.open();
ServerSocketChannel ssc = ServerSocketChannel.open();
ssc.configureBlocking(false);
ssc.bind(new InetSocketAddress(8080));
ssc.register(selector, SelectionKey.OP_ACCEPT);

while (true) {
    selector.select();  // blocks until event
    Set<SelectionKey> keys = selector.selectedKeys();
    for (SelectionKey key : keys) {
        if (key.isAcceptable()) { accept(key); }
        else if (key.isReadable()) { read(key); }
    }
    keys.clear();
}
ByteBuffer
flip() switches from write to read mode. clear() resets for writing. compact() keeps unread bytes, moves to front.

Restrict which classes can extend/implement a sealed class/interface. Enables exhaustive pattern matching in switch.

34 ReentrantReadWriteLock vs StampedLock
rwlockstampedlockoptimistic
Hard 72%
ReentrantReadWriteLock
Multiple concurrent readers OR one exclusive writer. Writer starvation risk if readers never release.
ReadWriteLock rwl = new ReentrantReadWriteLock();
Lock rl = rwl.readLock();
Lock wl = rwl.writeLock();

// Read
rl.lock(); try { return value; } finally { rl.unlock(); }
// Write
wl.lock(); try { value = newVal; } finally { wl.unlock(); }
StampedLock (Java 8)
Better throughput via optimistic reads — no lock acquisition for reads if no writer active.
StampedLock sl = new StampedLock();

// Optimistic read (no blocking):
long stamp = sl.tryOptimisticRead();
int val = value;                      // read without lock
if (!sl.validate(stamp)) {            // check if writer intervened
    stamp = sl.readLock();            // fallback to real read lock
    try { val = value; } finally { sl.unlockRead(stamp); }
}

// Write:
long ws = sl.writeLock();
try { value = newVal; } finally { sl.unlockWrite(ws); }
When to use
  • RRW Lock: read-heavy, need reentrant locking
  • StampedLock: read-heavy, max throughput, no reentrancy needed
  • Avoid StampedLock if writes are frequent (optimistic reads will always fail)

35 Java modules system (JPMS — Java 9+)
jpmsmodulesmodule-info
Medium 68%
What is JPMS
Java Platform Module System (Java 9). Introduces strong encapsulation at the package level. Replaces classpath with modulepath. Eliminates split packages, illegal access.
module-info.java
// com.myapp.service module
module com.myapp.service {
    requires java.net.http;       // depend on module
    requires com.myapp.model;
    exports com.myapp.service.api; // expose this package
    exports com.myapp.service.impl to com.myapp.web; // targeted export
    provides com.myapp.spi.Parser  // service provider
        with com.myapp.service.impl.JsonParser;
}
Benefits
  • Strong encapsulation: internal packages hidden by default
  • Reliable configuration: missing dependencies fail at startup, not runtime
  • Smaller JVM images with jlink
Classpath vs Modulepath
Classpath: no encapsulation, all public APIs accessible. Modulepath: only exported packages visible. Automatic modules for legacy JARs.
