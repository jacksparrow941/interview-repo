1 Goroutines vs OS threads
goroutinesthreadsgmp
Medium 92%
Goroutines vs OS Threads
  • Goroutine: ~2KB initial stack (grows dynamically to hundreds of MB if needed). M:N threading — N goroutines multiplexed onto M OS threads. Scheduled by Go runtime.
  • OS Thread: ~1MB stack (fixed at creation). 1:1 with kernel thread. Expensive context switch (μs).
  • Can run millions of goroutines. Thousands of OS threads = OOM.
GMP Model (brief)
  • G: Goroutine (the task)
  • M: OS thread (the runner)
  • P: Processor/scheduler context (GOMAXPROCS Ps). Each P has local run queue.
  • When G blocks on syscall → M + G detach from P → P gets another M to continue work
Follow-ups
• What is goroutine stack growth mechanism? (segmented stacks → copying stacks since Go 1.4)
• What is GOMAXPROCS and when would you change it?
• How do goroutines avoid the 10K thread problem?

2 Channels: buffered vs unbuffered
channelsbufferedsynchronous
Medium 90%
Buffered vs Unbuffered Channels
  • Unbuffered make(chan T): Sender blocks until receiver is ready. Receiver blocks until sender sends. Strict synchronization point (rendezvous).
  • Buffered make(chan T, n): Sender blocks only when buffer full. Receiver blocks only when buffer empty. Decouples send and receive timing.
Usage Patterns
// Semaphore (limit concurrency to 5):
sem := make(chan struct{}, 5)
for _, job := range jobs {
    sem <- struct{}{}  // acquire
    go func(j Job) {
        defer func() { <-sem }()  // release
        process(j)
    }(job)
}

// Signal (done channel):
done := make(chan struct{})
go func() { defer close(done); doWork() }()
<-done  // wait for completion
Closing Channels
Only sender should close. Closing a closed channel panics. Reading from closed channel returns zero value + false: v, ok := <-ch; if !ok { // closed }

6 defer, panic, recover — full semantics and patterns
deferpanicrecover
Medium 88%
defer
Deferred call runs when surrounding function returns (normal or panic). Arguments evaluated immediately; call deferred. LIFO order.
func processFile(path string) (err error) {
    f, err := os.Open(path)
    if err != nil { return }
    defer f.Close()           // runs even on early return/panic
    defer func() {            // named return: modify err on cleanup failure
        if cerr := f.Close(); cerr != nil && err == nil {
            err = cerr
        }
    }()
    // ... process f
    return
}
panic / recover
func safeDiv(a, b int) (result int, err error) {
    defer func() {
        if r := recover(); r != nil {     // recover() catches panic
            err = fmt.Errorf("panic: %v", r)
        }
    }()
    return a / b, nil  // panics if b==0
}

// recover() returns nil if no panic, or the panic value
// ONLY works inside a deferred function
Rules
  • recover() only stops a panic if called directly from a deferred function
  • Panic unwinds stack, running deferred functions
  • Use panic for truly unrecoverable states (programming errors), not business logic
  • HTTP handlers should recover panics to avoid crashing the whole server
Follow-ups
• What is the difference between os.Exit and panic?
• Can you defer a method call? (yes)
• What is the defer overhead? (small but measurable in hot loops)

8 goroutine leak — how to detect and prevent
goroutine-leakcontextdone-channel
Medium 86%
What is a goroutine leak
Goroutines that are started but never terminate. They consume memory (~2KB initial stack, can grow), CPU for scheduling, and keep referenced objects alive.
Common Causes
  • Blocked channel read/write with no one to unblock
  • Not passing/checking context.Context
  • Infinite loops without exit condition
  • Forgotten goroutines in tests
Prevention Pattern
func worker(ctx context.Context, jobs <-chan Job) {
    for {
        select {
        case <-ctx.Done():
            return  // clean exit
        case job, ok := <-jobs:
            if !ok { return }  // channel closed
            process(job)
        }
    }
}
Detection with pprof

12 Go interfaces — nil interface trap, empty interface
interfacenilempty-interface
Medium 84%
Interface internals
A Go interface value has two words: (type, pointer). An interface is nil only when both type and pointer are nil.
The Nil Trap
type MyError struct{ msg string }
func (e *MyError) Error() string { return e.msg }

func getError() error {
    var err *MyError = nil
    return err  // TRAP: returns (type=*MyError, ptr=nil) — NOT nil interface!
}

if err := getError(); err != nil {
    fmt.Println("This prints!")  // Bug!
}

// Fix: return nil explicitly
func getError() error {
    var err *MyError
    if conditionFailed { return err }  // still buggy
    return nil  // correct
}

var i interface{} = "hello"

// Type assertion

// Type switch

case int:     fmt.Println("int:", v)

}

13 Channel patterns — fan-out, fan-in, pipeline, done channel
channelspipelinefan-out
Hard 84%
Pipeline
func gen(nums ...int) <-chan int {
    out := make(chan int)
    go func() {
        defer close(out)
        for _, n := range nums { out <- n }
    }()
    return out
}
func sq(in <-chan int) <-chan int {
    out := make(chan int)
    go func() { defer close(out); for n := range in { out <- n*n } }()
    return out
}
// Usage: for v := range sq(sq(gen(2,3,4))) { fmt.Println(v) }
Fan-Out
func fanOut(in <-chan int, workers int) []<-chan int {
    outs := make([]<-chan int, workers)
    for i := range outs {
        outs[i] = sq(in)  // each worker reads from same input
    }
    return outs
}
Fan-In (Merge)
func merge(cs ...<-chan int) <-chan int {
    var wg sync.WaitGroup
    out := make(chan int)
    output := func(c <-chan int) {
        defer wg.Done()
        for v := range c { out <- v }
    }
    wg.Add(len(cs))
    for _, c := range cs { go output(c) }
    go func() { wg.Wait(); close(out) }()
    return out
}
Done Channel (Cancellation)
func sq(done <-chan struct{}, in <-chan int) <-chan int {
    out := make(chan int)
    go func() {
        defer close(out)
        for n := range in {
            select {
            case out <- n*n:
            case <-done: return  // cancelled
            }
        }
    }()
    return out
}
// Use context.Context in production instead of done channel

14 sync.Mutex vs sync.RWMutex
mutexrwmutexsynchronization
Medium 82%
sync.Mutex vs sync.RWMutex
  • sync.Mutex: Exclusive lock. One goroutine at a time (readers OR writer).
  • sync.RWMutex: Multiple concurrent readers OR one exclusive writer. Writers must wait for all readers. Readers don't block each other. Great for read-heavy workloads (config, caches).
Code
type SafeMap struct {
    mu   sync.RWMutex
    data map[string]string
}
func (m *SafeMap) Get(key string) string {
    m.mu.RLock()         // shared read lock
    defer m.mu.RUnlock()
    return m.data[key]
}
func (m *SafeMap) Set(key, val string) {
    m.mu.Lock()          // exclusive write lock
    defer m.mu.Unlock()
    m.data[key] = val
}
When RWMutex hurts
RWMutex adds overhead for writer starvation prevention. If writes are frequent, plain Mutex is faster. Profile before switching.

• How does sync.Map differ from RWMutex-protected map? (optimized for append-only + stable key sets)

20 Functional options pattern in Go

Problem
How to provide optional configuration to a constructor without breaking API as options grow? Config structs are verbose; many parameters are messy.
Functional Options Pattern
type Server struct {
    host    string
    port    int
    timeout time.Duration
    maxConn int
}

type Option func(*Server)

func WithPort(p int) Option      { return func(s *Server) { s.port = p } }
func WithTimeout(d time.Duration) Option { return func(s *Server) { s.timeout = d } }
func WithMaxConn(n int) Option   { return func(s *Server) { s.maxConn = n } }

func NewServer(host string, opts ...Option) *Server {
    s := &Server{host: host, port: 8080, timeout: 30*time.Second, maxConn: 100}  // defaults
    for _, opt := range opts { opt(s) }
    return s
}

// Usage (clean, readable, extensible):

    WithPort(9090),
    WithTimeout(5*time.Second),
)

  • Backward compatible — add new options without changing signature
  • Self-documenting call sites
  • Easy to set sensible defaults
  • Options are first-class values — can be composed, stored, passed around

23 errgroup — coordinating concurrent goroutines with error handling
errgroupconcurrentwait-group
Medium 78%
Problem
sync.WaitGroup doesn't propagate errors. Manual error collection is error-prone.
errgroup solution
import "golang.org/x/sync/errgroup"

func fetchAll(ctx context.Context, ids []int) ([]User, error) {
    g, ctx := errgroup.WithContext(ctx)
    results := make([]User, len(ids))

    for i, id := range ids {
        i, id := i, id  // capture loop vars
        g.Go(func() error {
            user, err := fetchUser(ctx, id)
            if err != nil { return err }
            results[i] = user
            return nil
        })
    }

    if err := g.Wait(); err != nil {
        return nil, fmt.Errorf("fetchAll: %w", err)
    }
    return results, nil
}
Key behaviours
  • First error cancels derived context (ctx.Done() triggers)
  • g.Wait() blocks until all goroutines finish, returns first error
  • Limit concurrency: g.SetLimit(10) (Go 1.20+)
Follow-ups
• How do you collect ALL errors instead of just the first?

24 sync.Once, sync.Map — when and how to use

sync.Once
Guarantees a function runs exactly once, even if called concurrently. Perfect for lazy initialization.
sync.Once Example
var (
    instance *DB
    once     sync.Once
)

func GetDB() *DB {
    once.Do(func() {
        instance = connectDB()  // runs exactly once
    })
    return instance
}
// Thread-safe singleton. Once completes, all goroutines see instance.
sync.Map
Concurrent map without external locking. Optimized for two use cases: (1) write once, read many; (2) different goroutines write different keys.
sync.Map Example

m.Store("key", "value")
v, ok := m.Load("key")
m.Delete("key")
m.Range(func(k, v any) bool {
    fmt.Println(k, v)
    return true  // continue iteration
})
sync.Map vs map+RWMutex
  • sync.Map: better for high-read, diverse-keys workloads
  • map+RWMutex: better for small maps or when you need atomic multi-op

28 Go GMP scheduler — deep dive (G, M, P, work stealing)
gmpschedulergoroutine
Hard 74%
GMP Model
  • G (Goroutine): Lightweight coroutine. ~2KB initial stack, grows dynamically. Millions possible.
  • M (Machine/Thread): OS thread. One M executes one G at a time. Limited by GOMAXPROCS for Go code; more Ms created for blocking syscalls.
  • P (Processor): Scheduling context. GOMAXPROCS Ps (default = CPU cores). Each P has a local run queue (LRQ) of Gs.
Scheduling Flow
1. goroutine created → added to P's LRQ
2. P pops G from LRQ, assigns to M → runs
3. G blocks on syscall → M + G detached from P
   → P finds idle M (or creates new) → continues running other Gs
4. Syscall completes → G goes back to global run queue (GRQ)
5. Work stealing: idle P steals half of busy P's LRQ → balanced load
Preemption
Go uses cooperative preemption (yield at function calls) + async preemption (sysmon thread sends SIGURG after 10ms to interrupt G). Long CPU-bound goroutines preempted automatically.
GOMAXPROCS
Number of OS threads for Go code = number of Ps. runtime.GOMAXPROCS(n) or GOMAXPROCS=n env var.

29 Go memory escape analysis and optimization
escape-analysisstackheap
Hard 74%
Escape Analysis
Go compiler determines at compile time whether a variable can live on the stack (cheap, GC-free) or must escape to the heap (GC pressure, slower).
go build -gcflags='-m -m' ./... shows escape decisions.
Common Escape Causes
  • Variable address taken and returned: return &x — x escapes
  • Stored in interface: var i interface{} = x — x escapes (if not pointer-sized)
  • Closure captures variable: go func(){ use(x) }() — x may escape
  • Slice/map of large type — backing array on heap
Avoiding Escapes
// Bad: escapes to heap
func newPoint(x,y int) *Point { return &Point{x,y} }

// Good: caller allocates on stack
func initPoint(p *Point, x,y int) { p.X,p.Y = x,y }
var p Point; initPoint(&p, 3, 4)  // stays on stack

// Bad: interface boxing causes escape
func log(msg interface{}) { fmt.Println(msg) }  // allocates
// Good:
func log(msg string) { fmt.Println(msg) }  // no alloc
sync.Pool
Reuse heap-allocated objects across goroutines to reduce GC pressure.
pool := sync.Pool{New: func() any { return &Buffer{} }}

31 How does Go's memory allocator work? (mcache, mcentral, mheap)
memory-allocatormcachemheap
Hard 72%
Architecture (inspired by TCMalloc)
  • mcache: Per-P (logical processor) cache of small object spans. Lock-free allocation for objects <32KB.
  • mcentral: Per-size-class central lists. Replenishes mcache when empty.
  • mheap: Global heap of OS memory. Allocates large objects (>32KB) directly.
Size Classes
Objects grouped into ~70 size classes (8B, 16B, 24B, ... 32KB). Reduces fragmentation. Large objects go directly to mheap.
Stack Allocation
Go prefers stack allocation (escape analysis). Objects that don't escape the function go on stack — zero GC pressure.
Practical Impact
// Stack allocated (no GC)
func sum(a, b int) int { return a + b }

// Heap allocated (escapes via interface)
func boxed(x int) interface{} { return x }  // x escapes!
