2 Design Twitter/X timeline — fan-out on write vs fan-out on read
twittertimelinefan-out
Hard 92%
Approaches
  • Fan-out on Write (Push): When user tweets, push tweet ID to all followers' home timeline caches (Redis sorted sets). Read is fast (O(1) from cache). Write is expensive for users with millions of followers (celebrities).
  • Fan-out on Read (Pull): On timeline load, fetch tweets from all followed users, merge, sort. Write is O(1). Read is expensive (100 follows = 100 DB queries).
  • Hybrid (Twitter's actual approach): Fan-out on write for users with <10K followers. Fan-out on read for celebrities (Lady Gaga: 100M followers — can't write to 100M caches per tweet).
Storage Architecture
Tweet Service:
  - MySQL: tweet metadata (id, user_id, text, created_at)
  - Blob store (S3): media files
  - Redis: home timeline cache per user (sorted set by tweet_id)

Timeline Service:
  - Read from Redis cache
  - For celebrities: merge from DB query on read
  - Ranked feed: ML model scores tweets, inserted in order
Key Design Decisions
  • Tweet ID as Snowflake (time-sortable → no ORDER BY timestamp needed)
  • Timeline cache: Redis ZSET with tweet_id as score, cap at 800 entries
  • Notifications: Kafka topics per user for async fan-out workers
  • Search: Elasticsearch for full-text search, Earlybird for real-time tweet index
Cross-questions
  • How do you handle a celebrity tweet without overloading fan-out workers?
  • How do you implement the ranking algorithm without recomputing for every read?
  • How does Twitter handle timeline when you follow 5000 accounts?
Follow-ups
• How does Instagram feed differ from Twitter feed architecture?
• What is the Thundering Herd problem in feed generation?
• How do you implement "who to follow" recommendations?

3 Design Uber dispatch system — matching drivers to riders
uberdispatchgeospatial

Components

                             ↓
                    Location Service (driver positions)
                    Matching Service (find nearest drivers)
                    ETA Service (maps API)

Location Service
Driver apps send GPS every 4-5 seconds. Store in Redis geospatial index (GEOADD). Query: GEORADIUS 37.7749 -122.4194 1 km ASC COUNT 5 → nearest 5 drivers within 1km. Google S2 geometry library for complex polygon queries.
Matching Algorithm
On ride request:
1. GEORADIUS → candidate drivers in 500m-2km
2. Filter: available (not on trip), accepts request type, car type matches
3. Score each: ETA + acceptance rate + rating
4. Offer to top driver (timeout 10s) → if rejected, next driver
5. On accept: create trip in DB, notify rider
Surge Pricing
Supply (available drivers) vs demand (open requests) per H3 hexagon. If demand/supply > threshold → surge multiplier. Displayed to rider before booking.

4 Design a payment system — processing, idempotency, reconciliation
paymentsidempotencysaga
Hard 92%
Payment Flow
Customer → Payment Gateway → Razorpay/Stripe
                              ↓
                    Payment Processor → Card Network (Visa/Mastercard)
                                          ↓
                                  Issuing Bank (authorize)
                                          ↓ (approve/decline)
                    Settlement Service (T+1 or T+2 days)
                    Ledger Service (double-entry bookkeeping)
Idempotency
Critical: if client retries payment request, must not double-charge.
Client sends: POST /payments
              Idempotency-Key: uuid-v4-from-client

Server: INSERT INTO payments (idempotency_key, ...)
        ON CONFLICT (idempotency_key) DO NOTHING
        RETURNING *;
// If key exists → return stored result (no double processing)
Saga Pattern for Distributed Payment
1. Reserve inventory
2. Debit customer account
3. Credit merchant account
4. Fulfill order
On failure at step 3: compensate (refund), release inventory
Ledger / Double-Entry
Every transaction = two entries: debit one account, credit another. Prevents money creation/destruction. Immutable append-only ledger. Balance = sum(credits) - sum(debits) from ledger.

5 Design WhatsApp — messaging, delivery receipts, group chat
whatsappmessagingwebsocket
Hard 90%
Core Architecture
Client ←→ WebSocket/XMPP ←→ Chat Server → Message Queue (Kafka)
                                        ↓
                              Message Store (Cassandra)
                              Delivery Service → Notification (FCM/APNs)
Message Flow
1. Sender connects via WebSocket to Chat Server (sticky session)
2. Sends message → Chat Server stores in Cassandra:
   (conversation_id, message_id [Snowflake], sender, content, ts, status=SENT)
3. Delivery: if recipient online (same/different server)
   → Use presence service / Redis pub-sub for server routing
   → Forward via WebSocket → recipient sends ACK → status=DELIVERED
4. Read receipt: recipient opens chat → status=READ
5. Offline: store message in Cassandra, push via FCM/APNs on reconnect sync
Group Chat (256 members)
  • Small groups (<256): Fan-out message to all member connections. Store once, deliver to all.
  • Very large groups: Store one copy, each member fetches on demand (cursor-based pagination)
  • Last-seen / delivery tracking: Redis set per message_id of delivered user_ids
End-to-End Encryption
Signal Protocol: each message encrypted with recipient's public key. Server stores only encrypted blobs. Key exchange via identity/one-time prekeys.

6 Design Twitter/Feed System
fanoutpush-pullredis-sorted-set
Hard 88%
Design a Scalable Key-Value Store
Like DynamoDB/Redis Cluster. Key decisions: partitioning, replication, consistency.
Architecture
  • Consistent hashing ring with virtual nodes for partitioning
  • Replication: N=3. Coordinator writes to 3 nodes.
  • Quorum: W=2, R=2. W+R>N → strong consistency. W=1,R=1 → eventual.
  • Storage engine: LSM-tree (RocksDB) for write optimization
  • Gossip protocol for cluster membership/failure detection
Data Flow
PUT key=A value=X:
  1. Client → any node (coordinator)
  2. Hash(A) → ring position → 3 responsible nodes
  3. Coordinator writes to all 3, waits for W=2 acks
  4. Returns success

GET key=A:
  1. Coordinator queries R=2 nodes
  2. Returns latest version (by timestamp or vector clock)
  3. Read repair: update stale replica asynchronously
Follow-ups
• How does hinted handoff handle temporarily unavailable nodes?
• What is sloppy quorum vs strict quorum?
• How do you handle hot keys? (request sharding, local cache)

9 Design a distributed key-value store (like Redis/DynamoDB)
distributed-kvconsistent-hashingreplication
Hard 88%
Architecture
Client → Load Balancer → Coordinator Node
                            ↓ (consistent hash ring)
                        Partition 0 → Replica A, B, C
                        Partition 1 → Replica D, E, F
                        ...
Data Distribution
Consistent hashing: keys mapped to ring. Each node owns a range. Virtual nodes (vnodes): each physical node = 100-200 vnodes for even distribution. Adding/removing node: only adjacent vnodes affected.
Replication
Each key replicated to N nodes (typically N=3, DynamoDB style). Coordinator writes to all N. Quorum: W=2 (write), R=2 (read) → W+R>N = strong consistency. W=1, R=1 → eventual consistency, highest availability.
Conflict Resolution
Vector clocks track causality. On divergent versions (network partition): return both to client (DynamoDB shopping cart), or last-write-wins (LWW) for simpler cases.
Storage Engine
LSM Tree (write-optimized): MemTable → immutable SSTable → compaction. B+Tree (read-optimized): InnoDB, LMDB. LSM preferred for KV stores: fast sequential writes, compaction amortizes cost.
Cross-questions
  • How do you handle hot keys? (request sharding, local cache)
  • How does gossip protocol maintain cluster membership?
  • How does hinted handoff handle temporary node failure?
Follow-ups
• What is sloppy quorum and hinted handoff in DynamoDB?
• How does Redis Cluster implement hash slots? (16384 slots)
• Compare DynamoDB vs Cassandra vs Redis Cluster architecture.

16 Design a Search Engine (web-scale)
search-engineinverted-indexcrawling
Hard 84%
Components
1. Crawler: Fetch web pages (BFS from seed URLs)
2. Parser: Extract text, links, metadata
3. Indexer: Build inverted index
4. Ranker: Score results (TF-IDF, PageRank, ML)
5. Searcher: Query processing, retrieve, rank, return
6. Cache: Query result cache, bloom filter for crawled URLs
Inverted Index
Maps term → list of (document_id, positions, frequency). Query 'distributed systems' → intersect posting lists → ranked by TF-IDF × PageRank.
Index: { 'distributed': [(doc1, [3,7], 2), (doc4, [1], 1)],
         'systems':     [(doc1, [4,8], 2), (doc2, [5], 1)] }
Query 'distributed systems': doc1 (both terms, high freq) ranks highest
Elasticsearch
Distributed search based on Lucene. Shard data across nodes. Each shard = independent Lucene index. Replicas for read scaling + fault tolerance. Inverted index + doc_values (column store for aggregations) + BKD trees (numeric/geo ranges).
PageRank
Iterative algorithm: rank(A) = (1-d) + d × Σ(rank(B)/outlinks(B)) for all B→A. Pages with many quality inbound links rank higher.

  • How do you update the index for real-time news? (incremental indexing, Kafka → Elasticsearch)
  • How do you implement spell correction? (n-gram index, edit distance)
Follow-ups

• How does vector search (ANN) work for semantic search? (FAISS, HNSW)

20 Design a CDN from scratch
cdnedgepop
Hard 82%
Global Architecture
Origin Server (S3 / API)
    ↑ Cache Miss (Origin Pull)
Edge PoPs (Points of Presence):
  - 200+ cities globally
  - Each: SSD cache (hot), object store (warm), scrubber
  - Anycast BGP routing → client reaches nearest PoP
  - PoP cache miss → Regional cache (shield) → origin
Routing
Anycast: Multiple PoPs announce same IP via BGP. Client's ISP routes to nearest by BGP path. Latency: 20-30ms to nearest edge vs 150-300ms to origin.
GeoDNS fallback: Different IP per region when anycast not available.
Cache Hierarchy
Client → L1 Edge (city) → L2 Shield (regional aggregator) → Origin
         Hot: SSD 1-2TB      Warm: NVMe 50-100TB       Cold: S3
         Miss rate: 5-15%    Miss rate: 0.1-2%
Cache Invalidation
  • URL-based purge: CDN.purge('https://example.com/logo.png')
  • Tag-based purge: tag all product page assets with product_id → invalidate on update
  • Surrogate-Control: s-maxage=3600 (CDN TTL separate from browser)
Security at Edge
  • TLS termination at edge (no TLS to origin for static assets)
  • DDoS mitigation: rate limiting, IP reputation, challenge page
  • WAF (Web Application Firewall): block OWASP top 10, SQL injection, XSS
Cross-questions

  • How does Cloudflare Tiered Cache reduce origin load?
  • How would you implement edge computing (Cloudflare Workers)?

23 Design Distributed ID Generator (Snowflake)
snowflaketimestampmonotonic
Medium 78%
Snowflake ID — 64-bit Layout
0 | 41 bits timestamp (ms) | 10 bits worker ID | 12 bits sequence
↑ unused                    ↑ datacenter(5)+machine(5)

Timestamp: ms since custom epoch (e.g., Jan 1 2015)
Worker ID: unique per service instance (assigned from ZK or env var)
Sequence:  0-4095 per millisecond per worker; resets each ms
Clock Skew Handling
if currentTime < lastTimestamp:
    # clock moved backwards!
    wait until currentTime >= lastTimestamp  # wait up to a few ms
    # OR: raise error and fail fast
    # OR: use sequence from future slots of last timestamp
Monotonicity
IDs are roughly time-sortable (within clock skew tolerance). No sort needed for recent data. Avoids random B-tree page writes = better index write performance.
Follow-ups
• What is the maximum QPS per worker? (4096/ms = ~4M/s per machine)
• How does Twitter Snowflake differ from Instagram ID generation?
• How do you handle the epoch overflow in 2079?
