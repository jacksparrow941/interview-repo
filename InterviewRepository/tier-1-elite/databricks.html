3 Network Delay Time (Dijkstra)
dijkstraheap
Medium 72%
Dijkstra's Algorithm
Min-heap (priority queue) for greedy shortest path. Relax all edges from current shortest node.
Solution
import heapq
def networkDelayTime(times, n, k):
    graph = defaultdict(list)
    for u,v,w in times: graph[u].append((v,w))
    dist = {k: 0}
    heap = [(0, k)]
    while heap:
        d, u = heapq.heappop(heap)
        if d > dist.get(u, float('inf')): continue
        for v, w in graph[u]:
            nd = d + w
            if nd < dist.get(v, float('inf')):
                dist[v] = nd; heapq.heappush(heap, (nd,v))
    return max(dist.values()) if len(dist)==n else -1
Complexity
Time: O((V+E) log V) | Space: O(V+E)

Data Distribution
Consistent hashing: keys mapped to ring. Each node owns a range. Virtual nodes (vnodes): each physical node = 100-200 vnodes for even distribution. Adding/removing node: only adjacent vnodes affected.
Replication
Each key replicated to N nodes (typically N=3, DynamoDB style). Coordinator writes to all N. Quorum: W=2 (write), R=2 (read) → W+R>N = strong consistency. W=1, R=1 → eventual consistency, highest availability.

Storage Engine
LSM Tree (write-optimized): MemTable → immutable SSTable → compaction. B+Tree (read-optimized): InnoDB, LMDB. LSM preferred for KV stores: fast sequential writes, compaction amortizes cost.

1 What is consistent hashing?
consistent-hashingvirtual-nodes
Hard 86%
Consistent Hashing
Problem with naive modulo hashing: adding/removing 1 server remaps N/S keys (massive cache miss storm).

Ring approach: Hash servers and keys to same circular space (0 to 2^32). A key is assigned to the first server found clockwise from its hash position.
Virtual Nodes
Each physical server = 100-200 virtual nodes on the ring → even distribution even with few servers. Fewer hot spots. When server added/removed: only 1/N keys remapped.
class ConsistentHash:
    def __init__(self, replicas=150):
        self.ring = {}
        self.sorted_keys = []
        self.replicas = replicas

    def add_server(self, server):
        for i in range(self.replicas):
            key = hash(f'{server}:{i}')
            self.ring[key] = server
        self.sorted_keys = sorted(self.ring)

    def get_server(self, item):
        h = hash(item)
        for k in self.sorted_keys:
            if h <= k: return self.ring[k]
        return self.ring[self.sorted_keys[0]]  # wrap around

3 Explain eventual consistency vs strong consistency
consistencycappaxos
Medium 84%
Strong Consistency
All nodes see the same data at the same time. After a write completes, all reads return the new value. Requires synchronous replication. Used in: financial systems, leader election (etcd, ZooKeeper).
Eventual Consistency
Given no new updates, all replicas will eventually converge. Reads may return stale data temporarily. Higher availability and partition tolerance. Used in: DNS, S3, DynamoDB (default), Cassandra.
CAP Theorem
In presence of network Partition, choose Consistency OR Availability:
  • CP: HBase, MongoDB (primary), etcd, ZooKeeper — prefer consistency over availability
  • AP: Cassandra, DynamoDB, CouchDB — prefer availability over consistency
  • CA systems only work without partitions (single node databases)
PACELC
Extension of CAP: Even without partitions, trade-off exists between Latency and Consistency.

5 Explain CQRS and Event Sourcing
cqrsevent-sourcingread-model
Hard 66%
CQRS — Command Query Responsibility Segregation
Separate write model (commands: create, update, delete) from read model (queries: optimized for reads). Read model can be denormalized, use different database (e.g., Elasticsearch for search, Redis for fast reads). Scales independently.
Event Sourcing
State is derived from a sequence of immutable events, not current state snapshot. Events are appended to an event store (log). State reconstructed by replaying events.
Events: OrderPlaced → ItemAdded → PaymentProcessed → OrderShipped
Current state: replay all events → Order{status=SHIPPED, items=[...], payment=PAID}
Benefits and Costs
  • Benefits: Full audit log, time travel (replay to any point), event-driven integration
  • Costs: Eventual consistency between command and query model, complex querying, schema evolution of events, snapshot needed for long histories

2 Database isolation levels
isolationmvccphantom
Hard 87%
ACID Properties
  • Atomicity: All operations in transaction succeed or all are rolled back. No partial updates.
  • Consistency: Transaction brings DB from one valid state to another. Constraints never violated.
  • Isolation: Concurrent transactions behave as if sequential. Anomalies depend on isolation level.
  • Durability: Committed transactions survive crashes. Guaranteed by WAL.
Isolation Levels & Anomalies
READ UNCOMMITTED: dirty read allowed (see uncommitted data)
READ COMMITTED:  no dirty read | phantom read possible
REPEATABLE READ: no dirty/non-repeatable read | phantom possible (MySQL: solved by gap locks)
SERIALIZABLE:   full isolation, slowest — SSI (PostgreSQL) or locking (MySQL)
How Implemented
PostgreSQL: MVCC for Repeatable Read and below. Serializable: SSI (Serializable Snapshot Isolation). MySQL InnoDB: row-level locking + MVCC + gap locks for Repeatable Read.

Sharding Strategies
  • Range-based: Shard by range (A-G, H-P, Q-Z). Simple routing. Risk: hot spots on recent data (time-based IDs all go to last shard).

  • Transactions: 2PC expensive; use Saga instead

  • Hot key: add random suffix to key, fan out writes, merge reads

6 PostgreSQL MVCC
mvccxminxmax
Hard 78%
PostgreSQL MVCC Internals
Each row version has xmin (created by txn) and xmax (deleted by txn, 0 if alive).
A txn sees a row if: xmin committed AND xmin <= txn_snapshot AND (xmax=0 OR xmax > txn_snapshot OR xmax not committed)
How it enables isolation
  • Readers never block writers (different row versions)
  • Writers never block readers
  • REPEATABLE READ: txn gets a snapshot at start, sees consistent view throughout
  • No shared read locks needed — eliminates reader-writer contention
VACUUM
Dead tuples (old xmax'd versions) accumulate. VACUUM marks them as free space. AUTOVACUUM: background process. Bloat: table grows with dead tuples. VACUUM ANALYZE: also updates planner statistics.

1 ABA problem in lock-free programming
abacasversion-counter
Hard 72%
ABA Problem
Thread 1 reads value A. Thread 2 changes A→B→A. Thread 1 does CAS: sees A, thinks nothing changed — succeeds. But the state HAS changed (e.g., a node was removed and re-inserted in a lock-free list).
Solution — Tagged Pointers
// 64-bit pointer: high bits = ABA counter (version)
struct TaggedPointer {
    Node* ptr;
    uint64_t tag;  // monotonically increasing
};

// CAS on BOTH ptr and tag:
expected = { nodeA, 5 };
if (CAS(&head, expected, { nodeB, 6 })) { /* won */ }
// Even if ptr went A→B→A, tag goes 5→6→7 — never same tagged value
Alternative: Hazard Pointers
Before accessing a node, register its pointer in per-thread hazard pointer array. Reclaimer checks all hazard pointers before freeing memory. Used in folly::ConcurrentLinkedList.

Java Memory Model (JMM) Happens-Before
If action A happens-before B, then A's writes are visible to B. Established by:
  • Monitor unlock happens-before lock by any thread
  • volatile write happens-before volatile read of same field
  • Thread.start() happens-before all actions in started thread
  • Thread.join() happens-before all actions after join returns
  • Program order within single thread
volatile vs synchronized
  • volatile: Visibility + ordering for single variable. No atomicity for compound ops (i++ is not atomic).
  • synchronized: Mutual exclusion + full memory visibility. Heavier.
  • Atomic classes: CAS-based, lock-free, best for single variable atomic operations.

2 Explain transformer architecture and attention mechanism
transformerattentionself-attention
Hard 82%
Self-Attention Mechanism
Input: sequence of tokens → embeddings (d_model=768 for BERT-base)

For each token, compute:
  Q (query) = embedding × W_Q
  K (key)   = embedding × W_K
  V (value) = embedding × W_V

Attention weights = softmax(Q × K^T / sqrt(d_k))
Output = Attention_weights × V

# Each token attends to all other tokens — captures long-range dependencies
# Multi-head: run h parallel attention heads, concat, project
Transformer Architecture
  • Encoder (BERT): Bidirectional. Sees full context. Used for classification, NER, embeddings.
  • Decoder (GPT): Autoregressive. Each token attends only to previous tokens (causal mask). Used for generation.
  • Encoder-Decoder (T5, BART): Seq2seq tasks: translation, summarization, QA.
Why Transformers replaced RNNs
  • RNN: sequential computation → no parallelism. Gradient vanishing for long sequences.
  • Transformer: parallel over all positions. Self-attention = O(n²d) but parallelizable on GPU.
  • Position encoding: sinusoidal or learned — since attention is permutation-invariant, positional info must be added explicitly.

4 How do you detect and handle model drift?

Types of Drift
  • Data drift (covariate shift): Input feature distribution changes. User behavior changed, new user segment, seasonality. Model predictions become unreliable.
  • Concept drift: Relationship between features and label changes. E.g., 'fraud' patterns evolve.
  • Label drift: Output distribution changes. E.g., more fraudulent transactions in new season.
Detection Methods

  • Continuous training: Retrain on rolling window of recent data (online learning for fast-moving data)
  • Canary deployment: New model serves 5% traffic, compare metrics before full rollout

2 Cache strategies — cache-aside, read-through, write-through, write-back
cachingrediscache-aside
Medium 88%
Cache Strategies
  • Cache-Aside (Lazy loading): App checks cache first; on miss, reads DB, populates cache. Cache only stores what's actually requested. Risk: thundering herd on cold start.
  • Read-Through: Cache reads from DB automatically on miss (library handles it). App always reads from cache. DB not directly accessed by app.
  • Write-Through: Write to cache AND DB synchronously. Cache never stale. High write latency (must wait for both). Good for read-heavy.
  • Write-Back (Write-Behind): Write to cache, return immediately. Write to DB asynchronously. Fast writes. Risk: data loss if cache crashes before flush.
Cache-Aside Pattern (most common)

6 How does CPU caching work and why does it matter for performance?

Memory Hierarchy
L1 cache:  ~32KB per core,   ~1ns  latency
L2 cache: ~256KB per core,   ~4ns  latency
L3 cache:   ~8MB shared,     ~40ns latency
RAM:        ~16-64GB,       ~100ns latency

Cache Lines
Data loaded in 64-byte cache lines. Accessing one byte loads entire 64-byte block. Sequential access (arrays) → excellent cache utilization. Random access (linked lists) → cache miss per node.

# Two threads update different variables in same cache line:
# Thread 1 updates counter_a, Thread 2 updates counter_b

struct PaddedCounter {

1 Implement a thread-safe LRU Cache in C++

Hard 88%
Design
std::list (doubly-linked list) + std::unordered_map<K, list::iterator>.
Most recently used at front. On access: move node to front. On eviction: remove from back.
Implementation
template<typename K, typename V>
class LRUCache {
    int cap;
    std::list<std::pair<K,V>> lst;
    std::unordered_map<K, decltype(lst.begin())> mp;
    std::mutex mu;
public:
    LRUCache(int cap) : cap(cap) {}

    std::optional<V> get(const K& key) {
        std::lock_guard lock(mu);
        auto it = mp.find(key);
        if (it == mp.end()) return {};
        lst.splice(lst.begin(), lst, it->second);  // move to front
        return it->second->second;
    }

    void put(const K& key, V val) {
        std::lock_guard lock(mu);
        if (mp.count(key)) lst.erase(mp[key]);
        else if ((int)lst.size() == cap) {
            mp.erase(lst.back().first);
            lst.pop_back();
        }
        lst.push_front({key, val});
        mp[key] = lst.begin();
    }
};
Complexity
get/put: O(1) average. Thread-safe with a single mutex. For higher concurrency: use reader-writer lock or shard by key hash.

If you define any of: destructor, copy constructor, copy assignment, you should define all three. (Managing raw resource → need custom copy + destructor)

Add move constructor + move assignment. Without them, moves fall back to copies (expensive).

    char* data; size_t sz;

Full Producer-Consumer

void producer() {
    for(int i=0;i<10;i++) {

15 Implement a lock-free stack using CAS

Design
Use std::atomic<Node*> for head. CAS in a loop for push/pop.
Implementation
template<typename T>
class LockFreeStack {
    struct Node { T data; Node* next; };
    std::atomic<Node*> head{nullptr};
public:
    void push(T val) {
        Node* n = new Node{std::move(val), nullptr};
        n->next = head.load(std::memory_order_relaxed);
        while (!head.compare_exchange_weak(n->next, n,
               std::memory_order_release, std::memory_order_relaxed));
    }
    std::optional<T> pop() {
        Node* old = head.load(std::memory_order_acquire);
        while (old && !head.compare_exchange_weak(old, old->next,
               std::memory_order_release, std::memory_order_acquire));
        if (!old) return {};
        T val = std::move(old->data);
        // DANGER: delete old  ← ABA problem / use-after-free with concurrent pops
        return val;
    }
};
ABA Problem
After loading old = A, another thread pops A, pushes B, pushes A back. CAS sees A and succeeds but old->next points to stale node. Fix: tagged pointers (version counter) or hazard pointers for safe memory reclamation.

3 Design a Bloom Filter

Hard 82%
What is a Bloom Filter
Space-efficient probabilistic data structure. Answers: 'definitely not in set' OR 'probably in set'. No false negatives, configurable false positive rate.
Implementation
class BloomFilter {
    private final BitSet bits;
    private final int numBits;
    private final int numHashFunctions;

    BloomFilter(int expectedItems, double falsePositiveRate) {
        // Optimal bit count: -n*ln(p) / (ln2)^2
        numBits = (int)(-expectedItems * Math.log(falsePositiveRate) / (Math.log(2)*Math.log(2)));
        // Optimal hash count: (m/n) * ln2
        numHashFunctions = (int)(numBits * 1.0 / expectedItems * Math.log(2));
        bits = new BitSet(numBits);
    }

    void add(String item) {
        for (int i = 0; i < numHashFunctions; i++)
            bits.set(Math.abs(hash(item, i)) % numBits);
    }

    boolean mightContain(String item) {
        for (int i = 0; i < numHashFunctions; i++)
            if (!bits.get(Math.abs(hash(item, i)) % numBits)) return false;  // Definitely not
        return true;  // Probably yes
    }

    private int hash(String s, int seed) {
        return Objects.hash(s, seed);
    }
}

Coffman's Four Necessary Conditions
  • Mutual Exclusion: Resources not sharable
  • Hold and Wait: Process holds resource while waiting for another
  • No Preemption: Resources can't be forcibly taken

Each process declares max resource claim. System checks if granting a request leaves system in safe state (all processes can complete). If unsafe → deny and wait. Used in theory; impractical for dynamic systems.

VFS (Virtual File System)
Abstraction layer. Provides uniform API (open/read/write/close) for all file systems (ext4, XFS, btrfs, tmpfs, NFS, procfs). Drivers implement VFS operations.
Inode
Fixed-size metadata structure for each file:
  • File type, permissions, owner (UID/GID)
  • Size, timestamps (atime/mtime/ctime)
  • Block pointers (direct, indirect, double-indirect)
  • Link count (hard links)
  • NOT: file name (stored in directory entry)
Dentry (Directory Entry)
Cache of name → inode mappings. Path lookup: /home/user/file.txt → traverse dentries: root dentry → home dentry → user dentry → file inode. Dentry cache (dcache) avoids repeated disk lookups.
Page Cache
Buffer for file data. read() → kernel checks page cache first. On miss: read from disk, cache page. write() → write to page cache (writeback=async), or writethrough, or direct I/O (O_DIRECT bypasses cache). free command: 'cached' = page cache using RAM (can be reclaimed).

11 NUMA (Non-Uniform Memory Access) — impact on performance
numamemory-localitycpu-affinity
Hard 72%
NUMA Architecture
Multi-socket servers: each CPU socket has its own local DRAM. Accessing local memory: fast (~80ns). Accessing remote memory (other socket's DRAM): slow (~150ns, ~2x). OS/hardware provides NUMA node topology.
NUMA Problems
  • Thread on node 0 allocates, migrated to node 1 → remote memory access
  • False sharing: different threads on different NUMA nodes modify same cache line → cache coherence traffic
  • Memory-intensive apps (databases, ML) severely impacted
Mitigation
  • numactl --membind=0 --cpubind=0 ./app — bind to single NUMA node
  • numactl --interleave=all — round-robin allocation across nodes (reduces hot-spots)
  • NUMA-aware memory allocators (jemalloc, tcmalloc have NUMA support)
  • Database NUMA awareness: MySQL/PostgreSQL can bind buffer pool per node
Cache Hierarchy
L1 (4 cycles, 32KB per core) → L2 (12 cycles, 256KB per core) → L3 (30-50 cycles, shared per socket, 32-64MB) → DRAM (~200 cycles) → Remote DRAM (~400 cycles) → NVMe SSD (~100μs) → HDD (~10ms).
