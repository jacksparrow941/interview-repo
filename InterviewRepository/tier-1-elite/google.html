2 Number of Islands
dfsbfsunion-find
Medium 92%
Approach
DFS or BFS. When land cell found, increment count and DFS to mark all connected land as visited.
Solution
def numIslands(grid):
    if not grid: return 0
    count = 0
    def dfs(r, c):
        if r < 0 or r >= len(grid) or c < 0 or c >= len(grid[0]): return
        if grid[r][c] != '1': return
        grid[r][c] = '0'  # mark visited
        for dr, dc in [(0,1),(0,-1),(1,0),(-1,0)]:
            dfs(r+dr, c+dc)
    for r in range(len(grid)):
        for c in range(len(grid[0])):
            if grid[r][c] == '1':
                count += 1; dfs(r, c)
    return count

6 Three Sum
two-pointerssorting
Medium 85%
Approach
Sort array. For each element, use two pointers on the rest to find pairs summing to -nums[i]. Skip duplicates at each level.
Solution
def threeSum(nums):
    nums.sort(); res = []
    for i in range(len(nums)-2):
        if i > 0 and nums[i] == nums[i-1]: continue
        l, r = i+1, len(nums)-1
        while l < r:
            s = nums[i]+nums[l]+nums[r]
            if s == 0: res.append([nums[i],nums[l],nums[r]]); l+=1; r-=1
            while l < r and nums[l]==nums[l-1]: l+=1
            while l < r and nums[r]==nums[r+1]: r-=1
            elif s < 0: l+=1
            else: r-=1
    return res
Complexity
Time: O(n²) | Space: O(1) excluding output
Follow-ups
• How does 4-Sum extend this? (add outer loop, O(n³))
• What is the hash-map approach and why is two-pointer preferred?

15 Meeting Rooms II
heapgreedyintervals
Medium 82%
Approach
DP with memoization. dp[i][j] = LCS length of s1[i:] and s2[j:]. If chars match: 1 + dp[i+1][j+1]. Else max(dp[i+1][j], dp[i][j+1]).
Solution
def longestCommonSubsequence(text1, text2):
    m, n = len(text1), len(text2)
    dp = [[0]*(n+1) for _ in range(m+1)]
    for i in range(m-1,-1,-1):
        for j in range(n-1,-1,-1):
            if text1[i]==text2[j]:
                dp[i][j] = 1 + dp[i+1][j+1]

    return dp[0][0]

def trap(height):
    l, r = 0, len(height)-1
    lmax = rmax = water = 0
    while l < r:
        if height[l] <= height[r]:
            if height[l] >= lmax: lmax = height[l]

51 Network Delay Time (Dijkstra)
dijkstraheap
Medium 72%
Dijkstra's Algorithm
Min-heap (priority queue) for greedy shortest path. Relax all edges from current shortest node.
Solution
import heapq
def networkDelayTime(times, n, k):
    graph = defaultdict(list)
    for u,v,w in times: graph[u].append((v,w))
    dist = {k: 0}
    heap = [(0, k)]
    while heap:
        d, u = heapq.heappop(heap)
        if d > dist.get(u, float('inf')): continue
        for v, w in graph[u]:
            nd = d + w
            if nd < dist.get(v, float('inf')):
                dist[v] = nd; heapq.heappush(heap, (nd,v))
    return max(dist.values()) if len(dist)==n else -1
Complexity
Time: O((V+E) log V) | Space: O(V+E)

• All-pairs shortest path? (Floyd-Warshall O(V³))
• Negative cycle detection? (Bellman-Ford: after V-1 iterations, try once more)

Consistent Hashing
Problem with naive modulo hashing: adding/removing 1 server remaps N/S keys (massive cache miss storm).

Ring approach: Hash servers and keys to same circular space (0 to 2^32). A key is assigned to the first server found clockwise from its hash position.
Virtual Nodes
Each physical server = 100-200 virtual nodes on the ring → even distribution even with few servers. Fewer hot spots. When server added/removed: only 1/N keys remapped.

        self.ring = {}
        self.sorted_keys = []
        self.replicas = replicas

All nodes see the same data at the same time. After a write completes, all reads return the new value. Requires synchronous replication. Used in: financial systems, leader election (etcd, ZooKeeper).

2 Implement a thread-safe LRU Cache in C++
lruthread-safeunordered_map
Hard 88%
Design
std::list (doubly-linked list) + std::unordered_map<K, list::iterator>.
Most recently used at front. On access: move node to front. On eviction: remove from back.
Implementation
template<typename K, typename V>
class LRUCache {
    int cap;
    std::list<std::pair<K,V>> lst;
    std::unordered_map<K, decltype(lst.begin())> mp;
    std::mutex mu;
public:
    LRUCache(int cap) : cap(cap) {}

    std::optional<V> get(const K& key) {
        std::lock_guard lock(mu);
        auto it = mp.find(key);
        if (it == mp.end()) return {};
        lst.splice(lst.begin(), lst, it->second);  // move to front
        return it->second->second;
    }

    void put(const K& key, V val) {
        std::lock_guard lock(mu);
        if (mp.count(key)) lst.erase(mp[key]);
        else if ((int)lst.size() == cap) {
            mp.erase(lst.back().first);
            lst.pop_back();
        }
        lst.push_front({key, val});
        mp[key] = lst.begin();
    }
};
Complexity
get/put: O(1) average. Thread-safe with a single mutex. For higher concurrency: use reader-writer lock or shard by key hash.

30 Implement a lock-free stack using CAS
lock-freecasatomic
Hard 72%
Design
Use std::atomic<Node*> for head. CAS in a loop for push/pop.
Implementation
template<typename T>
class LockFreeStack {
    struct Node { T data; Node* next; };
    std::atomic<Node*> head{nullptr};
public:
    void push(T val) {
        Node* n = new Node{std::move(val), nullptr};
        n->next = head.load(std::memory_order_relaxed);
        while (!head.compare_exchange_weak(n->next, n,
               std::memory_order_release, std::memory_order_relaxed));
    }
    std::optional<T> pop() {
        Node* old = head.load(std::memory_order_acquire);
        while (old && !head.compare_exchange_weak(old, old->next,
               std::memory_order_release, std::memory_order_acquire));
        if (!old) return {};
        T val = std::move(old->data);
        // DANGER: delete old  ← ABA problem / use-after-free with concurrent pops
        return val;
    }
};
ABA Problem
After loading old = A, another thread pops A, pushes B, pushes A back. CAS sees A and succeeds but old->next points to stale node. Fix: tagged pointers (version counter) or hazard pointers for safe memory reclamation.

22 Java GC algorithms — Mark-Sweep, Mark-Compact, Copying, Generational

Hard 76%
Mark-Sweep
Mark: traverse GC roots, mark all reachable objects. Sweep: scan heap, free unmarked objects. Problem: fragmentation — free spaces scattered.
Mark-Compact
Mark phase same. Compact phase: slide all live objects to one end. No fragmentation. Slower than sweep (extra copy). G1GC uses this for selected regions.
Copying Collection
Divide heap into From/To spaces. Copy live objects to To, flip spaces. No fragmentation, fast allocation (bump pointer). Wastes 50% of heap. Used for young generation.
Generational Hypothesis
Most objects die young. Java heap split:
  • Young (Eden + 2 Survivors): Minor GC — fast, copying collector
  • Old (Tenured): Major/Full GC — mark-compact or concurrent marking
Promotion: object surviving N minor GCs (default 15) moves to Old gen.
G1GC
Divides heap into equal regions (~1-32MB). Marks concurrently. Selects regions with most garbage (Garbage-First) for collection. Pause target: -XX:MaxGCPauseMillis=200.

defer
Deferred call runs when surrounding function returns (normal or panic). Arguments evaluated immediately; call deferred. LIFO order.
func processFile(path string) (err error) {

        }

    // ... process f
    return
}

func safeDiv(a, b int) (result int, err error) {

func merge(cs ...<-chan int) <-chan int {

    out := make(chan int)
    output := func(c <-chan int) {

        for v := range c { out <- v }

14 sync.Mutex vs sync.RWMutex

Medium 82%
sync.Mutex vs sync.RWMutex
  • sync.Mutex: Exclusive lock. One goroutine at a time (readers OR writer).
  • sync.RWMutex: Multiple concurrent readers OR one exclusive writer. Writers must wait for all readers. Readers don't block each other. Great for read-heavy workloads (config, caches).
Code
type SafeMap struct {
    mu   sync.RWMutex
    data map[string]string
}
func (m *SafeMap) Get(key string) string {
    m.mu.RLock()         // shared read lock
    defer m.mu.RUnlock()
    return m.data[key]
}
func (m *SafeMap) Set(key, val string) {
    m.mu.Lock()          // exclusive write lock
    defer m.mu.Unlock()
    m.data[key] = val
}
When RWMutex hurts
RWMutex adds overhead for writer starvation prevention. If writes are frequent, plain Mutex is faster. Profile before switching.

  • G (Goroutine): Lightweight coroutine. ~2KB initial stack, grows dynamically. Millions possible.
  • M (Machine/Thread): OS thread. One M executes one G at a time. Limited by GOMAXPROCS for Go code; more Ms created for blocking syscalls.
  • P (Processor): Scheduling context. GOMAXPROCS Ps (default = CPU cores). Each P has a local run queue (LRQ) of Gs.
Scheduling Flow
1. goroutine created → added to P's LRQ
2. P pops G from LRQ, assigns to M → runs
3. G blocks on syscall → M + G detached from P
   → P finds idle M (or creates new) → continues running other Gs
4. Syscall completes → G goes back to global run queue (GRQ)
5. Work stealing: idle P steals half of busy P's LRQ → balanced load
Preemption
Go uses cooperative preemption (yield at function calls) + async preemption (sysmon thread sends SIGURG after 10ms to interrupt G). Long CPU-bound goroutines preempted automatically.
GOMAXPROCS
Number of OS threads for Go code = number of Ps. runtime.GOMAXPROCS(n) or GOMAXPROCS=n env var.

17 TCP flow control (receive window) vs congestion control (CWND)
tcpflow-controlcongestion
Hard 82%
Flow Control (Receiver-side)
Prevents sender from overwhelming receiver's buffer.
Receiver advertises receive window (rwnd) in ACK headers. Sender must not have more than rwnd unacknowledged bytes in flight.
Congestion Control (Network-side)
Prevents sender from overwhelming the network (routers/links).
Sender maintains congestion window (cwnd). Effective window = min(cwnd, rwnd).
Congestion Control Phases
  • Slow Start: cwnd=1 MSS → doubles each RTT until ssthresh or packet loss
  • Congestion Avoidance: cwnd grows +1 MSS per RTT (linear)
  • Fast Retransmit: 3 duplicate ACKs → retransmit lost segment immediately (don't wait for timeout)
  • Fast Recovery (CUBIC, BBR): On loss: ssthresh = cwnd/2, cwnd = ssthresh (not back to 1)
BBR (Google)
Model-based congestion control. Estimates bottleneck bandwidth and RTT. Less reactive to loss, better for high-bandwidth long-distance links. Used in YouTube, cloud networking.

6 Explain transformer architecture and attention mechanism
transformerattentionself-attention
Hard 82%
Self-Attention Mechanism
Input: sequence of tokens → embeddings (d_model=768 for BERT-base)

For each token, compute:
  Q (query) = embedding × W_Q
  K (key)   = embedding × W_K
  V (value) = embedding × W_V

Attention weights = softmax(Q × K^T / sqrt(d_k))
Output = Attention_weights × V

# Each token attends to all other tokens — captures long-range dependencies
# Multi-head: run h parallel attention heads, concat, project
Transformer Architecture
  • Encoder (BERT): Bidirectional. Sees full context. Used for classification, NER, embeddings.
  • Decoder (GPT): Autoregressive. Each token attends only to previous tokens (causal mask). Used for generation.
  • Encoder-Decoder (T5, BART): Seq2seq tasks: translation, summarization, QA.
Why Transformers replaced RNNs
  • RNN: sequential computation → no parallelism. Gradient vanishing for long sequences.
  • Transformer: parallel over all positions. Self-attention = O(n²d) but parallelizable on GPU.
  • Position encoding: sinusoidal or learned — since attention is permutation-invariant, positional info must be added explicitly.

Docker images are built as read-only layers stacked using a Union Filesystem (OverlayFS/AUFS). Each RUN, COPY, ADD instruction in a Dockerfile creates a new layer.

8 Compare-and-swap (CAS) operation

Medium 78%
Compare-And-Swap (CAS)
Atomic hardware instruction: CAS(addr, expected, new) → bool. If *addr == expected, atomically set *addr = new and return true. Else return false.
Lock-free Stack with CAS
class LockFreeStack<T> {
    AtomicReference<Node<T>> top = new AtomicReference<>();
    
    void push(T val) {
        Node<T> newNode = new Node<>(val);
        do {
            newNode.next = top.get();  // read current top
        } while (!top.compareAndSet(newNode.next, newNode));  // retry if top changed
    }
    
    T pop() {
        Node<T> old;
        do {
            old = top.get();
            if (old == null) return null;
        } while (!top.compareAndSet(old, old.next));
        return old.val;
    }
}
CAS vs Mutex
CAS: no sleep, no context switch, no kernel call. But: retry loop wastes CPU under high contention. Best for: low contention, short operations. Use mutex for long critical sections.

ABA Problem
Thread 1 reads value A. Thread 2 changes A→B→A. Thread 1 does CAS: sees A, thinks nothing changed — succeeds. But the state HAS changed (e.g., a node was removed and re-inserted in a lock-free list).

Virtual Memory
Each process has its own virtual address space (e.g., 0 to 2^48 on 64-bit). OS maps virtual pages → physical frames via page table. Allows: isolation between processes, overcommit memory, memory-mapped files, copy-on-write.
Multi-level Page Tables
64-bit systems use 4-level (x86-64) or 5-level page tables to reduce space. Each level is a 4KB page of 512 8-byte entries. Virtual address split:
[sign ext | L4 (9) | L3 (9) | L2 (9) | L1 (9) | Offset (12)]
TLB (Translation Lookaside Buffer)
Hardware cache for recent virtual→physical translations. TLB hit: 1 cycle. TLB miss: walk page table (several cycles + memory accesses). TLB flushed on context switch (unless ASID used). Huge pages (2MB/1GB) reduce TLB misses.
Page Fault
  • Minor: Page in memory but not mapped (memory-mapped file, copy-on-write) → map it
  • Major: Page not in memory → read from disk (swap). Expensive (~ms)
  • Invalid: Access to unmapped address → SIGSEGV

Coffman's Four Necessary Conditions

18 NUMA (Non-Uniform Memory Access) — impact on performance

Hard 72%
NUMA Architecture
Multi-socket servers: each CPU socket has its own local DRAM. Accessing local memory: fast (~80ns). Accessing remote memory (other socket's DRAM): slow (~150ns, ~2x). OS/hardware provides NUMA node topology.
NUMA Problems
  • Thread on node 0 allocates, migrated to node 1 → remote memory access
  • False sharing: different threads on different NUMA nodes modify same cache line → cache coherence traffic
  • Memory-intensive apps (databases, ML) severely impacted
Mitigation
  • numactl --membind=0 --cpubind=0 ./app — bind to single NUMA node
  • numactl --interleave=all — round-robin allocation across nodes (reduces hot-spots)
  • NUMA-aware memory allocators (jemalloc, tcmalloc have NUMA support)
  • Database NUMA awareness: MySQL/PostgreSQL can bind buffer pool per node
Cache Hierarchy
L1 (4 cycles, 32KB per core) → L2 (12 cycles, 256KB per core) → L3 (30-50 cycles, shared per socket, 32-64MB) → DRAM (~200 cycles) → Remote DRAM (~400 cycles) → NVMe SSD (~100μs) → HDD (~10ms).

15 PostgreSQL MVCC — how it achieves non-blocking reads
mvccpostgresqlsnapshot
Hard 82%
MVCC = Multi-Version Concurrency Control
Each row has hidden columns:
  • xmin: transaction ID that inserted this version
  • xmax: transaction ID that deleted/updated this version (0 = still live)
Reads see a snapshot: only versions where xmin ≤ snapshot_xid < xmax.
How it works
T1 (xid=100): UPDATE users SET name='Bob' WHERE id=1
→ Old row: xmin=50, xmax=100  (now dead to T1)
→ New row: xmin=100, xmax=0   (live)

T2 (xid=99, started before T1):
→ Sees old row (xmin=50 <= 99 < xmax=100) ✓
→ Sees 'Alice' — no blocking!

T3 (xid=101, started after T1 commits):
→ Old row: xmax=100 <= 101 → dead, skip
→ New row: xmin=100 <= 101, xmax=0 → live, sees 'Bob' ✓
VACUUM
Dead rows (old versions) accumulate. VACUUM reclaims space. AUTOVACUUM runs automatically. Transaction ID wraparound prevented by freezing old rows.

What is a Deadlock
Two or more transactions each hold a lock the other needs.
T1: LOCK A → wait for B
T2: LOCK B → wait for A
→ Circular wait = deadlock
Deadlock Detection
Most DBs run a background detector (PostgreSQL, MySQL InnoDB).
Builds a wait-for graph: node = transaction, edge = T1 waits for lock held by T2. Cycle = deadlock → kill victim transaction (least expensive to rollback).

CAP Theorem Recap
In presence of network partition (P), choose between Consistency (C) or Availability (A). Most distributed systems choose AP → eventual consistency.

Contrast to ACID.

20 Write-Ahead Logging (WAL) — how databases ensure durability
waldurabilityredo-log
Hard 78%
What is WAL
Before modifying data pages in memory (buffer pool), the change is written to the WAL log first. On crash: replay WAL from last checkpoint to recover committed transactions. Guarantee: committed data never lost, even on sudden crash.
Write Flow
1. Transaction modifies data in buffer pool (in-memory dirty page)
2. WAL record written to WAL buffer → flushed to disk (fsync)
   [WAL written BEFORE data page written — Write-Ahead!]
3. Transaction commits: commit WAL record flushed
4. Background: dirty pages periodically checkpointed to data files
5. WAL records before checkpoint can be deleted
PostgreSQL WAL
WAL files in pg_wal/. Controls: fsync=on (durability), synchronous_commit=on/off. Turning off synchronous_commit: ~10% faster writes, risk of last 100ms of data on crash.
Uses beyond recovery
  • Streaming replication: replicas stream WAL from primary
  • Point-in-time recovery (PITR): replay WAL to any past state
  • Logical replication: parse WAL for row-level changes (Debezium/CDC)

class SlidingWindowRateLimiter {
    private final int maxRequests;
    private final long windowMs;
    private final Map<String, Deque<Long>> windows = new ConcurrentHashMap<>();

    boolean allow(String clientId) {
        long now = System.currentTimeMillis();

        Deque<Long> timestamps = windows.computeIfAbsent(clientId, k -> new ArrayDeque<>());

class SnowflakeIdGenerator {
    private final long EPOCH = 1288834974657L;  // Nov 4, 2010
    private final long MACHINE_ID;              // 0-1023
    private long sequence = 0;
    private long lastTs = -1;

    synchronized long nextId() {
        long ts = System.currentTimeMillis();
        if (ts == lastTs) {
            sequence = (sequence + 1) & 0xFFF;  // 12-bit mask
            if (sequence == 0) ts = waitNextMs(lastTs);  // sequence exhausted
        } else { sequence = 0; }
        lastTs = ts;
        return ((ts - EPOCH) << 22) | (MACHINE_ID << 12) | sequence;
    }

    private long waitNextMs(long ts) {
        long now = System.currentTimeMillis();
        while (now <= ts) now = System.currentTimeMillis();
        return now;
    }
}

8 Design a Circuit Breaker

States
CLOSED → calls go through. OPEN → calls fail-fast (no downstream). HALF_OPEN → probe call, if succeeds → CLOSED, else → OPEN.
Full Implementation
enum State { CLOSED, OPEN, HALF_OPEN }

class CircuitBreaker {
    State state = CLOSED;
    int failCount = 0, successCount = 0;
    final int failThreshold = 5;
    final int successThreshold = 2;
    Instant openedAt;
    final Duration timeout = Duration.ofSeconds(30);
    final ReentrantLock lock = new ReentrantLock();

    <T> T call(Supplier<T> fn) {
        lock.lock(); try {
            if (state == OPEN) {
                if (Duration.between(openedAt, Instant.now()).compareTo(timeout) > 0)
                    state = HALF_OPEN;
                else throw new CircuitOpenException();
            }
        } finally { lock.unlock(); }

        try {
            T result = fn.get();
            onSuccess(); return result;
        } catch (Exception e) { onFailure(); throw e; }
    }

    void onSuccess() {
        lock.lock(); try {
            if (state == HALF_OPEN && ++successCount >= successThreshold) {
                state = CLOSED; failCount = 0; successCount = 0;
            }
        } finally { lock.unlock(); }
    }

    void onFailure() {
        lock.lock(); try {
            if (++failCount >= failThreshold || state == HALF_OPEN) {
                state = OPEN; openedAt = Instant.now(); successCount = 0;
            }
        } finally { lock.unlock(); }
    }
}

        Comparator.comparingLong((Job j) -> j.scheduledAt)
                  .thenComparing(j -> -j.priority));
    ScheduledExecutorService executor = Executors.newScheduledThreadPool(4);
    Map<String, ScheduledFuture<?>> running = new ConcurrentHashMap<>();

        queue.offer(job);
        return job.id;
    }

    void processJobs() {
        while (!Thread.currentThread().isInterrupted()) {
            Job job = queue.peek();
            if (job == null || job.scheduledAt > System.currentTimeMillis()) {
                Thread.sleep(10); continue;
            }
            queue.poll();
            executor.submit(() -> executeWithRetry(job));
        }
    }

        try { job.task.run(); job.status = COMPLETED; }
        catch (Exception e) {
            if (job.retryCount++ < job.maxRetries) {
                job.scheduledAt = System.currentTimeMillis() + backoff(job.retryCount);
                queue.offer(job);
            } else { job.status = FAILED; }
        }
    }
}

What is a Bloom Filter
Space-efficient probabilistic data structure. Answers: 'definitely not in set' OR 'probably in set'. No false negatives, configurable false positive rate.
Implementation
class BloomFilter {
    private final BitSet bits;
    private final int numBits;
    private final int numHashFunctions;

    BloomFilter(int expectedItems, double falsePositiveRate) {
        // Optimal bit count: -n*ln(p) / (ln2)^2
        numBits = (int)(-expectedItems * Math.log(falsePositiveRate) / (Math.log(2)*Math.log(2)));
        // Optimal hash count: (m/n) * ln2
        numHashFunctions = (int)(numBits * 1.0 / expectedItems * Math.log(2));
        bits = new BitSet(numBits);
    }

    void add(String item) {
        for (int i = 0; i < numHashFunctions; i++)
            bits.set(Math.abs(hash(item, i)) % numBits);
    }

    boolean mightContain(String item) {
        for (int i = 0; i < numHashFunctions; i++)
            if (!bits.get(Math.abs(hash(item, i)) % numBits)) return false;  // Definitely not
        return true;  // Probably yes
    }

    private int hash(String s, int seed) {
        return Objects.hash(s, seed);
    }
}

class ConnectionPool {
    BlockingDeque<Connection> pool;
    AtomicInteger totalCreated;
    int maxSize, minIdle;
    long acquireTimeoutMs;

    Connection borrow() throws Exception {
        Connection conn = pool.pollFirst(acquireTimeoutMs, MILLISECONDS);
        if (conn == null) {
            if (totalCreated.get() < maxSize) {
                conn = createConnection(); totalCreated.incrementAndGet();
            } else throw new TimeoutException("Pool exhausted");
        }
        if (!conn.isValid()) { conn.close(); return borrow(); }  // retry
        return conn;
    }

    void release(Connection conn) {
        if (conn.isValid()) pool.offerFirst(conn);
        else { conn.close(); totalCreated.decrementAndGet(); }
    }

    // Health check thread: periodically validate idle connections
    void startHealthCheck() {
        scheduler.scheduleAtFixedRate(() -> {
            pool.forEach(c -> { if (!c.isValid()) { pool.remove(c); totalCreated.decrementAndGet(); } });
            while (pool.size() < minIdle) pool.add(createConnection());
        }, 30, 30, SECONDS);
    }

How CSRF works

2 Cache strategies — cache-aside, read-through, write-through, write-back

Medium 88%
Cache Strategies
  • Cache-Aside (Lazy loading): App checks cache first; on miss, reads DB, populates cache. Cache only stores what's actually requested. Risk: thundering herd on cold start.
  • Read-Through: Cache reads from DB automatically on miss (library handles it). App always reads from cache. DB not directly accessed by app.
  • Write-Through: Write to cache AND DB synchronously. Cache never stale. High write latency (must wait for both). Good for read-heavy.
  • Write-Back (Write-Behind): Write to cache, return immediately. Write to DB asynchronously. Fast writes. Risk: data loss if cache crashes before flush.

6 How does CPU caching work and why does it matter for performance?

Hard 74%
Memory Hierarchy
L1 cache:  ~32KB per core,   ~1ns  latency
L2 cache: ~256KB per core,   ~4ns  latency
L3 cache:   ~8MB shared,     ~40ns latency
RAM:        ~16-64GB,       ~100ns latency
SSD NVMe:              ~100μs latency
HDD:                    ~10ms latency
Cache Lines
Data loaded in 64-byte cache lines. Accessing one byte loads entire 64-byte block. Sequential access (arrays) → excellent cache utilization. Random access (linked lists) → cache miss per node.
False Sharing
# Two threads update different variables in same cache line:
# Thread 1 updates counter_a, Thread 2 updates counter_b
# If they're adjacent in memory → same cache line → cache coherence traffic
# Core 1 invalidates Core 2's cache line on every write → performance degrades!

# Fix: padding
struct PaddedCounter {
    alignas(64) std::atomic<int64_t> value;  // 64-byte aligned
    char padding[64 - sizeof(std::atomic<int64_t>)];  // fill rest of cache line
};
Practical Impact
  • Array of structs vs Struct of arrays (SOA): SOA = better cache usage for column-wise processing
  • Cache-oblivious algorithms (recursive divide) beat sequential for large matrices
  • Go: sync.Mutex padded to avoid false sharing with adjacent data
