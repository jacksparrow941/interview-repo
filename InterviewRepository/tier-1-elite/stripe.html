1 REST vs GraphQL vs gRPC — when to use each?
restgraphqlgrpc
Medium 90%
REST vs GraphQL vs gRPC
  • REST: Stateless, resource-based (nouns), HTTP verbs. Cacheable, universally supported. Over-fetching (get entire user object for just the name) / under-fetching (need 3 calls for related data).
  • GraphQL: Single endpoint. Client specifies exact fields. Eliminates over/under-fetching. Schema as contract. N+1 problem (use DataLoader). Good for complex UIs, mobile (save bandwidth).
  • gRPC: HTTP/2 + Protocol Buffers. Binary, strongly typed, 5-10x smaller than JSON. Bidirectional streaming. Generated client/server stubs. Best for internal microservices.
Decision Matrix
  • Public API / browser-to-server → REST
  • Complex UI with diverse data needs → GraphQL
  • Internal microservice-to-microservice → gRPC
  • Real-time bidirectional → WebSocket

3 Distributed transactions: 2PC vs Saga
2pcsagadistributed-tx
Hard 80%
2PC — Two-Phase Commit
Phase 1 (Prepare): Coordinator sends PREPARE to all participants. Each votes YES (prepared, locked) or NO.
Phase 2 (Commit/Abort): If all YES → send COMMIT; if any NO → send ABORT.
Problems: Coordinator failure in phase 2 → participants stuck holding locks. Blocking protocol. Network partition → split brain possible.
Saga Pattern
Choreography: Each service publishes event → next service reacts. No central coordinator. Decoupled but hard to trace.
Orchestration: Saga Orchestrator sends commands to each service, receives replies. Easier to manage state.
Compensating transactions: On failure, execute rollback steps in reverse order.
Example: E-commerce order
1. Reserve inventory → 2. Debit payment → 3. Assign delivery → 4. Confirm order
Failure at step 3: Release payment (compensate) → Release inventory (compensate)

5 How would you implement distributed locks?
redisredlockzookeeper
Hard 80%
Distributed Locks
Requirements: Mutual exclusion, no deadlock, fault tolerance, lock expiry.
Redis SET NX EX (simple)
SET resource_key unique_token NX EX 30  # NX: only if not exists, EX: expire 30s
# Release: Lua script to check token before delete (atomic)
if redis.call('GET', key) == token then
    redis.call('DEL', key)
end
Redlock (HA Redis)
Acquire lock on N/2+1 independent Redis nodes. If majority acquired within validity time → lock granted. Release on all nodes. Controversial: Martin Kleppmann argues it's unsafe with clock drift.
ZooKeeper Ephemeral Nodes
Create sequential ephemeral node. Lock acquired if lowest sequence number. On disconnect: ZK auto-deletes ephemeral node → no zombie locks. More reliable than Redis.
Fencing Tokens
Lock returns a monotonically increasing token. Storage layer rejects requests with stale token. Prevents GC pauses or clock drift from causing split-brain.

6 Explain the circuit breaker pattern
circuit-breakerhystrix
Medium 78%
Circuit Breaker States
  • CLOSED: Normal operation. Failure counter tracks errors. If failures > threshold → OPEN.
  • OPEN: All calls fail immediately (fail-fast). No downstream load. After timeout → HALF_OPEN.
  • HALF_OPEN: Allow one probe request. If succeeds → CLOSED. If fails → OPEN again.
Why it matters
Without circuit breaker: one slow service causes thread pool exhaustion in caller → cascading failure across the system. Circuit breaker prevents this by failing fast and giving downstream service recovery time.
Libraries
  • Resilience4j (Java): sliding window (count/time based), bulkhead pattern
  • Hystrix (deprecated): used at Netflix, pioneered the pattern
  • Go: sony/gobreaker, mercadolibre/go-breakers

8 Explain CQRS and Event Sourcing
cqrsevent-sourcingread-model
Hard 66%
CQRS — Command Query Responsibility Segregation
Separate write model (commands: create, update, delete) from read model (queries: optimized for reads). Read model can be denormalized, use different database (e.g., Elasticsearch for search, Redis for fast reads). Scales independently.
Event Sourcing
State is derived from a sequence of immutable events, not current state snapshot. Events are appended to an event store (log). State reconstructed by replaying events.
Events: OrderPlaced → ItemAdded → PaymentProcessed → OrderShipped
Current state: replay all events → Order{status=SHIPPED, items=[...], payment=PAID}
Benefits and Costs
  • Benefits: Full audit log, time travel (replay to any point), event-driven integration
  • Costs: Eventual consistency between command and query model, complex querying, schema evolution of events, snapshot needed for long histories

3 Design a distributed key-value store (like Redis/DynamoDB)
distributed-kvconsistent-hashingreplication
Hard 88%
Architecture
Client → Load Balancer → Coordinator Node
                            ↓ (consistent hash ring)
                        Partition 0 → Replica A, B, C
                        Partition 1 → Replica D, E, F
                        ...
Data Distribution
Consistent hashing: keys mapped to ring. Each node owns a range. Virtual nodes (vnodes): each physical node = 100-200 vnodes for even distribution. Adding/removing node: only adjacent vnodes affected.
Replication
Each key replicated to N nodes (typically N=3, DynamoDB style). Coordinator writes to all N. Quorum: W=2 (write), R=2 (read) → W+R>N = strong consistency. W=1, R=1 → eventual consistency, highest availability.
Conflict Resolution
Vector clocks track causality. On divergent versions (network partition): return both to client (DynamoDB shopping cart), or last-write-wins (LWW) for simpler cases.
Storage Engine
LSM Tree (write-optimized): MemTable → immutable SSTable → compaction. B+Tree (read-optimized): InnoDB, LMDB. LSM preferred for KV stores: fast sequential writes, compaction amortizes cost.

2 B+ Tree index internals — structure, splits, range queries
b-plus-treeindexrange-query
Hard 88%
Structure
  • Internal nodes: keys only, no data. Fan-out typically 100-200 keys per node.
  • Leaf nodes: keys + actual row pointers (or clustered data). Linked list for range scans.
  • Height: ~3-4 levels for millions of rows (log_200(1M) ≈ 3). Fits in memory.
Why B+ over B-Tree
All data in leaves → range queries traverse leaf linked list without backtracking. Internal nodes store more keys (no data) → wider fan-out → shallower tree.
Operations
  • Search: O(log_t n) — traverse from root to leaf
  • Insert: find leaf, insert, split if overflow (cascade up)
  • Delete: find leaf, remove, merge or redistribute if underflow
  • Range scan: find start leaf, traverse linked list → sequential I/O (fast)
Clustered vs Secondary
Clustered: Data rows stored in leaf nodes in index order (InnoDB primary key). One per table.
Secondary: Leaf stores PK value → extra lookup for row data. Multiple allowed.

3 Read replicas — replication lag, use cases, consistency
replicationreplica-lagread-replica
Hard 88%
Replication Mechanics (MySQL binlog / PostgreSQL WAL)
Primary records every write as binary log events. Replica connects, streams binlog, applies changes. Replication can be:
  • Async (default): Primary doesn't wait for replica. Replica may lag.
  • Semi-sync: Primary waits for at least 1 replica to acknowledge before committing.
  • Sync (PostgreSQL synchronous_commit=on): All replicas acknowledge. Highest durability, slowest.
Replication Lag Causes
  • Large transactions (long to replay)
  • High write throughput on primary
  • Network latency between primary and replica
  • Single-threaded replay (older MySQL — use parallel replication)
Handling Lag in Applications
  • Read-your-own-writes: route reads after writes to primary for 1s, or use session stickiness
  • For stale-tolerant reads (reports, analytics): use replica
  • Monitor lag: SHOW REPLICA STATUS → Seconds_Behind_Source

• How does logical replication differ from physical replication?

4 SQL query optimization — indexes, covering indexes, composite indexes
indexcovering-indexcomposite
Medium 88%
Composite Index Column Order
-- Query: WHERE a = 1 AND b > 5 ORDER BY c
-- Best index: (a, b, c) — leftmost prefix rule
-- a → equality filter (most selective first)
-- b → range filter
-- c → ORDER BY (eliminates sort)

-- Index (b, a) won't use b for range + a for equality efficiently
Covering Index
Index includes all columns needed by query — no heap lookup.
-- Query:
SELECT email FROM users WHERE user_id = 42;

-- If index is (user_id, email): Index Only Scan — never touches table!
CREATE INDEX idx_user_email ON users(user_id) INCLUDE (email);  -- PostgreSQL
Index Selectivity
High selectivity (few rows per value) = good for index. Low selectivity (boolean, gender) = index often not used. n_distinct in pg_stats shows estimate. Use partial index for low-selectivity cases:
CREATE INDEX ON orders(status) WHERE status = 'PENDING';
Anti-patterns
  • SELECT * prevents covering index
  • Function on indexed column: WHERE LOWER(email) = ... → can't use index. Use functional index.
  • Leading % in LIKE: WHERE name LIKE '%Smith' → full scan. Use full-text search or reverse index.
  • Implicit type cast: WHERE varchar_col = 123 → type mismatch → seq scan

5 Database isolation levels
isolationmvccphantom
Hard 87%
ACID Properties
  • Atomicity: All operations in transaction succeed or all are rolled back. No partial updates.
  • Consistency: Transaction brings DB from one valid state to another. Constraints never violated.
  • Isolation: Concurrent transactions behave as if sequential. Anomalies depend on isolation level.
  • Durability: Committed transactions survive crashes. Guaranteed by WAL.
Isolation Levels & Anomalies
READ UNCOMMITTED: dirty read allowed (see uncommitted data)
READ COMMITTED:  no dirty read | phantom read possible
REPEATABLE READ: no dirty/non-repeatable read | phantom possible (MySQL: solved by gap locks)
SERIALIZABLE:   full isolation, slowest — SSI (PostgreSQL) or locking (MySQL)
How Implemented
PostgreSQL: MVCC for Repeatable Read and below. Serializable: SSI (Serializable Snapshot Isolation). MySQL InnoDB: row-level locking + MVCC + gap locks for Repeatable Read.

Key Operations
  • Seq Scan: Full table scan. Fast for small tables / low selectivity.
  • Index Scan: Uses B+ tree index. Best for high selectivity (<10% rows).
  • Index Only Scan: All needed columns in index (covering index). Fastest.
  • Bitmap Heap Scan: Index scan → bitmap of pages → sorted page access. Good for 5-20% rows.
  • Nested Loop: Join — for each outer row, find matching inner. Good for small outer result.
  • Hash Join: Build hash table from smaller table → probe with larger. Good for large unsorted.
  • Merge Join: Both sides sorted. Fast but needs sort step.

8 Connection pooling — PgBouncer, HikariCP, patterns
connection-poolpgbouncerhikaricp
Medium 84%
Why Pool Connections
PostgreSQL creates a new OS process per connection (~5-10MB RAM). Opening connection takes ~30-100ms. 1000 connections = 5-10GB RAM, GC overhead, scheduler pressure.
PgBouncer
Lightweight connection pooler for PostgreSQL. Sits between app and DB.
  • Session mode: App gets same DB connection for session duration. All features work.
  • Transaction mode: Connection returned to pool after each transaction. Supports many more app connections (1000s) with few DB connections (50). Restrictions: no SET, no prepared statements per session.
  • Statement mode: Return after each statement. Most restrictive.
HikariCP (Java)
Fast JDBC connection pool.
HikariConfig cfg = new HikariConfig();
cfg.setJdbcUrl("jdbc:postgresql://host/db");
cfg.setMaximumPoolSize(10);
cfg.setConnectionTimeout(30000);
cfg.setIdleTimeout(600000);
cfg.setMaxLifetime(1800000);  // 30min to prevent stale conns
DataSource ds = new HikariDataSource(cfg);
Sizing
Pool size = (core_count × 2) + effective_spindle_count. Smaller than you think — more connections ≠ more throughput.

9 PostgreSQL MVCC — how it achieves non-blocking reads
mvccpostgresqlsnapshot
Hard 82%
MVCC = Multi-Version Concurrency Control
Each row has hidden columns:
  • xmin: transaction ID that inserted this version
  • xmax: transaction ID that deleted/updated this version (0 = still live)
Reads see a snapshot: only versions where xmin ≤ snapshot_xid < xmax.
How it works
T1 (xid=100): UPDATE users SET name='Bob' WHERE id=1
→ Old row: xmin=50, xmax=100  (now dead to T1)
→ New row: xmin=100, xmax=0   (live)

T2 (xid=99, started before T1):
→ Sees old row (xmin=50 <= 99 < xmax=100) ✓
→ Sees 'Alice' — no blocking!

T3 (xid=101, started after T1 commits):
→ Old row: xmax=100 <= 101 → dead, skip
→ New row: xmin=100 <= 101, xmax=0 → live, sees 'Bob' ✓
VACUUM
Dead rows (old versions) accumulate. VACUUM reclaims space. AUTOVACUUM runs automatically. Transaction ID wraparound prevented by freezing old rows.

What is a Deadlock
Two or more transactions each hold a lock the other needs.
T1: LOCK A → wait for B
T2: LOCK B → wait for A
→ Circular wait = deadlock
Deadlock Detection
Most DBs run a background detector (PostgreSQL, MySQL InnoDB).

  • Timeout: SET lock_timeout = '1s' — transaction aborts if wait too long

CAP Theorem Recap
In presence of network partition (P), choose between Consistency (C) or Availability (A). Most distributed systems choose AP → eventual consistency.

Contrast to ACID.
  • Basically Available: System works, even during partial failure (stale data OK)
  • Soft State: State may change without input (replication catching up)
  • Eventually Consistent: Given no new updates, all replicas converge to same state

  • Eventual: Converges eventually. DNS, S3.
  • Monotonic Read: Once you read version V, you never see older version. (client stickiness)
  • Read-Your-Writes: You always see your own writes immediately. (session token pinning)
  • Causal: If A caused B, everyone sees A before B. (vector clocks)
  • Sequential: All operations appear in a global order consistent with program order.
  • Linearizable (Strict): Strongest. Operations appear instantaneous. ZooKeeper, etcd.

PostgreSQL MVCC Internals
Each row version has xmin (created by txn) and xmax (deleted by txn, 0 if alive).
A txn sees a row if: xmin committed AND xmin <= txn_snapshot AND (xmax=0 OR xmax > txn_snapshot OR xmax not committed)
How it enables isolation
  • Readers never block writers (different row versions)

13 Write-Ahead Logging (WAL) — how databases ensure durability
waldurabilityredo-log
Hard 78%
What is WAL
Before modifying data pages in memory (buffer pool), the change is written to the WAL log first. On crash: replay WAL from last checkpoint to recover committed transactions. Guarantee: committed data never lost, even on sudden crash.
Write Flow
1. Transaction modifies data in buffer pool (in-memory dirty page)
2. WAL record written to WAL buffer → flushed to disk (fsync)
   [WAL written BEFORE data page written — Write-Ahead!]
3. Transaction commits: commit WAL record flushed
4. Background: dirty pages periodically checkpointed to data files
5. WAL records before checkpoint can be deleted
PostgreSQL WAL
WAL files in pg_wal/. Controls: fsync=on (durability), synchronous_commit=on/off. Turning off synchronous_commit: ~10% faster writes, risk of last 100ms of data on crash.
Uses beyond recovery

  • Point-in-time recovery (PITR): replay WAL to any past state
  • Logical replication: parse WAL for row-level changes (Debezium/CDC)

How CSRF works
1. User logs into bank.com (session cookie stored)

2 Cache strategies — cache-aside, read-through, write-through, write-back

Cache Strategies
  • Cache-Aside (Lazy loading): App checks cache first; on miss, reads DB, populates cache. Cache only stores what's actually requested. Risk: thundering herd on cold start.
  • Read-Through: Cache reads from DB automatically on miss (library handles it). App always reads from cache. DB not directly accessed by app.
  • Write-Through: Write to cache AND DB synchronously. Cache never stale. High write latency (must wait for both). Good for read-heavy.
  • Write-Back (Write-Behind): Write to cache, return immediately. Write to DB asynchronously. Fast writes. Risk: data loss if cache crashes before flush.
Cache-Aside Pattern (most common)
def get_user(user_id):
    # Try cache first
    user = redis.get(f"user:{user_id}")
    if user:
        return deserialize(user)  # cache hit
    
    # Cache miss — read from DB
    user = db.query("SELECT * FROM users WHERE id=%s", user_id)
    
    # Populate cache with TTL
    redis.setex(f"user:{user_id}", ttl=3600, value=serialize(user))
    return user

def update_user(user_id, data):
    db.execute("UPDATE users SET ... WHERE id=%s", user_id)
    redis.delete(f"user:{user_id}")  # invalidate — don't update!

12 TCP flow control (receive window) vs congestion control (CWND)
tcpflow-controlcongestion
Hard 82%
Flow Control (Receiver-side)
Prevents sender from overwhelming receiver's buffer.
Receiver advertises receive window (rwnd) in ACK headers. Sender must not have more than rwnd unacknowledged bytes in flight.
Congestion Control (Network-side)
Prevents sender from overwhelming the network (routers/links).
Sender maintains congestion window (cwnd). Effective window = min(cwnd, rwnd).
Congestion Control Phases
  • Slow Start: cwnd=1 MSS → doubles each RTT until ssthresh or packet loss
  • Congestion Avoidance: cwnd grows +1 MSS per RTT (linear)
  • Fast Retransmit: 3 duplicate ACKs → retransmit lost segment immediately (don't wait for timeout)
  • Fast Recovery (CUBIC, BBR): On loss: ssthresh = cwnd/2, cwnd = ssthresh (not back to 1)
BBR (Google)
Model-based congestion control. Estimates bottleneck bandwidth and RTT. Less reactive to loss, better for high-bandwidth long-distance links. Used in YouTube, cloud networking.

1 Implement a thread-safe LRU Cache in C++
lruthread-safeunordered_map
Hard 88%
Design
std::list (doubly-linked list) + std::unordered_map<K, list::iterator>.
Most recently used at front. On access: move node to front. On eviction: remove from back.
Implementation
template<typename K, typename V>
class LRUCache {
    int cap;
    std::list<std::pair<K,V>> lst;
    std::unordered_map<K, decltype(lst.begin())> mp;
    std::mutex mu;
public:
    LRUCache(int cap) : cap(cap) {}

    std::optional<V> get(const K& key) {
        std::lock_guard lock(mu);
        auto it = mp.find(key);
        if (it == mp.end()) return {};
        lst.splice(lst.begin(), lst, it->second);  // move to front
        return it->second->second;
    }

    void put(const K& key, V val) {
        std::lock_guard lock(mu);
        if (mp.count(key)) lst.erase(mp[key]);
        else if ((int)lst.size() == cap) {
            mp.erase(lst.back().first);
            lst.pop_back();
        }
        lst.push_front({key, val});
        mp[key] = lst.begin();
    }
};
Complexity
get/put: O(1) average. Thread-safe with a single mutex. For higher concurrency: use reader-writer lock or shard by key hash.

3 Rule of 0, Rule of 3, Rule of 5 — explain with examples

Rule of 3 (pre-C++11)
If you define any of: destructor, copy constructor, copy assignment, you should define all three. (Managing raw resource → need custom copy + destructor)
Rule of 5 (C++11+)
Add move constructor + move assignment. Without them, moves fall back to copies (expensive).
class Buffer {
    char* data; size_t sz;
public:
    Buffer(size_t n) : data(new char[n]), sz(n) {}
    ~Buffer() { delete[] data; }               // 1: destructor
    Buffer(const Buffer& o)                   // 2: copy ctor
        : data(new char[o.sz]), sz(o.sz) { memcpy(data,o.data,sz); }
    Buffer& operator=(const Buffer& o) {       // 3: copy assign
        if(this==&o) return *this;
        delete[] data; sz=o.sz; data=new char[sz]; memcpy(data,o.data,sz); return *this;

        : data(o.data), sz(o.sz) { o.data=nullptr; o.sz=0; }
    Buffer& operator=(Buffer&& o) noexcept {   // 5: move assign

        delete[] data; data=o.data; sz=o.sz; o.data=nullptr; return *this;

4 std::condition_variable — producer-consumer pattern

Full Producer-Consumer

#include <condition_variable>
#include <queue>

std::mutex mtx;
std::condition_variable cv;
std::queue<int> q;
bool done = false;

void producer() {
    for(int i=0;i<10;i++) {
        std::unique_lock lock(mtx);
        q.push(i);
        cv.notify_one();  // wake one consumer
    }
    { std::lock_guard lock(mtx); done=true; }
    cv.notify_all();
}

void consumer() {
    while(true) {
        std::unique_lock lock(mtx);
        cv.wait(lock, []{ return !q.empty() || done; });  // predicate prevents spurious wakeup
        while(!q.empty()) { process(q.front()); q.pop(); }
        if(done) break;
    }
}

Key Differences
  • Boot time: VM ~1-2 min | Container ~100ms
  • Size: VM ~GBs | Container ~MBs (shared layers)
  • Isolation: VM = full kernel isolation | Container = namespace isolation (kernel shared)
  • Use case: VM for multi-OS, strong isolation | Container for microservices, CI/CD

Answer
Docker images are built as read-only layers stacked using a Union Filesystem (OverlayFS/AUFS). Each RUN, COPY, ADD instruction in a Dockerfile creates a new layer.

func merge(cs ...<-chan int) <-chan int {
    var wg sync.WaitGroup
    out := make(chan int)
    output := func(c <-chan int) {
        defer wg.Done()
        for v := range c { out <- v }
    }

    for _, c := range cs { go output(c) }
    go func() { wg.Wait(); close(out) }()
    return out
}

class SlidingWindowRateLimiter {
    private final int maxRequests;
    private final long windowMs;
    private final Map<String, Deque<Long>> windows = new ConcurrentHashMap<>();

    boolean allow(String clientId) {
        long now = System.currentTimeMillis();
        long cutoff = now - windowMs;

        Deque<Long> timestamps = windows.computeIfAbsent(clientId, k -> new ArrayDeque<>());

            if (timestamps.size() >= maxRequests) return false;
            timestamps.addLast(now);
            return true;
        }
    }

class TokenBucketRateLimiter {
    private final long capacity;
    private final double refillRatePerMs;

    private long lastRefillTime;

    public TokenBucketRateLimiter(long capacity, long refillPerSecond) {
        this.capacity = capacity;
        this.refillRatePerMs = refillPerSecond / 1000.0;
        this.tokens = capacity;
        this.lastRefillTime = System.currentTimeMillis();
    }

    public synchronized boolean allowRequest() {
        refill();
        if (tokens >= 1) { tokens--; return true; }
        return false;
    }

    private void refill() {
        long now = System.currentTimeMillis();
        double toAdd = (now - lastRefillTime) * refillRatePerMs;
        tokens = Math.min(capacity, tokens + toAdd);
        lastRefillTime = now;
    }
}

class SnowflakeIdGenerator {
    private final long EPOCH = 1288834974657L;  // Nov 4, 2010
    private final long MACHINE_ID;              // 0-1023
    private long sequence = 0;
    private long lastTs = -1;

    synchronized long nextId() {
        long ts = System.currentTimeMillis();
        if (ts == lastTs) {
            sequence = (sequence + 1) & 0xFFF;  // 12-bit mask
            if (sequence == 0) ts = waitNextMs(lastTs);  // sequence exhausted
        } else { sequence = 0; }
        lastTs = ts;
        return ((ts - EPOCH) << 22) | (MACHINE_ID << 12) | sequence;
    }

    private long waitNextMs(long ts) {
        long now = System.currentTimeMillis();
        while (now <= ts) now = System.currentTimeMillis();
        return now;
    }
}

States
CLOSED → calls go through. OPEN → calls fail-fast (no downstream). HALF_OPEN → probe call, if succeeds → CLOSED, else → OPEN.
Full Implementation
enum State { CLOSED, OPEN, HALF_OPEN }

class CircuitBreaker {
    State state = CLOSED;
    int failCount = 0, successCount = 0;
    final int failThreshold = 5;
    final int successThreshold = 2;
    Instant openedAt;
    final Duration timeout = Duration.ofSeconds(30);
    final ReentrantLock lock = new ReentrantLock();

    <T> T call(Supplier<T> fn) {
        lock.lock(); try {
            if (state == OPEN) {
                if (Duration.between(openedAt, Instant.now()).compareTo(timeout) > 0)
                    state = HALF_OPEN;
                else throw new CircuitOpenException();
            }
        } finally { lock.unlock(); }

        try {
            T result = fn.get();
            onSuccess(); return result;
        } catch (Exception e) { onFailure(); throw e; }
    }

    void onSuccess() {
        lock.lock(); try {
            if (state == HALF_OPEN && ++successCount >= successThreshold) {
                state = CLOSED; failCount = 0; successCount = 0;
            }
        } finally { lock.unlock(); }
    }

    void onFailure() {
        lock.lock(); try {
            if (++failCount >= failThreshold || state == HALF_OPEN) {
                state = OPEN; openedAt = Instant.now(); successCount = 0;
            }
        } finally { lock.unlock(); }
    }
}

        Comparator.comparingLong((Job j) -> j.scheduledAt)
                  .thenComparing(j -> -j.priority));
    ScheduledExecutorService executor = Executors.newScheduledThreadPool(4);
    Map<String, ScheduledFuture<?>> running = new ConcurrentHashMap<>();

    String schedule(Runnable task, long delayMs, int priority) {

        queue.offer(job);
        return job.id;
    }

    void processJobs() {
        while (!Thread.currentThread().isInterrupted()) {
            Job job = queue.peek();
            if (job == null || job.scheduledAt > System.currentTimeMillis()) {
                Thread.sleep(10); continue;
            }
            queue.poll();
            executor.submit(() -> executeWithRetry(job));
        }
    }

    void executeWithRetry(Job job) {
        try { job.task.run(); job.status = COMPLETED; }
        catch (Exception e) {
            if (job.retryCount++ < job.maxRetries) {
                job.scheduledAt = System.currentTimeMillis() + backoff(job.retryCount);
                queue.offer(job);
            } else { job.status = FAILED; }
        }
    }
}

What is a Bloom Filter
Space-efficient probabilistic data structure. Answers: 'definitely not in set' OR 'probably in set'. No false negatives, configurable false positive rate.

class BloomFilter {
    private final BitSet bits;
    private final int numBits;
    private final int numHashFunctions;

    BloomFilter(int expectedItems, double falsePositiveRate) {
        // Optimal bit count: -n*ln(p) / (ln2)^2
        numBits = (int)(-expectedItems * Math.log(falsePositiveRate) / (Math.log(2)*Math.log(2)));
        // Optimal hash count: (m/n) * ln2
        numHashFunctions = (int)(numBits * 1.0 / expectedItems * Math.log(2));
        bits = new BitSet(numBits);
    }

    void add(String item) {
        for (int i = 0; i < numHashFunctions; i++)
            bits.set(Math.abs(hash(item, i)) % numBits);
    }

    boolean mightContain(String item) {
        for (int i = 0; i < numHashFunctions; i++)
            if (!bits.get(Math.abs(hash(item, i)) % numBits)) return false;  // Definitely not
        return true;  // Probably yes
    }

    private int hash(String s, int seed) {
        return Objects.hash(s, seed);
    }
}

    }
