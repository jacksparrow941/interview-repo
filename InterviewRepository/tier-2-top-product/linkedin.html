2 Number of Islands

Medium 92%
Approach
DFS or BFS. When land cell found, increment count and DFS to mark all connected land as visited.
Solution
def numIslands(grid):
    if not grid: return 0
    count = 0
    def dfs(r, c):
        if r < 0 or r >= len(grid) or c < 0 or c >= len(grid[0]): return
        if grid[r][c] != '1': return
        grid[r][c] = '0'  # mark visited
        for dr, dc in [(0,1),(0,-1),(1,0),(-1,0)]:
            dfs(r+dr, c+dc)
    for r in range(len(grid)):
        for c in range(len(grid[0])):
            if grid[r][c] == '1':
                count += 1; dfs(r, c)
    return count

5 Three Sum
two-pointerssorting
Medium 85%
Approach
Sort array. For each element, use two pointers on the rest to find pairs summing to -nums[i]. Skip duplicates at each level.
Solution
def threeSum(nums):
    nums.sort(); res = []
    for i in range(len(nums)-2):
        if i > 0 and nums[i] == nums[i-1]: continue
        l, r = i+1, len(nums)-1
        while l < r:
            s = nums[i]+nums[l]+nums[r]
            if s == 0: res.append([nums[i],nums[l],nums[r]]); l+=1; r-=1
            while l < r and nums[l]==nums[l-1]: l+=1
            while l < r and nums[r]==nums[r+1]: r-=1
            elif s < 0: l+=1
            else: r-=1
    return res
Complexity
Time: O(n²) | Space: O(1) excluding output
Follow-ups
• How does 4-Sum extend this? (add outer loop, O(n³))
• What is the hash-map approach and why is two-pointer preferred?

def longestCommonSubsequence(text1, text2):
    m, n = len(text1), len(text2)
    dp = [[0]*(n+1) for _ in range(m+1)]

30 Network Delay Time (Dijkstra)
dijkstraheap
Medium 72%
Dijkstra's Algorithm
Min-heap (priority queue) for greedy shortest path. Relax all edges from current shortest node.
Solution
import heapq
def networkDelayTime(times, n, k):
    graph = defaultdict(list)
    for u,v,w in times: graph[u].append((v,w))
    dist = {k: 0}
    heap = [(0, k)]
    while heap:
        d, u = heapq.heappop(heap)
        if d > dist.get(u, float('inf')): continue
        for v, w in graph[u]:
            nd = d + w
            if nd < dist.get(v, float('inf')):
                dist[v] = nd; heapq.heappush(heap, (nd,v))
    return max(dist.values()) if len(dist)==n else -1
Complexity
Time: O((V+E) log V) | Space: O(V+E)
Follow-ups
• When does Dijkstra fail? (negative edge weights — use Bellman-Ford)
• All-pairs shortest path? (Floyd-Warshall O(V³))
• Negative cycle detection? (Bellman-Ford: after V-1 iterations, try once more)

2 Design Twitter/X timeline — fan-out on write vs fan-out on read

Approaches
  • Fan-out on Write (Push): When user tweets, push tweet ID to all followers' home timeline caches (Redis sorted sets). Read is fast (O(1) from cache). Write is expensive for users with millions of followers (celebrities).

Storage Architecture
Tweet Service:

  - Blob store (S3): media files
  - Redis: home timeline cache per user (sorted set by tweet_id)

Timeline Service:

  - For celebrities: merge from DB query on read

  • Tweet ID as Snowflake (time-sortable → no ORDER BY timestamp needed)
  • Timeline cache: Redis ZSET with tweet_id as score, cap at 800 entries

2 What is consistent hashing?
consistent-hashingvirtual-nodes
Hard 86%
Consistent Hashing
Problem with naive modulo hashing: adding/removing 1 server remaps N/S keys (massive cache miss storm).

Ring approach: Hash servers and keys to same circular space (0 to 2^32). A key is assigned to the first server found clockwise from its hash position.
Virtual Nodes
Each physical server = 100-200 virtual nodes on the ring → even distribution even with few servers. Fewer hot spots. When server added/removed: only 1/N keys remapped.
class ConsistentHash:
    def __init__(self, replicas=150):
        self.ring = {}
        self.sorted_keys = []
        self.replicas = replicas

    def add_server(self, server):
        for i in range(self.replicas):
            key = hash(f'{server}:{i}')
            self.ring[key] = server
        self.sorted_keys = sorted(self.ring)

    def get_server(self, item):
        h = hash(item)
        for k in self.sorted_keys:
            if h <= k: return self.ring[k]
        return self.ring[self.sorted_keys[0]]  # wrap around

5 Explain eventual consistency vs strong consistency

Medium 84%
Strong Consistency
All nodes see the same data at the same time. After a write completes, all reads return the new value. Requires synchronous replication. Used in: financial systems, leader election (etcd, ZooKeeper).
Eventual Consistency
Given no new updates, all replicas will eventually converge. Reads may return stale data temporarily. Higher availability and partition tolerance. Used in: DNS, S3, DynamoDB (default), Cassandra.
CAP Theorem
In presence of network Partition, choose Consistency OR Availability:
  • CP: HBase, MongoDB (primary), etcd, ZooKeeper — prefer consistency over availability
  • AP: Cassandra, DynamoDB, CouchDB — prefer availability over consistency
  • CA systems only work without partitions (single node databases)
PACELC
Extension of CAP: Even without partitions, trade-off exists between Latency and Consistency.

27 Java GC algorithms — Mark-Sweep, Mark-Compact, Copying, Generational
gc-algorithmsmark-sweepgenerational
Hard 76%
Mark-Sweep
Mark: traverse GC roots, mark all reachable objects. Sweep: scan heap, free unmarked objects. Problem: fragmentation — free spaces scattered.
Mark-Compact
Mark phase same. Compact phase: slide all live objects to one end. No fragmentation. Slower than sweep (extra copy). G1GC uses this for selected regions.
Copying Collection
Divide heap into From/To spaces. Copy live objects to To, flip spaces. No fragmentation, fast allocation (bump pointer). Wastes 50% of heap. Used for young generation.
Generational Hypothesis
Most objects die young. Java heap split:
  • Young (Eden + 2 Survivors): Minor GC — fast, copying collector
  • Old (Tenured): Major/Full GC — mark-compact or concurrent marking
Promotion: object surviving N minor GCs (default 15) moves to Old gen.
G1GC
Divides heap into equal regions (~1-32MB). Marks concurrently. Selects regions with most garbage (Garbage-First) for collection. Pause target: -XX:MaxGCPauseMillis=200.

15 PostgreSQL MVCC — how it achieves non-blocking reads
mvccpostgresqlsnapshot
Hard 82%
MVCC = Multi-Version Concurrency Control
Each row has hidden columns:
  • xmin: transaction ID that inserted this version
  • xmax: transaction ID that deleted/updated this version (0 = still live)
Reads see a snapshot: only versions where xmin ≤ snapshot_xid < xmax.
How it works
T1 (xid=100): UPDATE users SET name='Bob' WHERE id=1
→ Old row: xmin=50, xmax=100  (now dead to T1)
→ New row: xmin=100, xmax=0   (live)

T2 (xid=99, started before T1):
→ Sees old row (xmin=50 <= 99 < xmax=100) ✓
→ Sees 'Alice' — no blocking!

T3 (xid=101, started after T1 commits):
→ Old row: xmax=100 <= 101 → dead, skip
→ New row: xmin=100 <= 101, xmax=0 → live, sees 'Bob' ✓
VACUUM
Dead rows (old versions) accumulate. VACUUM reclaims space. AUTOVACUUM runs automatically. Transaction ID wraparound prevented by freezing old rows.

What is a Deadlock
Two or more transactions each hold a lock the other needs.
T1: LOCK A → wait for B
T2: LOCK B → wait for A
→ Circular wait = deadlock
Deadlock Detection
Most DBs run a background detector (PostgreSQL, MySQL InnoDB).

In presence of network partition (P), choose between Consistency (C) or Availability (A). Most distributed systems choose AP → eventual consistency.

20 Write-Ahead Logging (WAL) — how databases ensure durability
waldurabilityredo-log
Hard 78%
What is WAL
Before modifying data pages in memory (buffer pool), the change is written to the WAL log first. On crash: replay WAL from last checkpoint to recover committed transactions. Guarantee: committed data never lost, even on sudden crash.
Write Flow
1. Transaction modifies data in buffer pool (in-memory dirty page)
2. WAL record written to WAL buffer → flushed to disk (fsync)
   [WAL written BEFORE data page written — Write-Ahead!]
3. Transaction commits: commit WAL record flushed
4. Background: dirty pages periodically checkpointed to data files
5. WAL records before checkpoint can be deleted
PostgreSQL WAL
WAL files in pg_wal/. Controls: fsync=on (durability), synchronous_commit=on/off. Turning off synchronous_commit: ~10% faster writes, risk of last 100ms of data on crash.
Uses beyond recovery
  • Streaming replication: replicas stream WAL from primary
  • Point-in-time recovery (PITR): replay WAL to any past state
  • Logical replication: parse WAL for row-level changes (Debezium/CDC)

2 Cache strategies — cache-aside, read-through, write-through, write-back
cachingrediscache-aside
Medium 88%
Cache Strategies
  • Cache-Aside (Lazy loading): App checks cache first; on miss, reads DB, populates cache. Cache only stores what's actually requested. Risk: thundering herd on cold start.
  • Read-Through: Cache reads from DB automatically on miss (library handles it). App always reads from cache. DB not directly accessed by app.
  • Write-Through: Write to cache AND DB synchronously. Cache never stale. High write latency (must wait for both). Good for read-heavy.
  • Write-Back (Write-Behind): Write to cache, return immediately. Write to DB asynchronously. Fast writes. Risk: data loss if cache crashes before flush.
Cache-Aside Pattern (most common)
def get_user(user_id):
    # Try cache first
    user = redis.get(f"user:{user_id}")
    if user:
        return deserialize(user)  # cache hit
    
    # Cache miss — read from DB
    user = db.query("SELECT * FROM users WHERE id=%s", user_id)
    
    # Populate cache with TTL
    redis.setex(f"user:{user_id}", ttl=3600, value=serialize(user))
    return user

def update_user(user_id, data):
    db.execute("UPDATE users SET ... WHERE id=%s", user_id)
    redis.delete(f"user:{user_id}")  # invalidate — don't update!
Cache Eviction Policies
  • LRU: Evict least recently used. Good general-purpose.
  • LFU: Evict least frequently used. Better for skewed access patterns.
  • TTL: Time-based expiry. Always stale by at most TTL seconds.
  • Allkeys-lru (Redis): Apply LRU across all keys when memory full.

JWT Structure

Header: {"alg": "RS256", "typ": "JWT"}

  • Use RS256 (asymmetric): private key signs, public key verifies — microservices can verify without shared secret

Docker images are built as read-only layers stacked using a Union Filesystem (OverlayFS/AUFS). Each RUN, COPY, ADD instruction in a Dockerfile creates a new layer.

5 Compare-and-swap (CAS) operation

Compare-And-Swap (CAS)
Atomic hardware instruction: CAS(addr, expected, new) → bool. If *addr == expected, atomically set *addr = new and return true. Else return false.
Lock-free Stack with CAS
class LockFreeStack<T> {
    AtomicReference<Node<T>> top = new AtomicReference<>();
    
    void push(T val) {
        Node<T> newNode = new Node<>(val);
        do {
            newNode.next = top.get();  // read current top
        } while (!top.compareAndSet(newNode.next, newNode));  // retry if top changed
    }
    
    T pop() {
        Node<T> old;
        do {
            old = top.get();
            if (old == null) return null;
        } while (!top.compareAndSet(old, old.next));
        return old.val;
    }
}
CAS vs Mutex
CAS: no sleep, no context switch, no kernel call. But: retry loop wastes CPU under high contention. Best for: low contention, short operations. Use mutex for long critical sections.

1 Design a Sliding Window Rate Limiter (code-level)

Sliding Window Log Algorithm
Store timestamps of each request in a sorted set. On each request: remove old entries, count remaining, allow if below limit.
In-Memory Thread-Safe
class SlidingWindowRateLimiter {
    private final int maxRequests;
    private final long windowMs;
    private final Map<String, Deque<Long>> windows = new ConcurrentHashMap<>();

    boolean allow(String clientId) {
        long now = System.currentTimeMillis();
        long cutoff = now - windowMs;

        Deque<Long> timestamps = windows.computeIfAbsent(clientId, k -> new ArrayDeque<>());

        synchronized (timestamps) {
            // Remove expired
            while (!timestamps.isEmpty() && timestamps.peekFirst() <= cutoff)
                timestamps.pollFirst();
            if (timestamps.size() >= maxRequests) return false;
            timestamps.addLast(now);
            return true;
        }
    }
}

2 Design a Snowflake-style Distributed ID Generator

Twitter Snowflake Structure (64-bit)
| 1 bit sign | 41 bits timestamp (ms) | 10 bits machine ID | 12 bits sequence |

- Timestamp: ms since custom epoch (Jan 1, 2010)

- Machine ID: 10 bits → 1024 machines
- Sequence: 12 bits → 4096 IDs/ms/machine

Implementation
class SnowflakeIdGenerator {
    private final long EPOCH = 1288834974657L;  // Nov 4, 2010
    private final long MACHINE_ID;              // 0-1023
    private long sequence = 0;
    private long lastTs = -1;

    synchronized long nextId() {
        long ts = System.currentTimeMillis();
        if (ts == lastTs) {
            sequence = (sequence + 1) & 0xFFF;  // 12-bit mask
            if (sequence == 0) ts = waitNextMs(lastTs);  // sequence exhausted
        } else { sequence = 0; }
        lastTs = ts;
        return ((ts - EPOCH) << 22) | (MACHINE_ID << 12) | sequence;
    }

    private long waitNextMs(long ts) {
        long now = System.currentTimeMillis();
        while (now <= ts) now = System.currentTimeMillis();
        return now;
    }
}

    }

    void processJobs() {
        while (!Thread.currentThread().isInterrupted()) {
            Job job = queue.peek();
            if (job == null || job.scheduledAt > System.currentTimeMillis()) {
                Thread.sleep(10); continue;
            }
            queue.poll();
            executor.submit(() -> executeWithRetry(job));
        }
    }

    void executeWithRetry(Job job) {
        try { job.task.run(); job.status = COMPLETED; }
        catch (Exception e) {
            if (job.retryCount++ < job.maxRetries) {
                job.scheduledAt = System.currentTimeMillis() + backoff(job.retryCount);
                queue.offer(job);
            } else { job.status = FAILED; }
        }
    }
}

High latency (mobile), packet loss, many parallel requests, clients switching networks. Major adopters: Google, Meta, Cloudflare, YouTube.

Client → Server: ClientHello + key_share (ECDHE public key) + supported ciphers

Client verifies server cert chain up to trusted CA root. CT (Certificate Transparency) logs prevent mis-issuance. OCSP stapling for revocation.

14 TCP flow control (receive window) vs congestion control (CWND)
tcpflow-controlcongestion
Hard 82%
Flow Control (Receiver-side)
Prevents sender from overwhelming receiver's buffer.
Receiver advertises receive window (rwnd) in ACK headers. Sender must not have more than rwnd unacknowledged bytes in flight.
Congestion Control (Network-side)
Prevents sender from overwhelming the network (routers/links).
Sender maintains congestion window (cwnd). Effective window = min(cwnd, rwnd).
Congestion Control Phases
  • Slow Start: cwnd=1 MSS → doubles each RTT until ssthresh or packet loss
  • Congestion Avoidance: cwnd grows +1 MSS per RTT (linear)
  • Fast Retransmit: 3 duplicate ACKs → retransmit lost segment immediately (don't wait for timeout)
  • Fast Recovery (CUBIC, BBR): On loss: ssthresh = cwnd/2, cwnd = ssthresh (not back to 1)
BBR (Google)
Model-based congestion control. Estimates bottleneck bandwidth and RTT. Less reactive to loss, better for high-bandwidth long-distance links. Used in YouTube, cloud networking.

2 Deadlock conditions (Coffman)
deadlockmutual-exclusionhold-wait
Medium 86%
Coffman Conditions for Deadlock
ALL 4 must hold simultaneously for deadlock:
  • Mutual Exclusion: Resource can only be held by one process
  • Hold and Wait: Process holds resources while waiting for more
  • No Preemption: Resources can't be forcibly taken away
  • Circular Wait: Chain of processes each waiting for next in chain
Prevention Strategies
  • Break Hold and Wait: request all resources at once (but reduces concurrency)
  • Break Circular Wait: impose total ordering on lock acquisition (always lock A before B)
  • Allow Preemption: rollback and retry (used in databases)
  • Detection + Recovery: build wait-for graph, detect cycles, kill one process
Banker's Algorithm
Safe state check: simulate allocation, see if all processes can eventually complete. Grant request only if system remains in safe state. O(n²×m) too slow for real OS but used in theory.
