Chapter 2 — Lexer: Tokenization

The lexer splits source text into tokens — the smallest meaningful units. It ignores whitespace and comments. Tokens carry type and value.

✅ DO THIS
// Hand-written lexer for a simple expression language
enum class Token {
    NUMBER, IDENT, PLUS, MINUS, STAR, SLASH,
    LPAREN, RPAREN, ASSIGN, SEMICOLON, EOF_TK
};

struct Tok {
    Token kind;
    std::string value;
    int line;
};

class Lexer {
    std::string src_;
    size_t pos_ = 0;
    int    line_ = 1;

    char peek()   const { return pos_ < src_.size() ? src_[pos_] : '\0'; }
    char advance() { char c = peek(); ++pos_; if(c=='\n')++line_; return c; }

    Tok lex_number() {
        std::string num;
        while (isdigit(peek())) num += advance();
        if (peek() == '.') {
            num += advance();
            while (isdigit(peek())) num += advance();
        }
        return {Token::NUMBER, num, line_};
    }

public:
    std::vector<Tok> tokenize() {
        std::vector<Tok> tokens;
        while (pos_ < src_.size()) {
            while (isspace(peek())) advance();  // skip whitespace
            if (!peek()) break;
            if (isdigit(peek()))     tokens.push_back(lex_number());
            else if (isalpha(peek())) tokens.push_back(lex_ident());
            else switch (advance()) {
                case '+': tokens.push_back({Token::PLUS,  "+", line_}); break;
                case '-': tokens.push_back({Token::MINUS, "-", line_}); break;
                case '*': tokens.push_back({Token::STAR,  "*", line_}); break;
                case '/':
                    if (peek() == '/') {  // line comment
                        while (peek() != '\n') advance();
                    } else tokens.push_back({Token::SLASH, "/", line_});
                    break;
            }
        }
        tokens.push_back({Token::EOF_TK, "", line_});
        return tokens;
    }
};
✅ Why this works: A hand-written lexer is fastest but more work. For production compilers use DFA (finite automaton) generated from regex specs. Clang uses a hand-written lexer for speed.

Chapter 3 — Parser: Building the AST

Recursive descent parsers encode grammar rules as mutually recursive functions. The call hierarchy implicitly handles operator precedence.

Grammar (lowest to highest precedence): expr → term (('+' | '-') term)* term → factor (('*' | '/') factor)* factor → NUMBER | IDENT | '(' expr ')' | '-' factor Input: 3 + 4 * 2 Parsing: expr() term() → factor() → 3 '+' term() factor() → 4 '*' factor() → 2 returns 4*2=BinOp(*,4,2) returns 3 + BinOp(*,4,2) AST: (+) / \ 3 (*) / \ 4 2
✅ DO THIS
// Recursive descent parser — expression subset
struct Expr {
    virtual double eval() = 0;
    virtual ~Expr() = default;
};
struct Number : Expr {
    double v;
    explicit Number(double v) : v(v) {}
    double eval() override { return v; }
};
struct BinOp : Expr {
    char op;
    std::unique_ptr<Expr> lhs, rhs;
    double eval() override {
        switch (op) {
            case '+': return lhs->eval() + rhs->eval();
            case '-': return lhs->eval() - rhs->eval();
            case '*': return lhs->eval() * rhs->eval();
            case '/': return lhs->eval() / rhs->eval();
        }
        return 0;
    }
};

class Parser {
    std::vector<Tok> toks_;
    size_t pos_ = 0;
    Tok& cur() { return toks_[pos_]; }
    Tok& consume() { return toks_[pos_++]; }
    bool match(Token t) { return cur().kind == t; }

    std::unique_ptr<Expr> parse_factor() {
        if (match(Token::NUMBER)) {
            double v = std::stod(consume().value);
            return std::make_unique<Number>(v);
        }
        if (match(Token::LPAREN)) {
            consume();   // '('
            auto e = parse_expr();
            if (!match(Token::RPAREN)) throw std::runtime_error("expected )");
            consume();   // ')'
            return e;
        }
        throw std::runtime_error("unexpected token: " + cur().value);
    }
    std::unique_ptr<Expr> parse_term() {
        auto lhs = parse_factor();
        while (match(Token::STAR) || match(Token::SLASH)) {
            char op = consume().value[0];
            lhs = std::make_unique<BinOp>(op, std::move(lhs), parse_factor());
        }
        return lhs;
    }
public:
    std::unique_ptr<Expr> parse_expr() {
        auto lhs = parse_term();
        while (match(Token::PLUS) || match(Token::MINUS)) {
            char op = consume().value[0];
            lhs = std::make_unique<BinOp>(op, std::move(lhs), parse_term());
        }
        return lhs;
    }
};
✅ Why this works: The call hierarchy encodes precedence: parse_expr calls parse_term which calls parse_factor. Lower in the call stack = higher precedence. This is why multiplication binds tighter than addition.

Chapter 4 — SSA Form and LLVM IR

SSA (Static Single Assignment): every variable is assigned exactly once. At control flow join points, phi (φ) nodes select between different definitions. SSA makes compiler analyses and optimizations dramatically simpler.

Source code: int x = a + b; if (a > 0) x = x * 2; return x; SSA form: x1 = a + b ; first definition t1 = a > 0 branch t1 → L1 else L2 L1: x2 = x1 * 2 ; second definition jump L2 L2: x3 = phi(x1, x2) ; PHI: x3=x1 if came from entry, x3=x2 if from L1 return x3 Each variable defined exactly once → use-def chain is trivial to compute
✅ DO THIS
; LLVM IR for add function — human-readable SSA
; Compile from C++: clang++ -emit-llvm -S -O1 add.cpp
define i32 @add(i32 %a, i32 %b) {
entry:
    %sum = add nsw i32 %a, %b    ; nsw = no signed overflow (enables more opts)
    ret i32 %sum
}

; More complex: absolute value
define i32 @abs_val(i32 %x) {
entry:
    %cmp = icmp slt i32 %x, 0    ; x < 0 ?
    br i1 %cmp, label %negative, label %positive
negative:
    %neg = sub i32 0, %x         ; -x
    br label %done
positive:
    br label %done
done:
    %result = phi i32 [%neg, %negative], [%x, %positive]  ; PHI node
    ret i32 %result
}

; To write your own LLVM pass (new pass manager):
#include "llvm/IR/PassManager.h"
#include "llvm/Passes/PassBuilder.h"

struct PrintFunctions : llvm::PassInfoMixin<PrintFunctions> {
    llvm::PreservedAnalyses run(llvm::Function& F,
                                llvm::FunctionAnalysisManager&) {
        llvm::outs() << "Function: " << F.getName()
                     << " (" << F.arg_size() << " args)\n";
        for (auto& BB : F)
            for (auto& I : BB)
                llvm::outs() << "  " << I << "\n";
        return llvm::PreservedAnalyses::all();
    }
};
✅ Why this works: Reading LLVM IR is a core skill for compiler engineers. clang -emit-llvm -S shows the IR for any C++ file — study how your optimizations transform IR.

✅ DO THIS
// Observe optimizations via compiler explorer (godbolt.org)
// or: g++ -O2 -S -masm=intel code.cpp -o code.s

// Example: LICM (Loop Invariant Code Motion)
// Source code:
for (int i = 0; i < N; ++i)
    result += data[i] * sqrt(threshold);   // sqrt called N times!

// After -O2: compiler hoists sqrt(threshold) out:
double tmp = sqrt(threshold);   // computed once
for (int i = 0; i < N; ++i)
    result += data[i] * tmp;

// Help the compiler: mark const what is const
const double factor = sqrt(threshold);   // explicit hoist = guaranteed

// Vectorization with SIMD:
// Source: for(int i=0;i<N;++i) a[i] += b[i];
// After -O3 -march=native:
// vmovups ymm0, [b+i]    ; load 8 floats
// vaddps  ymm1, ymm1, ymm0  ; add 8 floats
// vmovups [a+i], ymm1    ; store 8 floats
// 8x throughput on AVX2!
✅ Why this works: Use -O2 -march=native in production — it enables all safe optimizations plus target-specific SIMD. -O3 enables aggressive optimizations that can occasionally break code with strict aliasing violations.
❌ AVOID THIS
// BAD: blocking vectorization with pointer aliasing
void bad_add(float* a, float* b, float* c, int n) {
    for (int i = 0; i < n; ++i)
        a[i] = b[i] + c[i];   // compiler: a, b, c might alias! Can't vectorize
}
// Compiler must assume b and c could point into a → can't reorder loads/stores

// GOOD: tell compiler pointers don't alias
void good_add(float* __restrict__ a,
              float* __restrict__ b,
              float* __restrict__ c, int n) {
    for (int i = 0; i < n; ++i)
        a[i] = b[i] + c[i];   // __restrict__: no aliasing → vectorized!
}
// Generates: vmovups + vaddps (8 floats at once) — 8x throughput

// BAD: defeating inlining with opaque function pointers
std::function<int(int)> transform = [](int x){ return x * 2; };
for (int i = 0; i < N; ++i)
    result += transform(data[i]);  // std::function: type-erased, no inline
// Better: use template or direct lambda (inlined by compiler)
❌ Why this fails: Pointer aliasing is the most common reason auto-vectorization fails. __restrict__ (GCC/Clang extension) or separate input/output arrays enables vectorization. Check with -fopt-info-vec-missed.

Interview Q&A — Compiler

❓ What is SSA and why does every modern compiler use it?
SSA (Static Single Assignment): every variable has exactly one definition. At control flow merges, phi (φ) nodes select among definitions from different incoming paths. Why compilers use it: (1) Use-def chains are explicit — each use points to exactly one definition. (2) Constant propagation: if x = 5 always, all uses of x can be replaced by 5 trivially. (3) Dead code elimination: if a definition is never used, remove it immediately (no transitive tracking needed). (4) Global value numbering: if two computations produce the same SSA value, they're identical — one can be eliminated. (5) Register allocation: live ranges are precise (definition to last use of each SSA variable). LLVM IR is SSA. GCC uses GIMPLE which is also SSA-based internally.
Follow-up questions interviewers ask:
  • What is a phi node? Give a concrete example.
  • How does SSA handle loops (back-edges)?
  • What is the difference between SSA construction and phi placement?
Common mistakes in answers:
  • Saying SSA means no variable can be modified — SSA is about definitions, not about mutability at source level.
  • Confusing SSA with immutability in functional languages — different concepts.
❓ Explain register allocation. Why is it NP-complete and how do compilers handle it?
Register allocation maps unlimited virtual registers (SSA values) to a finite set of physical registers. When there are more live values than registers, some must be 'spilled' to stack. Why NP-complete: equivalent to graph coloring. Build a live-range interference graph: nodes are virtual registers, edges between registers that are alive at the same time. Graph coloring with K colors = allocating K physical registers. Graph k-colorability is NP-complete. How compilers handle it: (1) Linear scan allocation (LLVM): scan live ranges in order, greedily assign registers. O(n) — fast, good enough for JIT compilers. (2) Graph coloring (GCC): Chaitin's algorithm — iteratively remove low-degree nodes, attempt coloring, spill if necessary. Better code quality but slower. (3) SSA-based allocation: exploit SSA structure to simplify the interference graph (most modern compilers).
Follow-up questions interviewers ask:
  • What is spill code? What is the cost of spilling?
  • What is a calling convention? Who defines it?
  • How does LLVM's regalloc decide what to spill?
