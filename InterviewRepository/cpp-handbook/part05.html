Chapter 1 — GDB: From Basics to Expert Debugging

GDB (GNU Debugger) is the standard debugger for C/C++ on Linux. Understanding it deeply is what separates engineers who fix bugs in minutes from those who spend hours with printf debugging.

CommandWhat It DoesWhen to Use
gdb ./bin core.PIDDebug a core dump (crash analysis)Production crashes, segfaults
gdb -p PIDAttach to running processHung process, performance issue
break class::methodSet breakpoint on methodDebugging specific code path
watch exprBreak when expression changes valueFind what's modifying a variable
rwatch exprBreak on READ of expressionFind who's reading incorrect data
backtrace full / btFull stack with localsCrash analysis — where and why
thread apply all btAll thread backtracesDeadlock analysis

frame NSwitch to stack frame NInspect local variables in that frame
x/20xg addrExamine 20 hex 64-bit words at addrRaw memory inspection

✅ DO THIS
# Practical debugging session for a segfault:

# 1. Compile with debug info (always use -g, even for release builds ideally)
g++ -g -O1 -fsanitize=address server.cpp -o server

# 2. Enable core dumps
ulimit -c unlimited
echo "core.%e.%p" | sudo tee /proc/sys/kernel/core_pattern

# 3. Reproduce crash
./server  # crashes, creates core.server.12345

# 4. Analyze core dump
gdb ./server core.server.12345
(gdb) bt full           # full backtrace with local variables
(gdb) frame 3           # jump to frame where crash originated
(gdb) info locals       # see local variables in that frame
(gdb) print *ptr        # inspect the pointer that was dereferenced
(gdb) x/4xb ptr         # examine 4 bytes at ptr's address

# 5. Find deadlock
gdb -p $(pgrep server)  # attach to hung server
(gdb) thread apply all bt   # all thread stacks — look for futex_wait
(gdb) info threads           # find threads in "futex_wait" state
✅ Why this works: Always compile production binaries with -g (debug symbols) AND store the binary alongside the core dump. Without matching symbols, GDB shows only hex addresses.
❌ AVOID THIS
# BAD: debugging with -O2 optimized code only
g++ -O2 main.cpp -o app   # no -g flag
gdb ./app core
(gdb) bt
# Output: ??() at 0x401234   ← useless! No symbols, no function names
# Variables: <optimized out>  ← compiler removed them

# BAD: no core dump configured → crash is undebuggable
# Default: ulimit -c 0 → no core dump generated
./server  # crashes with "Segmentation fault" — that's all you know
# You have to reproduce the crash under GDB interactively

# BAD: attaching GDB to production without being careful
gdb -p $PRODUCTION_PID   # attaches, pauses the process!
# Production server is now PAUSED — all requests timeout
# Use: gdb --batch -ex 'bt' -ex 'detach' -ex 'quit' -p $PID
# Or: eu-stack or bpftrace for non-pausing stack capture
❌ Why this fails: Attaching GDB to production pauses the process. Use bpftrace, perf, or eu-stack for non-intrusive production debugging.

Chapter 2 — perf: CPU Performance Analysis

perf is the Linux kernel's performance tool. It uses hardware performance counters (PMU) and software events to profile without instrumentation overhead.

perf workflow: perf stat → count events (cycles, instructions, cache misses, branch misses) IPC = instructions/cycles cache miss rate < 1% is good branch miss rate < 1% is good perf record → sample execution at N Hz, record call stack at each sample perf report → interactive TUI showing % CPU per function perf script → raw samples for flamegraph generation Key insight: a sample doesn't mean that exact instruction is slow — it means the CPU was THERE when sampled. High count = hot code.
✅ DO THIS
# Step 1: Quick health check
perf stat -e cycles,instructions,cache-misses,cache-references,           branch-misses,branches,LLC-load-misses ./app
# Interpret:
# IPC (instructions/cycles) < 1.0 → memory bound
# IPC > 3.0                       → compute bound
# cache-miss rate > 5%            → cache optimization needed
# branch-miss rate > 1%           → branch prediction problem

# Step 2: Find hot functions
perf record -g --call-graph=dwarf -F 99 ./app
perf report   # interactive TUI, navigate with arrows

# Step 3: Generate flamegraph (best visualization)
perf script > perf.script
git clone https://github.com/brendangregg/FlameGraph
./FlameGraph/stackcollapse-perf.pl perf.script |   ./FlameGraph/flamegraph.pl > flamegraph.svg
# Open flamegraph.svg in browser — click to zoom into call trees

# Step 4: Detect false sharing (cache-to-cache contention)
perf c2c record -g ./app   # records cache line events
perf c2c report            # shows lines with high HITM (Hit Modified)
# High HITM on a cache line = two cores writing to same cache line

# Step 5: Memory bandwidth and latency
perf stat -e mem-loads,mem-stores,           cpu/mem-loads-aux/,cpu/mem-stores-aux/ ./app
✅ Why this works: Flamegraphs are the most actionable output from perf. The width of a frame shows time spent — wide frames at the top are your optimization targets.
❌ AVOID THIS
# BAD: profiling debug build
g++ -O0 -g app.cpp -o app   # debug build
perf record ./app            # profiling debug build
# Results are misleading: debug build has function call overhead
# for inlined functions, extra stack frames, no vectorization
# Profile your release build (-O2 or -O3), with -g for symbols

# BAD: interpreting perf on a single run with short duration
perf stat ./app  # runs for 0.01 seconds
# Statistical noise dominates — cache is cold, startup dominates
# Warm up first, then profile steady state:
./app --warmup-rounds 5 && perf record ./app --benchmark-rounds 100

# BAD: optimizing based on function names without line-level info
# perf report shows "compute_hash" is 40% CPU
# But which line IN compute_hash?
# Fix: perf annotate compute_hash   ← assembly-level annotation
#   or: perf report --sort=srcline  ← source line attribution
❌ Why this fails: Always profile with representative workloads at steady state. Cold-start profiling shows initialization costs, not hot-path performance.

Chapter 3 — Sanitizers: Catch Bugs Before Production

SanitizerFlagWhat It CatchesOverhead
AddressSanitizer (ASan)fsanitize=addressHeap/stack/global overflow, UAF, double-free, leaks2x slowdown
ThreadSanitizer (TSan)fsanitize=threadData races between threads5-15x slowdown
UndefinedBehaviorSan (UBSan)fsanitize=undefinedInteger overflow, null deref, bad shift, OOB<2x slowdown
MemorySanitizer (MSan)fsanitize=memoryReads of uninitialised memory (clang only)3x slowdown

✅ DO THIS
# Compile with multiple sanitizers
g++ -fsanitize=address,undefined     -fno-sanitize-recover=all   \   # abort on first error (not just warn)
    -g -O1                      \   # O1: some optimizations, still readable
    app.cpp -o app_san

# Run — errors printed to stderr with full stack trace
./app_san input.txt

# ASan output example:
# ==1234==ERROR: AddressSanitizer: heap-buffer-overflow
# WRITE of size 4 at 0x602000000030 thread T0
#     #0 0x401234 in process_data app.cpp:42
#     #1 0x401567 in main app.cpp:87
# SUMMARY: heap-buffer-overflow
# Shadow bytes around the buggy address:
#   0x0c047fff8000: fa fa fd fd fa fa fd fa
# (fa=heap-right-redzone, fd=freed)

# ThreadSanitizer (separate build — incompatible with ASan)
g++ -fsanitize=thread -g -O1 app.cpp -o app_tsan
./app_tsan
# TSan output: data race between read in thread #2 and write in thread #1
# Shows exact locations of both the read and write
✅ Why this works: Run both ASan and TSan builds in CI. They catch different classes of bugs and can't be combined. ASan has 2x overhead — acceptable for test runs; not for production.
❌ AVOID THIS
// BAD: not running sanitizers in CI → bugs reach production
// Real scenario: heap-buffer-overflow due to off-by-one
void process_array(int* arr, int n) {
    for (int i = 0; i <= n; ++i)   // BUG: should be < n, not <= n
        arr[i] = compute(i);
    // With ASan: immediate error at line pointing to arr[i] = compute(i)
    // Without ASan: corrupts adjacent heap memory silently
    //   → random crash hours later in a completely different function
    //   → 6 hours debugging the symptom, not the cause
}

// BAD: ignoring TSan output in CI because "it's slow"
// TSan 5-15x slowdown is real, but data races cause:
// - Occasional wrong results (hard to reproduce)
// - Crashes under load only (hard to reproduce)
// - Crashes only on NUMA systems (very hard to reproduce)
// TSan in CI pays for itself in the first race it catches
❌ Why this fails: Data races are the hardest bugs to reproduce and debug without TSan. They manifest non-deterministically, often only under high load or specific hardware configurations.

Chapter 4 — strace and System Call Tracing

✅ DO THIS
# See every syscall with timing
strace -T ./app 2>&1 | head -50

# Count syscalls and find expensive ones
strace -c ./app
# Output:
# % time  seconds   calls  errors syscall
# 55.23   0.001234   5000    0    futex        ← lots of mutex contention
# 22.14   0.000498    100    0    mmap
# 11.05   0.000248  10000    0    read
# Insight: 5000 futex calls means lots of lock contention

# Trace specific syscalls relevant to your issue
strace -e trace=network,ipc ./server   # network + IPC calls only
strace -e trace=openat,read,write ./app   # file I/O only
strace -f ./app   # trace child processes too (follow forks)

# Attach to running process
strace -p $(pgrep server) -T -e trace=futex 2>&1 | head -20
# Immediately see if it's blocking on futex (mutex/condvar)
✅ Why this works: strace -c is the fastest way to see if your program is syscall-bound. Too many futex calls = lock contention. Too many mmap calls = excessive allocations. Too many read/write = unbuffered I/O.

Chapter 5 — vmstat and iostat

✅ DO THIS
# vmstat: memory, swap, CPU, and block I/O summary
vmstat 1 10   # 1 second intervals, 10 samples
# Fields:
# r: runnable processes (> num_cpus = overloaded)
# b: blocked processes (waiting for I/O — bad if nonzero)
# swpd: swap used (nonzero = RAM pressure)
# si/so: swap in/out per second (nonzero = swapping = severe RAM shortage)
# us: user-space CPU %, sy: kernel CPU %, id: idle %, wa: I/O wait %
# I/O wait > 10%: disk is bottleneck

# iostat: per-disk statistics
iostat -xz 1   # -x extended, -z skip zero devices
# Fields:
# %util: disk busy percentage (>80% = saturated)
# await: average I/O wait time in ms (>10ms = high latency)
# r/s, w/s: reads and writes per second
# rMB/s, wMB/s: throughput

# free: memory breakdown
free -h
# important: 'available' not 'free' — available includes reclaimable cache
✅ Why this works: I/O wait (wa) in vmstat tells you if disk is the bottleneck. 20% wa means 20% of CPU time is wasted waiting for disk. Solution: SSD, io_uring, or reducing I/O.

Interview Q&A — Linux & Performance

❓ Walk me through how you'd diagnose a production performance regression.
(1) top / htop: Is it CPU-bound (high %us), I/O-bound (high %wa), or lock-bound (high %sy from futex)? (2) If CPU-bound: perf record -g + flamegraph. Identify hot function. perf annotate for line-level. (3) If memory-bound: perf stat -e cache-misses,LLC-load-misses. High LLC misses = working set too large for LLC. Optimize data layout (SoA, cache blocking). (4) If lock-bound: strace -c -e trace=futex. Too many futex calls. Look for lock contention: perf lock record/report. (5) If I/O-bound: iostat -x. Check await (latency) and %util (saturation). Profile with blktrace for per-I/O details. (6) Always compare against a baseline — run both old and new binary with identical workload and compare perf stat output.
Follow-up questions interviewers ask:
  • What if the regression only appears under load?
  • How do you profile without impacting production?
  • What is a flamegraph and how do you read it?
Common mistakes in answers:
  • Starting with code changes before profiling — always measure first.
  • Profiling debug builds — they're not representative of production.
❓ What is a cache miss? How do you detect and fix it?
A cache miss occurs when the CPU requests data not in L1/L2/L3 cache — requires DRAM access (~100ns, ~300 cycles penalty vs ~1 cycle for L1 hit). Types: Cold miss (first access — unavoidable), Capacity miss (working set > cache size — fix: reduce data size or process in blocks), Conflict miss (cache associativity — fix: change data layout). Detection: perf stat -e L1-dcache-load-misses,LLC-load-misses. Fixes: (1) Sequential access — hardware prefetcher handles stride-1 patterns automatically. (2) SoA (Structure of Arrays) instead of AoS — process each field of all objects together. (3) Cache blocking (tiling) for matrix ops — process NxN blocks that fit in L1. (4) Pack data smaller — int16 instead of float32 where precision allows. (5) Prefetch with __builtin_prefetch(addr, rw, locality).
Follow-up questions interviewers ask:
  • What is cache line size and why does alignment matter?
  • Explain false sharing with an example.
  • What is NUMA and how does it affect cache performance?
