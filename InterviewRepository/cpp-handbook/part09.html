Chapter 1 — AI Runtime Architecture

An AI runtime is the software stack that takes a trained model and executes it efficiently on target hardware (GPU, NPU, CPU). Understanding internals is essential for roles at Kinara, NVIDIA, Qualcomm, and AMD.

Full AI Runtime Pipeline: Model File (ONNX / TensorFlow / PyTorch) │ ▼ Loader & Parser Computation Graph (DAG of operators) │ nodes: Conv2D, BatchNorm, ReLU, MatMul, Reshape... │ edges: tensors (name, dtype, shape) │ ▼ Graph Optimizer Optimized Graph │ - Constant folding: eval ops with constant inputs │ - Dead node elimination: remove unused outputs │ - Operator fusion: Conv+BN+ReLU → single fused op │ - Layout optimization: NCHW ↔ NHWC per device │ ▼ Memory Planner Buffer Assignments │ - Liveness analysis: per-tensor lifetime [first_use, last_use] │ - Buffer reuse: tensors with non-overlapping lifetimes share memory │ ▼ Kernel Dispatcher Execution Schedule │ - Maps each op to best kernel (cuDNN, custom CUDA, etc.) │ - Handles CPU↔GPU data movement │ ▼ Execute (async GPU / NPU / CPU) Output Tensor
✅ DO THIS
// ONNX graph traversal in C++ (using ONNX Runtime C++ API)
#include "onnxruntime/core/session/onnxruntime_cxx_api.h"

Ort::Env env(ORT_LOGGING_LEVEL_WARNING, "inference");
Ort::SessionOptions opts;
opts.SetIntraOpNumThreads(4);
opts.SetGraphOptimizationLevel(GraphOptimizationLevel::ORT_ENABLE_ALL);
// Add GPU execution provider
OrtCUDAProviderOptions cuda_opts; cuda_opts.device_id = 0;
opts.AppendExecutionProvider_CUDA(cuda_opts);

Ort::Session session(env, L"model.onnx", opts);

// Get input/output metadata
auto mem_info = Ort::MemoryInfo::CreateCpu(OrtArenaAllocator, OrtMemTypeDefault);
std::vector<float> input_data(1 * 3 * 224 * 224);   // NCHW batch=1
std::vector<int64_t> input_shape = {1, 3, 224, 224};

Ort::Value input_tensor = Ort::Value::CreateTensor<float>(
    mem_info, input_data.data(), input_data.size(),
    input_shape.data(), input_shape.size());

const char* input_names[]  = {"input"};
const char* output_names[] = {"output"};

auto outputs = session.Run(
    Ort::RunOptions{nullptr},
    input_names, &input_tensor, 1,
    output_names, 1);

float* result = outputs[0].GetTensorMutableData<float>();
✅ Why this works: ONNX Runtime's C++ API is zero-copy when possible — tensors backed by user memory avoid allocation. Always set GraphOptimizationLevel::ORT_ENABLE_ALL for production inference.
❌ AVOID THIS
// BAD: re-creating Ort::Session for every request
void handle_request(const Request& req) {
    Ort::Session session(env, L"model.onnx", opts);  // loads model, JIT compiles kernels!
    // Session creation: ~500ms for a ResNet-50 (loading weights + engine build)
    auto result = session.Run(...);
    // Session destroyed — all setup work wasted
}
// 500ms overhead for a request that should take 10ms
// FIX: create Session once at startup, reuse for all requests

// BAD: ignoring batch dimension — one request at a time
std::vector<float> input(3 * 224 * 224);  // single image, no batch
// GPU has 1000s of cores — running one image uses ~1% of compute
// FIX: batch multiple requests (dynamic batching covers this)
❌ Why this fails: Session creation is expensive (weight loading + kernel compilation). Create once at startup, use thread-safe Run() for concurrent requests — ONNX Runtime's session is thread-safe.

Chapter 2 — TensorRT: Maximum GPU Inference

TensorRT is NVIDIA's inference optimizer and runtime. It builds an optimized engine for a specific GPU by profiling multiple kernel implementations and selecting the fastest for each layer.

TensorRT Build Phase (offline, done once): ONNX Model │ ▼ Parse TRT Network Definition │ ▼ Optimization │ 1. Layer fusion: Conv+BN+ReLU → CBA (single kernel) │ 2. Precision calibration: FP32 → FP16 or INT8 │ 3. Kernel autotuning: profile 100s of cuDNN algos per layer │ 4. Memory planning: minimize peak GPU memory │ 5. CUDA graph capture: reduce kernel launch overhead ▼ Serialized Engine (.trt file, GPU-specific!) TensorRT Runtime Phase (fast, repeated): Load serialized engine → ExecutionContext → enqueueV3() → GPU async execute
✅ DO THIS
// TensorRT Build (Python — typically done offline, serialize to disk)
import tensorrt as trt
logger = trt.Logger(trt.Logger.WARNING)
builder = trt.Builder(logger)
network = builder.create_network(
    1 << int(trt.NetworkDefinitionCreationFlag.EXPLICIT_BATCH))
parser = trt.OnnxParser(network, logger)
with open("resnet50.onnx", "rb") as f:
    parser.parse(f.read())

config = builder.create_builder_config()
config.set_memory_pool_limit(trt.MemoryPoolType.WORKSPACE, 2 << 30)  # 2GB
config.set_flag(trt.BuilderFlag.FP16)        # enable FP16
config.set_flag(trt.BuilderFlag.PREFER_PRECISION_CONSTRAINTS)

# Dynamic shapes — batch size 1 to 32
profile = builder.create_optimization_profile()
profile.set_shape("input", (1,3,224,224), (16,3,224,224), (32,3,224,224))
config.add_optimization_profile(profile)

engine = builder.build_serialized_network(network, config)
with open("resnet50.trt", "wb") as f:
    f.write(engine)  # save for reuse — build takes ~60 seconds
✅ Why this works: TensorRT engines are GPU-specific (SM version) and precision-specific. Build once per GPU model, serialize, distribute alongside your application. Don't rebuild at startup.
❌ AVOID THIS
// BAD: building TensorRT engine at service startup
void init_inference_server() {
    // Building engine takes 60-300 seconds depending on model + GPU
    engine_ = build_trt_engine("model.onnx");   // blocks startup for 5 minutes!
    // Service doesn't respond until engine is built
}
// FIX: pre-build engines offline, load serialized engine at startup (~1 second)

// BAD: INT8 without calibration → accuracy degradation
config.set_flag(trt.BuilderFlag.INT8);  // INT8 enabled
// WITHOUT providing a calibrator:
// TensorRT uses default scale = 1.0 for all layers
// Most layers will overflow or underflow → wrong results

// FIX: provide INT8 calibration dataset
class MyCalibrator(trt.IInt8EntropyCalibrator2):
    def get_batch(self, names):
        return [self.load_next_batch()]  # return ~500 representative images
config.int8_calibrator = MyCalibrator()
❌ Why this fails: INT8 without calibration gives up to 5% accuracy loss vs 0.1-0.5% with proper PTQ calibration. Always calibrate with at least 500 representative samples from your deployment distribution.

Chapter 3 — Quantization Deep Dive

Quantization maps FP32 values to lower-precision integers (INT8, INT4, FP16). Reduces model size (4x for INT8 vs FP32) and enables faster integer MAC units on NPUs and Tensor Cores on NVIDIA GPUs.

INT8 Quantization Math: FP32 tensor values: [-2.4, 0.0, 1.8, 3.2, -0.9] min = -2.4, max = 3.2 scale = (max - min) / (2^8 - 1) = (3.2 - (-2.4)) / 255 = 5.6 / 255 = 0.02196 zero_point = round(-min / scale) = round(2.4 / 0.02196) = round(109.3) = 109 Quantize: q = clamp(round(x / scale) + zero_point, 0, 255) -2.4 → clamp(round(-109.3) + 109, 0, 255) = clamp(0, 0, 255) = 0 0.0 → clamp(round(0) + 109, 0, 255) = 109 3.2 → clamp(round(145.7) + 109, 0, 255) = 255 Dequantize: x_approx = (q - zero_point) * scale q=0 → (0-109)*0.02196 = -2.394 (vs -2.4, error=0.006) q=109 → (109-109)*0.02196 = 0.000 (exact) q=255 → (255-109)*0.02196 = 3.206 (vs 3.2, error=0.006)
✅ DO THIS
// PTQ (Post-Training Quantization) — calibrate with representative data
// Step 1: Collect activation statistics on calibration dataset
void calibrate(const std::vector<cv::Mat>& cal_data, Model& model) {
    std::map<std::string, TensorStats> stats;
    for (const auto& img : cal_data) {
        auto outputs = model.run_fp32(img);
        for (auto& [name, tensor] : outputs) {
            auto& s = stats[name];
            s.min = std::min(s.min, tensor.min());
            s.max = std::max(s.max, tensor.max());
        }
    }
    // Compute per-tensor scale/zero_point from statistics
    for (auto& [name, s] : stats) {
        s.scale = (s.max - s.min) / 255.0f;
        s.zero_point = std::round(-s.min / s.scale);
    }
    model.set_quantization_params(stats);
}

// QAT (Quantization-Aware Training) — simulates quantization during training
// Inserts fake-quantize nodes that simulate INT8 rounding
// Gradients flow through via straight-through estimator
// Result: model learns to be robust to quantization error
// → 0.1-0.3% accuracy loss vs 0.5-2% for PTQ
✅ Why this works: Per-channel quantization (separate scale per output channel) is critical for weight quantization accuracy. Use per-tensor for activations (faster), per-channel for weights (more accurate).
❌ AVOID THIS
// BAD: using single scale for all weights in a layer (per-tensor)
// Conv layer weights: channel 0 range [0, 0.1]; channel 7 range [0, 10]
// Per-tensor scale = 10 / 255 = 0.039
// Channel 0 quantized: range [0, 0.1] → only 2-3 distinct INT8 values!
// → massive quantization error for small-range channels

// FIX: per-channel quantization
// Channel 0: scale = 0.1/255 = 0.00039 → 255 distinct values → good accuracy
// Channel 7: scale = 10/255  = 0.039   → 255 distinct values → good accuracy

// BAD: not verifying accuracy after quantization
// Applying INT8 quantization and shipping without testing:
// - Some models degrade 5-10% mAP with naive PTQ
// - Vision transformers (ViT) are particularly sensitive
// Always: quantize → run validation set → compare to FP32 baseline
❌ Why this fails: Never ship a quantized model without validating accuracy on a held-out test set. Batch normalization layers before quantization: fold BN into Conv weights first (TensorRT does this automatically).

Chapter 4 — Operator Fusion: Why It Matters

Modern NN inference is memory-bandwidth-bound, not compute-bound, for most layers. Fusing operators reduces memory traffic — the single most impactful optimization.

Without Fusion — 3 kernel launches, 3 DRAM read-write cycles: Conv2D kernel: read input from DRAM (128MB) → write output to DRAM (128MB) BatchNorm kernel: read from DRAM (128MB) → write to DRAM (128MB) ReLU kernel: read from DRAM (128MB) → write to DRAM (128MB) Total DRAM traffic: 6 × 128MB = 768MB for 1 layer forward pass With Fusion — 1 kernel launch, 2 DRAM accesses: Conv+BN+ReLU fused: read input from DRAM (128MB) compute conv → compute BN → apply ReLU (all in GPU registers/shared memory) write final output to DRAM (128MB) Total DRAM traffic: 2 × 128MB = 256MB ← 3x reduction! Speedup: 2-4x for bandwidth-bound layers (typical for conv layers)
✅ DO THIS
// Implement a graph-level fusion pass
struct FusionPattern {
    std::string first_op;    // e.g., "Conv"
    std::string second_op;   // e.g., "BatchNormalization"
    std::string fused_name;  // e.g., "ConvBN"
};

// Topological sort + pattern matching
void apply_conv_bn_relu_fusion(Graph& graph) {
    for (auto& node : graph.topological_order()) {
        if (node.op_type != "Conv") continue;
        // Check: single consumer, no side effects
        auto consumers = graph.get_consumers(node.output[0]);
        if (consumers.size() != 1) continue;

        auto* bn = consumers[0];
        if (bn->op_type != "BatchNormalization") continue;

        auto bn_consumers = graph.get_consumers(bn->output[0]);
        if (bn_consumers.size() == 1 && bn_consumers[0]->op_type == "Relu") {
            // Fuse Conv + BN + ReLU into one node
            auto* relu = bn_consumers[0];
            graph.replace_with_fused(
                {&node, bn, relu},
                "ConvBNReLU",
                node.inputs,  // conv inputs
                {relu->output[0]},
                merge_attributes(node, *bn)
            );
        }
    }
}

// Fold BatchNorm into Conv weights (reduces BN to just scale + bias):
// BN: y = gamma * (x - mean) / sqrt(var + eps) + beta
// After folding into Conv:
// new_weight[i] = weight[i] * gamma[i] / sqrt(var[i] + eps)
// new_bias[i]   = -mean[i] * gamma[i] / sqrt(var[i] + eps) + beta[i]
✅ Why this works: BN folding into Conv is a prerequisite for INT8 quantization — it eliminates the normalization operation entirely, making the Conv output directly quantizable.

Interview Q&A — AI Runtime

❓ How does TensorRT achieve speedup over standard PyTorch inference?
(1) Operator fusion: Conv+BN+ReLU → single CUDA kernel, 3x less DRAM traffic. (2) Precision reduction: FP16 Tensor Cores give 2x-8x throughput vs FP32 CUDA cores on A100. INT8 gives another 2x. (3) Kernel auto-tuning: TRT profiles 100+ cuDNN algorithm implementations per layer and picks the fastest for your specific GPU, input size, and precision. (4) Memory optimization: tensor buffer reuse based on liveness analysis — peak GPU memory minimized. (5) CUDA Graph capture: reduces kernel launch overhead from ~50µs per layer to ~5µs total for the entire network. (6) Layer-specific optimizations: implicit GEMM for depthwise conv, Winograd for 3x3 conv. Typical end-to-end speedup vs FP32 PyTorch: 2-8x depending on model and GPU.
Follow-up questions interviewers ask:
  • What is kernel auto-tuning? How many algorithms does it try?
  • What is a CUDA graph? What overhead does it eliminate?
  • How does TRT handle dynamic input shapes (variable batch size)?
Common mistakes in answers:
  • Saying TRT is always faster — for dynamic shapes or unsupported ops, TRT may fall back to generic implementations that are slower than PyTorch.
  • Forgetting that TRT engines are tied to a specific GPU architecture — a Turing-built engine won't work on Ampere (or will be suboptimal).
❓ Explain how memory planning works in an inference runtime.
Memory planning minimizes peak GPU memory by reusing buffers for tensors whose lifetimes don't overlap. Steps: (1) Liveness analysis: for each tensor, compute [first_op_idx, last_op_idx] — the range of operations where the tensor is alive. (2) Build interference graph: two tensors interfere if their live ranges overlap — they cannot share memory. (3) Graph coloring / greedy assignment: assign buffers greedily — if an existing free buffer is large enough for a new tensor and their ranges don't overlap, reuse it. Otherwise, allocate a new buffer. (4) Alignment: ensure all buffers meet hardware alignment requirements (e.g., 256-byte for CUDA). Example: ResNet-50 without memory planning: 400MB peak. With memory planning: 150MB peak (tensors for skip connections reuse memory from early layers that have finished). This is the difference between fitting on a 4GB GPU vs not.
Follow-up questions interviewers ask:
  • How does memory planning handle skip connections (residual paths)?
  • What is the difference between static and dynamic memory planning?
  • How does gradient checkpointing apply the same idea to training?
