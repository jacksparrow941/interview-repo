Part XIV

Resume Principles for Systems Engineers

Your resume is a marketing document. Every line competes for attention against 200 other resumes. The goal: 6 seconds of recruiter attention → interview shortlist. The secret: specific numbers make you memorable.

The Power Formula for Bullet Points

[Strong Action Verb] + [What You Built/Did] + [How (Technology/Method)] + [Impact (Metric)]

✅ DO THIS
// Strong bullet examples — these get callbacks
• Engineered INT8 quantization pipeline for ResNet-50 using TensorRT PTQ,
  achieving 3.8x throughput improvement (1,240 → 4,700 imgs/sec) on NVIDIA A10G

• Eliminated 45ms p99 latency spike by identifying and replacing O(n²) distance
  computation in the routing algorithm with spatial hashing (C++17, unordered_map)

• Reduced inference memory footprint by 62% through liveness-analysis-based tensor
  buffer reuse, enabling deployment on Jetson AGX Orin (16GB) vs prior 40GB GPU requirement

• Led migration of 14 ONNX models to custom NPU backend; implemented graph
  partitioning algorithm in C++ that increased NPU utilization from 31% to 84%

• Designed and implemented lock-free SPSC queue in C++ (release/acquire memory order)
  serving as zero-copy data path between camera ISR and inference pipeline at 30fps

• Diagnosed production latency regression from 87ms to 340ms using perf flamegraphs;
  root cause: false sharing in counter array; padded to cache-line boundaries; resolved in 4h
✅ Why this works: Each bullet has: action verb (Engineered, Eliminated, Reduced), what (quantization pipeline, latency spike, memory footprint), how (TensorRT, spatial hashing, liveness analysis), and number (3.8x, 45ms, 62%).
❌ AVOID THIS
// Weak bullets — these get rejected
• Worked on inference optimization                    ← no specifics, no impact
• Helped improve model performance                   ← "helped" implies not owning
• Implemented various features for the runtime        ← vague, "various" is a red flag
• Responsible for memory management                   ← "responsible for" = not done
• Contributed to a 3x faster pipeline                ← "contributed to" = unclear role
• Fixed several bugs in the threading code            ← "several", no impact stated
❌ Why this fails: Recruiters scan for: numbers, strong verbs, technology names. 'Worked on', 'helped', 'contributed to', 'various', 'several' are signals of low ownership and low impact. Delete them.

Quantifying Impact When You Don't Have Perfect Numbers

If you don't have exact metrics, use estimates with proper hedging. Better to say '~3x improvement (estimated from benchmark runs)' than to omit numbers entirely.

Impact TypeHow to Quantify
PerformanceLatency (p50/p99 before/after), throughput (QPS/imgs/sec), memory (MB/GB)
ScaleUsers affected, requests/day, data size (TB), nodes in cluster
ReliabilityUptime % before/after, MTTR (mean time to resolve), incidents prevented
EfficiencyCost reduction ($, %), engineering hours saved/week, FTE-equivalent automation
Code qualityTest coverage % change, bug reduction rate, cyclomatic complexity
Team impactEngineers onboarded, design decisions influenced, cross-team adoption

// Organized, honest, specific

Frameworks:   ONNX Runtime, TensorRT 8.x, PyTorch, OpenCV, gRPC, Protocol Buffers

              operator fusion, quantization (INT8/FP16), RTOS (FreeRTOS), DMA
✅ Why this works: Organize skills by category. Level qualifiers (expert/proficient/learning) are honest and save time in interviews — interviewers won't ask you CUDA expert questions if you say 'learning'.
❌ AVOID THIS
// Red flags in skills sections

        MySQL, PostgreSQL, MongoDB, Redis, Cassandra, DynamoDB,             ← quantity not quality

// Problems:
// 1. Listing 30 technologies implies shallow knowledge of each
// 2. Interviewers may ask deep questions on ANY item you list
// 3. Shows lack of focus — what are you actually good at?

// Rule: list only what you'd be comfortable being interviewed on at an expert level
❌ Why this fails: Every skill you list is fair game for deep technical questions. List 'CUDA' only if you can explain warp divergence, memory coalescing, and occupancy optimization.

Answering 'Walk Me Through Your Resume'

This is the most common opening question. You have 90 seconds to tell your career story in a compelling narrative. Prepare and rehearse this.

✅ DO THIS
// Strong narrative structure (90 seconds):
"I started as a software engineer focused on C++ systems programming at [Company A],
where I spent 2 years building high-performance data pipelines — that's where I first
encountered the challenge of real-time latency requirements.

That led me to my current role at [Company B], where I've been for 3 years building
the inference runtime for our custom NPU. The most interesting work there was
implementing the quantization pipeline — taking models from 87MB FP32 down to 22MB INT8
while maintaining 99.4% of the original accuracy. I also led the memory planner redesign
that reduced peak GPU memory by 60%.

I'm now looking for a role where I can work at the intersection of compiler optimization
and AI hardware — which is exactly what [Company] is doing with [specific product].
I'm particularly excited about [specific technical detail you researched] because
[genuine reason that shows you've thought about it]."

// Why this works:
// - Career trajectory is clear (C++ → systems → AI runtime)
// - Each role has ONE specific concrete achievement with a number
// - Natural setup for "tell me more about X"
// - Ends with specific, researched interest in this role
✅ Why this works: The narrative should flow chronologically and build logically. Each role is a sentence. End with a genuine, researched connection to the current role.
❌ AVOID THIS
// Weak walk-through:
"I graduated in 2019 with a CS degree and then joined Company A where I worked on
various projects including backend development, some machine learning work, database
optimization, and also helped with deployment. Then I moved to Company B where I'm
currently working on the AI team doing inference stuff and optimization and also
some compiler work. I'm looking for new opportunities because I want to grow."

// Problems:
// - "various projects" = no specific ownership or impact
// - "some" and "stuff" show lack of confidence/pride
// - "helped with" signals non-ownership
// - No numbers anywhere
// - Generic ending ("want to grow")
❌ Why this fails: 'Various', 'some', 'helped with', 'stuff' — these words kill your narrative. Every sentence should have a specific technology or specific achievement. Rehearse until every sentence is crisp.

Project Deep Dive — What Questions to Prepare

Interviewers will pick 1-2 projects from your resume and drill into every detail. Prepare answers for ALL of these for every significant project on your resume.

CategoryQuestions to Prepare
Technical depthWhat was the hardest technical challenge? How did you solve it?
Design decisionsWhy did you choose X over Y? What alternatives did you consider?
MeasurementHow did you measure success? What metrics did you track?
FailureWhat didn't work? What would you do differently?
ScaleWhat happens at 10x the load? What breaks first?
OwnershipWhat specifically did YOU do vs teammates?
ImpactWho used this? How did it change their experience?
Follow-upWhat would the next iteration look like?
✅ DO THIS
// Prepared answers for a memory planner project:
Q: Why did you use liveness analysis rather than static allocation?
A: "Static allocation requires knowing all tensor sizes at compile time.
   Our NPU supports dynamic input shapes (variable batch size), so tensor sizes
   aren't known until runtime. Liveness analysis works at execution time:
   it tracks which tensors are live during each operator, then assigns buffers
   greedily based on lifetime overlap. We got 60% peak memory reduction vs
   naive allocation where every tensor has its own buffer."

Q: What was the hardest bug you encountered?
A: "The trickiest bug was with residual connections in ResNet. Tensors in
   a residual branch need to outlive the last use we can see locally —
   they're also consumed at the add() operation much later in the graph.
   My initial liveness analysis didn't cross operator boundaries for
   branch tracking. Fixed by walking the data-flow graph backward from
   each use to all definitions, properly tracking merge points. Took 2 days
   to diagnose, 4 hours to fix."

Q: How would it handle 10x more models?
A: "Currently memory is planned per-model load. At 10x models, we'd need
   global memory planning across models — share buffers between models with
   non-overlapping execution windows. This requires a model scheduler that
   knows which models are active simultaneously. It's architecturally feasible
   but we hadn't needed it yet at our scale."
   
// Notice: every answer has specifics, numbers where possible,
// and shows genuine understanding of the tradeoffs.
✅ Why this works: Prepare 3-5 detailed project stories with this level of depth. Having these ready means no stuttering when the interviewer drills. The 'hardest bug' and 'what you'd do differently' answers are almost always asked.

Salary Negotiation

✅ DO THIS
// Framework: Never give a number first. Always ask for 48 hours.

// When asked for salary expectations:
"I'm flexible on compensation and would love to understand the full band for this role.
What's the target range you have in mind?"
// You've answered without giving a number.

// After receiving an offer:
"Thank you so much for the offer — I'm genuinely excited about this role.
Could I have 48 hours to review the full compensation package?"
// ALWAYS take time. Immediate acceptance leaves money on the table.

// Counter-offer:
"I've done my research on levels.fyi and Glassdoor for similar roles,
and I was hoping we could get to $[X] in base, or alternatively increase
the equity by [Y]%. My current package is $[Z], so this needs to make
sense as a move. Is there flexibility?"
// Specific number. Market data reference. Current package as anchor.

// What to negotiate:
// - Base salary (most negotiable in big tech)
// - Signing bonus (often easier to increase than base)
// - Equity grant size or cliff (can ask for smaller cliff)
// - Start date (can buy you an extra paycheck at current job)
// - Title (Senior vs Staff can be 20% comp difference)
✅ Why this works: Negotiating doesn't hurt your offer — companies expect it. Not negotiating leaves 10-20% comp on the table. The worst they can say is no, and no well-run company rescinds an offer for negotiating professionally.
