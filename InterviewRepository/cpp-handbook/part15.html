❓ How would you design a memory manager for an NPU with 4MB SRAM and unknown model sizes at compile time?
The question tests: memory management theory + hardware awareness + practical inference knowledge.
Answer: Two-tier approach: (1) Static allocation for models with fixed shapes (most common): run liveness analysis on the ONNX graph offline. Tensors with non-overlapping live ranges share memory. Assign offsets using greedy interval scheduling — O(n log n). Produces a flat memory map with zero runtime overhead. (2) Dynamic allocation for variable-shape tensors: pool allocator with size classes (64B, 256B, 1KB, 4KB, 16KB). Each size class is a singly-linked free list. O(1) alloc/free. No system malloc — deterministic latency. Critical constraints: 32-byte alignment for DMA. Power-of-2 size classes for fast lookup (bit shift). Never exceed 4MB at peak — fail loudly during model loading if peak memory exceeds budget (calculated from liveness analysis).
Follow-up questions interviewers ask:

// Kinara-style: verify inference correctness against reference
// "Golden output" regression test for each model
bool verify_output_correctness(
    const Model& model,
    const Tensor& input,
    const Tensor& expected_output,  // computed by ONNX Runtime (reference)
    float atol = 1e-3f,
    float rtol = 1e-3f)
{
    auto actual = model.infer(input);  // your NPU runtime
    if (actual.shape() != expected_output.shape()) return false;

    // Element-wise comparison: |actual - expected| <= atol + rtol * |expected|
    for (size_t i = 0; i < actual.size(); ++i) {
        float diff = std::abs(actual[i] - expected_output[i]);
        float thresh = atol + rtol * std::abs(expected_output[i]);
        if (diff > thresh) {
            printf("MISMATCH at %zu: actual=%.6f expected=%.6f diff=%.6f thresh=%.6f\n",
                   i, actual[i], expected_output[i], diff, thresh);
            return false;
        }
    }
    // Cosine similarity check (catches systematic scale errors)
    float dot=0, na=0, nb=0;
    for (size_t i=0;i<actual.size();++i){dot+=actual[i]*expected_output[i];na+=actual[i]*actual[i];nb+=expected_output[i]*expected_output[i];}
    float cosine = dot / (std::sqrt(na) * std::sqrt(nb));
    return cosine > 0.999f;
}
✅ Why this works: Always validate correctness by comparing against a reference runtime (ONNX Runtime, PyTorch). Quantization, layout changes, and kernel bugs can all introduce subtle numerical errors.

❓ How do you maximize occupancy for a CUDA kernel?
Occupancy = active warps / max warps per SM. Limited by three resources: (1) Registers per thread: more registers = fewer warps can co-reside. Check: nvcc --ptxas-options=-v to see register usage. Reduce with -maxrregcount=N (may cause register spilling — tradeoff). (2) Shared memory per block: more shared mem = fewer blocks per SM. Solution: reduce shared memory usage, or use dynamic allocation to share across blocks. (3) Block size: too small = not enough warps per SM. Too large = limited by registers/smem. Sweet spot: 128-256 threads per block, multiple of 32 (warp size). Analyze with: Nsight Compute → 'Warp State Statistics' → check achieved vs theoretical occupancy. Important: occupancy > 50% rarely matters. What matters is hiding memory latency — if your kernel has enough in-flight memory requests, 50% occupancy may be sufficient. Use Nsight's roofline model.

// NVIDIA-style: profile-driven kernel optimization
// Step 1: measure baseline
ncu --set full ./kernel_test   // Nsight Compute full profile
// Look at: % of peak FLOPS, % of peak memory bandwidth

// Step 2: check memory access pattern
// Coalesced: consecutive threads access consecutive memory addresses
// thread 0 → addr 0, thread 1 → addr 1, ..., thread 31 → addr 31
// → one 128-byte memory transaction for the warp
__global__ void good_kernel(float* A, int N) {
    int i = blockIdx.x * blockDim.x + threadIdx.x;
    if (i < N) A[i] *= 2.0f;   // coalesced: stride-1 access
}

// Uncoalesced: stride > 1 → multiple transactions per warp
__global__ void bad_kernel(float* A, int N, int stride) {
    int i = (blockIdx.x * blockDim.x + threadIdx.x) * stride;
    if (i < N) A[i] *= 2.0f;   // stride-N: N transactions per warp!
}

// Step 3: use shared memory for reuse
// Matrix multiply tile: load 16x16 tile into shared, compute, repeat
__shared__ float tile_A[16][16];
__shared__ float tile_B[16][16];
// Loads: 16×16 = 256 floats per tile (coalesced)
// Compute: 16×16×16 = 4096 MACs from 256 loads
// Arithmetic intensity: 4096/256 = 16 FLOPs/float loaded → compute-bound
✅ Why this works: Always analyze arithmetic intensity first. If your kernel is memory-bound (intensity < ridge point on roofline), shared memory and access pattern optimization matter. If compute-bound, optimize instruction throughput.

AMD

📌 Note: Focus: ROCm, HIP (CUDA-compatible), RDNA/CDNA GPU architecture, OpenCL, compiler (LLVM-based AMD backend). Know how HIP differs from CUDA.
❓ What is HIP and what are the key differences from CUDA?
HIP (Heterogeneous-compute Interface for Portability): AMD's CUDA-compatible API. Nearly identical API — hipMalloc vs cudaMalloc, hip<<<>>> vs cuda<<<>>>. HIP code can compile for both NVIDIA GPUs (via nvcc backend) and AMD GPUs (via amdclang++). Key differences: (1) AMD uses wavefronts of 64 threads (CDNA) or 32 threads (RDNA) — same concept as CUDA warp. (2) LDS (Local Data Share) = CUDA shared memory. (3) Different register file size per CU. (4) AMD CDNA has MFMA instructions (Matrix Fused Multiply-Add) — equivalent to CUDA Tensor Cores. (5) ROCm replaces CUDA ecosystem: rocBLAS (cuBLAS), MIOpen (cuDNN), hipBLAS. hipify-perl tool converts most CUDA code automatically (~90%). Manual work: warp-level intrinsics (different names), SM-specific optimizations, PTX inline assembly.
Follow-up questions interviewers ask:
  • How do you port a CUDA kernel that uses warp shuffle operations to HIP?
  • What is AMD's Infinity Fabric and how does it affect multi-GPU performance?

Intel

📌 Note: Focus: oneAPI (DPC++/SYCL), OpenVINO, Gaudi accelerator, CPU microarchitecture, AVX-512 SIMD, memory hierarchy. Strong emphasis on performance engineering depth.
❓ Explain Intel's CPU execution pipeline and how to optimize for it.
Modern Intel CPUs (Ice Lake, Tiger Lake, Alder Lake) are out-of-order superscalar. Key concepts: (1) Front-end: fetch → decode → micro-op cache (DSB). Decoded streams go to Reservation Station. (2) Out-of-order execution: 12-wide issue, ~400-500 entry ROB (Reorder Buffer). Instructions execute as dependencies are resolved. (3) Execution units: 4 integer ALUs, 2 FP/SIMD units (256-bit), branch unit, load/store units. (4) Memory hierarchy: L1=48KB 4-cycle, L2=512KB 12-cycle, L3=per-core slice, DDR4=~100 cycles. Optimization: (a) Avoid store-to-load forwarding stalls: don't write and immediately read the same address. (b) Branch prediction: sorted loops, predictable branch patterns. (c) Vectorize inner loops: -O3 -march=native + __restrict__ on pointers. (d) Prefetch: __builtin_prefetch for irregular access. (e) Avoid false dependency: XOR-zero registers before use (mov eax, eax creates false dep on old eax).
Follow-up questions interviewers ask:
  • What is micro-op fusion? What is macro-op fusion?
  • When does AVX-512 actually help vs hurt performance (frequency scaling)?

Qualcomm

📌 Note: Focus: Hexagon DSP, SNPE/QNN SDK, Snapdragon SoC architecture, mobile power optimization, on-device AI. Strong embedded + mobile AI knowledge required.
❓ How does SNPE/QNN decide which backend (CPU/GPU/DSP/HTP) to use for each operator?
QNN (Qualcomm AI Engine Direct): operator assignment algorithm: (1) Operator support check: each backend registers supported ops and dtypes. If op not supported → must use CPU. (2) Performance profiling: QNN can profile each op on each backend offline, build a lookup table of latency per backend per op shape. (3) Data layout conversion cost: switching between backends requires tensor format conversion (NCHW↔NHWC, FP32↔INT8). This cost is added to the assignment decision. (4) Graph partitioning: minimize cross-backend boundaries (each crossing = copy + conversion). (5) Power budget: HTP (Hexagon Tensor Processor) is most efficient for INT8 ops. GPU is faster for FP16 but more power. CPU for unsupported ops. In practice: quantized convolutions → HTP. FP16 activations → GPU. Non-quantizable ops (log, softmax with FP32) → CPU. The goal is to maximize time on HTP while minimizing CPU fallback.
Follow-up questions interviewers ask:
  • How do you debug a QNN model where accuracy drops after quantization?
  • What is the difference between HTA and HTP on Snapdragon?

Google

📌 Note: Focus: Strong algorithms (LC Hard expected), system design at scale, C++ at scale (Abseil, Protobuf), ML systems (XLA, JAX, TPU). 5-7 rounds. Coding standard is very high.
❓ Explain XLA's compilation pipeline.
XLA (Accelerated Linear Algebra): domain-specific compiler for ML workloads, used by TensorFlow and JAX. Pipeline: (1) HLO (High-Level Operations) IR: TF/JAX computation graphs are lowered to HLO — abstract ops like dot(), convolution(), reduce(). (2) HLO analysis and optimization: constant folding, algebraic simplification, reshape elimination, CSE. (3) Layout assignment: choose NCHW or NHWC for each tensor based on hardware preference. (4) Fusion: combine elementwise ops into a single kernel — critical for bandwidth-bound layers. (5) Buffer assignment: SSA-based liveness analysis, minimize peak memory. (6) Backend codegen: LLVM for CPU/GPU, custom ISA for TPU. (7) For TPU: JIT compiles entire training step into one 'program' — no Python overhead during execution, very tight loop. Key differentiator: XLA aggressively fuses across op boundaries — ReLU+bias+matmul all in one kernel. This is why JAX+XLA can match or beat hand-tuned cuDNN for some workloads.
Follow-up questions interviewers ask:
  • How does XLA handle dynamic shapes? What are the tradeoffs of JIT re-tracing?
  • What is the difference between XLA and TVM?
  • How does TPU v4 differ architecturally from NVIDIA A100?

❓ Tell me about a time you made a system faster using minimal resources.
This tests: Dive Deep + Invent & Simplify + Deliver Results. Answer structure: Lead with the metric (what got faster, by how much, with what constraint). Then explain the technical insight (not just 'I profiled and fixed it'). Show the specific insight that made the difference. End with business impact (cost savings, capacity freed). Example: 'Our embedding lookup was taking 45% of total inference time. I profiled with perf — LLC miss rate was 78%, because the embedding table (8GB) didn't fit in any cache level. The key insight: during inference, we only needed ~2% of embeddings per batch. I implemented a hash-based hot embedding cache (512MB, LRU) that covered 73% of lookups. The 45% overhead dropped to 12%. No hardware change. This freed enough compute to handle 2.4x more QPS on the same fleet — equivalent to deferring a $2.1M hardware purchase by 18 months.'
Follow-up questions interviewers ask:

  • How did you validate the impact in production?

// Each of these shows:
// - You've thought about real engineering problems

// - You're evaluating THEM as much as they're evaluating you

❌ AVOID THIS
// Weak questions — show you didn't prepare
"What does [Company] do?"              ← shows no preparation
"What's the work-life balance like?"   ← HR conversation, not interviewer
"When will I hear back?"               ← practical, but not your best question

"What's the salary range?"             ← ask HR, not the engineering interviewer
