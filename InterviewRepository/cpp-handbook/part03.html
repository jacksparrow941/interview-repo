✅ DO THIS
// fork() + exec() — the shell pattern
// Used to launch every external program from a shell

pid_t pid = fork();
if (pid < 0) {
    perror("fork failed"); exit(1);
}
if (pid == 0) {
    // CHILD: replace process image with new program
    char* args[] = {"/bin/ls", "-la", "/tmp", nullptr};
    execv("/bin/ls", args);   // replaces code/data/stack with ls
    perror("exec failed");    // only reached if exec() fails
    _exit(1);                 // use _exit in child after fork (no atexit handlers)
}
// PARENT: continues here
int status;
waitpid(pid, &status, 0);    // wait for child to finish
if (WIFEXITED(status))
    printf("child exited with %d\n", WEXITSTATUS(status));
✅ Why this works: fork() uses Copy-on-Write (CoW): parent and child share physical pages marked read-only. Only when a page is written does the OS create a private copy. fork() is O(page table entries), not O(memory size).
❌ AVOID THIS
// BAD: calling fork() in a multi-threaded program
// Only the calling thread is copied to child — other threads VANISH
// If another thread held a mutex when fork() was called:
//   child inherits locked mutex with no thread to release it → DEADLOCK

std::mutex db_mtx;
void thread_worker() {
    std::lock_guard lk(db_mtx);  // holds mutex
    // ... if fork() is called by main thread here ...
    // child has db_mtx locked with NO thread to unlock it
}

// Rule: if you must fork() in a multi-threaded program:
// - Call exec() immediately in child (before doing anything else)
// - Or use pthread_atfork() handlers
// - Or: use separate process for forking (avoid the issue entirely)
❌ Why this fails: fork() in multi-threaded programs is a well-known trap. The POSIX specification says only async-signal-safe functions can be called between fork() and exec() in a multi-threaded program.

Chapter 2 — CPU Scheduling

The scheduler decides which runnable thread/process runs next. Linux uses CFS (Completely Fair Scheduler) for normal tasks and SCHED_FIFO/SCHED_RR for real-time tasks.

Chapter 3 — Virtual Memory and Paging

Virtual memory gives each process the illusion of a large, contiguous, private address space. The MMU (Memory Management Unit) hardware translates virtual to physical addresses on every access.

4-Level Page Table Walk (x86-64, 48-bit virtual address): Virtual address: [63:48=sign ext][47:39=PGD][38:30=PUD][29:21=PMD][20:12=PT][11:0=offset] CR3 register → PGD table → PUD table → PMD table → PT table → Physical Frame (physical addr) (512 entries) (512 entries) (512 entries) (512 entries) Each entry: 8 bytes = 4KB table. Full 4-level page table: 256TB virtual space TLB (Translation Lookaside Buffer): Cache of recent virtual→physical translations (~64-1500 entries) TLB hit: 1 cycle TLB miss: page table walk ~100+ cycles
✅ DO THIS
// mmap: map anonymous memory (no file backing)
void* buf = mmap(nullptr, 64 * 1024 * 1024,   // 64MB
                 PROT_READ | PROT_WRITE,
                 MAP_PRIVATE | MAP_ANONYMOUS,
                 -1, 0);
// Pages not allocated yet — only virtual address reserved
// First access to each page triggers a page fault → OS allocates physical page

// mmap: map a file (zero-copy file I/O)
int fd = open("model_weights.bin", O_RDWR);
struct stat st; fstat(fd, &st);
float* weights = (float*)mmap(nullptr, st.st_size,
                               PROT_READ,   // read-only
                               MAP_SHARED,  // changes visible to all mappings
                               fd, 0);
close(fd);   // fd can be closed after mmap — mapping stays
// weights[i] is now a direct pointer into file — no read() syscall needed
// OS reads pages on demand via page faults (demand paging)
// Multiple processes mapping same file share physical pages → huge RAM savings
msync(weights, st.st_size, MS_SYNC);   // flush dirty pages to disk
munmap(weights, st.st_size);
✅ Why this works: mmap for model weights is used by PyTorch, TensorFlow, and most inference engines. Multiple inference server instances map the same weights file — they share the same physical RAM pages (read-only mapping).
❌ AVOID THIS
// BAD: reading a large file with read() into a buffer
// Example: loading 4GB model weights
char* buf = (char*)malloc(4ULL * 1024 * 1024 * 1024);   // 4GB malloc!
int fd = open("model.bin", O_RDONLY);
read(fd, buf, 4GB);   // copies 4GB from kernel page cache to user buffer
// Problems:
// 1. Double memory: file in page cache + your buffer = 8GB used
// 2. Full copy upfront even if you only need part of the file
// 3. No sharing: two processes both read() = two copies in memory

// BETTER: mmap — shared, demand-paged, no upfront copy
❌ Why this fails: mmap avoids the double-buffering problem. The file's page cache IS your buffer — no copy needed. Access patterns drive demand-paging so you only use RAM for pages actually accessed.

✅ DO THIS
// Producer-consumer via POSIX shared memory + semaphore
// Producer (process 1):
const int SHM_SIZE = 4096;
int shm_fd = shm_open("/mydata", O_CREAT | O_RDWR, 0666);
ftruncate(shm_fd, SHM_SIZE);
void* shm = mmap(nullptr, SHM_SIZE, PROT_READ|PROT_WRITE, MAP_SHARED, shm_fd, 0);

// Use a pthread mutex/semaphore in shared memory for sync
sem_t* sem = sem_open("/mysem", O_CREAT, 0666, 0);
memcpy(shm, &data, sizeof(data));   // write data
sem_post(sem);   // signal consumer

// Consumer (process 2):
int shm_fd2 = shm_open("/mydata", O_RDWR, 0666);
void* shm2 = mmap(nullptr, SHM_SIZE, PROT_READ|PROT_WRITE, MAP_SHARED, shm_fd2, 0);
sem_t* sem2 = sem_open("/mysem", 0);
sem_wait(sem2);   // block until data ready
memcpy(&local, shm2, sizeof(local));   // read data
✅ Why this works: Shared memory is the fastest IPC — data doesn't need to be copied through the kernel. The kernel only needs to be involved in setup (shm_open) and synchronization (sem_post/wait).

Interview Q&A — OS

❓ What happens when you call malloc()?
glibc malloc (ptmalloc2) has multiple strategies: For small allocations (<128KB): maintains thread-local arenas with free lists organized by size class (bins). Returns a freed block if one of matching size exists — very fast. Otherwise uses sbrk()/mmap() to get memory from OS. For large allocations (>128KB): directly calls mmap(MAP_ANONYMOUS) — gets memory directly from OS. Each allocation has a 16-byte hidden header (on 64-bit) storing size and flags. Alignment: 16-byte aligned. Thread safety: each thread has its own arena (up to 8 arenas per CPU) to reduce lock contention. free(): returns block to bin — adjacent free blocks are coalesced to reduce fragmentation.
Follow-up questions interviewers ask:
  • What is jemalloc/tcmalloc? When would you use them?
  • What causes heap fragmentation?
  • Why does new [] require delete [] and not delete?
Common mistakes in answers:
  • Saying malloc always calls sbrk — modern malloc uses mmap for large allocations.
  • Forgetting that malloc doesn't zero memory (use calloc for zeroed allocation).
❓ Explain page fault handling.
A page fault occurs when the CPU tries to access a virtual address that has no valid physical mapping. The hardware raises a fault, the OS page fault handler runs: (1) Is the address in a valid VMA (Virtual Memory Area)? No → SIGSEGV (segfault). (2) Is it a permission fault (writing to read-only)? Maybe CoW: allocate new page, copy contents, remap as writable. (3) Valid but not present (demand paging): find the backing storage (file or swap), load page, update page table, resume execution. Cost: minor fault (page in RAM but not mapped) ~1µs; major fault (page on disk) ~1ms+. reduce with mlock() or mlockall() to pin pages.
Follow-up questions interviewers ask:
  • What is the difference between minor and major page fault?
  • What is thrashing?
  • How does mlock() affect performance?
