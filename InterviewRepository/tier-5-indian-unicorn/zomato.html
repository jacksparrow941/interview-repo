1 Explain the circuit breaker pattern
circuit-breakerhystrix
Medium 78%
Circuit Breaker States
  • CLOSED: Normal operation. Failure counter tracks errors. If failures > threshold → OPEN.
  • OPEN: All calls fail immediately (fail-fast). No downstream load. After timeout → HALF_OPEN.
  • HALF_OPEN: Allow one probe request. If succeeds → CLOSED. If fails → OPEN again.
Why it matters
Without circuit breaker: one slow service causes thread pool exhaustion in caller → cascading failure across the system. Circuit breaker prevents this by failing fast and giving downstream service recovery time.
Libraries
  • Resilience4j (Java): sliding window (count/time based), bulkhead pattern
  • Hystrix (deprecated): used at Netflix, pioneered the pattern
  • Go: sony/gobreaker, mercadolibre/go-breakers
Follow-ups
• What is the bulkhead pattern and how does it complement circuit breaker?
• How do you set the right failure threshold to avoid flapping?
• What is the difference between circuit breaker and retry with exponential backoff?

1 Goroutines vs OS threads
goroutinesthreadsgmp
Medium 92%
Goroutines vs OS Threads
  • Goroutine: ~2KB initial stack (grows dynamically to hundreds of MB if needed). M:N threading — N goroutines multiplexed onto M OS threads. Scheduled by Go runtime.
  • OS Thread: ~1MB stack (fixed at creation). 1:1 with kernel thread. Expensive context switch (μs).
  • Can run millions of goroutines. Thousands of OS threads = OOM.
GMP Model (brief)
  • G: Goroutine (the task)
  • M: OS thread (the runner)
  • P: Processor/scheduler context (GOMAXPROCS Ps). Each P has local run queue.
  • When G blocks on syscall → M + G detach from P → P gets another M to continue work
Follow-ups
• What is goroutine stack growth mechanism? (segmented stacks → copying stacks since Go 1.4)
• What is GOMAXPROCS and when would you change it?
• How do goroutines avoid the 10K thread problem?

5 defer, panic, recover — full semantics and patterns
deferpanicrecover
Medium 88%
defer
Deferred call runs when surrounding function returns (normal or panic). Arguments evaluated immediately; call deferred. LIFO order.
func processFile(path string) (err error) {
    f, err := os.Open(path)
    if err != nil { return }
    defer f.Close()           // runs even on early return/panic
    defer func() {            // named return: modify err on cleanup failure
        if cerr := f.Close(); cerr != nil && err == nil {
            err = cerr
        }
    }()
    // ... process f
    return
}
panic / recover
func safeDiv(a, b int) (result int, err error) {
    defer func() {
        if r := recover(); r != nil {     // recover() catches panic
            err = fmt.Errorf("panic: %v", r)
        }
    }()
    return a / b, nil  // panics if b==0
}

// recover() returns nil if no panic, or the panic value
// ONLY works inside a deferred function
Rules
  • recover() only stops a panic if called directly from a deferred function
  • Panic unwinds stack, running deferred functions
  • Use panic for truly unrecoverable states (programming errors), not business logic
  • HTTP handlers should recover panics to avoid crashing the whole server

• Can you defer a method call? (yes)

6 goroutine leak — how to detect and prevent

Medium 86%
What is a goroutine leak
Goroutines that are started but never terminate. They consume memory (~2KB initial stack, can grow), CPU for scheduling, and keep referenced objects alive.
Common Causes
  • Blocked channel read/write with no one to unblock
  • Not passing/checking context.Context
  • Infinite loops without exit condition
  • Forgotten goroutines in tests
Prevention Pattern
func worker(ctx context.Context, jobs <-chan Job) {
    for {
        select {
        case <-ctx.Done():
            return  // clean exit
        case job, ok := <-jobs:
            if !ok { return }  // channel closed
            process(job)
        }
    }
}

Interface internals
A Go interface value has two words: (type, pointer). An interface is nil only when both type and pointer are nil.
The Nil Trap
type MyError struct{ msg string }
func (e *MyError) Error() string { return e.msg }

func getError() error {
    var err *MyError = nil
    return err  // TRAP: returns (type=*MyError, ptr=nil) — NOT nil interface!
}

if err := getError(); err != nil {
    fmt.Println("This prints!")  // Bug!
}

// Fix: return nil explicitly
func getError() error {
    var err *MyError
    if conditionFailed { return err }  // still buggy
    return nil  // correct
}

var i interface{} = "hello"

// Type assertion

Pipeline
func gen(nums ...int) <-chan int {
    out := make(chan int)
    go func() {
        defer close(out)
        for _, n := range nums { out <- n }
    }()
    return out
}
func sq(in <-chan int) <-chan int {
    out := make(chan int)
    go func() { defer close(out); for n := range in { out <- n*n } }()
    return out
}
// Usage: for v := range sq(sq(gen(2,3,4))) { fmt.Println(v) }
Fan-Out
func fanOut(in <-chan int, workers int) []<-chan int {
    outs := make([]<-chan int, workers)
    for i := range outs {
        outs[i] = sq(in)  // each worker reads from same input
    }
    return outs
}
Fan-In (Merge)
func merge(cs ...<-chan int) <-chan int {
    var wg sync.WaitGroup
    out := make(chan int)
    output := func(c <-chan int) {
        defer wg.Done()
        for v := range c { out <- v }
    }
    wg.Add(len(cs))
    for _, c := range cs { go output(c) }
    go func() { wg.Wait(); close(out) }()
    return out
}
Done Channel (Cancellation)
func sq(done <-chan struct{}, in <-chan int) <-chan int {
    out := make(chan int)
    go func() {
        defer close(out)
        for n := range in {
            select {
            case out <- n*n:
            case <-done: return  // cancelled
            }
        }
    }()
    return out
}
// Use context.Context in production instead of done channel

11 Functional options pattern in Go
functional-optionsdesign-patternconfiguration
Medium 80%
Problem
How to provide optional configuration to a constructor without breaking API as options grow? Config structs are verbose; many parameters are messy.
Functional Options Pattern
type Server struct {
    host    string
    port    int
    timeout time.Duration
    maxConn int
}

type Option func(*Server)

func WithPort(p int) Option      { return func(s *Server) { s.port = p } }
func WithTimeout(d time.Duration) Option { return func(s *Server) { s.timeout = d } }
func WithMaxConn(n int) Option   { return func(s *Server) { s.maxConn = n } }

func NewServer(host string, opts ...Option) *Server {
    s := &Server{host: host, port: 8080, timeout: 30*time.Second, maxConn: 100}  // defaults
    for _, opt := range opts { opt(s) }
    return s
}

// Usage (clean, readable, extensible):
srv := NewServer("localhost",
    WithPort(9090),
    WithTimeout(5*time.Second),
)
Advantages
  • Backward compatible — add new options without changing signature
  • Self-documenting call sites
  • Easy to set sensible defaults
  • Options are first-class values — can be composed, stored, passed around

Replication Mechanics (MySQL binlog / PostgreSQL WAL)
Primary records every write as binary log events. Replica connects, streams binlog, applies changes. Replication can be:

  • High write throughput on primary
  • Network latency between primary and replica

7 PostgreSQL MVCC — how it achieves non-blocking reads
mvccpostgresqlsnapshot
Hard 82%
MVCC = Multi-Version Concurrency Control
Each row has hidden columns:
  • xmin: transaction ID that inserted this version
  • xmax: transaction ID that deleted/updated this version (0 = still live)
Reads see a snapshot: only versions where xmin ≤ snapshot_xid < xmax.
How it works
T1 (xid=100): UPDATE users SET name='Bob' WHERE id=1
→ Old row: xmin=50, xmax=100  (now dead to T1)
→ New row: xmin=100, xmax=0   (live)

T2 (xid=99, started before T1):
→ Sees old row (xmin=50 <= 99 < xmax=100) ✓
→ Sees 'Alice' — no blocking!

T3 (xid=101, started after T1 commits):
→ Old row: xmax=100 <= 101 → dead, skip
→ New row: xmin=100 <= 101, xmax=0 → live, sees 'Bob' ✓
VACUUM
Dead rows (old versions) accumulate. VACUUM reclaims space. AUTOVACUUM runs automatically. Transaction ID wraparound prevented by freezing old rows.

8 Database deadlocks — detection, prevention, resolution
deadlocklockwait-for-graph
Hard 82%
What is a Deadlock
Two or more transactions each hold a lock the other needs.
T1: LOCK A → wait for B
T2: LOCK B → wait for A
→ Circular wait = deadlock
Deadlock Detection
Most DBs run a background detector (PostgreSQL, MySQL InnoDB).
Builds a wait-for graph: node = transaction, edge = T1 waits for lock held by T2. Cycle = deadlock → kill victim transaction (least expensive to rollback).
Prevention Strategies
  • Lock ordering: Always acquire locks in the same global order (e.g., lower ID first)
  • Timeout: SET lock_timeout = '1s' — transaction aborts if wait too long
  • SELECT FOR UPDATE SKIP LOCKED: Skip locked rows instead of waiting (job queues)
  • Reduce transaction scope: Short transactions hold locks briefly
Application-Level Fix
-- Instead of long transaction:
BEGIN;
  UPDATE account SET bal = bal - 100 WHERE id = 1;  -- locks row
  -- ... complex computation (seconds) ...
  UPDATE account SET bal = bal + 100 WHERE id = 2;  -- deadlock risk!
COMMIT;

-- Better: do computation outside transaction, then short UPDATE

9 Eventual consistency models — BASE, read-your-writes, monotonic reads
eventual-consistencybasecausal
Hard 82%
CAP Theorem Recap
In presence of network partition (P), choose between Consistency (C) or Availability (A). Most distributed systems choose AP → eventual consistency.
BASE (Basically Available, Soft state, Eventually consistent)
Contrast to ACID.
  • Basically Available: System works, even during partial failure (stale data OK)
  • Soft State: State may change without input (replication catching up)
  • Eventually Consistent: Given no new updates, all replicas converge to same state
Consistency Models (weakest to strongest)
  • Eventual: Converges eventually. DNS, S3.
  • Monotonic Read: Once you read version V, you never see older version. (client stickiness)
  • Read-Your-Writes: You always see your own writes immediately. (session token pinning)
  • Causal: If A caused B, everyone sees A before B. (vector clocks)
  • Sequential: All operations appear in a global order consistent with program order.
  • Linearizable (Strict): Strongest. Operations appear instantaneous. ZooKeeper, etcd.

Sliding Window Log Algorithm
Store timestamps of each request in a sorted set. On each request: remove old entries, count remaining, allow if below limit.
In-Memory Thread-Safe
class SlidingWindowRateLimiter {
    private final int maxRequests;
    private final long windowMs;
    private final Map<String, Deque<Long>> windows = new ConcurrentHashMap<>();

    boolean allow(String clientId) {
        long now = System.currentTimeMillis();
        long cutoff = now - windowMs;

        Deque<Long> timestamps = windows.computeIfAbsent(clientId, k -> new ArrayDeque<>());

        synchronized (timestamps) {
            // Remove expired
            while (!timestamps.isEmpty() && timestamps.peekFirst() <= cutoff)
                timestamps.pollFirst();
            if (timestamps.size() >= maxRequests) return false;
            timestamps.addLast(now);
            return true;
        }
    }
}

3 Design a Snowflake-style Distributed ID Generator

Twitter Snowflake Structure (64-bit)
| 1 bit sign | 41 bits timestamp (ms) | 10 bits machine ID | 12 bits sequence |

- Timestamp: ms since custom epoch (Jan 1, 2010)
  → supports 2^41 ms ≈ 69 years
- Machine ID: 10 bits → 1024 machines
- Sequence: 12 bits → 4096 IDs/ms/machine

Implementation
class SnowflakeIdGenerator {
    private final long EPOCH = 1288834974657L;  // Nov 4, 2010
    private final long MACHINE_ID;              // 0-1023
    private long sequence = 0;
    private long lastTs = -1;

    synchronized long nextId() {
        long ts = System.currentTimeMillis();
        if (ts == lastTs) {
            sequence = (sequence + 1) & 0xFFF;  // 12-bit mask
            if (sequence == 0) ts = waitNextMs(lastTs);  // sequence exhausted
        } else { sequence = 0; }
        lastTs = ts;
        return ((ts - EPOCH) << 22) | (MACHINE_ID << 12) | sequence;
    }

    private long waitNextMs(long ts) {
        long now = System.currentTimeMillis();
        while (now <= ts) now = System.currentTimeMillis();
        return now;
    }
}

5 I/O Models
  • Blocking I/O: Thread blocks until data ready. Simple. Scales poorly (1 thread/connection).
  • Non-blocking I/O: Returns EAGAIN immediately if no data. Polling loop wastes CPU.
  • I/O Multiplexing (select/poll/epoll): One thread watches many fds. Blocks on select, wakes when any fd ready. Efficient for many connections.

  • epoll: O(1) event notification. Register fds once (epoll_ctl), wait (epoll_wait) returns only ready fds. Kernel red-black tree for O(log n) add/remove. Level-triggered or edge-triggered modes.
io_uring (Modern Linux)
Fully async: app submits I/O requests to SQ ring, kernel processes, posts completions to CQ ring. Zero syscall on fast path. Used in: Tokio (Rust), QEMU, PostgreSQL, Nginx.

Virtual Memory
Each process has its own virtual address space (e.g., 0 to 2^48 on 64-bit). OS maps virtual pages → physical frames via page table. Allows: isolation between processes, overcommit memory, memory-mapped files, copy-on-write.
Multi-level Page Tables

3 Deadlock — conditions, prevention, avoidance, detection
deadlockcoffmanbanker
Hard 88%
Coffman's Four Necessary Conditions
  • Mutual Exclusion: Resources not sharable
  • Hold and Wait: Process holds resource while waiting for another
  • No Preemption: Resources can't be forcibly taken
  • Circular Wait: T1→waits for T2→waits for T3→waits for T1
Breaking any one prevents deadlock.
Prevention
  • Eliminate Hold and Wait: Request all resources at once before starting
  • Allow Preemption: If waiting, release held resources (costly)
  • Eliminate Circular Wait: Global ordering of resources (always lock in same order)
Avoidance — Banker's Algorithm
Each process declares max resource claim. System checks if granting a request leaves system in safe state (all processes can complete). If unsafe → deny and wait. Used in theory; impractical for dynamic systems.
Detection and Recovery
Allow deadlocks to occur. Periodically run deadlock detector (wait-for graph cycle detection). Recovery: kill one victim process, or preempt + rollback resources.

What is Context Switch
OS saving state of running process/thread and restoring another's. Triggered by: timer interrupt (preemption), syscall, I/O wait, voluntary yield.
