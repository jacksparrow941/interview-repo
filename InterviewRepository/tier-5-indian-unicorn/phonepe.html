1 Two Sum

Easy 95%
Approach
Use a hash map to store complement = target - num as you iterate. If current number exists in map → found the pair.
Solution
def twoSum(nums, target):
    seen = {}
    for i, num in enumerate(nums):
        if num in seen:
            return [seen[num], i]
        seen[target - num] = i
Complexity
Time: O(n) | Space: O(n)
Follow-ups

• What if we need ALL pairs? (collect instead of return first)

2 Subarray Sum Equals K
prefix-sumhash-map
Medium 74%
Approach
Prefix sum: if prefixSum[j] - prefixSum[i] = k, then subarray i+1..j sums to k. Store count of each prefix sum in a hash map.
Solution
def subarraySum(nums, k):
    count = prefix = 0
    freq = {0: 1}
    for n in nums:
        prefix += n
        count += freq.get(prefix - k, 0)
        freq[prefix] = freq.get(prefix, 0) + 1
    return count
Complexity
Time: O(n) | Space: O(n)

1 REST vs GraphQL vs gRPC — when to use each?

REST vs GraphQL vs gRPC
  • REST: Stateless, resource-based (nouns), HTTP verbs. Cacheable, universally supported. Over-fetching (get entire user object for just the name) / under-fetching (need 3 calls for related data).
  • GraphQL: Single endpoint. Client specifies exact fields. Eliminates over/under-fetching. Schema as contract. N+1 problem (use DataLoader). Good for complex UIs, mobile (save bandwidth).
  • gRPC: HTTP/2 + Protocol Buffers. Binary, strongly typed, 5-10x smaller than JSON. Bidirectional streaming. Generated client/server stubs. Best for internal microservices.
Decision Matrix
  • Public API / browser-to-server → REST
  • Complex UI with diverse data needs → GraphQL
  • Internal microservice-to-microservice → gRPC
  • Real-time bidirectional → WebSocket

Kafka Architecture
  • Topic: Named category. Divided into partitions (immutable ordered log).
  • Producer: Writes to partition (by key hash or round-robin). Acks: 0/1/all.

  • Exactly-once: idempotent producer + transactional API.
  • Page cache: Kafka relies on OS page cache for near-disk-speed throughput.

5 Distributed transactions: 2PC vs Saga
2pcsagadistributed-tx
Hard 80%
2PC — Two-Phase Commit
Phase 1 (Prepare): Coordinator sends PREPARE to all participants. Each votes YES (prepared, locked) or NO.
Phase 2 (Commit/Abort): If all YES → send COMMIT; if any NO → send ABORT.
Problems: Coordinator failure in phase 2 → participants stuck holding locks. Blocking protocol. Network partition → split brain possible.
Saga Pattern
Choreography: Each service publishes event → next service reacts. No central coordinator. Decoupled but hard to trace.
Orchestration: Saga Orchestrator sends commands to each service, receives replies. Easier to manage state.
Compensating transactions: On failure, execute rollback steps in reverse order.
Example: E-commerce order
1. Reserve inventory → 2. Debit payment → 3. Assign delivery → 4. Confirm order
Failure at step 3: Release payment (compensate) → Release inventory (compensate)

Indexes — Types and Internals
  • B+ Tree: Default in PostgreSQL/MySQL. O(log n) for equality and range queries. Leaf nodes form linked list for range scans.
  • Hash Index: O(1) for equality only. No range queries. Used in memory engines (MEMORY in MySQL).
  • GiST/GIN: PostgreSQL generalized indexes for full-text search, JSONB, arrays.
  • Bitmap Index: Low-cardinality columns. Efficient AND/OR on multiple conditions.
Clustered vs Secondary
  • Clustered (InnoDB Primary Key): Data physically stored in index order. Range scans very fast. Only 1 per table.
  • Secondary: Leaf stores primary key value → extra lookup for full row. Covering index eliminates this lookup.
Index Design Tips
  • Composite index: equality columns first, range columns last, ORDER BY columns last
  • Cover frequently queried columns with INCLUDE
  • Partial index for low-cardinality: WHERE status='PENDING'
  • Avoid index on frequently updated columns (write overhead)

3 B+ Tree index internals — structure, splits, range queries
b-plus-treeindexrange-query
Hard 88%
Structure
  • Internal nodes: keys only, no data. Fan-out typically 100-200 keys per node.
  • Leaf nodes: keys + actual row pointers (or clustered data). Linked list for range scans.
  • Height: ~3-4 levels for millions of rows (log_200(1M) ≈ 3). Fits in memory.
Why B+ over B-Tree
All data in leaves → range queries traverse leaf linked list without backtracking. Internal nodes store more keys (no data) → wider fan-out → shallower tree.
Operations
  • Search: O(log_t n) — traverse from root to leaf
  • Insert: find leaf, insert, split if overflow (cascade up)
  • Delete: find leaf, remove, merge or redistribute if underflow
  • Range scan: find start leaf, traverse linked list → sequential I/O (fast)
Clustered vs Secondary
Clustered: Data rows stored in leaf nodes in index order (InnoDB primary key). One per table.
Secondary: Leaf stores PK value → extra lookup for row data. Multiple allowed.

4 Read replicas — replication lag, use cases, consistency
replicationreplica-lagread-replica
Hard 88%
Replication Mechanics (MySQL binlog / PostgreSQL WAL)
Primary records every write as binary log events. Replica connects, streams binlog, applies changes. Replication can be:
  • Async (default): Primary doesn't wait for replica. Replica may lag.
  • Semi-sync: Primary waits for at least 1 replica to acknowledge before committing.
  • Sync (PostgreSQL synchronous_commit=on): All replicas acknowledge. Highest durability, slowest.
Replication Lag Causes
  • Large transactions (long to replay)
  • High write throughput on primary
  • Network latency between primary and replica
  • Single-threaded replay (older MySQL — use parallel replication)
Handling Lag in Applications
  • Read-your-own-writes: route reads after writes to primary for 1s, or use session stickiness
  • For stale-tolerant reads (reports, analytics): use replica
  • Monitor lag: SHOW REPLICA STATUS → Seconds_Behind_Source
Follow-ups
• What is GTID-based replication?
• How does logical replication differ from physical replication?
• What is PgBouncer and what problem does it solve?

5 SQL query optimization — indexes, covering indexes, composite indexes
indexcovering-indexcomposite
Medium 88%
Composite Index Column Order
-- Query: WHERE a = 1 AND b > 5 ORDER BY c
-- Best index: (a, b, c) — leftmost prefix rule
-- a → equality filter (most selective first)
-- b → range filter
-- c → ORDER BY (eliminates sort)

-- Index (b, a) won't use b for range + a for equality efficiently
Covering Index
Index includes all columns needed by query — no heap lookup.
-- Query:
SELECT email FROM users WHERE user_id = 42;

-- If index is (user_id, email): Index Only Scan — never touches table!
CREATE INDEX idx_user_email ON users(user_id) INCLUDE (email);  -- PostgreSQL
Index Selectivity
High selectivity (few rows per value) = good for index. Low selectivity (boolean, gender) = index often not used. n_distinct in pg_stats shows estimate. Use partial index for low-selectivity cases:
CREATE INDEX ON orders(status) WHERE status = 'PENDING';
Anti-patterns
  • SELECT * prevents covering index
  • Function on indexed column: WHERE LOWER(email) = ... → can't use index. Use functional index.
  • Leading % in LIKE: WHERE name LIKE '%Smith' → full scan. Use full-text search or reverse index.
  • Implicit type cast: WHERE varchar_col = 123 → type mismatch → seq scan

6 Database sharding strategies

Sharding Strategies
  • Range-based: Shard by range (A-G, H-P, Q-Z). Simple routing. Risk: hot spots on recent data (time-based IDs all go to last shard).
  • Hash-based: shard = hash(key) % N. Even distribution. No range queries across shards. Resharding = move all data.
  • Consistent Hashing: Virtual nodes on ring. Minimal data movement on resharding. Used by Cassandra, DynamoDB.
  • Directory-based: Lookup table maps key → shard. Flexible but single point of failure.
Cross-Shard Challenges
  • Joins: must scatter-gather or denormalize
  • Transactions: 2PC expensive; use Saga instead
  • Global aggregations: fan out to all shards, merge in application
  • Hot key: add random suffix to key, fan out writes, merge reads

7 EXPLAIN ANALYZE — reading query execution plans
explainquery-planseq-scan
Medium 86%
Key Operations
  • Seq Scan: Full table scan. Fast for small tables / low selectivity.
  • Index Scan: Uses B+ tree index. Best for high selectivity (<10% rows).
  • Index Only Scan: All needed columns in index (covering index). Fastest.
  • Bitmap Heap Scan: Index scan → bitmap of pages → sorted page access. Good for 5-20% rows.
  • Nested Loop: Join — for each outer row, find matching inner. Good for small outer result.
  • Hash Join: Build hash table from smaller table → probe with larger. Good for large unsorted.
  • Merge Join: Both sides sorted. Fast but needs sort step.
Reading EXPLAIN

8 Database partitioning strategies — range, hash, list
partitioningrangehash
Hard 84%
Range Partitioning
Divide by value range. Common for time-series data.
CREATE TABLE orders (id bigint, created_at date, ...)
PARTITION BY RANGE (created_at);

CREATE TABLE orders_2023 PARTITION OF orders
    FOR VALUES FROM ('2023-01-01') TO ('2024-01-01');
CREATE TABLE orders_2024 PARTITION OF orders
    FOR VALUES FROM ('2024-01-01') TO ('2025-01-01');
Pruning: WHERE created_at >= '2024-01-01' → only scans 2024 partition.
Hash Partitioning
Distribute evenly by hash of key. Good for write distribution.
PARTITION BY HASH (user_id);
-- Partition 0: user_id % 4 = 0
-- Partition 1: user_id % 4 = 1 ...
List Partitioning
By enumerated values. Good for geographic/categorical data.
PARTITION BY LIST (region);
-- India: ('IN'), US: ('US','CA')
Benefits

10 PostgreSQL MVCC — how it achieves non-blocking reads
mvccpostgresqlsnapshot
Hard 82%
MVCC = Multi-Version Concurrency Control
Each row has hidden columns:
  • xmin: transaction ID that inserted this version
  • xmax: transaction ID that deleted/updated this version (0 = still live)
Reads see a snapshot: only versions where xmin ≤ snapshot_xid < xmax.
How it works
T1 (xid=100): UPDATE users SET name='Bob' WHERE id=1
→ Old row: xmin=50, xmax=100  (now dead to T1)
→ New row: xmin=100, xmax=0   (live)

T2 (xid=99, started before T1):
→ Sees old row (xmin=50 <= 99 < xmax=100) ✓
→ Sees 'Alice' — no blocking!

T3 (xid=101, started after T1 commits):
→ Old row: xmax=100 <= 101 → dead, skip
→ New row: xmin=100 <= 101, xmax=0 → live, sees 'Bob' ✓
VACUUM
Dead rows (old versions) accumulate. VACUUM reclaims space. AUTOVACUUM runs automatically. Transaction ID wraparound prevented by freezing old rows.

11 Database deadlocks — detection, prevention, resolution

Hard 82%
What is a Deadlock
Two or more transactions each hold a lock the other needs.
T1: LOCK A → wait for B
T2: LOCK B → wait for A
→ Circular wait = deadlock
Deadlock Detection
Most DBs run a background detector (PostgreSQL, MySQL InnoDB).
Builds a wait-for graph: node = transaction, edge = T1 waits for lock held by T2. Cycle = deadlock → kill victim transaction (least expensive to rollback).
Prevention Strategies
  • Lock ordering: Always acquire locks in the same global order (e.g., lower ID first)
  • Timeout: SET lock_timeout = '1s' — transaction aborts if wait too long
  • SELECT FOR UPDATE SKIP LOCKED: Skip locked rows instead of waiting (job queues)
  • Reduce transaction scope: Short transactions hold locks briefly
Application-Level Fix
-- Instead of long transaction:
BEGIN;
  UPDATE account SET bal = bal - 100 WHERE id = 1;  -- locks row
  -- ... complex computation (seconds) ...
  UPDATE account SET bal = bal + 100 WHERE id = 2;  -- deadlock risk!
COMMIT;

-- Better: do computation outside transaction, then short UPDATE

12 Eventual consistency models — BASE, read-your-writes, monotonic reads

Hard 82%
CAP Theorem Recap
In presence of network partition (P), choose between Consistency (C) or Availability (A). Most distributed systems choose AP → eventual consistency.
BASE (Basically Available, Soft state, Eventually consistent)
Contrast to ACID.
  • Basically Available: System works, even during partial failure (stale data OK)
  • Soft State: State may change without input (replication catching up)
  • Eventually Consistent: Given no new updates, all replicas converge to same state
Consistency Models (weakest to strongest)
  • Eventual: Converges eventually. DNS, S3.
  • Monotonic Read: Once you read version V, you never see older version. (client stickiness)
  • Read-Your-Writes: You always see your own writes immediately. (session token pinning)
  • Causal: If A caused B, everyone sees A before B. (vector clocks)
  • Sequential: All operations appear in a global order consistent with program order.
  • Linearizable (Strict): Strongest. Operations appear instantaneous. ZooKeeper, etcd.

13 Write-Ahead Logging (WAL) — how databases ensure durability
waldurabilityredo-log
Hard 78%
What is WAL
Before modifying data pages in memory (buffer pool), the change is written to the WAL log first. On crash: replay WAL from last checkpoint to recover committed transactions. Guarantee: committed data never lost, even on sudden crash.
Write Flow
1. Transaction modifies data in buffer pool (in-memory dirty page)
2. WAL record written to WAL buffer → flushed to disk (fsync)
   [WAL written BEFORE data page written — Write-Ahead!]
3. Transaction commits: commit WAL record flushed
4. Background: dirty pages periodically checkpointed to data files
5. WAL records before checkpoint can be deleted
PostgreSQL WAL
WAL files in pg_wal/. Controls: fsync=on (durability), synchronous_commit=on/off. Turning off synchronous_commit: ~10% faster writes, risk of last 100ms of data on crash.
Uses beyond recovery
  • Streaming replication: replicas stream WAL from primary
  • Point-in-time recovery (PITR): replay WAL to any past state
  • Logical replication: parse WAL for row-level changes (Debezium/CDC)

1 I/O models — blocking, non-blocking, I/O multiplexing, async, signals

5 I/O Models
  • Blocking I/O: Thread blocks until data ready. Simple. Scales poorly (1 thread/connection).
  • Non-blocking I/O: Returns EAGAIN immediately if no data. Polling loop wastes CPU.
  • I/O Multiplexing (select/poll/epoll): One thread watches many fds. Blocks on select, wakes when any fd ready. Efficient for many connections.
  • Signal-driven I/O (SIGIO): Signal when data ready. Complex, rarely used.
  • Async I/O (AIO, io_uring): Kernel does I/O, notifies completion. True async. io_uring (Linux 5.1+): submission/completion queues in shared memory, no syscall overhead.
epoll vs select vs poll
  • select: fd_set bitmap, max 1024 fds, O(n) scan, copies fd_set each call
  • poll: array of pollfd, no 1024 limit, still O(n) scan
  • epoll: O(1) event notification. Register fds once (epoll_ctl), wait (epoll_wait) returns only ready fds. Kernel red-black tree for O(log n) add/remove. Level-triggered or edge-triggered modes.
io_uring (Modern Linux)
Fully async: app submits I/O requests to SQ ring, kernel processes, posts completions to CQ ring. Zero syscall on fast path. Used in: Tokio (Rust), QEMU, PostgreSQL, Nginx.

2 Virtual memory — paging, page tables, TLB
virtual-memorypagingpage-table
Hard 88%
Virtual Memory
Each process has its own virtual address space (e.g., 0 to 2^48 on 64-bit). OS maps virtual pages → physical frames via page table. Allows: isolation between processes, overcommit memory, memory-mapped files, copy-on-write.
Multi-level Page Tables
64-bit systems use 4-level (x86-64) or 5-level page tables to reduce space. Each level is a 4KB page of 512 8-byte entries. Virtual address split:
[sign ext | L4 (9) | L3 (9) | L2 (9) | L1 (9) | Offset (12)]
TLB (Translation Lookaside Buffer)
Hardware cache for recent virtual→physical translations. TLB hit: 1 cycle. TLB miss: walk page table (several cycles + memory accesses). TLB flushed on context switch (unless ASID used). Huge pages (2MB/1GB) reduce TLB misses.
Page Fault
  • Minor: Page in memory but not mapped (memory-mapped file, copy-on-write) → map it
  • Major: Page not in memory → read from disk (swap). Expensive (~ms)
  • Invalid: Access to unmapped address → SIGSEGV

3 Deadlock — conditions, prevention, avoidance, detection
deadlockcoffmanbanker
Hard 88%
Coffman's Four Necessary Conditions
  • Mutual Exclusion: Resources not sharable
  • Hold and Wait: Process holds resource while waiting for another
  • No Preemption: Resources can't be forcibly taken
  • Circular Wait: T1→waits for T2→waits for T3→waits for T1
Breaking any one prevents deadlock.
Prevention
  • Eliminate Hold and Wait: Request all resources at once before starting
  • Allow Preemption: If waiting, release held resources (costly)
  • Eliminate Circular Wait: Global ordering of resources (always lock in same order)
Avoidance — Banker's Algorithm
Each process declares max resource claim. System checks if granting a request leaves system in safe state (all processes can complete). If unsafe → deny and wait. Used in theory; impractical for dynamic systems.
Detection and Recovery
Allow deadlocks to occur. Periodically run deadlock detector (wait-for graph cycle detection). Recovery: kill one victim process, or preempt + rollback resources.

4 Context switching — cost, what is saved/restored

What is Context Switch
OS saving state of running process/thread and restoring another's. Triggered by: timer interrupt (preemption), syscall, I/O wait, voluntary yield.
Saved State
  • CPU registers: PC (instruction pointer), SP (stack pointer), general-purpose registers, EFLAGS
  • FPU/SIMD state (optional, lazy)
  • TLB entries (or flush TLB on switch — expensive on older hardware)

  • Thread (same process): no page table switch → cheaper (~1-10μs vs ~10-100μs)

Reducing Context Switches
  • Thread pools (avoid creation overhead)
  • Async I/O / event loops (fewer threads, less switching)
  • CPU affinity (keep thread on same core → warm L1/L2 cache)
  • Lock-free algorithms (avoid blocking)

class SlidingWindowRateLimiter {
    private final int maxRequests;
    private final long windowMs;
    private final Map<String, Deque<Long>> windows = new ConcurrentHashMap<>();

    boolean allow(String clientId) {
        long now = System.currentTimeMillis();

            return true;
        }
    }

3 Design a Snowflake-style Distributed ID Generator

Hard 88%
Twitter Snowflake Structure (64-bit)
| 1 bit sign | 41 bits timestamp (ms) | 10 bits machine ID | 12 bits sequence |

- Timestamp: ms since custom epoch (Jan 1, 2010)
  → supports 2^41 ms ≈ 69 years
- Machine ID: 10 bits → 1024 machines
- Sequence: 12 bits → 4096 IDs/ms/machine

Total: ~4 million IDs/second per machine, globally unique, sortable!
Implementation
class SnowflakeIdGenerator {
    private final long EPOCH = 1288834974657L;  // Nov 4, 2010
    private final long MACHINE_ID;              // 0-1023
    private long sequence = 0;
    private long lastTs = -1;

    synchronized long nextId() {
        long ts = System.currentTimeMillis();
        if (ts == lastTs) {
            sequence = (sequence + 1) & 0xFFF;  // 12-bit mask
            if (sequence == 0) ts = waitNextMs(lastTs);  // sequence exhausted
        } else { sequence = 0; }
        lastTs = ts;
        return ((ts - EPOCH) << 22) | (MACHINE_ID << 12) | sequence;
    }

    private long waitNextMs(long ts) {
        long now = System.currentTimeMillis();
        while (now <= ts) now = System.currentTimeMillis();
        return now;
    }
}

5 Design a Circuit Breaker

Hard 86%
States
CLOSED → calls go through. OPEN → calls fail-fast (no downstream). HALF_OPEN → probe call, if succeeds → CLOSED, else → OPEN.
Full Implementation
enum State { CLOSED, OPEN, HALF_OPEN }

class CircuitBreaker {
    State state = CLOSED;
    int failCount = 0, successCount = 0;
    final int failThreshold = 5;
    final int successThreshold = 2;
    Instant openedAt;
    final Duration timeout = Duration.ofSeconds(30);
    final ReentrantLock lock = new ReentrantLock();

    <T> T call(Supplier<T> fn) {
        lock.lock(); try {
            if (state == OPEN) {
                if (Duration.between(openedAt, Instant.now()).compareTo(timeout) > 0)
                    state = HALF_OPEN;
                else throw new CircuitOpenException();
            }
        } finally { lock.unlock(); }

        try {
            T result = fn.get();
            onSuccess(); return result;
        } catch (Exception e) { onFailure(); throw e; }
    }

    void onSuccess() {
        lock.lock(); try {
            if (state == HALF_OPEN && ++successCount >= successThreshold) {
                state = CLOSED; failCount = 0; successCount = 0;
            }
        } finally { lock.unlock(); }
    }

    void onFailure() {
        lock.lock(); try {
            if (++failCount >= failThreshold || state == HALF_OPEN) {
                state = OPEN; openedAt = Instant.now(); successCount = 0;
            }
        } finally { lock.unlock(); }
    }
}

1 SQL Injection — how it works and prevention
sql-injectionprepared-statementsparameterized
Easy 92%
How it works
# Vulnerable code:
query = "SELECT * FROM users WHERE name='" + username + "' AND pwd='" + password + "'";

# Attacker input: username = admin' --
# Resulting query:
SELECT * FROM users WHERE name='admin' --' AND pwd='anything'
# -- comments out the password check → logged in as admin!

# Even worse:
username = "'; DROP TABLE users; --"
# Drops the entire users table!
Prevention
# Java PreparedStatement:
PreparedStatement stmt = conn.prepareStatement(
    "SELECT * FROM users WHERE name=? AND pwd=?");
stmt.setString(1, username);
stmt.setString(2, hashedPassword);

# Python SQLAlchemy:
result = db.execute("SELECT * FROM users WHERE name=:n", {"n": username})

# ORM (Hibernate/JPA): inherently parameterized
User user = em.createQuery("FROM User WHERE name=:n", User.class)
    .setParameter("n", username).getSingleResult();
Defense in depth
  • Least privilege DB user (SELECT only for read, no DROP)
  • WAF (Web Application Firewall) to detect patterns
  • Input validation (whitelist expected characters)
  • Error messages: never expose DB error details to client

2 JWT — structure, validation, vulnerabilities
jwtrs256alg-none
Medium 90%
JWT Structure
header.payload.signature

Header: {"alg": "RS256", "typ": "JWT"}
Payload: {"sub": "user123", "role": "admin", "exp": 1700000000, "iat": 1699996400}
Signature: RS256(base64url(header)+"."+base64url(payload), privateKey)

Verification: RS256(received_header+"."+payload, publicKey) == received_signature
Critical Vulnerabilities
  • alg:none attack: Attacker sets alg to 'none', removes signature. Old libraries accept it. Fix: whitelist allowed algorithms explicitly — NEVER accept alg from token.
  • HS256 with public key: If server uses RS256, attacker changes alg to HS256 and signs with the PUBLIC key. Server uses public key to verify HS256 = accepts! Fix: separate verify logic per algorithm.
  • Weak secret (HS256): Brute-force offline if secret is short. Use 256-bit+ random secrets.
  • Missing expiry check: Always validate exp claim.
  • Sensitive data in payload: JWT is base64 NOT encrypted. Anyone can decode it.
Best Practices
  • Use RS256 (asymmetric): private key signs, public key verifies — microservices can verify without shared secret
  • Short access token TTL (15min) + refresh token (7-30 days in HttpOnly cookie)
  • Store refresh tokens server-side for revocation capability
  • Refresh token rotation: each use issues a new refresh token

5 CSRF — Cross-Site Request Forgery attack and prevention
csrfsamesitedouble-submit
Medium 84%
How CSRF works
1. User logs into bank.com (session cookie stored)
2. User visits malicious.com
3. malicious.com has hidden form:
   <form action="https://bank.com/transfer" method="POST">
     <input name="to" value="attacker"/>
     <input name="amount" value="10000"/>
   </form>
   <script>document.forms[0].submit();</script>
4. Browser sends POST to bank.com with session cookie
5. Bank.com sees valid session → transfers money!
Prevention
  • SameSite cookie attribute: SameSite=Strict (never cross-site) or SameSite=Lax (top-level GET allowed). Modern browsers default to Lax.
  • CSRF Token: Server generates random token per session. Client includes in all state-changing requests. Server validates. Attacker can't read token from different origin.
  • Double-Submit Cookie: Token in both cookie and request body/header. Server checks they match.
  • Custom Request Header: X-Requested-With: XMLHttpRequest. Cross-origin forms can't set custom headers.
CSRF vs XSS
XSS: inject script into target site. CSRF: trick user's browser to make authenticated request. XSS bypasses CSRF protection (can read CSRF token).

7 Password hashing — bcrypt vs Argon2 vs PBKDF2
bcryptargon2password-hashing
Medium 82%
Why not MD5/SHA?
MD5/SHA are fast → GPU can try billions/sec. Rainbow table: precompute hash for common passwords.
Password Hashing Algorithms
  • bcrypt: Work factor (cost). Each increment doubles computation. Built-in 128-bit salt. Memory-light (can be GPU-accelerated). Widely supported.
  • Argon2 (winner of Password Hashing Competition 2015): Memory-hard. Three variants: Argon2i (side-channel resistant), Argon2d (GPU-resistant), Argon2id (recommended — hybrid). Parameters: time, memory, parallelism.
  • PBKDF2: NIST/FIPS approved. Iterations + HMAC. Less memory-hard than Argon2. Required for some compliance frameworks.
  • scrypt: Memory-hard. Used by Litecoin. Harder to tune than Argon2.
Best Practices
# Python — Argon2
from argon2 import PasswordHasher
ph = PasswordHasher(time_cost=2, memory_cost=65536, parallelism=2)
hash = ph.hash("user_password")      # store this
ph.verify(hash, "input_password")    # True/False

# Spring Security (bcrypt strength 12):
PasswordEncoder encoder = new BCryptPasswordEncoder(12);
String hash = encoder.encode(rawPassword);
encoder.matches(rawPassword, hash);  // timing-safe comparison
