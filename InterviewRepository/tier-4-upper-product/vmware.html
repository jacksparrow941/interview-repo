1 Smart pointers: unique_ptr, shared_ptr, weak_ptr
smart-pointersraiimemory
Medium 92%
Smart Pointer Types
  • unique_ptr: Exclusive ownership. Non-copyable, move-only. Zero overhead vs raw pointer. Use as default for heap objects.
  • shared_ptr: Shared ownership via reference count. Thread-safe refcount (atomic). Overhead: control block allocation + atomic ops.
  • weak_ptr: Non-owning observer of shared_ptr. Breaks circular references. Must lock() before use — returns shared_ptr (empty if object deleted).
Code Examples
auto up = std::make_unique<Widget>();     // unique_ptr
auto sp = std::make_shared<Widget>();     // shared_ptr (single allocation)
std::weak_ptr<Widget> wp = sp;             // weak_ptr
if (auto spt = wp.lock()) { spt->use(); } // safe access

// Cycle breaking:
struct Node { std::weak_ptr<Node> parent; std::shared_ptr<Node> children; };
Custom Deleter
unique_ptr<FILE, decltype(&fclose)> f(fopen("x","r"), fclose);
Follow-ups
• Why prefer make_shared over shared_ptr(new T)? (single allocation for object+control block)
• What is enable_shared_from_this and when do you need it?
• When would you still use a raw pointer?

2 Explain RAII
raiiexceptionsresource
Medium 87%
RAII — Resource Acquisition Is Initialization
Resource lifetime is bound to object lifetime. Acquire in constructor, release in destructor. Guarantees release even on exceptions (stack unwinding calls destructors).
Examples
class FileGuard {
    FILE* f;
public:
    explicit FileGuard(const char* path) : f(fopen(path, "r")) {
        if (!f) throw std::runtime_error("open failed");
    }
    ~FileGuard() { if (f) fclose(f); }  // always runs
    // Delete copy; use move only
    FileGuard(const FileGuard&) = delete;
    FileGuard& operator=(const FileGuard&) = delete;
};

// RAII wrappers: lock_guard, unique_lock, ifstream, unique_ptr, jthread
Why it matters
Without RAII: every error path must manually release resources → leak-prone. With RAII: destructor always called → exception-safe, leak-free.

• How does RAII differ from finally blocks in Java/Python?
• What is the ScopeGuard pattern?
• How does RAII interact with noexcept?

3 Move semantics — rvalue references, std::move, std::forward
move-semanticsrvalueforward
Hard 86%
Rvalue References
int&& r = 42;           // rvalue reference: binds to temporaries
void take(std::string&& s); // accepts rvalue (temporary)

std::string s = "hello";
take(std::move(s));    // cast to rvalue (s is now valid-but-unspecified)
take("world");         // temporary: OK
std::move
Cast to rvalue reference — enables move constructor/assignment to be called. After move, source is in valid but unspecified state. Do NOT use moved-from object except to assign or destroy.
std::forward — Perfect Forwarding
// Forward preserves value category (lvalue stays lvalue, rvalue stays rvalue)
template<typename T, typename... Args>
T* create(Args&&... args) {
    return new T(std::forward<Args>(args)...);
}
// If passed lvalue → forwards as lvalue
// If passed rvalue → forwards as rvalue
Universal Reference
T&& in a template (deduced context) is a universal/forwarding reference, not an rvalue reference. With T=int&, T&& collapses to int& (reference collapsing).

5 How does vtable work?
vtablevirtualpolymorphism
Hard 82%
vtable Mechanism
For each class with virtual functions, compiler generates a vtable — a static array of function pointers. Each object has a hidden vptr pointing to its class's vtable (set in constructor).
Virtual Dispatch
class Animal {
public:
    virtual void sound() { printf("..."); }
    virtual ~Animal() {}
};
// vtable_Animal = { &Animal::sound, &Animal::~Animal }

class Dog : public Animal {
    void sound() override { printf("Bark"); }
};
// vtable_Dog = { &Dog::sound, &Dog::~Dog }

Animal* a = new Dog();
a->sound();  // a->vptr -> vtable_Dog[0] = Dog::sound() → "Bark"
Costs
  • Memory: 1 vptr per object (8 bytes on 64-bit)
  • Time: extra pointer indirection per call (cache miss possible)
  • No inlining: compiler can't inline virtual calls (mostly)
  • Final keyword: hints compiler to devirtualize
Follow-ups
• What is devirtualization and when does the compiler perform it?
• How does CRTP achieve static polymorphism without vtable overhead?
• Why is virtual destructor needed in base classes?

6 Rule of 0, Rule of 3, Rule of 5 — explain with examples
rule-of-3rule-of-5move
Hard 82%
Rule of 3 (pre-C++11)
If you define any of: destructor, copy constructor, copy assignment, you should define all three. (Managing raw resource → need custom copy + destructor)
Rule of 5 (C++11+)
Add move constructor + move assignment. Without them, moves fall back to copies (expensive).
class Buffer {
    char* data; size_t sz;
public:
    Buffer(size_t n) : data(new char[n]), sz(n) {}
    ~Buffer() { delete[] data; }               // 1: destructor
    Buffer(const Buffer& o)                   // 2: copy ctor
        : data(new char[o.sz]), sz(o.sz) { memcpy(data,o.data,sz); }
    Buffer& operator=(const Buffer& o) {       // 3: copy assign
        if(this==&o) return *this;
        delete[] data; sz=o.sz; data=new char[sz]; memcpy(data,o.data,sz); return *this;
    }
    Buffer(Buffer&& o) noexcept                // 4: move ctor
        : data(o.data), sz(o.sz) { o.data=nullptr; o.sz=0; }
    Buffer& operator=(Buffer&& o) noexcept {   // 5: move assign
        if(this==&o) return *this;
        delete[] data; data=o.data; sz=o.sz; o.data=nullptr; return *this;
    }
};
Rule of 0
Best practice: design classes to own no raw resources. Use RAII wrappers (unique_ptr, vector, string). Then you need ZERO custom special members — compiler generates correct ones.

• What is the copy-and-swap idiom?
• When is a move constructor marked noexcept important?

7 std::condition_variable — producer-consumer pattern
condition-variablemutexnotify
Medium 78%
Full Producer-Consumer
#include <mutex>
#include <condition_variable>
#include <queue>

std::mutex mtx;
std::condition_variable cv;
std::queue<int> q;
bool done = false;

void producer() {
    for(int i=0;i<10;i++) {
        std::unique_lock lock(mtx);
        q.push(i);
        cv.notify_one();  // wake one consumer
    }
    { std::lock_guard lock(mtx); done=true; }
    cv.notify_all();
}

void consumer() {
    while(true) {
        std::unique_lock lock(mtx);
        cv.wait(lock, []{ return !q.empty() || done; });  // predicate prevents spurious wakeup
        while(!q.empty()) { process(q.front()); q.pop(); }
        if(done) break;
    }
}
Spurious Wakeups
Always use cv.wait(lock, predicate) — without predicate, spurious wakeups cause bugs. Equivalent to: while(!pred()) cv.wait(lock);
notify_one vs notify_all
notify_one: wake 1 waiter (use for single-consumer or rotating consumers). notify_all: wake all waiters (use for broadcast events like shutdown).
Follow-ups
• What is std::condition_variable_any?
• Why must you always hold the mutex when calling notify?

8 unique_lock vs lock_guard vs scoped_lock
lock-guardunique-lockscoped-lock
Medium 76%
lock_guard (C++11)
Simplest RAII wrapper. Locks on construction, unlocks on destruction. Cannot be unlocked/relocked. Cannot be moved. Use when you need a simple lock for a scope.
std::lock_guard<std::mutex> lock(m);
unique_lock (C++11)
More flexible. Can unlock/relock, deferred locking, timed locking. Required for condition_variable.
std::unique_lock lock(m, std::defer_lock);  // don't lock yet
lock.lock();        // lock later
lock.unlock();      // unlock early
bool got = lock.try_lock_for(100ms);  // timed
scoped_lock (C++17)
Locks multiple mutexes atomically without deadlock (uses deadlock-free algorithm). Replaces std::lock(m1,m2) + lock_guard(adopt) pattern.
std::scoped_lock lock(m1, m2, m3); // all or nothing
When to use
  • lock_guard: simple scope lock, no condition_variable
  • unique_lock: condition_variable, deferred/timed locking, early unlock
  • scoped_lock: locking 2+ mutexes, avoiding deadlock
Follow-ups
• How does scoped_lock prevent deadlock? (std::lock uses try-lock backoff)
• What is std::adopt_lock and std::defer_lock?

10 std::string_view vs std::string — performance implications
string-viewnon-owningzero-copy
Easy 75%
std::string_view
A non-owning, read-only view into a character sequence. No heap allocation. Just a pointer + length. O(1) construction from any string-like object.
Performance Comparison
// Bad: copies string for each call
void log(std::string msg);

// Good: zero-copy read
void log(std::string_view msg);

// Works with: string, const char*, string literals, substrings
log("hello");         // no alloc
log(user_string);    // no alloc
log(str.substr(0,5)); // DANGER: substr returns string, but view is valid

// Safe substring (zero-copy):
log(std::string_view(str).substr(0, 5));
Dangers
  • Dangling reference if underlying string is destroyed
  • Not null-terminated (can't pass to C APIs directly)
  • Don't store string_view as a class member if source may outlive it

std::optional<T>
Represents a value that may or may not be present. Replaces nullable pointers and sentinel values.
std::optional<User> findUser(int id);

std::variant<T1,T2,...>
Type-safe union. Holds exactly one of a fixed set of types.
std::variant<int, double, std::string> v = 42;

    [](int i)   { cout << "int: " << i; },

Holds any type at runtime (type-erased). Use std::any_cast. Performance overhead: heap allocation for large objects. Use sparingly.
When to use

  • variant: Known set of alternatives (Result type, AST nodes, event types)
  • any: Truly unknown type at compile time (config maps, plugin systems)

14 What is the PIMPL idiom and why use it?
pimplcompilation-firewallbinary-compatibility
Medium 72%
PIMPL = Pointer to IMPLementation
Hide implementation details behind a pointer. Reduces compilation dependencies and enables ABI stability.
Example
// widget.h (public header)
class Widget {
    struct Impl;  // forward declaration
    std::unique_ptr<Impl> pImpl;
public:
    Widget();
    ~Widget();  // must be defined where Impl is complete
    void draw();
};

// widget.cpp
struct Widget::Impl { /* all private data here */ int x, y; SDL_Surface* surf; };
Widget::Widget() : pImpl(std::make_unique<Impl>()) {}
void Widget::draw() { /* use pImpl->x */ }
Benefits
  • Compilation firewall: header changes don't propagate to all users
  • ABI stability: adding private members doesn't break binary compatibility
  • Encapsulation: private data truly hidden
Costs
Extra heap allocation, one level of indirection, requires explicit dtor definition.
Follow-ups
• How does PIMPL affect move semantics?
• What is the fast PIMPL (in-place storage)?
• Compare to using abstract interface (pure virtual).

15 Virtual inheritance and the diamond problem
virtual-inheritancediamondmultiple-inheritance
Hard 72%
Diamond Problem
struct A { int x; };
struct B : A {};
struct C : A {};
struct D : B, C {};   // D has TWO copies of A!
D d;
d.x = 5;              // Error: ambiguous — B::A::x or C::A::x?
Virtual Inheritance Fix
struct A { int x; };
struct B : virtual A {};
struct C : virtual A {};
struct D : B, C {};   // Only ONE shared A
D d; d.x = 5;         // OK: unambiguous
How it works
With virtual inheritance, B and C each store a virtual base pointer (vbptr) pointing to the shared A subobject. D's constructor directly initializes A.
Cost
Extra pointer per virtual base. More complex object layout. dynamic_cast needed for cross-casting. Avoid in performance-critical code.
Follow-ups
• Who initializes the virtual base in the most-derived class?
• What is object slicing in virtual inheritance?
• How does virtual inheritance affect sizeof?

1 Process vs Thread vs Goroutine
processthreadgoroutine
Medium 90%
Processes vs Threads
  • Process: Independent address space, separate heap/stack/code/data. Isolated — one process crash doesn't affect others. IPC needed (pipes, sockets, shared memory).
  • Thread: Shares address space (heap, code, global data) with other threads in same process. Has own stack + registers. Cheaper to create/switch than process. Direct memory sharing.
Context Switch Cost
  • Process switch: save/restore full CPU state + page table switch (TLB flush) → ~100μs
  • Thread switch (same process): save/restore registers, stack pointer. No TLB flush → ~1-10μs
  • Goroutine/fiber switch: userspace, ~100ns
Linux Internals
Both processes and threads are task_struct in Linux kernel. Threads created with CLONE_VM flag — share address space. fork() creates new address space.
Follow-ups
• What is a zombie process?
• What is the difference between fork() and vfork()?
• How do Python GIL and threads interact?

2 Context switching — what and cost
context-switchcachetlb
Medium 86%
Scheduling Algorithms
  • FCFS: Non-preemptive. Convoy effect (short jobs wait behind long ones).
  • SJF: Shortest job first. Optimal average wait time. Requires knowing burst time.
  • Round Robin: Time quantum (10-100ms). Fair. High throughput for interactive tasks.
  • Priority Scheduling: Highest priority runs first. Risk of starvation (aging fixes this).
  • CFS (Linux): Virtual runtime. Always runs goroutine with minimum vruntime. Weighted fair sharing.
  • MLFQ: Multiple queues with decreasing priority + aging. Adapts to CPU vs I/O bound behavior.
Preemptive vs Non-Preemptive
Preemptive: OS can force context switch (timer interrupt). Necessary for interactive systems. Non-preemptive: process runs until done or blocks. Simpler but poor interactivity.
Follow-ups
• What is starvation and how does aging solve it?
• How does Linux CFS handle I/O-bound vs CPU-bound processes?
• What is the difference between preemptive priority scheduling and non-preemptive?

3 Mutex vs Semaphore vs Spinlock
mutexsemaphorespinlock
Medium 84%
Synchronization Primitives
  • Mutex (Mutual Exclusion): Binary lock. Owner must release. Sleeping lock — blocked thread sleeps, woken by OS. Priority inversion risk.
  • Semaphore: Counter (0..N). Binary semaphore ≈ mutex but no ownership. Counting semaphore for resource pools (N available resources).
  • Spinlock: Busy-wait loop checking flag. No context switch. Great for very short critical sections (kernel code). Wastes CPU if held long.
  • Condition Variable: Wait + signal pattern. Used WITH mutex (monitor). Always use predicate loop (spurious wakeups).
Futex (Linux)
Fast Userspace muTEX. Fast path: atomic CAS in userspace (no syscall). Slow path (contended): syscall to sleep. Basis for pthreads mutex and Java's synchronized.

• What is priority inversion and how does Mars Pathfinder demonstrate it?
• What is a recursive mutex and when do you need it?

4 Virtual memory and page tables
virtual-memorypagingmmu
Hard 83%
Page Replacement Algorithms
  • OPT (Optimal): Replace page that won't be used for longest time. Theoretical baseline.
  • FIFO: Evict oldest loaded page. Simple. Belady's anomaly (more frames → more faults).
  • LRU: Evict least recently used. Approximates OPT well. Expensive exact tracking.
  • Clock (LRU approximation): Circular list. Reference bit: on access set to 1, on clock hand pass clear to 0, evict when 0. Linux uses clock-PRO.
  • LFU: Evict least frequently used. Doesn't adapt to recent access pattern changes.
Working Set
Set of pages currently needed by process. If working set > available frames → thrashing (process spends more time swapping than executing). OS monitors WSS, suspends processes if needed.
Follow-ups
• What is Belady's anomaly? (FIFO gets more page faults with more frames)
• How does Linux implement page replacement? (kswapd, active/inactive lists)
• What is the difference between paging and segmentation?

1 How does CPU caching work and why does it matter for performance?
cpu-cachecache-linefalse-sharing
Hard 74%
Memory Hierarchy
L1 cache:  ~32KB per core,   ~1ns  latency
L2 cache: ~256KB per core,   ~4ns  latency
L3 cache:   ~8MB shared,     ~40ns latency
RAM:        ~16-64GB,       ~100ns latency
SSD NVMe:              ~100μs latency
HDD:                    ~10ms latency
Cache Lines
Data loaded in 64-byte cache lines. Accessing one byte loads entire 64-byte block. Sequential access (arrays) → excellent cache utilization. Random access (linked lists) → cache miss per node.
False Sharing
# Two threads update different variables in same cache line:
# Thread 1 updates counter_a, Thread 2 updates counter_b
# If they're adjacent in memory → same cache line → cache coherence traffic
# Core 1 invalidates Core 2's cache line on every write → performance degrades!

# Fix: padding
struct PaddedCounter {
    alignas(64) std::atomic<int64_t> value;  // 64-byte aligned
    char padding[64 - sizeof(std::atomic<int64_t>)];  // fill rest of cache line
};
Practical Impact
  • Array of structs vs Struct of arrays (SOA): SOA = better cache usage for column-wise processing
  • Cache-oblivious algorithms (recursive divide) beat sequential for large matrices
  • Go: sync.Mutex padded to avoid false sharing with adjacent data
Follow-ups
• What is NUMA (Non-Uniform Memory Access) and how does it affect multi-socket servers?
• How does prefetching work and how can you hint the CPU to prefetch?
• What is the impact of cache misses on a tight loop processing 100M integers?
