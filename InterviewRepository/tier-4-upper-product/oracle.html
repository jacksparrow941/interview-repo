1 ACID properties
acidtransactions
Easy 93%
Indexes — Types and Internals
  • B+ Tree: Default in PostgreSQL/MySQL. O(log n) for equality and range queries. Leaf nodes form linked list for range scans.
  • Hash Index: O(1) for equality only. No range queries. Used in memory engines (MEMORY in MySQL).
  • GiST/GIN: PostgreSQL generalized indexes for full-text search, JSONB, arrays.
  • Bitmap Index: Low-cardinality columns. Efficient AND/OR on multiple conditions.
Clustered vs Secondary
  • Clustered (InnoDB Primary Key): Data physically stored in index order. Range scans very fast. Only 1 per table.
  • Secondary: Leaf stores primary key value → extra lookup for full row. Covering index eliminates this lookup.
Index Design Tips
  • Composite index: equality columns first, range columns last, ORDER BY columns last
  • Cover frequently queried columns with INCLUDE
  • Partial index for low-cardinality: WHERE status='PENDING'
  • Avoid index on frequently updated columns (write overhead)

• How does an index affect INSERT/UPDATE/DELETE performance?

3 B+ Tree index internals — structure, splits, range queries
b-plus-treeindexrange-query
Hard 88%
Structure
  • Internal nodes: keys only, no data. Fan-out typically 100-200 keys per node.
  • Leaf nodes: keys + actual row pointers (or clustered data). Linked list for range scans.
  • Height: ~3-4 levels for millions of rows (log_200(1M) ≈ 3). Fits in memory.
Why B+ over B-Tree
All data in leaves → range queries traverse leaf linked list without backtracking. Internal nodes store more keys (no data) → wider fan-out → shallower tree.
Operations
  • Search: O(log_t n) — traverse from root to leaf
  • Insert: find leaf, insert, split if overflow (cascade up)
  • Delete: find leaf, remove, merge or redistribute if underflow
  • Range scan: find start leaf, traverse linked list → sequential I/O (fast)
Clustered vs Secondary
Clustered: Data rows stored in leaf nodes in index order (InnoDB primary key). One per table.
Secondary: Leaf stores PK value → extra lookup for row data. Multiple allowed.

4 Read replicas — replication lag, use cases, consistency
replicationreplica-lagread-replica
Hard 88%
Replication Mechanics (MySQL binlog / PostgreSQL WAL)
Primary records every write as binary log events. Replica connects, streams binlog, applies changes. Replication can be:
  • Async (default): Primary doesn't wait for replica. Replica may lag.
  • Semi-sync: Primary waits for at least 1 replica to acknowledge before committing.
  • Sync (PostgreSQL synchronous_commit=on): All replicas acknowledge. Highest durability, slowest.
Replication Lag Causes
  • Large transactions (long to replay)
  • High write throughput on primary
  • Network latency between primary and replica
  • Single-threaded replay (older MySQL — use parallel replication)
Handling Lag in Applications
  • Read-your-own-writes: route reads after writes to primary for 1s, or use session stickiness
  • For stale-tolerant reads (reports, analytics): use replica
  • Monitor lag: SHOW REPLICA STATUS → Seconds_Behind_Source
Follow-ups
• What is GTID-based replication?
• How does logical replication differ from physical replication?
• What is PgBouncer and what problem does it solve?

5 SQL query optimization — indexes, covering indexes, composite indexes
indexcovering-indexcomposite
Medium 88%
Composite Index Column Order
-- Query: WHERE a = 1 AND b > 5 ORDER BY c
-- Best index: (a, b, c) — leftmost prefix rule
-- a → equality filter (most selective first)
-- b → range filter
-- c → ORDER BY (eliminates sort)

-- Index (b, a) won't use b for range + a for equality efficiently
Covering Index
Index includes all columns needed by query — no heap lookup.
-- Query:
SELECT email FROM users WHERE user_id = 42;

-- If index is (user_id, email): Index Only Scan — never touches table!
CREATE INDEX idx_user_email ON users(user_id) INCLUDE (email);  -- PostgreSQL
Index Selectivity
High selectivity (few rows per value) = good for index. Low selectivity (boolean, gender) = index often not used. n_distinct in pg_stats shows estimate. Use partial index for low-selectivity cases:
CREATE INDEX ON orders(status) WHERE status = 'PENDING';
Anti-patterns
  • SELECT * prevents covering index
  • Function on indexed column: WHERE LOWER(email) = ... → can't use index. Use functional index.
  • Leading % in LIKE: WHERE name LIKE '%Smith' → full scan. Use full-text search or reverse index.
  • Implicit type cast: WHERE varchar_col = 123 → type mismatch → seq scan
Follow-ups
• What is an index bloat and how do you fix it?
• When does PostgreSQL ignore an index? (planner cost estimate)

6 Database isolation levels
isolationmvccphantom
Hard 87%
ACID Properties
  • Atomicity: All operations in transaction succeed or all are rolled back. No partial updates.
  • Consistency: Transaction brings DB from one valid state to another. Constraints never violated.
  • Isolation: Concurrent transactions behave as if sequential. Anomalies depend on isolation level.
  • Durability: Committed transactions survive crashes. Guaranteed by WAL.
Isolation Levels & Anomalies
READ UNCOMMITTED: dirty read allowed (see uncommitted data)
READ COMMITTED:  no dirty read | phantom read possible
REPEATABLE READ: no dirty/non-repeatable read | phantom possible (MySQL: solved by gap locks)
SERIALIZABLE:   full isolation, slowest — SSI (PostgreSQL) or locking (MySQL)
How Implemented
PostgreSQL: MVCC for Repeatable Read and below. Serializable: SSI (Serializable Snapshot Isolation). MySQL InnoDB: row-level locking + MVCC + gap locks for Repeatable Read.
Follow-ups
• What is a phantom read and how do gap locks prevent it?
• What is lost update anomaly?

7 EXPLAIN ANALYZE — reading query execution plans
explainquery-planseq-scan
Medium 86%
Key Operations
  • Seq Scan: Full table scan. Fast for small tables / low selectivity.
  • Index Scan: Uses B+ tree index. Best for high selectivity (<10% rows).
  • Index Only Scan: All needed columns in index (covering index). Fastest.
  • Bitmap Heap Scan: Index scan → bitmap of pages → sorted page access. Good for 5-20% rows.
  • Nested Loop: Join — for each outer row, find matching inner. Good for small outer result.
  • Hash Join: Build hash table from smaller table → probe with larger. Good for large unsorted.
  • Merge Join: Both sides sorted. Fast but needs sort step.
Reading EXPLAIN
EXPLAIN ANALYZE SELECT * FROM orders WHERE user_id = 42;

-> Index Scan using idx_orders_user on orders
   Index Cond: (user_id = 42)
   rows=150 (estimated)  rows=143 (actual)
   Buffers: shared hit=12  (pages from cache)
   Planning: 0.3ms  Execution: 2.1ms
Tuning Signals
  • Seq scan on large table with high selectivity → missing index
  • Estimated rows ≫ actual → stale statistics → run ANALYZE
  • Sort in plan → add index with ORDER BY columns
  • Hash join with large table → may need work_mem increase
Follow-ups

9 Database partitioning strategies — range, hash, list
partitioningrangehash
Hard 84%
Range Partitioning
Divide by value range. Common for time-series data.
CREATE TABLE orders (id bigint, created_at date, ...)
PARTITION BY RANGE (created_at);

CREATE TABLE orders_2023 PARTITION OF orders
    FOR VALUES FROM ('2023-01-01') TO ('2024-01-01');
CREATE TABLE orders_2024 PARTITION OF orders
    FOR VALUES FROM ('2024-01-01') TO ('2025-01-01');
Pruning: WHERE created_at >= '2024-01-01' → only scans 2024 partition.
Hash Partitioning
Distribute evenly by hash of key. Good for write distribution.
PARTITION BY HASH (user_id);
-- Partition 0: user_id % 4 = 0
-- Partition 1: user_id % 4 = 1 ...
List Partitioning
By enumerated values. Good for geographic/categorical data.
PARTITION BY LIST (region);
-- India: ('IN'), US: ('US','CA')
Benefits
  • Partition pruning: query only relevant partition
  • Faster VACUUM, index maintenance (smaller partitions)
  • Easy archival: DETACH PARTITION orders_2022
Partitioning vs Sharding
Partitioning: single database, multiple internal tables. Sharding: multiple databases, data split across machines. Sharding requires application-level routing.

10 Connection pooling — PgBouncer, HikariCP, patterns
connection-poolpgbouncerhikaricp
Medium 84%
Why Pool Connections
PostgreSQL creates a new OS process per connection (~5-10MB RAM). Opening connection takes ~30-100ms. 1000 connections = 5-10GB RAM, GC overhead, scheduler pressure.
PgBouncer
Lightweight connection pooler for PostgreSQL. Sits between app and DB.
  • Session mode: App gets same DB connection for session duration. All features work.
  • Transaction mode: Connection returned to pool after each transaction. Supports many more app connections (1000s) with few DB connections (50). Restrictions: no SET, no prepared statements per session.
  • Statement mode: Return after each statement. Most restrictive.
HikariCP (Java)
Fast JDBC connection pool.
HikariConfig cfg = new HikariConfig();
cfg.setJdbcUrl("jdbc:postgresql://host/db");
cfg.setMaximumPoolSize(10);
cfg.setConnectionTimeout(30000);
cfg.setIdleTimeout(600000);
cfg.setMaxLifetime(1800000);  // 30min to prevent stale conns
DataSource ds = new HikariDataSource(cfg);
Sizing
Pool size = (core_count × 2) + effective_spindle_count. Smaller than you think — more connections ≠ more throughput.

12 PostgreSQL MVCC — how it achieves non-blocking reads
mvccpostgresqlsnapshot
Hard 82%
MVCC = Multi-Version Concurrency Control
Each row has hidden columns:
  • xmin: transaction ID that inserted this version
  • xmax: transaction ID that deleted/updated this version (0 = still live)
Reads see a snapshot: only versions where xmin ≤ snapshot_xid < xmax.
How it works
T1 (xid=100): UPDATE users SET name='Bob' WHERE id=1
→ Old row: xmin=50, xmax=100  (now dead to T1)
→ New row: xmin=100, xmax=0   (live)

T2 (xid=99, started before T1):
→ Sees old row (xmin=50 <= 99 < xmax=100) ✓
→ Sees 'Alice' — no blocking!

T3 (xid=101, started after T1 commits):
→ Old row: xmax=100 <= 101 → dead, skip
→ New row: xmin=100 <= 101, xmax=0 → live, sees 'Bob' ✓
VACUUM
Dead rows (old versions) accumulate. VACUUM reclaims space. AUTOVACUUM runs automatically. Transaction ID wraparound prevented by freezing old rows.

13 Database deadlocks — detection, prevention, resolution
deadlocklockwait-for-graph
Hard 82%
What is a Deadlock
Two or more transactions each hold a lock the other needs.
T1: LOCK A → wait for B
T2: LOCK B → wait for A
→ Circular wait = deadlock
Deadlock Detection
Most DBs run a background detector (PostgreSQL, MySQL InnoDB).
Builds a wait-for graph: node = transaction, edge = T1 waits for lock held by T2. Cycle = deadlock → kill victim transaction (least expensive to rollback).
Prevention Strategies
  • Lock ordering: Always acquire locks in the same global order (e.g., lower ID first)
  • Timeout: SET lock_timeout = '1s' — transaction aborts if wait too long
  • SELECT FOR UPDATE SKIP LOCKED: Skip locked rows instead of waiting (job queues)
  • Reduce transaction scope: Short transactions hold locks briefly
Application-Level Fix
-- Instead of long transaction:
BEGIN;
  UPDATE account SET bal = bal - 100 WHERE id = 1;  -- locks row
  -- ... complex computation (seconds) ...
  UPDATE account SET bal = bal + 100 WHERE id = 2;  -- deadlock risk!
COMMIT;

-- Better: do computation outside transaction, then short UPDATE
Follow-ups
• What is the difference between a deadlock and a livelock?
• How does SELECT FOR UPDATE NOWAIT differ from SKIP LOCKED?
• What is intention locking (IS, IX, S, X)?

14 Eventual consistency models — BASE, read-your-writes, monotonic reads
eventual-consistencybasecausal
Hard 82%
CAP Theorem Recap
In presence of network partition (P), choose between Consistency (C) or Availability (A). Most distributed systems choose AP → eventual consistency.
BASE (Basically Available, Soft state, Eventually consistent)
Contrast to ACID.
  • Basically Available: System works, even during partial failure (stale data OK)
  • Soft State: State may change without input (replication catching up)
  • Eventually Consistent: Given no new updates, all replicas converge to same state
Consistency Models (weakest to strongest)
  • Eventual: Converges eventually. DNS, S3.
  • Monotonic Read: Once you read version V, you never see older version. (client stickiness)
  • Read-Your-Writes: You always see your own writes immediately. (session token pinning)
  • Causal: If A caused B, everyone sees A before B. (vector clocks)
  • Sequential: All operations appear in a global order consistent with program order.
  • Linearizable (Strict): Strongest. Operations appear instantaneous. ZooKeeper, etcd.
Follow-ups
• How does DynamoDB implement eventual consistency vs strong consistency?
• What is quorum read/write (R + W > N)?
• What are vector clocks and how do they enable causal consistency?

16 Write-Ahead Logging (WAL) — how databases ensure durability
waldurabilityredo-log
Hard 78%
What is WAL
Before modifying data pages in memory (buffer pool), the change is written to the WAL log first. On crash: replay WAL from last checkpoint to recover committed transactions. Guarantee: committed data never lost, even on sudden crash.
Write Flow
1. Transaction modifies data in buffer pool (in-memory dirty page)
2. WAL record written to WAL buffer → flushed to disk (fsync)
   [WAL written BEFORE data page written — Write-Ahead!]
3. Transaction commits: commit WAL record flushed
4. Background: dirty pages periodically checkpointed to data files
5. WAL records before checkpoint can be deleted
PostgreSQL WAL
WAL files in pg_wal/. Controls: fsync=on (durability), synchronous_commit=on/off. Turning off synchronous_commit: ~10% faster writes, risk of last 100ms of data on crash.
Uses beyond recovery
  • Streaming replication: replicas stream WAL from primary
  • Point-in-time recovery (PITR): replay WAL to any past state
  • Logical replication: parse WAL for row-level changes (Debezium/CDC)
Follow-ups
• What is a checkpoint and why is checkpoint distance important?
• How does InnoDB redo log differ from PostgreSQL WAL?
• What is CDC (Change Data Capture) and how does it use WAL?

1 JVM memory model: heap, stack, metaspace
jvmmemorygc
Medium 92%
JVM Memory Areas
  • Heap: All objects (new). Divided into Young (Eden + 2 Survivors) + Old/Tenured. GC managed.
  • Stack: Per-thread. Holds stack frames: local variables, operand stack, method calls. Fixed size (typically 512KB-1MB). StackOverflowError if exceeded.
  • Metaspace (Java 8+): Class metadata (class bytecode, method data). Native memory, grows dynamically. Replaced PermGen which had fixed max size.
  • Code Cache: JIT-compiled native code.
  • Direct Memory: Off-heap via NIO ByteBuffer.allocateDirect(). Not GC'd, must be freed explicitly.
Tuning Flags
-Xms512m -Xmx4g       # initial and max heap
-XX:MetaspaceSize=256m # initial metaspace
-XX:MaxMetaspaceSize=512m
-Xss512k               # thread stack size

3 HashMap internals in Java 8+
hashmaptreeifycollision
Medium 90%
HashMap Internals
// Java 8+ structure:
// Node<K,V>[] table  (array of buckets, power of 2 size)
// Each bucket: null | Node (linked list) | TreeNode (red-black tree)

// Hash calculation:
static int hash(Object key) {
    int h;
    return (key == null) ? 0 : (h = key.hashCode()) ^ (h >>> 16);
    // XOR high bits into low bits — better distribution
}
// Bucket index: (n-1) & hash  (n = table length, power of 2)
Thresholds
  • TREEIFY_THRESHOLD = 8: Bucket with >8 nodes → convert to red-black tree (O(log n) per op)
  • UNTREEIFY_THRESHOLD = 6: Tree shrinks back to list on removal
  • LOAD_FACTOR = 0.75: Resize (double) when size/capacity > 0.75
Thread Safety
HashMap is NOT thread-safe. Use ConcurrentHashMap (lock-striping, CAS) or Collections.synchronizedMap() (coarse lock).
Follow-ups
• What is the time complexity of get() in worst case? O(log n) with tree buckets
• Why XOR high bits into low bits in hash()? (prevents collision when table size is small)
• What is the difference between HashMap.keySet() and EntrySet iteration performance?

4 HashMap vs LinkedHashMap vs TreeMap internals
hashmaplinkedhashmaptreemap
Medium 84%
HashMap
Array of Node<K,V> buckets. Hash → index via (n-1) & hash. Collision: linked list, then treeify at threshold 8 (TREEIFY_THRESHOLD). Resize (double) at 75% load factor. Java 8: balanced BST (TreeNode) for long chains.
LinkedHashMap
Extends HashMap. Adds doubly-linked list through all entries maintaining insertion order. Can be configured for access order (LRU behaviour) with constructor parameter.
// LRU Cache using LinkedHashMap
Map<K,V> lru = new LinkedHashMap<>(16, 0.75f, true) {  // accessOrder=true
    protected boolean removeEldestEntry(Map.Entry<K,V> e) {
        return size() > capacity;
    }
};
TreeMap
Red-Black tree. Keys always sorted (natural order or Comparator). O(log n) get/put/remove. Extra operations: floorKey, ceilingKey, headMap, tailMap, subMap.
Quick Comparison
  • HashMap: O(1) avg, unordered, null key/values allowed
  • LinkedHashMap: O(1) avg, insertion/access ordered, LRU capable
  • TreeMap: O(log n), sorted, no null key
Follow-ups
• What is HashMap's initial capacity and load factor trade-off?
• Why is String a good HashMap key? (immutable, cached hashCode)

7 Hibernate L1 and L2 cache — how they work
hibernatecachel1
Medium 76%
L1 Cache (Session Cache)
Default, always on. Scoped to a single Session (transaction). Within a session, the same entity loaded twice returns the same object (identity map). Cleared on session.close() or session.clear().
L2 Cache (Shared Cache)
Optional, cross-session. Shared across all sessions in a SessionFactory. Must be explicitly configured. Providers: Ehcache, Caffeine, Infinispan, Redis.
L2 Setup
# application.properties
spring.jpa.properties.hibernate.cache.use_second_level_cache=true
spring.jpa.properties.hibernate.cache.region.factory_class=\
    org.hibernate.cache.jcache.JCacheRegionFactory

# Entity
@Entity
@Cache(usage = CacheConcurrencyStrategy.READ_WRITE)
public class Product { ... }
Query Cache
Cache for JPQL/HQL query results. Must also have L2 enabled. Stores primary keys, not entities. Invalidated when any entity in result changes.
Cache Strategies
READ_ONLY, NONSTRICT_READ_WRITE, READ_WRITE, TRANSACTIONAL

9 Java ClassLoader hierarchy and how class loading works
classloaderbootstrapdelegation
Hard 76%
ClassLoader Hierarchy
  • Bootstrap ClassLoader: Loads JDK core classes (java.lang, java.util) from rt.jar/modules. C++ code, no Java object.
  • Platform ClassLoader (was Extension): Loads java.se, java.xml etc.
  • Application ClassLoader: Loads from classpath (your app + third-party JARs).
  • Custom ClassLoaders: hot-deploy, OSGi, isolation (one classloader per plugin).
Delegation Model
When loading class X: check cache → delegate to parent → parent delegates to its parent → reach Bootstrap → if not found, child tries to load itself → ClassNotFoundException if all fail.
Class Identity
Same class name loaded by different ClassLoaders = different classes. ClassCastException when assigning across loaders. Root of hot-deploy complexity.
Custom ClassLoader
class HotLoader extends ClassLoader {
    @Override
    protected Class<?> findClass(String name) throws ClassNotFoundException {
        byte[] bytes = readBytesFromFile(name);
        return defineClass(name, bytes, 0, bytes.length);
    }
}

10 Java GC algorithms — Mark-Sweep, Mark-Compact, Copying, Generational
gc-algorithmsmark-sweepgenerational
Hard 76%
Mark-Sweep
Mark: traverse GC roots, mark all reachable objects. Sweep: scan heap, free unmarked objects. Problem: fragmentation — free spaces scattered.
Mark-Compact
Mark phase same. Compact phase: slide all live objects to one end. No fragmentation. Slower than sweep (extra copy). G1GC uses this for selected regions.
Copying Collection
Divide heap into From/To spaces. Copy live objects to To, flip spaces. No fragmentation, fast allocation (bump pointer). Wastes 50% of heap. Used for young generation.
Generational Hypothesis
Most objects die young. Java heap split:
  • Young (Eden + 2 Survivors): Minor GC — fast, copying collector
  • Old (Tenured): Major/Full GC — mark-compact or concurrent marking
Promotion: object surviving N minor GCs (default 15) moves to Old gen.
G1GC
Divides heap into equal regions (~1-32MB). Marks concurrently. Selects regions with most garbage (Garbage-First) for collection. Pause target: -XX:MaxGCPauseMillis=200.

What is Reactive Programming
Non-blocking, event-driven programming with backpressure. Publisher emits data only as fast as subscriber can consume.
Project Reactor Types
  • Mono<T> — 0 or 1 element (like CompletableFuture)
  • Flux<T> — 0 to N elements (stream)
Example
// Blocking (Spring MVC)
@GetMapping("/user/{id}")
public User getUser(@PathVariable Long id) {
    return userService.findById(id);  // blocks thread!
}

// Reactive (Spring WebFlux)
@GetMapping("/user/{id}")
public Mono<User> getUser(@PathVariable Long id) {
    return userService.findById(id)  // non-blocking Mono
        .map(UserDto::from)
        .switchIfEmpty(Mono.error(new NotFoundException()));
}

  • High-concurrency I/O bound workloads (thousands of concurrent connections)
  • Streaming data (SSE, WebSocket)
  • Avoid: CPU-bound work, blocking libraries (use bounded elastic scheduler)

Region-based collector. Divides heap into equal regions (~1-32MB). Concurrent marking + stop-the-world compaction of selected regions. Target: balance throughput with pause goals.

13 Java NIO — Channels, Buffers, Selectors (non-blocking I/O)
niochannelbuffer
Hard 74%
NIO vs Old IO
  • Old IO (java.io): Stream-based, blocking, thread-per-connection
  • NIO (java.nio): Buffer-based, non-blocking, multiplexed via Selector
Key Components
  • Buffer: Fixed-size data container (ByteBuffer, IntBuffer). Has position, limit, capacity.
  • Channel: Bidirectional, non-blocking I/O endpoint (SocketChannel, FileChannel, ServerSocketChannel)
  • Selector: Monitors multiple channels on one thread. OS epoll/kqueue underneath.
Non-blocking Server Skeleton
Selector selector = Selector.open();
ServerSocketChannel ssc = ServerSocketChannel.open();
ssc.configureBlocking(false);
ssc.bind(new InetSocketAddress(8080));
ssc.register(selector, SelectionKey.OP_ACCEPT);

while (true) {
    selector.select();  // blocks until event
    Set<SelectionKey> keys = selector.selectedKeys();
    for (SelectionKey key : keys) {
        if (key.isAcceptable()) { accept(key); }
        else if (key.isReadable()) { read(key); }
    }
    keys.clear();
}
ByteBuffer
flip() switches from write to read mode. clear() resets for writing. compact() keeps unread bytes, moves to front.

15 Java modules system (JPMS — Java 9+)

What is JPMS
Java Platform Module System (Java 9). Introduces strong encapsulation at the package level. Replaces classpath with modulepath. Eliminates split packages, illegal access.
module-info.java
// com.myapp.service module
module com.myapp.service {
    requires java.net.http;       // depend on module
    requires com.myapp.model;
    exports com.myapp.service.api; // expose this package
    exports com.myapp.service.impl to com.myapp.web; // targeted export
    provides com.myapp.spi.Parser  // service provider
        with com.myapp.service.impl.JsonParser;
}
Benefits
  • Strong encapsulation: internal packages hidden by default
  • Reliable configuration: missing dependencies fail at startup, not runtime
  • Smaller JVM images with jlink
Classpath vs Modulepath
Classpath: no encapsulation, all public APIs accessible. Modulepath: only exported packages visible. Automatic modules for legacy JARs.

1 Role-based (RBAC) vs Attribute-based (ABAC) access control
rbacabacauthorization
Medium 80%
RBAC — Role-Based Access Control
User → assigned Roles → Roles have Permissions

Roles: ADMIN, EDITOR, VIEWER, BILLING
Permissions: read:posts, write:posts, delete:posts, view:billing

User Alice: [EDITOR] → can read:posts + write:posts
User Bob:   [VIEWER] → can only read:posts

Simple, performant, easy to audit. Rigid: can't express context-based rules.
ABAC — Attribute-Based Access Control
Policy: user.department == resource.department AND resource.classification <= user.clearance

Request evaluated at runtime against policy engine (OPA — Open Policy Agent)

Attributes:
  Subject: {role, department, clearance, location}
  Resource: {classification, owner, department, sensitivity}
  Action: {read, write, delete}
  Environment: {time, IP, MFA_verified}

More expressive but complex. Used in enterprise, healthcare, government.
Implementation with OPA
# Rego policy (OPA):
allow { input.user.role == "admin" }
allow {
    input.action == "read"
    input.resource.owner == input.user.id
}
