1 Two Sum
hash-maparrays
Easy 95%
Approach
Use a hash map to store complement = target - num as you iterate. If current number exists in map → found the pair.
Solution
def twoSum(nums, target):
    seen = {}
    for i, num in enumerate(nums):
        if num in seen:
            return [seen[num], i]
        seen[target - num] = i
Complexity
Time: O(n) | Space: O(n)
Follow-ups
• What if the array is sorted? (two pointers, O(1) space)
• What if we need ALL pairs? (collect instead of return first)
• 4-Sum approach?

4 Binary Tree Inorder Traversal (Iterative)
stackdfs
Easy 78%
Approach
Iterative inorder: use explicit stack. Go left as far as possible, process node, move right.
Solution
def inorderTraversal(root):
    res, stack, cur = [], [], root
    while cur or stack:
        while cur:
            stack.append(cur); cur = cur.left
        cur = stack.pop()
        res.append(cur.val)
        cur = cur.right
    return res
Complexity
Time: O(n) | Space: O(h) where h = tree height

1 JVM memory model: heap, stack, metaspace
jvmmemorygc
Medium 92%
JVM Memory Areas
  • Heap: All objects (new). Divided into Young (Eden + 2 Survivors) + Old/Tenured. GC managed.
  • Stack: Per-thread. Holds stack frames: local variables, operand stack, method calls. Fixed size (typically 512KB-1MB). StackOverflowError if exceeded.
  • Metaspace (Java 8+): Class metadata (class bytecode, method data). Native memory, grows dynamically. Replaced PermGen which had fixed max size.
  • Code Cache: JIT-compiled native code.
  • Direct Memory: Off-heap via NIO ByteBuffer.allocateDirect(). Not GC'd, must be freed explicitly.
Tuning Flags
-Xms512m -Xmx4g       # initial and max heap
-XX:MetaspaceSize=256m # initial metaspace
-XX:MaxMetaspaceSize=512m
-Xss512k               # thread stack size
Follow-ups
• What causes OutOfMemoryError in heap vs metaspace vs direct memory?
• What is object header size in JVM? (12-16 bytes: mark word + klass pointer)
• How does compressed OOPs affect memory usage?

2 HashMap internals in Java 8+
hashmaptreeifycollision
Medium 90%
HashMap Internals
// Java 8+ structure:
// Node<K,V>[] table  (array of buckets, power of 2 size)
// Each bucket: null | Node (linked list) | TreeNode (red-black tree)

// Hash calculation:
static int hash(Object key) {
    int h;
    return (key == null) ? 0 : (h = key.hashCode()) ^ (h >>> 16);
    // XOR high bits into low bits — better distribution
}
// Bucket index: (n-1) & hash  (n = table length, power of 2)
Thresholds
  • TREEIFY_THRESHOLD = 8: Bucket with >8 nodes → convert to red-black tree (O(log n) per op)
  • UNTREEIFY_THRESHOLD = 6: Tree shrinks back to list on removal
  • LOAD_FACTOR = 0.75: Resize (double) when size/capacity > 0.75
Thread Safety
HashMap is NOT thread-safe. Use ConcurrentHashMap (lock-striping, CAS) or Collections.synchronizedMap() (coarse lock).
Follow-ups
• What is the time complexity of get() in worst case? O(log n) with tree buckets
• Why XOR high bits into low bits in hash()? (prevents collision when table size is small)
• What is the difference between HashMap.keySet() and EntrySet iteration performance?

5 HashMap vs LinkedHashMap vs TreeMap internals
hashmaplinkedhashmaptreemap
Medium 84%
HashMap
Array of Node<K,V> buckets. Hash → index via (n-1) & hash. Collision: linked list, then treeify at threshold 8 (TREEIFY_THRESHOLD). Resize (double) at 75% load factor. Java 8: balanced BST (TreeNode) for long chains.
LinkedHashMap
Extends HashMap. Adds doubly-linked list through all entries maintaining insertion order. Can be configured for access order (LRU behaviour) with constructor parameter.
// LRU Cache using LinkedHashMap
Map<K,V> lru = new LinkedHashMap<>(16, 0.75f, true) {  // accessOrder=true
    protected boolean removeEldestEntry(Map.Entry<K,V> e) {
        return size() > capacity;
    }
};
TreeMap
Red-Black tree. Keys always sorted (natural order or Comparator). O(log n) get/put/remove. Extra operations: floorKey, ceilingKey, headMap, tailMap, subMap.
Quick Comparison
  • HashMap: O(1) avg, unordered, null key/values allowed
  • LinkedHashMap: O(1) avg, insertion/access ordered, LRU capable
  • TreeMap: O(log n), sorted, no null key
Follow-ups
• What is HashMap's initial capacity and load factor trade-off?
• Why is String a good HashMap key? (immutable, cached hashCode)
• What causes ConcurrentModificationException?

7 Java Memory Leaks — common causes and detection
memory-leakheapjvm
Medium 80%
Common Causes
  • Static references: Static fields holding large objects or collections never GC'd
  • ThreadLocal leak: In thread pools, ThreadLocal not removed → memory leak per thread
  • Listeners/callbacks: Registered but never removed (event listeners, MBean)
  • Unclosed resources: Connection pools, file handles (use try-with-resources)
  • Cache without eviction: Unbounded HashMap growing forever
  • ClassLoader leak: Hot deployment in app servers — classloader + all loaded classes retained
Detection Tools
  • jmap -histo <pid> — histogram of heap objects
  • jmap -dump:format=b,file=heap.hprof <pid> — heap dump
  • Eclipse MAT / VisualVM — analyze heap dump, find GC roots
  • Java Flight Recorder (JFR) + JMC — low-overhead production profiling
  • async-profiler — CPU and allocation profiling
ThreadLocal Fix
private static final ThreadLocal<Context> ctx = new ThreadLocal<>();

try {
    ctx.set(new Context());
    doWork();
} finally {
    ctx.remove();  // CRITICAL in thread pools!
}

8 Hibernate L1 and L2 cache — how they work
hibernatecachel1
Medium 76%
L1 Cache (Session Cache)
Default, always on. Scoped to a single Session (transaction). Within a session, the same entity loaded twice returns the same object (identity map). Cleared on session.close() or session.clear().
L2 Cache (Shared Cache)
Optional, cross-session. Shared across all sessions in a SessionFactory. Must be explicitly configured. Providers: Ehcache, Caffeine, Infinispan, Redis.
L2 Setup

Query Cache
Cache for JPQL/HQL query results. Must also have L2 enabled. Stores primary keys, not entities. Invalidated when any entity in result changes.

9 Java ClassLoader hierarchy and how class loading works
classloaderbootstrapdelegation
Hard 76%
ClassLoader Hierarchy
  • Bootstrap ClassLoader: Loads JDK core classes (java.lang, java.util) from rt.jar/modules. C++ code, no Java object.
  • Platform ClassLoader (was Extension): Loads java.se, java.xml etc.
  • Application ClassLoader: Loads from classpath (your app + third-party JARs).
  • Custom ClassLoaders: hot-deploy, OSGi, isolation (one classloader per plugin).
Delegation Model
When loading class X: check cache → delegate to parent → parent delegates to its parent → reach Bootstrap → if not found, child tries to load itself → ClassNotFoundException if all fail.
Class Identity
Same class name loaded by different ClassLoaders = different classes. ClassCastException when assigning across loaders. Root of hot-deploy complexity.
Custom ClassLoader
class HotLoader extends ClassLoader {
    @Override
    protected Class<?> findClass(String name) throws ClassNotFoundException {
        byte[] bytes = readBytesFromFile(name);
        return defineClass(name, bytes, 0, bytes.length);
    }
}
Follow-ups
• What is the ClassLoader leak in application servers?
• How does OSGi use ClassLoaders for module isolation?
• What is --add-opens in Java 9+ and why is it needed?

Indexes — Types and Internals
  • B+ Tree: Default in PostgreSQL/MySQL. O(log n) for equality and range queries. Leaf nodes form linked list for range scans.
  • Hash Index: O(1) for equality only. No range queries. Used in memory engines (MEMORY in MySQL).
  • GiST/GIN: PostgreSQL generalized indexes for full-text search, JSONB, arrays.
  • Bitmap Index: Low-cardinality columns. Efficient AND/OR on multiple conditions.
Clustered vs Secondary
  • Clustered (InnoDB Primary Key): Data physically stored in index order. Range scans very fast. Only 1 per table.
  • Secondary: Leaf stores primary key value → extra lookup for full row. Covering index eliminates this lookup.
Index Design Tips
  • Composite index: equality columns first, range columns last, ORDER BY columns last
  • Cover frequently queried columns with INCLUDE
  • Partial index for low-cardinality: WHERE status='PENDING'
  • Avoid index on frequently updated columns (write overhead)
Follow-ups
• What is an index scan vs bitmap heap scan in PostgreSQL?
• How does an index affect INSERT/UPDATE/DELETE performance?
• When would you use a partial index?

1 How does std::vector grow?
vectoramortizedreallocation
Easy 86%
std::vector Growth
When capacity is exceeded, vector allocates new buffer (typically 2× current capacity), moves all elements, then deallocates old buffer. Amortized O(1) push_back.
Internals
struct vector_internals {
    T* begin;    // pointer to first element
    T* end;      // pointer past last element (size)
    T* cap_end;  // pointer to end of allocation (capacity)
};
// size() = end - begin
// capacity() = cap_end - begin
Important APIs
  • reserve(n): pre-allocate without changing size. Prevents reallocations.
  • shrink_to_fit(): release excess capacity (non-binding request).
  • emplace_back(args): construct in-place, avoids extra copy/move.

1 TCP vs UDP — when to use each?
tcpudpreliability
Easy 90%
TCP vs UDP
  • TCP: Connection-oriented (3-way handshake). Reliable (ACKs, retransmit). Ordered. Flow + congestion control. ~20-60byte headers. Higher latency.
  • UDP: Connectionless. No guarantees. No ordering. No congestion control. ~8byte header. Lower latency. Can multicast.
When to use UDP
  • Gaming / VoIP / video calls: stale data worse than loss. TCP retransmit would cause jitter.
  • DNS: single request-response, small payload. Retry at app layer if timeout.
  • DHCP, TFTP, SNMP: simple protocols where TCP overhead isn't worth it.
  • HTTP/3 (QUIC): UDP + built-in reliability at QUIC layer — gets benefits of both.
Follow-ups
• What is QUIC and why does it use UDP?
• How do game engines handle packet loss with UDP? (delta compression, interpolation)
• What is the difference between TCP TIME_WAIT and CLOSE_WAIT?

2 TCP three-way handshake
tcpsynack
Easy 88%
TCP Handshake
Client          Server
  |---SYN(seq=x)---->|  Client: CLOSED→SYN_SENT
  |<--SYN-ACK(seq=y,ack=x+1)---|
  |---ACK(ack=y+1)-->|  Both: ESTABLISHED

Teardown (4-way):
  |---FIN----------->|  Client: ESTABLISHED→FIN_WAIT_1
  |<--ACK-----------|
  |<--FIN-----------|
  |---ACK----------->|  Client: TIME_WAIT (2×MSL = 60-120s)
                       Server: CLOSED
TIME_WAIT purpose
Ensures delayed packets from old connection don't confuse new connection on same 4-tuple. 2×MSL (Maximum Segment Lifetime). Can cause port exhaustion on high-traffic servers. Fix: SO_REUSEADDR, SO_REUSEPORT, or increase local port range.
SYN Flood
Attacker sends many SYN packets, never completes handshake. Server holds half-open connections (SYN_RCVD state). Defense: SYN cookies — encode state in ISN, allocate resources only after ACK.
Follow-ups
• Why is teardown 4-way but handshake is 3-way?
• What is TCP Fast Open (TFO) and how does it reduce latency?
• What is the maximum number of connections per IP:port pair?

1 Race condition — what and how to prevent
race-conditionmutexatomic
Easy 92%
Race Condition
Two or more threads access shared mutable state without synchronization. Result depends on thread scheduling (timing). Non-deterministic bugs.
Examples and Fixes
# Python — unsafe counter (GIL helps here but not in C/Java)
counter = 0
def increment():
    global counter
    counter += 1  # NOT atomic in Java/C: read, add, write — 3 ops

# Java fix:
AtomicInteger counter = new AtomicInteger(0);
counter.incrementAndGet();  // single atomic CAS instruction

# OR use synchronized:
synchronized void increment() { counter++; }

# Go: use atomic
var counter int64
atomic.AddInt64(&counter, 1)
# OR: go run -race ./...  (built-in race detector)
Detection
Go: go run -race. Java: ThreadSanitizer (TSAN) in native, FindBugs for JVM. Helgrind (Valgrind) for C/C++.
Follow-ups
• What is a benign data race and when is it acceptable?
• How does the Go race detector work? (shadow memory — 4 words per memory location tracking last 4 accesses)
• What is the difference between a race condition and a data race?

1 Process vs Thread vs Goroutine
processthreadgoroutine
Medium 90%
Processes vs Threads
  • Process: Independent address space, separate heap/stack/code/data. Isolated — one process crash doesn't affect others. IPC needed (pipes, sockets, shared memory).
  • Thread: Shares address space (heap, code, global data) with other threads in same process. Has own stack + registers. Cheaper to create/switch than process. Direct memory sharing.
Context Switch Cost
  • Process switch: save/restore full CPU state + page table switch (TLB flush) → ~100μs
  • Thread switch (same process): save/restore registers, stack pointer. No TLB flush → ~1-10μs
  • Goroutine/fiber switch: userspace, ~100ns
Linux Internals
Both processes and threads are task_struct in Linux kernel. Threads created with CLONE_VM flag — share address space. fork() creates new address space.

2 Deadlock conditions (Coffman)
deadlockmutual-exclusionhold-wait
Medium 86%
Coffman Conditions for Deadlock
ALL 4 must hold simultaneously for deadlock:
  • Mutual Exclusion: Resource can only be held by one process
  • Hold and Wait: Process holds resources while waiting for more
  • No Preemption: Resources can't be forcibly taken away
  • Circular Wait: Chain of processes each waiting for next in chain
Prevention Strategies
  • Break Hold and Wait: request all resources at once (but reduces concurrency)
  • Break Circular Wait: impose total ordering on lock acquisition (always lock A before B)
  • Allow Preemption: rollback and retry (used in databases)
  • Detection + Recovery: build wait-for graph, detect cycles, kill one process
Banker's Algorithm
Safe state check: simulate allocation, see if all processes can eventually complete. Grant request only if system remains in safe state. O(n²×m) too slow for real OS but used in theory.

3 Mutex vs Semaphore vs Spinlock
mutexsemaphorespinlock
Medium 84%
Synchronization Primitives
  • Mutex (Mutual Exclusion): Binary lock. Owner must release. Sleeping lock — blocked thread sleeps, woken by OS. Priority inversion risk.
  • Semaphore: Counter (0..N). Binary semaphore ≈ mutex but no ownership. Counting semaphore for resource pools (N available resources).
  • Spinlock: Busy-wait loop checking flag. No context switch. Great for very short critical sections (kernel code). Wastes CPU if held long.
  • Condition Variable: Wait + signal pattern. Used WITH mutex (monitor). Always use predicate loop (spurious wakeups).
Futex (Linux)
Fast Userspace muTEX. Fast path: atomic CAS in userspace (no syscall). Slow path (contended): syscall to sleep. Basis for pthreads mutex and Java's synchronized.

1 SQL Injection — how it works and prevention
sql-injectionprepared-statementsparameterized
Easy 92%
How it works
# Vulnerable code:
query = "SELECT * FROM users WHERE name='" + username + "' AND pwd='" + password + "'";

# Attacker input: username = admin' --
# Resulting query:
SELECT * FROM users WHERE name='admin' --' AND pwd='anything'
# -- comments out the password check → logged in as admin!

# Even worse:
username = "'; DROP TABLE users; --"
# Drops the entire users table!
Prevention
# Java PreparedStatement:
PreparedStatement stmt = conn.prepareStatement(
    "SELECT * FROM users WHERE name=? AND pwd=?");
stmt.setString(1, username);
stmt.setString(2, hashedPassword);

# Python SQLAlchemy:
result = db.execute("SELECT * FROM users WHERE name=:n", {"n": username})

# ORM (Hibernate/JPA): inherently parameterized
User user = em.createQuery("FROM User WHERE name=:n", User.class)
    .setParameter("n", username).getSingleResult();
Defense in depth
  • Least privilege DB user (SELECT only for read, no DROP)
  • WAF (Web Application Firewall) to detect patterns
  • Input validation (whitelist expected characters)
  • Error messages: never expose DB error details to client
Follow-ups

• How does NoSQL injection work in MongoDB? ($where, $regex)
