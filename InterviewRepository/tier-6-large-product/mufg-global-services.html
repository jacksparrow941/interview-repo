1 HashMap vs ConcurrentHashMap — thread safety and internal differences
hashmapconcurrenthashmapthread-safety
Medium 95%
HashMap (Not Thread-Safe)
Array of Node<K,V> buckets. Hash → bucket via (n-1)&hash. Collisions: linked list → red-black tree at TREEIFY_THRESHOLD=8. Resizes (doubles) at 75% load. Multi-threaded writes: race on resize, data loss, infinite loop (Java 7).
ConcurrentHashMap (Thread-Safe)
Java 8+: CAS + synchronized per bucket (not the whole map). Reads are lock-free (volatile). No null keys/values (unlike HashMap). Iteration is weakly consistent — no ConcurrentModificationException.
Code
Map<String,Integer> cmap = new ConcurrentHashMap<>();
cmap.put("TXN-001", 5000);
cmap.putIfAbsent("TXN-001", 3000);         // atomic
cmap.compute("TXN-001", (k,v)-> v+1);      // atomic increment
// Banking: CHM used for dedup cache (idempotency key → status)
Key Differences
  • Null key/val: HashMap ✓, CHM ✗
  • Locking: none vs per-bucket CAS/sync
  • size(): exact vs approximate (sumCount)
  • CHM >> Collections.synchronizedMap() under contention
Follow-ups
• putIfAbsent vs computeIfAbsent — difference?
• Why is CopyOnWriteArrayList useful for rarely-written lists?
• How does CHM handle resize concurrently?

2 How to use a POJO as a key in HashMap — hashCode/equals contract
hashmappojohashcode
Medium 92%
The Problem
HashMap uses hashCode() to find the bucket, equals() to match the key. Without overriding both, default Object identity is used — two logically equal POJOs go to different buckets.
Contract
  • If a.equals(b) → a.hashCode()==b.hashCode() (mandatory)
  • Reverse not required (collision allowed)
  • Never mutate fields used in hashCode while object is a map key
Correct Implementation
public final class TradeKey {          // final fields = safe as key
    private final String tradeId;
    private final String bookId;

    @Override public boolean equals(Object o) {
        if (!(o instanceof TradeKey)) return false;
        TradeKey k = (TradeKey) o;
        return Objects.equals(tradeId, k.tradeId)
            && Objects.equals(bookId, k.bookId);
    }
    @Override public int hashCode() {
        return Objects.hash(tradeId, bookId);
    }
}
// Map.get(new TradeKey("TXN-001","BOOK-A")) — finds the entry correctly
Follow-ups
• What if hashCode always returns 0? (all keys in one bucket → O(n))
• Can an enum be a safe HashMap key? (yes — identity-based equals + stable hashCode)
• Lombok @Data generates hashCode/equals — pitfall with mutable fields?

Props vs State
  • Props: Read-only data passed from parent to child. Child cannot modify props.
  • State: Mutable data local to a component. Managed via useState.
  • Changing either causes a re-render. State updates are asynchronous and batched.

Key Hooks
  • useState(init) — local state
  • useEffect(fn, deps) — side effects (API calls, subscriptions, timers)

  • useMemo(fn, deps) — memoize expensive computation

Use Case — Trade Enrichment
MUFG trade booking: fetch FX rate, counterparty details, limit check in parallel, then combine results. Sequential = 3 × 200ms = 600ms. Parallel = 200ms.

 getFxRate  getCP    checkLimit
 (200ms)  (150ms)   (180ms)
  |         |          |
  +----+----+----------+
       | allOf().join()
       v
  combineAndSave()
  total: ~200ms (not 530ms)

public TradeBookingResult bookTrade(TradeRequest req) {
    ExecutorService pool = Executors.newFixedThreadPool(10);

    CompletableFuture<FxRate> fxFuture =
        CompletableFuture.supplyAsync(() -> fxService.getRate(req.getCurrency()), pool)
            .orTimeout(500, TimeUnit.MILLISECONDS)
            .exceptionally(ex -> FxRate.fallback());

    CompletableFuture<Counterparty> cpFuture =
        CompletableFuture.supplyAsync(() -> cpService.get(req.getCounterpartyId()), pool);

    CompletableFuture<LimitCheck> limitFuture =
        CompletableFuture.supplyAsync(() -> limitService.check(req), pool);

    CompletableFuture.allOf(fxFuture, cpFuture, limitFuture).join();

    if (!limitFuture.join().isApproved())
        throw new LimitBreachException();

    return tradeRepo.save(Trade.builder()
        .amount(req.getAmount().multiply(fxFuture.join().getRate()))
        .counterparty(cpFuture.join())
        .build());
}

CompletableFuture<EnrichedTrade> enriched =

        .thenCompose(trade -> enrichmentService.enrich(trade));

Flux vs Redux
Flux (Facebook pattern): Unidirectional data flow. Action → Dispatcher → Store → View → Action. Multiple stores allowed.
Redux: Evolution of Flux. Single store, pure reducer functions, time-travel debugging. Used in MUFG trade dashboards for shared state (auth, filters, trade list).

const tradesReducer = (state = [], action) => {

Why JMM Matters in Banking
Without JMM guarantees: Thread A writes trade status=SETTLED, Thread B reads stale PENDING from CPU cache → double settlement!
Happens-Before Rules
  Rule                      | Guarantee
  --------------------------+-----------------------------
  Program order             | Actions in thread are ordered
  Monitor lock (sync block) | unlock HB next lock
  volatile write/read       | write HB subsequent read
  Thread.start()            | start() HB any action in thread
  Thread.join()             | all actions HB join() return
volatile vs synchronized vs AtomicLong
// volatile: visibility ONLY, no atomicity
private volatile boolean running = true;   // safe for simple flag
private volatile long counter = 0;          // NOT safe for i++!

// synchronized: visibility + atomicity
private long counter = 0;
public synchronized void increment() { counter++; }  // safe

// AtomicLong: lock-free CAS — best for high-contention counters
private final AtomicLong tradeCount = new AtomicLong(0);
tradeCount.incrementAndGet();  // CAS at CPU level

// Double-checked locking — MUST use volatile
private static volatile TradeCache instance;
public static TradeCache getInstance() {
    if (instance == null) {
        synchronized (TradeCache.class) {
            if (instance == null)
                instance = new TradeCache();  // volatile ensures write visible
        }
    }
    return instance;
}

What is SAML 2.0
Security Assertion Markup Language 2.0 — XML-based standard for Single Sign-On (SSO). Used extensively in enterprise banking for federated identity. MUFG employees authenticate once via corporate Identity Provider (ADFS/Okta) and access multiple apps.

Key Actors:
  • Identity Provider (IdP): Authenticates user, issues SAML assertion (ADFS, Okta, PingFederate)
  • Service Provider (SP): Your app (Spring Boot). Trusts IdP's assertions.
  • Principal: The end user (MUFG employee)

5. IdP authenticates → creates SAML Assertion XML:

1 LRU Cache — implement O(1) get/put using HashMap + DoublyLinkedList

Problem

Design Diagram
  HashMap<key, Node>              DoublyLinkedList
  +----+--------+              HEAD <-> [A] <-> [B] <-> [C] <-> TAIL
  | A  | Node*A |              (MRU)                           (LRU)
  | B  | Node*B |
  | C  | Node*C |  get(A): move A to HEAD  -- O(1)
  +----+--------+  put(D): add D to HEAD, remove TAIL (C) -- O(1)
Java Implementation
class LRUCache {
    private final int capacity;
    private final Map<Integer, Node> map = new HashMap<>();
    private final Node head = new Node(0,0), tail = new Node(0,0);

    public LRUCache(int capacity) {
        this.capacity = capacity;
        head.next = tail; tail.prev = head;
    }

    public int get(int key) {
        if (!map.containsKey(key)) return -1;
        Node n = map.get(key);
        moveToFront(n);
        return n.val;
    }

    public void put(int key, int val) {
        if (map.containsKey(key)) {
            map.get(key).val = val;
            moveToFront(map.get(key));
        } else {
            if (map.size() == capacity)
                map.remove(removeLast());
            Node n = new Node(key, val);
            map.put(key, n);
            addToFront(n);
        }
    }

    private void addToFront(Node n) {
        n.next = head.next; n.prev = head;
        head.next.prev = n; head.next = n;
    }
    private void moveToFront(Node n) { remove(n); addToFront(n); }
    private void remove(Node n) { n.prev.next = n.next; n.next.prev = n.prev; }
    private int removeLast() {
        Node lru = tail.prev; remove(lru); return lru.key;
    }
    static class Node { int key, val; Node prev, next; Node(int k, int v){key=k;val=v;} }
}

Sliding Window: Maintain a window [left, right]. Expand right, shrink left when condition violated. Avoids O(n²) nested loops → O(n).

Fixed Window — Max Sum of K Elements
public int maxSum(int[] arr, int k) {
    int windowSum = 0, maxSum = 0;
    for (int i = 0; i < k; i++) windowSum += arr[i];  // first window
    maxSum = windowSum;
    for (int i = k; i < arr.length; i++) {
        windowSum += arr[i] - arr[i - k];  // slide: add right, remove left
        maxSum = Math.max(maxSum, windowSum);
    }
    return maxSum;
}

public int lengthOfLongestSubstring(String s) {
    Map<Character, Integer> freq = new HashMap<>();
    int left = 0, maxLen = 0;
    for (int right = 0; right < s.length(); right++) {
        freq.merge(s.charAt(right), 1, Integer::sum);
        while (freq.get(s.charAt(right)) > 1) {
            freq.merge(s.charAt(left), -1, Integer::sum);
            if (freq.get(s.charAt(left)) == 0) freq.remove(s.charAt(left));
            left++;
        }
        maxLen = Math.max(maxLen, right - left + 1);
    }
    return maxLen;
}

public int[] merge(int[] a, int[] b) {
