1 ACID properties
acidtransactions
Easy 93%
Indexes — Types and Internals
  • B+ Tree: Default in PostgreSQL/MySQL. O(log n) for equality and range queries. Leaf nodes form linked list for range scans.
  • Hash Index: O(1) for equality only. No range queries. Used in memory engines (MEMORY in MySQL).
  • GiST/GIN: PostgreSQL generalized indexes for full-text search, JSONB, arrays.
  • Bitmap Index: Low-cardinality columns. Efficient AND/OR on multiple conditions.
Clustered vs Secondary
  • Clustered (InnoDB Primary Key): Data physically stored in index order. Range scans very fast. Only 1 per table.
  • Secondary: Leaf stores primary key value → extra lookup for full row. Covering index eliminates this lookup.
Index Design Tips
  • Composite index: equality columns first, range columns last, ORDER BY columns last
  • Cover frequently queried columns with INCLUDE
  • Partial index for low-cardinality: WHERE status='PENDING'
  • Avoid index on frequently updated columns (write overhead)

2 N+1 Query Problem — detect and fix with JPA/Hibernate in Spring Boot
n+1-queryhibernatejpa
Hard 92%
The Problem
N+1 queries: 1 query to load N parent records + N queries for each child = N+1 DB calls.
MUFG example: Load 100 trades → 1 query + 100 queries for counterparty = 101 round-trips!
How It Happens
@Entity
public class Trade {
    @ManyToOne(fetch = FetchType.LAZY)  // LAZY is default
    private Counterparty counterparty;
}

List<Trade> trades = tradeRepo.findAll(); // 1 SELECT
for (Trade t : trades) {
    t.getCounterparty().getName(); // triggers N SELECTs!
}
// Hibernate logs:
// SELECT * FROM trades;
// SELECT * FROM counterparty WHERE id=1
// SELECT * FROM counterparty WHERE id=2  ... x100
Fix 1 — JOIN FETCH
@Query("SELECT t FROM Trade t JOIN FETCH t.counterparty")
List<Trade> findAllWithCounterparty();
// 1 SQL: SELECT t.*, c.* FROM trades t JOIN counterparty c ON t.cp_id=c.id
Fix 2 — @EntityGraph
@EntityGraph(attributePaths = {"counterparty", "instrument"})
@Query("SELECT t FROM Trade t")
List<Trade> findAllEager();
// Best for multiple associations — cleaner than FETCH JOIN
// Avoids Cartesian product with multiple collections
Fix 3 — Batch Size
@BatchSize(size = 25)
@ManyToOne(fetch = FetchType.LAZY)
private Counterparty counterparty;
// 100 trades -> 4 batch queries instead of 100
// spring.jpa.properties.hibernate.default_batch_fetch_size=25
Detect N+1
# application.properties
spring.jpa.properties.hibernate.generate_statistics=true
logging.level.org.hibernate.stat=DEBUG
# See: 101 queries for 100 trades -> N+1 confirmed!
# Tools: p6spy, datasource-proxy, Hypersistence Optimizer

3 CAP theorem
capconsistencyavailability
Medium 90%
CAP Theorem
In a distributed system under network Partition: choose Consistency OR Availability.
  • CP systems: Refuse to respond if cannot guarantee consistency. etcd, ZooKeeper, HBase, MongoDB (primary read). Good for: leader election, config stores.
  • AP systems: Respond with potentially stale data. Cassandra, CouchDB, DynamoDB (default), Riak. Good for: user profiles, social feeds.
PACELC Extension
Even without partition: latency vs consistency trade-off.
Cassandra: HIGH availability + LOW latency but eventual consistency.
Spanner: HIGH consistency but HIGHER latency (TrueTime atomic clocks, Paxos).

6 B+ Tree index internals — structure, splits, range queries
b-plus-treeindexrange-query
Hard 88%
Structure
  • Internal nodes: keys only, no data. Fan-out typically 100-200 keys per node.
  • Leaf nodes: keys + actual row pointers (or clustered data). Linked list for range scans.
  • Height: ~3-4 levels for millions of rows (log_200(1M) ≈ 3). Fits in memory.
Why B+ over B-Tree
All data in leaves → range queries traverse leaf linked list without backtracking. Internal nodes store more keys (no data) → wider fan-out → shallower tree.
Operations
  • Search: O(log_t n) — traverse from root to leaf
  • Insert: find leaf, insert, split if overflow (cascade up)
  • Delete: find leaf, remove, merge or redistribute if underflow
  • Range scan: find start leaf, traverse linked list → sequential I/O (fast)
Clustered vs Secondary
Clustered: Data rows stored in leaf nodes in index order (InnoDB primary key). One per table.
Secondary: Leaf stores PK value → extra lookup for row data. Multiple allowed.

7 Read replicas — replication lag, use cases, consistency
replicationreplica-lagread-replica
Hard 88%
Replication Mechanics (MySQL binlog / PostgreSQL WAL)
Primary records every write as binary log events. Replica connects, streams binlog, applies changes. Replication can be:
  • Async (default): Primary doesn't wait for replica. Replica may lag.
  • Semi-sync: Primary waits for at least 1 replica to acknowledge before committing.
  • Sync (PostgreSQL synchronous_commit=on): All replicas acknowledge. Highest durability, slowest.
Replication Lag Causes
  • Large transactions (long to replay)
  • High write throughput on primary
  • Network latency between primary and replica
  • Single-threaded replay (older MySQL — use parallel replication)
Handling Lag in Applications
  • Read-your-own-writes: route reads after writes to primary for 1s, or use session stickiness
  • For stale-tolerant reads (reports, analytics): use replica
  • Monitor lag: SHOW REPLICA STATUS → Seconds_Behind_Source

8 SQL query optimization — indexes, covering indexes, composite indexes
indexcovering-indexcomposite
Medium 88%
Composite Index Column Order
-- Query: WHERE a = 1 AND b > 5 ORDER BY c
-- Best index: (a, b, c) — leftmost prefix rule
-- a → equality filter (most selective first)
-- b → range filter
-- c → ORDER BY (eliminates sort)

-- Index (b, a) won't use b for range + a for equality efficiently
Covering Index
Index includes all columns needed by query — no heap lookup.
-- Query:
SELECT email FROM users WHERE user_id = 42;

-- If index is (user_id, email): Index Only Scan — never touches table!
CREATE INDEX idx_user_email ON users(user_id) INCLUDE (email);  -- PostgreSQL
Index Selectivity
High selectivity (few rows per value) = good for index. Low selectivity (boolean, gender) = index often not used. n_distinct in pg_stats shows estimate. Use partial index for low-selectivity cases:
CREATE INDEX ON orders(status) WHERE status = 'PENDING';
Anti-patterns
  • SELECT * prevents covering index
  • Function on indexed column: WHERE LOWER(email) = ... → can't use index. Use functional index.
  • Leading % in LIKE: WHERE name LIKE '%Smith' → full scan. Use full-text search or reverse index.
  • Implicit type cast: WHERE varchar_col = 123 → type mismatch → seq scan

10 Database isolation levels
isolationmvccphantom
Hard 87%
ACID Properties
  • Atomicity: All operations in transaction succeed or all are rolled back. No partial updates.
  • Consistency: Transaction brings DB from one valid state to another. Constraints never violated.
  • Isolation: Concurrent transactions behave as if sequential. Anomalies depend on isolation level.
  • Durability: Committed transactions survive crashes. Guaranteed by WAL.
Isolation Levels & Anomalies
READ UNCOMMITTED: dirty read allowed (see uncommitted data)
READ COMMITTED:  no dirty read | phantom read possible
REPEATABLE READ: no dirty/non-repeatable read | phantom possible (MySQL: solved by gap locks)
SERIALIZABLE:   full isolation, slowest — SSI (PostgreSQL) or locking (MySQL)
How Implemented
PostgreSQL: MVCC for Repeatable Read and below. Serializable: SSI (Serializable Snapshot Isolation). MySQL InnoDB: row-level locking + MVCC + gap locks for Repeatable Read.

11 Database sharding strategies
shardingrangehash
Hard 86%
Sharding Strategies
  • Range-based: Shard by range (A-G, H-P, Q-Z). Simple routing. Risk: hot spots on recent data (time-based IDs all go to last shard).
  • Hash-based: shard = hash(key) % N. Even distribution. No range queries across shards. Resharding = move all data.
  • Consistent Hashing: Virtual nodes on ring. Minimal data movement on resharding. Used by Cassandra, DynamoDB.
  • Directory-based: Lookup table maps key → shard. Flexible but single point of failure.
Cross-Shard Challenges
  • Joins: must scatter-gather or denormalize
  • Transactions: 2PC expensive; use Saga instead
  • Global aggregations: fan out to all shards, merge in application
  • Hot key: add random suffix to key, fan out writes, merge reads

12 EXPLAIN ANALYZE — reading query execution plans
explainquery-planseq-scan
Medium 86%
Key Operations
  • Seq Scan: Full table scan. Fast for small tables / low selectivity.
  • Index Scan: Uses B+ tree index. Best for high selectivity (<10% rows).
  • Index Only Scan: All needed columns in index (covering index). Fastest.
  • Bitmap Heap Scan: Index scan → bitmap of pages → sorted page access. Good for 5-20% rows.
  • Nested Loop: Join — for each outer row, find matching inner. Good for small outer result.
  • Hash Join: Build hash table from smaller table → probe with larger. Good for large unsorted.
  • Merge Join: Both sides sorted. Fast but needs sort step.
Reading EXPLAIN
EXPLAIN ANALYZE SELECT * FROM orders WHERE user_id = 42;

-> Index Scan using idx_orders_user on orders
   Index Cond: (user_id = 42)
   rows=150 (estimated)  rows=143 (actual)
   Buffers: shared hit=12  (pages from cache)
   Planning: 0.3ms  Execution: 2.1ms
Tuning Signals
  • Seq scan on large table with high selectivity → missing index
  • Estimated rows ≫ actual → stale statistics → run ANALYZE
  • Sort in plan → add index with ORDER BY columns
  • Hash join with large table → may need work_mem increase

15 Database partitioning strategies — range, hash, list
partitioningrangehash
Hard 84%
Range Partitioning
Divide by value range. Common for time-series data.
CREATE TABLE orders (id bigint, created_at date, ...)
PARTITION BY RANGE (created_at);

CREATE TABLE orders_2023 PARTITION OF orders
    FOR VALUES FROM ('2023-01-01') TO ('2024-01-01');
CREATE TABLE orders_2024 PARTITION OF orders
    FOR VALUES FROM ('2024-01-01') TO ('2025-01-01');
Pruning: WHERE created_at >= '2024-01-01' → only scans 2024 partition.
Hash Partitioning
Distribute evenly by hash of key. Good for write distribution.
PARTITION BY HASH (user_id);
-- Partition 0: user_id % 4 = 0
-- Partition 1: user_id % 4 = 1 ...
List Partitioning
By enumerated values. Good for geographic/categorical data.
PARTITION BY LIST (region);
-- India: ('IN'), US: ('US','CA')
Benefits
  • Partition pruning: query only relevant partition
  • Faster VACUUM, index maintenance (smaller partitions)
  • Easy archival: DETACH PARTITION orders_2022
Partitioning vs Sharding
Partitioning: single database, multiple internal tables. Sharding: multiple databases, data split across machines. Sharding requires application-level routing.

16 Connection pooling — PgBouncer, HikariCP, patterns
connection-poolpgbouncerhikaricp
Medium 84%
Why Pool Connections
PostgreSQL creates a new OS process per connection (~5-10MB RAM). Opening connection takes ~30-100ms. 1000 connections = 5-10GB RAM, GC overhead, scheduler pressure.
PgBouncer
Lightweight connection pooler for PostgreSQL. Sits between app and DB.
  • Session mode: App gets same DB connection for session duration. All features work.
  • Transaction mode: Connection returned to pool after each transaction. Supports many more app connections (1000s) with few DB connections (50). Restrictions: no SET, no prepared statements per session.
  • Statement mode: Return after each statement. Most restrictive.
HikariCP (Java)
Fast JDBC connection pool.
HikariConfig cfg = new HikariConfig();
cfg.setJdbcUrl("jdbc:postgresql://host/db");
cfg.setMaximumPoolSize(10);
cfg.setConnectionTimeout(30000);
cfg.setIdleTimeout(600000);
cfg.setMaxLifetime(1800000);  // 30min to prevent stale conns
DataSource ds = new HikariDataSource(cfg);
Sizing
Pool size = (core_count × 2) + effective_spindle_count. Smaller than you think — more connections ≠ more throughput.

18 PostgreSQL MVCC — how it achieves non-blocking reads
mvccpostgresqlsnapshot
Hard 82%
MVCC = Multi-Version Concurrency Control
Each row has hidden columns:
  • xmin: transaction ID that inserted this version
  • xmax: transaction ID that deleted/updated this version (0 = still live)
Reads see a snapshot: only versions where xmin ≤ snapshot_xid < xmax.
How it works
T1 (xid=100): UPDATE users SET name='Bob' WHERE id=1
→ Old row: xmin=50, xmax=100  (now dead to T1)
→ New row: xmin=100, xmax=0   (live)

T2 (xid=99, started before T1):
→ Sees old row (xmin=50 <= 99 < xmax=100) ✓
→ Sees 'Alice' — no blocking!

T3 (xid=101, started after T1 commits):
→ Old row: xmax=100 <= 101 → dead, skip
→ New row: xmin=100 <= 101, xmax=0 → live, sees 'Bob' ✓
VACUUM
Dead rows (old versions) accumulate. VACUUM reclaims space. AUTOVACUUM runs automatically. Transaction ID wraparound prevented by freezing old rows.

19 Database deadlocks — detection, prevention, resolution
deadlocklockwait-for-graph
Hard 82%
What is a Deadlock
Two or more transactions each hold a lock the other needs.
T1: LOCK A → wait for B
T2: LOCK B → wait for A
→ Circular wait = deadlock
Deadlock Detection
Most DBs run a background detector (PostgreSQL, MySQL InnoDB).
Builds a wait-for graph: node = transaction, edge = T1 waits for lock held by T2. Cycle = deadlock → kill victim transaction (least expensive to rollback).
Prevention Strategies
  • Lock ordering: Always acquire locks in the same global order (e.g., lower ID first)
  • Timeout: SET lock_timeout = '1s' — transaction aborts if wait too long
  • SELECT FOR UPDATE SKIP LOCKED: Skip locked rows instead of waiting (job queues)
  • Reduce transaction scope: Short transactions hold locks briefly
Application-Level Fix
-- Instead of long transaction:
BEGIN;
  UPDATE account SET bal = bal - 100 WHERE id = 1;  -- locks row
  -- ... complex computation (seconds) ...
  UPDATE account SET bal = bal + 100 WHERE id = 2;  -- deadlock risk!
COMMIT;

-- Better: do computation outside transaction, then short UPDATE

• What is the difference between a deadlock and a livelock?
• How does SELECT FOR UPDATE NOWAIT differ from SKIP LOCKED?
• What is intention locking (IS, IX, S, X)?

20 Eventual consistency models — BASE, read-your-writes, monotonic reads
eventual-consistencybasecausal
Hard 82%
CAP Theorem Recap
In presence of network partition (P), choose between Consistency (C) or Availability (A). Most distributed systems choose AP → eventual consistency.
BASE (Basically Available, Soft state, Eventually consistent)
Contrast to ACID.
  • Basically Available: System works, even during partial failure (stale data OK)
  • Soft State: State may change without input (replication catching up)
  • Eventually Consistent: Given no new updates, all replicas converge to same state
Consistency Models (weakest to strongest)
  • Eventual: Converges eventually. DNS, S3.
  • Monotonic Read: Once you read version V, you never see older version. (client stickiness)
  • Read-Your-Writes: You always see your own writes immediately. (session token pinning)
  • Causal: If A caused B, everyone sees A before B. (vector clocks)
  • Sequential: All operations appear in a global order consistent with program order.
  • Linearizable (Strict): Strongest. Operations appear instantaneous. ZooKeeper, etcd.
Follow-ups

• What is quorum read/write (R + W > N)?
• What are vector clocks and how do they enable causal consistency?

23 PostgreSQL MVCC
mvccxminxmax
Hard 78%
PostgreSQL MVCC Internals
Each row version has xmin (created by txn) and xmax (deleted by txn, 0 if alive).
A txn sees a row if: xmin committed AND xmin <= txn_snapshot AND (xmax=0 OR xmax > txn_snapshot OR xmax not committed)
How it enables isolation
  • Readers never block writers (different row versions)
  • Writers never block readers
  • REPEATABLE READ: txn gets a snapshot at start, sees consistent view throughout
  • No shared read locks needed — eliminates reader-writer contention
VACUUM
Dead tuples (old xmax'd versions) accumulate. VACUUM marks them as free space. AUTOVACUUM: background process. Bloat: table grows with dead tuples. VACUUM ANALYZE: also updates planner statistics.

24 Write-Ahead Logging (WAL) — how databases ensure durability
waldurabilityredo-log
Hard 78%
What is WAL
Before modifying data pages in memory (buffer pool), the change is written to the WAL log first. On crash: replay WAL from last checkpoint to recover committed transactions. Guarantee: committed data never lost, even on sudden crash.
Write Flow
1. Transaction modifies data in buffer pool (in-memory dirty page)
2. WAL record written to WAL buffer → flushed to disk (fsync)
   [WAL written BEFORE data page written — Write-Ahead!]
3. Transaction commits: commit WAL record flushed
4. Background: dirty pages periodically checkpointed to data files
5. WAL records before checkpoint can be deleted
PostgreSQL WAL
WAL files in pg_wal/. Controls: fsync=on (durability), synchronous_commit=on/off. Turning off synchronous_commit: ~10% faster writes, risk of last 100ms of data on crash.
Uses beyond recovery
  • Streaming replication: replicas stream WAL from primary
  • Point-in-time recovery (PITR): replay WAL to any past state
  • Logical replication: parse WAL for row-level changes (Debezium/CDC)

26 Time-series databases — InfluxDB, TimescaleDB, architecture
time-seriesinfluxdbtimescaledb
Medium 74%
Why Special TSDBs
Regular relational DBs are poor for time-series: high write throughput, time-ordered data, bulk deletes (retention), time-range queries, downsampling.
TimescaleDB
PostgreSQL extension. Adds hypertables — automatically partitioned by time. Transparent to SQL. Best for: SQL queries + time-series. Compression: 90%+ space savings with native compression.
SELECT time_bucket('1 hour', time) AS hour,
       avg(temperature)
FROM metrics
WHERE time > NOW() - INTERVAL '7 days'
GROUP BY hour
ORDER BY hour;
InfluxDB
Purpose-built TSDB. Line protocol ingestion. InfluxQL or Flux query language. TSM (Time-Structured Merge Tree) storage engine optimized for time-ordered writes. Built-in retention policies, continuous queries (downsampling).
LSM Tree for writes
Most TSDBs use LSM (Log-Structured Merge Tree): fast sequential writes, compaction merges SSTables. Optimized for write-heavy append patterns.
