1 Smart pointers: unique_ptr, shared_ptr, weak_ptr
smart-pointersraiimemory
Medium 92%
Smart Pointer Types
  • unique_ptr: Exclusive ownership. Non-copyable, move-only. Zero overhead vs raw pointer. Use as default for heap objects.
  • shared_ptr: Shared ownership via reference count. Thread-safe refcount (atomic). Overhead: control block allocation + atomic ops.
  • weak_ptr: Non-owning observer of shared_ptr. Breaks circular references. Must lock() before use — returns shared_ptr (empty if object deleted).
Code Examples
auto up = std::make_unique<Widget>();     // unique_ptr
auto sp = std::make_shared<Widget>();     // shared_ptr (single allocation)
std::weak_ptr<Widget> wp = sp;             // weak_ptr
if (auto spt = wp.lock()) { spt->use(); } // safe access

// Cycle breaking:
struct Node { std::weak_ptr<Node> parent; std::shared_ptr<Node> children; };
Custom Deleter
unique_ptr<FILE, decltype(&fclose)> f(fopen("x","r"), fclose);
Follow-ups

2 Implement a thread-safe LRU Cache in C++
lruthread-safeunordered_map
Hard 88%
Design
std::list (doubly-linked list) + std::unordered_map<K, list::iterator>.
Most recently used at front. On access: move node to front. On eviction: remove from back.
Implementation
template<typename K, typename V>
class LRUCache {
    int cap;
    std::list<std::pair<K,V>> lst;
    std::unordered_map<K, decltype(lst.begin())> mp;
    std::mutex mu;
public:
    LRUCache(int cap) : cap(cap) {}

    std::optional<V> get(const K& key) {
        std::lock_guard lock(mu);
        auto it = mp.find(key);
        if (it == mp.end()) return {};
        lst.splice(lst.begin(), lst, it->second);  // move to front
        return it->second->second;
    }

    void put(const K& key, V val) {
        std::lock_guard lock(mu);
        if (mp.count(key)) lst.erase(mp[key]);
        else if ((int)lst.size() == cap) {
            mp.erase(lst.back().first);
            lst.pop_back();
        }
        lst.push_front({key, val});
        mp[key] = lst.begin();
    }
};
Complexity
get/put: O(1) average. Thread-safe with a single mutex. For higher concurrency: use reader-writer lock or shard by key hash.

3 Explain RAII
raiiexceptionsresource
Medium 87%
RAII — Resource Acquisition Is Initialization
Resource lifetime is bound to object lifetime. Acquire in constructor, release in destructor. Guarantees release even on exceptions (stack unwinding calls destructors).
Examples
class FileGuard {
    FILE* f;
public:
    explicit FileGuard(const char* path) : f(fopen(path, "r")) {
        if (!f) throw std::runtime_error("open failed");
    }
    ~FileGuard() { if (f) fclose(f); }  // always runs
    // Delete copy; use move only
    FileGuard(const FileGuard&) = delete;
    FileGuard& operator=(const FileGuard&) = delete;
};

// RAII wrappers: lock_guard, unique_lock, ifstream, unique_ptr, jthread
Why it matters
Without RAII: every error path must manually release resources → leak-prone. With RAII: destructor always called → exception-safe, leak-free.

4 Move semantics and rvalue references
move-semanticsrvalueperformance
Hard 86%
Move Semantics
C++11 introduces rvalue references (T&&). Move constructor/assignment steals resources from temporaries instead of copying. Enables zero-cost transfer of ownership.
Rvalue References
class Buffer {
    int* data; size_t size;
public:
    Buffer(Buffer&& other) noexcept :  // move constructor
        data(other.data), size(other.size) {
        other.data = nullptr; other.size = 0;  // leave source valid but empty
    }
    Buffer& operator=(Buffer&& other) noexcept {
        if (this != &other) {
            delete[] data;          // free own resource
            data = other.data; size = other.size;
            other.data = nullptr; other.size = 0;
        } return *this;
    }
};

void process(Buffer&& b) { Buffer local = std::move(b); } // move, not copy
Buffer create() { Buffer b(1024); return b; }  // NRVO: no copy at all!
std::move vs std::forward
std::move(x): unconditional cast to rvalue. std::forward<T>(x): conditional — preserves lvalue/rvalue category in template (perfect forwarding).

5 How does std::vector grow?

std::vector Growth
When capacity is exceeded, vector allocates new buffer (typically 2× current capacity), moves all elements, then deallocates old buffer. Amortized O(1) push_back.
Internals
struct vector_internals {
    T* begin;    // pointer to first element
    T* end;      // pointer past last element (size)
    T* cap_end;  // pointer to end of allocation (capacity)
};
// size() = end - begin
// capacity() = cap_end - begin
Important APIs
  • reserve(n): pre-allocate without changing size. Prevents reallocations.
  • shrink_to_fit(): release excess capacity (non-binding request).
  • emplace_back(args): construct in-place, avoids extra copy/move.

8 How does vtable work?
vtablevirtualpolymorphism
Hard 82%
vtable Mechanism
For each class with virtual functions, compiler generates a vtable — a static array of function pointers. Each object has a hidden vptr pointing to its class's vtable (set in constructor).
Virtual Dispatch
class Animal {
public:
    virtual void sound() { printf("..."); }
    virtual ~Animal() {}
};
// vtable_Animal = { &Animal::sound, &Animal::~Animal }

class Dog : public Animal {
    void sound() override { printf("Bark"); }
};
// vtable_Dog = { &Dog::sound, &Dog::~Dog }

Animal* a = new Dog();
a->sound();  // a->vptr -> vtable_Dog[0] = Dog::sound() → "Bark"
Costs
  • Memory: 1 vptr per object (8 bytes on 64-bit)
  • Time: extra pointer indirection per call (cache miss possible)
  • No inlining: compiler can't inline virtual calls (mostly)
  • Final keyword: hints compiler to devirtualize

9 Rule of 0, Rule of 3, Rule of 5 — explain with examples
rule-of-3rule-of-5move
Hard 82%
Rule of 3 (pre-C++11)
If you define any of: destructor, copy constructor, copy assignment, you should define all three. (Managing raw resource → need custom copy + destructor)
Rule of 5 (C++11+)
Add move constructor + move assignment. Without them, moves fall back to copies (expensive).
class Buffer {
    char* data; size_t sz;
public:
    Buffer(size_t n) : data(new char[n]), sz(n) {}
    ~Buffer() { delete[] data; }               // 1: destructor
    Buffer(const Buffer& o)                   // 2: copy ctor
        : data(new char[o.sz]), sz(o.sz) { memcpy(data,o.data,sz); }
    Buffer& operator=(const Buffer& o) {       // 3: copy assign
        if(this==&o) return *this;
        delete[] data; sz=o.sz; data=new char[sz]; memcpy(data,o.data,sz); return *this;
    }
    Buffer(Buffer&& o) noexcept                // 4: move ctor
        : data(o.data), sz(o.sz) { o.data=nullptr; o.sz=0; }
    Buffer& operator=(Buffer&& o) noexcept {   // 5: move assign
        if(this==&o) return *this;
        delete[] data; data=o.data; sz=o.sz; o.data=nullptr; return *this;
    }
};
Rule of 0
Best practice: design classes to own no raw resources. Use RAII wrappers (unique_ptr, vector, string). Then you need ZERO custom special members — compiler generates correct ones.

10 std::atomic and memory ordering
atomicmemory-orderinglock-free
Hard 80%
std::atomic
Guarantees atomic read-modify-write without undefined behavior. No data races. Hardware CAS instructions.
Memory Ordering
  • relaxed: No ordering guarantees. Only atomicity. Cheapest. Use for counters.
  • acquire: All subsequent reads see writes before the release on same var. (read fence)
  • release: All preceding writes visible to acquire on same var. (write fence)
  • acq_rel: Both acquire + release. Used for RMW operations.
  • seq_cst: Total global order. Strongest guarantee. Default for atomic ops.
Usage
std::atomic<int> counter{0};
counter.fetch_add(1, std::memory_order_relaxed);  // fast counter

std::atomic<bool> ready{false};
// Thread 1:
data = 42;
ready.store(true, std::memory_order_release);
// Thread 2:
while (!ready.load(std::memory_order_acquire));  // guaranteed to see data=42
Follow-ups
• What is a data race vs a race condition?
• When is relaxed ordering safe?
• What is the ABA problem in CAS-based algorithms?

13 std::condition_variable — producer-consumer pattern
condition-variablemutexnotify
Medium 78%
Full Producer-Consumer
#include <mutex>
#include <condition_variable>
#include <queue>

std::mutex mtx;
std::condition_variable cv;
std::queue<int> q;
bool done = false;

void producer() {
    for(int i=0;i<10;i++) {
        std::unique_lock lock(mtx);
        q.push(i);
        cv.notify_one();  // wake one consumer
    }
    { std::lock_guard lock(mtx); done=true; }
    cv.notify_all();
}

void consumer() {
    while(true) {
        std::unique_lock lock(mtx);
        cv.wait(lock, []{ return !q.empty() || done; });  // predicate prevents spurious wakeup
        while(!q.empty()) { process(q.front()); q.pop(); }
        if(done) break;
    }
}
Spurious Wakeups
Always use cv.wait(lock, predicate) — without predicate, spurious wakeups cause bugs. Equivalent to: while(!pred()) cv.wait(lock);
notify_one vs notify_all
notify_one: wake 1 waiter (use for single-consumer or rotating consumers). notify_all: wake all waiters (use for broadcast events like shutdown).

15 unique_lock vs lock_guard vs scoped_lock
lock-guardunique-lockscoped-lock
Medium 76%
lock_guard (C++11)
Simplest RAII wrapper. Locks on construction, unlocks on destruction. Cannot be unlocked/relocked. Cannot be moved. Use when you need a simple lock for a scope.
std::lock_guard<std::mutex> lock(m);
unique_lock (C++11)
More flexible. Can unlock/relock, deferred locking, timed locking. Required for condition_variable.
std::unique_lock lock(m, std::defer_lock);  // don't lock yet
lock.lock();        // lock later
lock.unlock();      // unlock early
bool got = lock.try_lock_for(100ms);  // timed
scoped_lock (C++17)
Locks multiple mutexes atomically without deadlock (uses deadlock-free algorithm). Replaces std::lock(m1,m2) + lock_guard(adopt) pattern.
std::scoped_lock lock(m1, m2, m3); // all or nothing
When to use
  • lock_guard: simple scope lock, no condition_variable
  • unique_lock: condition_variable, deferred/timed locking, early unlock
  • scoped_lock: locking 2+ mutexes, avoiding deadlock

30 Implement a lock-free stack using CAS
lock-freecasatomic
Hard 72%
Design
Use std::atomic<Node*> for head. CAS in a loop for push/pop.
Implementation
template<typename T>
class LockFreeStack {
    struct Node { T data; Node* next; };
    std::atomic<Node*> head{nullptr};
public:
    void push(T val) {
        Node* n = new Node{std::move(val), nullptr};
        n->next = head.load(std::memory_order_relaxed);
        while (!head.compare_exchange_weak(n->next, n,
               std::memory_order_release, std::memory_order_relaxed));
    }
    std::optional<T> pop() {
        Node* old = head.load(std::memory_order_acquire);
        while (old && !head.compare_exchange_weak(old, old->next,
               std::memory_order_release, std::memory_order_acquire));
        if (!old) return {};
        T val = std::move(old->data);
        // DANGER: delete old  ← ABA problem / use-after-free with concurrent pops
        return val;
    }
};
ABA Problem
After loading old = A, another thread pops A, pushes B, pushes A back. CAS sees A and succeeds but old->next points to stale node. Fix: tagged pointers (version counter) or hazard pointers for safe memory reclamation.
Follow-ups

• How do hazard pointers prevent use-after-free?
• When does lock-free actually outperform mutex? (high contention, many cores)

constexpr int s = square(5);  // compile-time
int n = 7; int r = square(n);  // runtime — also valid
consteval (C++20)
Must be evaluated at compile time. Immediate function. Compile error if runtime call attempted.
consteval int cube(int x) { return x*x*x; }
consteval auto getCube = cube(3);  // OK: 27 at compile time
int n=5; cube(n);                  // ERROR: n not constant
constinit (C++20)
Variable must be initialized at compile time (no static initialization order fiasco). Unlike constexpr, the variable itself can still be modified at runtime.
constinit int counter = 0;  // initialized at compile time
counter++;                  // runtime modification OK
When to use
  • constexpr: functions/variables that should work at both compile and runtime
  • consteval: guaranteed compile-time (type traits, code generation, DSLs)
  • constinit: global/static variables to avoid init-order issues

32 Virtual inheritance and the diamond problem
virtual-inheritancediamondmultiple-inheritance
Hard 72%
Diamond Problem
struct A { int x; };
struct B : A {};
struct C : A {};
struct D : B, C {};   // D has TWO copies of A!
D d;
d.x = 5;              // Error: ambiguous — B::A::x or C::A::x?
Virtual Inheritance Fix
struct A { int x; };
struct B : virtual A {};
struct C : virtual A {};
struct D : B, C {};   // Only ONE shared A
D d; d.x = 5;         // OK: unambiguous
How it works
With virtual inheritance, B and C each store a virtual base pointer (vbptr) pointing to the shared A subobject. D's constructor directly initializes A.
Cost
Extra pointer per virtual base. More complex object layout. dynamic_cast needed for cross-casting. Avoid in performance-critical code.
Follow-ups

34 Memory model — happens-before, acquire/release semantics

C++ Memory Orderings
  • memory_order_relaxed — no synchronization, only atomicity
  • memory_order_acquire — no loads/stores can move before this load
  • memory_order_release — no loads/stores can move after this store
  • memory_order_acq_rel — both acquire and release
  • memory_order_seq_cst — total ordering (default, most expensive)
Acquire-Release Pattern
// Producer
data.store(42, relaxed);
ready.store(true, memory_order_release);  // store is visible

// Consumer
while (!ready.load(memory_order_acquire));  // wait until acquire sees release
use(data.load(relaxed));  // guaranteed to see 42
Happens-before
A happens-before relationship guarantees that all writes before a release are visible after the corresponding acquire. Essential for lock-free programming.

35 CRTP — Curiously Recurring Template Pattern
crtpstatic-polymorphismmixin
Hard 70%
What is CRTP
Base class templated on its derived class. Enables static polymorphism (compile-time virtual dispatch) — zero vtable overhead.
Example: Static Polymorphism
template<typename Derived>
struct Shape {
    double area() const {
        return static_cast<const Derived*>(this)->area_impl();
    }
};
struct Circle : Shape<Circle> {
    double r;
    double area_impl() const { return 3.14*r*r; }
};
struct Square : Shape<Square> {
    double s;
    double area_impl() const { return s*s; }
};
// Caller (template function, not virtual):
template<typename S> void print(const Shape<S>& s) { std::cout << s.area(); }
CRTP for Mixins
template<typename T>
struct Comparable {
    bool operator!=(const T& o) const { return !(static_cast<const T&>(*this)==o); }
    bool operator> (const T& o) const { return o < static_cast<const T&>(*this); }
    // Derived only implements operator== and operator<
};
struct Point : Comparable<Point> {
    int x,y;
    bool operator==(const Point& o) const { return x==o.x && y==o.y; }
    bool operator< (const Point& o) const { return x<o.x || (x==o.x && y<o.y); }
};
CRTP vs Concepts (C++20)
CRTP: complex syntax, but works pre-C++20 with zero runtime cost. C++20 Concepts: cleaner constraints but still need virtual for runtime polymorphism.

43 What is EBO (Empty Base Optimization)?
eboempty-basesizeof
Hard 64%
The Problem
C++ requires each complete object to have a unique address, so empty classes have size >= 1. But storing an empty allocator/comparator as a member wastes space:
struct Allocator {};  // sizeof = 1
struct MyContainer {
    Allocator alloc;  // 1 byte (but likely padded to 8!)
    size_t size;      // 8 bytes
    // Total: 16 bytes instead of 8
};
EBO Solution
Inherit from the empty base instead of storing as member:
struct MyContainer : private Allocator {
    size_t size;  // Allocator takes 0 bytes here!
    // Total: 8 bytes
};
C++20 [[no_unique_address]]
Attribute that tells compiler it's OK for member to share address:
struct MyContainer {
    [[no_unique_address]] Allocator alloc;
    size_t size;  // 8 bytes total if Allocator is empty
};
Where it matters
std::vector, std::unique_ptr with stateless deleters, std::map with stateless comparators.
