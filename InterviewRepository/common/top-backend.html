1 REST vs GraphQL vs gRPC — when to use each?
restgraphqlgrpc
Medium 90%
REST vs GraphQL vs gRPC
  • REST: Stateless, resource-based (nouns), HTTP verbs. Cacheable, universally supported. Over-fetching (get entire user object for just the name) / under-fetching (need 3 calls for related data).
  • GraphQL: Single endpoint. Client specifies exact fields. Eliminates over/under-fetching. Schema as contract. N+1 problem (use DataLoader). Good for complex UIs, mobile (save bandwidth).
  • gRPC: HTTP/2 + Protocol Buffers. Binary, strongly typed, 5-10x smaller than JSON. Bidirectional streaming. Generated client/server stubs. Best for internal microservices.
Decision Matrix
  • Public API / browser-to-server → REST
  • Complex UI with diverse data needs → GraphQL
  • Internal microservice-to-microservice → gRPC
  • Real-time bidirectional → WebSocket
Follow-ups
• How does gRPC handle service discovery?
• What is the N+1 problem in GraphQL and how does DataLoader solve it? (batching + caching)

3 What is consistent hashing?
consistent-hashingvirtual-nodes
Hard 86%
Consistent Hashing
Problem with naive modulo hashing: adding/removing 1 server remaps N/S keys (massive cache miss storm).

Ring approach: Hash servers and keys to same circular space (0 to 2^32). A key is assigned to the first server found clockwise from its hash position.
Virtual Nodes
Each physical server = 100-200 virtual nodes on the ring → even distribution even with few servers. Fewer hot spots. When server added/removed: only 1/N keys remapped.
class ConsistentHash:
    def __init__(self, replicas=150):
        self.ring = {}
        self.sorted_keys = []
        self.replicas = replicas

    def add_server(self, server):
        for i in range(self.replicas):
            key = hash(f'{server}:{i}')
            self.ring[key] = server
        self.sorted_keys = sorted(self.ring)

    def get_server(self, item):
        h = hash(item)
        for k in self.sorted_keys:
            if h <= k: return self.ring[k]
        return self.ring[self.sorted_keys[0]]  # wrap around

4 Microservices vs Monolith — trade-offs
microservicesmonolitharchitecture
Medium 86%
Monolith vs Microservices Trade-offs
  • Monolith pros: Simple deployment, no network latency for inter-module calls, easier debugging, one codebase, great for small teams and early stage.
  • Monolith cons: Hard to scale individual components, tech lock-in, long build/deploy cycles, large blast radius on failure.
  • Microservices pros: Independent scale/deploy per service, tech diversity, fault isolation, team autonomy (Conway's Law).
  • Microservices cons: Distributed system complexity (network failures, eventual consistency), service discovery, distributed tracing, operational overhead (K8s, service mesh).
When to migrate
Only when: you have scaling problems a monolith can't solve, team is large enough (2-pizza rule), you have operational maturity (CI/CD, observability). Don't start with microservices (Martin Fowler: 'don't start with a microservices architecture').
Follow-ups

5 How would you design a rate limiter?
token-bucketredislua
Hard 85%
Rate Limiter Algorithms
  • Token Bucket: Bucket holds max N tokens. Refilled at rate R/sec. Request consumes 1 token. Allows bursting up to N. Most commonly implemented.
  • Sliding Window Log: Store timestamps of each request. Count within window. Accurate but memory-heavy.
  • Sliding Window Counter: Fix window divided into slots. Weighted count of previous window. Good balance.
  • Fixed Window: Simple counter per window. Burst possible at window boundary.
Distributed Implementation

7 How does Apache Kafka work internally?
kafkapartitionsoffset
Hard 84%
Kafka Architecture
  • Topic: Named category. Divided into partitions (immutable ordered log).
  • Producer: Writes to partition (by key hash or round-robin). Acks: 0/1/all.
  • Consumer Group: Each partition consumed by exactly 1 consumer in group. Multiple groups = independent reads.
  • Broker: Stores partition log. Replication: 1 leader + N-1 followers. ISR = in-sync replicas.
  • ZooKeeper / KRaft: Cluster metadata, leader election (KRaft = ZK-free since Kafka 3.x).
Internals
  • Messages appended to segment files. Retention by time or size.
  • Consumer tracks offset in __consumer_offsets topic.
  • Exactly-once: idempotent producer + transactional API.
  • Page cache: Kafka relies on OS page cache for near-disk-speed throughput.

9 Explain eventual consistency vs strong consistency
consistencycappaxos
Medium 84%
Strong Consistency
All nodes see the same data at the same time. After a write completes, all reads return the new value. Requires synchronous replication. Used in: financial systems, leader election (etcd, ZooKeeper).
Eventual Consistency
Given no new updates, all replicas will eventually converge. Reads may return stale data temporarily. Higher availability and partition tolerance. Used in: DNS, S3, DynamoDB (default), Cassandra.
CAP Theorem
In presence of network Partition, choose Consistency OR Availability:
  • CP: HBase, MongoDB (primary), etcd, ZooKeeper — prefer consistency over availability
  • AP: Cassandra, DynamoDB, CouchDB — prefer availability over consistency
  • CA systems only work without partitions (single node databases)
PACELC
Extension of CAP: Even without partitions, trade-off exists between Latency and Consistency.

public class TradeReportUploader {

    private final String bucket = "mufg-trade-reports";

    public void uploadReport(String tradeDate, byte[] pdfBytes) {
        String key = String.format("reports/%s/trade-report.pdf", tradeDate);
        s3.putObject(
            PutObjectRequest.builder()
                .bucket(bucket)
                .key(key)
                .contentType("application/pdf")
                .serverSideEncryption(ServerSideEncryption.AWS_KMS)  // encrypt at rest
                .build(),
            RequestBody.fromBytes(pdfBytes)
        );
    }

    public URL generatePresignedUrl(String key) {
        S3Presigner presigner = S3Presigner.create();
        PresignedGetObjectRequest req = presigner.presignGetObject(r ->
            r.signatureDuration(Duration.ofMinutes(15))
             .getObjectRequest(g -> g.bucket(bucket).key(key)));
        return req.url();
    }
}

13 Distributed transactions: 2PC vs Saga
2pcsagadistributed-tx
Hard 80%
2PC — Two-Phase Commit
Phase 1 (Prepare): Coordinator sends PREPARE to all participants. Each votes YES (prepared, locked) or NO.
Phase 2 (Commit/Abort): If all YES → send COMMIT; if any NO → send ABORT.
Problems: Coordinator failure in phase 2 → participants stuck holding locks. Blocking protocol. Network partition → split brain possible.
Saga Pattern
Choreography: Each service publishes event → next service reacts. No central coordinator. Decoupled but hard to trace.
Orchestration: Saga Orchestrator sends commands to each service, receives replies. Easier to manage state.
Compensating transactions: On failure, execute rollback steps in reverse order.
Example: E-commerce order
1. Reserve inventory → 2. Debit payment → 3. Assign delivery → 4. Confirm order
Failure at step 3: Release payment (compensate) → Release inventory (compensate)

• How does the Outbox Pattern ensure reliable event publishing with Saga?

14 What is idempotency and why critical?
idempotencyapipayments
Medium 80%
Idempotency
An operation is idempotent if performing it multiple times has the same effect as performing it once. Critical for retry logic in distributed systems (network timeouts, retries).
Implementation
# Client sends unique idempotency key
POST /payments
Idempotency-Key: client-generated-uuid-v4
{
  "amount": 1000,
  "currency": "INR"
}

# Server:
INSERT INTO payments (idempotency_key, status, result)
VALUES ('uuid', 'PROCESSING', NULL)
ON CONFLICT (idempotency_key) DO NOTHING
RETURNING *;

# If conflict → return stored result (same response for same key)
HTTP Methods
  • Idempotent by nature: GET, PUT, DELETE, HEAD, OPTIONS
  • NOT idempotent: POST (each call creates new resource)
  • Make POST idempotent with idempotency key header

15 How would you implement distributed locks?
redisredlockzookeeper
Hard 80%
Distributed Locks
Requirements: Mutual exclusion, no deadlock, fault tolerance, lock expiry.
Redis SET NX EX (simple)
SET resource_key unique_token NX EX 30  # NX: only if not exists, EX: expire 30s
# Release: Lua script to check token before delete (atomic)
if redis.call('GET', key) == token then
    redis.call('DEL', key)
end
Redlock (HA Redis)
Acquire lock on N/2+1 independent Redis nodes. If majority acquired within validity time → lock granted. Release on all nodes. Controversial: Martin Kleppmann argues it's unsafe with clock drift.
ZooKeeper Ephemeral Nodes
Create sequential ephemeral node. Lock acquired if lowest sequence number. On disconnect: ZK auto-deletes ephemeral node → no zombie locks. More reliable than Redis.
Fencing Tokens
Lock returns a monotonically increasing token. Storage layer rejects requests with stale token. Prevents GC pauses or clock drift from causing split-brain.
Follow-ups
• Why does Redlock fail under process pauses? (Martin Kleppmann paper)
• What is the difference between pessimistic and optimistic locking?
• How does etcd implement distributed locks? (lease + watch)

17 Explain the circuit breaker pattern
circuit-breakerhystrix
Medium 78%
Circuit Breaker States
  • CLOSED: Normal operation. Failure counter tracks errors. If failures > threshold → OPEN.
  • OPEN: All calls fail immediately (fail-fast). No downstream load. After timeout → HALF_OPEN.
  • HALF_OPEN: Allow one probe request. If succeeds → CLOSED. If fails → OPEN again.
Why it matters
Without circuit breaker: one slow service causes thread pool exhaustion in caller → cascading failure across the system. Circuit breaker prevents this by failing fast and giving downstream service recovery time.
Libraries
  • Resilience4j (Java): sliding window (count/time based), bulkhead pattern
  • Hystrix (deprecated): used at Netflix, pioneered the pattern
  • Go: sony/gobreaker, mercadolibre/go-breakers
Follow-ups
• What is the bulkhead pattern and how does it complement circuit breaker?
• How do you set the right failure threshold to avoid flapping?
• What is the difference between circuit breaker and retry with exponential backoff?

20 Blue-green vs Canary vs Rolling deployments
deploymentcanaryzero-downtime
Medium 74%
Deployment Strategies
  • Blue-Green: Two identical environments. New version deployed to 'green'. Switch traffic instantly. Easy rollback: flip back to 'blue'. Requires 2x infrastructure.
  • Canary: Route small % of traffic (1-5%) to new version. Monitor error rates / latency. Gradually increase if healthy. Slow, but minimizes blast radius.
  • Rolling: Replace instances one at a time (or in batches). Both versions run simultaneously. No extra infrastructure. Standard Kubernetes Deployment behavior.
  • Feature Flags: Deploy code disabled; enable per-user/segment at runtime. Decouple deploy from release.
In Kubernetes
# Canary with Argo Rollouts:
apiVersion: argoproj.io/v1alpha1
kind: Rollout
spec:
  strategy:
    canary:
      steps:
      - setWeight: 5    # 5% traffic to new
      - pause: {duration: 10m}
      - setWeight: 50
      - pause: {duration: 10m}
      - setWeight: 100

25 Explain CQRS and Event Sourcing
cqrsevent-sourcingread-model
Hard 66%
CQRS — Command Query Responsibility Segregation
Separate write model (commands: create, update, delete) from read model (queries: optimized for reads). Read model can be denormalized, use different database (e.g., Elasticsearch for search, Redis for fast reads). Scales independently.
Event Sourcing
State is derived from a sequence of immutable events, not current state snapshot. Events are appended to an event store (log). State reconstructed by replaying events.
Events: OrderPlaced → ItemAdded → PaymentProcessed → OrderShipped
Current state: replay all events → Order{status=SHIPPED, items=[...], payment=PAID}
Benefits and Costs
  • Benefits: Full audit log, time travel (replay to any point), event-driven integration
  • Costs: Eventual consistency between command and query model, complex querying, schema evolution of events, snapshot needed for long histories
Follow-ups
• How do you handle schema evolution of events in Event Sourcing?
• What is a projection in Event Sourcing?
• What is the Outbox Pattern and how does it prevent dual-write problems?
