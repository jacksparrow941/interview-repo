1 TCP 3-way handshake, 4-way termination, TIME_WAIT
tcphandshakesyn
Medium 92%
3-Way Handshake (Connection Setup)
Client ----- SYN (seq=x) --------> Server
Client <---- SYN-ACK (seq=y,ack=x+1)- Server
Client ----- ACK (ack=y+1) -------> Server
[Connection ESTABLISHED]

SYN_SENT → SYN_RECEIVED → ESTABLISHED
Purpose: synchronize initial sequence numbers, agree on connection parameters.
4-Way Termination
Active  --- FIN ---> Passive   (ACTIVE: FIN_WAIT_1)
Active  <-- ACK --- Passive   (ACTIVE: FIN_WAIT_2)
Active  <-- FIN --- Passive   (PASSIVE: sends own FIN)
Active  --- ACK --> Passive   (ACTIVE: TIME_WAIT → CLOSED after 2×MSL)
TIME_WAIT (2×MSL ≈ 60s-4min)
  • Ensures last ACK reaches passive closer
  • Prevents old duplicate packets from confusing new connection on same port
  • Causes: Cannot reuse port immediately. SO_REUSEADDR allows reuse in server context.
Follow-ups
• Why does the client go into TIME_WAIT, not the server?
• What is SYN flood attack and how is SYN cookies a defense?
• What is TCP Fast Open (TFO)?

2 TCP vs UDP — when to use each?
tcpudpreliability
Easy 90%
TCP vs UDP
  • TCP: Connection-oriented (3-way handshake). Reliable (ACKs, retransmit). Ordered. Flow + congestion control. ~20-60byte headers. Higher latency.
  • UDP: Connectionless. No guarantees. No ordering. No congestion control. ~8byte header. Lower latency. Can multicast.
When to use UDP
  • Gaming / VoIP / video calls: stale data worse than loss. TCP retransmit would cause jitter.
  • DNS: single request-response, small payload. Retry at app layer if timeout.
  • DHCP, TFTP, SNMP: simple protocols where TCP overhead isn't worth it.
  • HTTP/3 (QUIC): UDP + built-in reliability at QUIC layer — gets benefits of both.
Follow-ups
• What is QUIC and why does it use UDP?
• How do game engines handle packet loss with UDP? (delta compression, interpolation)
• What is the difference between TCP TIME_WAIT and CLOSE_WAIT?

3 Load balancer algorithms — round-robin, least-connections, consistent hashing
load-balancerround-robinconsistent-hashing
Medium 90%
Algorithms
  • Round Robin: Requests distributed evenly in rotation. Simple, ignores server load.
  • Weighted Round Robin: Servers with higher weight get more requests. For heterogeneous servers.
  • Least Connections: Route to server with fewest active connections. Better for varying request durations.
  • Least Response Time: Combines active connections + response latency.
  • IP Hash: Hash client IP → fixed server. Session stickiness (but unbalanced if some IPs dominate).
  • Random with 2 Choices (Power of Two): Pick 2 random servers, choose less loaded. Near-optimal, simple.
Consistent Hashing
Used for stateful routing (cache sharding, WebSocket servers).
Hash ring: servers placed on ring. Request hashed → clockwise to nearest server. Adding/removing server only remaps 1/N of keys (vs modulo hashing remaps all).
L4 vs L7 Load Balancer
  • L4 (Transport): Routes by TCP/UDP (IP + port). Faster, less overhead. No content awareness.
  • L7 (Application): Routes by HTTP headers, URL, cookies. Content-based routing, SSL termination, retries.
Follow-ups
• How does HAProxy differ from Nginx as a load balancer?
• What are virtual nodes in consistent hashing and why are they needed?
• How does a global load balancer (Anycast, GeoDNS) work?

4 REST vs gRPC vs GraphQL vs WebSocket — when to use each
restgrpcgraphql
Medium 90%
REST
HTTP/1.1 or 2, JSON/XML. Stateless, simple, widely supported. Cacheable (GET), intuitive with HTTP verbs. Cons: over-fetching/under-fetching, multiple round trips for related data. Best for: public APIs, simple CRUD, browser-to-server.
gRPC
HTTP/2 + Protocol Buffers. Binary, strongly typed, multiplexed. 5-10x smaller payload than JSON. Bidirectional streaming, connection reuse. Generated client/server code. Cons: not human-readable, no native browser support (grpc-web workaround). Best for: internal microservice communication, real-time streaming, polyglot services.
GraphQL
Single endpoint, client specifies exact data shape. Eliminates over-fetching. Subscriptions for real-time. Schema as contract. Cons: N+1 problem (use DataLoader), complex caching (no HTTP cache headers), schema overhead. Best for: complex UIs with diverse data needs (mobile apps, dashboards).
WebSocket
Full-duplex, persistent TCP connection. Low-latency bidirectional. Best for: chat, live collaboration, gaming, stock tickers, notifications.
Quick Decision
  • Public CRUD API → REST
  • Microservice-to-microservice → gRPC
  • Complex queries, mobile app → GraphQL
  • Real-time bidirectional → WebSocket
  • Server→client notifications → SSE
Follow-ups
• How does gRPC handle service discovery?
• What is the N+1 problem in GraphQL and how does DataLoader solve it?
• How do you version a REST API vs a GraphQL API?

5 TCP three-way handshake
tcpsynack
Easy 88%
TCP Handshake
Client          Server
  |---SYN(seq=x)---->|  Client: CLOSED→SYN_SENT
  |<--SYN-ACK(seq=y,ack=x+1)---|
  |---ACK(ack=y+1)-->|  Both: ESTABLISHED

Teardown (4-way):
  |---FIN----------->|  Client: ESTABLISHED→FIN_WAIT_1
  |<--ACK-----------|
  |<--FIN-----------|
  |---ACK----------->|  Client: TIME_WAIT (2×MSL = 60-120s)
                       Server: CLOSED
TIME_WAIT purpose
Ensures delayed packets from old connection don't confuse new connection on same 4-tuple. 2×MSL (Maximum Segment Lifetime). Can cause port exhaustion on high-traffic servers. Fix: SO_REUSEADDR, SO_REUSEPORT, or increase local port range.
SYN Flood
Attacker sends many SYN packets, never completes handshake. Server holds half-open connections (SYN_RCVD state). Defense: SYN cookies — encode state in ISN, allocate resources only after ACK.
Follow-ups
• Why is teardown 4-way but handshake is 3-way?
• What is TCP Fast Open (TFO) and how does it reduce latency?
• What is the maximum number of connections per IP:port pair?

6 HTTP/2 vs HTTP/3 (QUIC) — feature comparison
http2http3quic
Hard 88%
HTTP/2 Features
  • Multiplexing: Multiple streams over one TCP connection. No request queuing.
  • Header compression (HPACK): Reduce redundant headers (cookies, user-agent)
  • Server push: Server proactively sends resources before client requests
  • Binary framing: Efficient parsing vs text-based HTTP/1.1
  • Stream priority: Weighted dependency tree
  • Problem: TCP head-of-line blocking — one lost packet blocks ALL streams
HTTP/3 / QUIC
  • Runs over UDP, not TCP. Implements reliable delivery in userspace.
  • Stream-level reliability: Lost packet blocks only affected stream, not all
  • 0-RTT connection setup: QUIC + TLS 1.3 combined handshake (1-RTT new, 0-RTT resume)
  • Connection migration: Connection ID-based, survives IP change (WiFi → 4G)
  • QPACK: Header compression without HOL blocking (vs HPACK)
When HTTP/3 helps
High latency (mobile), packet loss, many parallel requests, clients switching networks. Major adopters: Google, Meta, Cloudflare, YouTube.
Follow-ups
• What is head-of-line blocking at TCP level?
• Why does QUIC run over UDP instead of redesigning TCP?
• How does server push in HTTP/2 compare to HTTP/103 Early Hints?

7 DNS resolution — full chain from browser to authoritative server
dnsresolverauthoritative
Medium 88%
Full Resolution Chain
1. Browser cache (TTL based)
2. OS cache / /etc/hosts
3. Stub Resolver → Recursive Resolver (ISP or 8.8.8.8)
4. Recursive Resolver cache
5. Root Name Server ("." zone) → returns NS for .com
6. TLD Name Server (.com zone) → returns NS for google.com
7. Authoritative Name Server (google.com zone) → returns A record
8. Recursive Resolver caches result (TTL seconds)
9. Returns to client → browser connects
Record Types
  • A: Domain → IPv4
  • AAAA: Domain → IPv6
  • CNAME: Alias → canonical name (followed recursively)
  • MX: Mail exchange server
  • TXT: SPF, DKIM, domain verification
  • NS: Authoritative name servers for domain
  • SRV: Service discovery (host + port + priority)
DNS in Kubernetes
CoreDNS runs as a pod. Service DNS: <service>.<namespace>.svc.cluster.local. Pods: <pod-ip>.<namespace>.pod.cluster.local.
Follow-ups
• What is DNSSEC and what does it protect against?
• How does DNS-based load balancing work? (multiple A records, low TTL)
• What is negative caching (NXDOMAIN) and its TTL?

8 TLS 1.3 handshake — 1-RTT and 0-RTT
tlstls1.3handshake
Hard 86%
TLS 1.3 Full Handshake (1-RTT)
Client → Server: ClientHello + key_share (ECDHE public key) + supported ciphers
Server → Client: ServerHello + key_share (server ECDHE public key)
                  + Certificate + CertificateVerify + Finished
[Both derive session keys immediately from shared ECDHE secret]
Client → Server: Finished + HTTP request
[TLS 1.2 needed 2-RTT; TLS 1.3 = 1-RTT]
0-RTT Session Resumption
Client stores session ticket from previous connection. On reconnect, sends early data in first packet — zero round trips before HTTP request. Risk: replay attacks (early data not protected against replay). Mitigate: use only for idempotent requests.
Key Improvements over TLS 1.2
  • 1-RTT instead of 2-RTT for new connections
  • Forward secrecy mandatory: ECDHE always used (ephemeral keys)
  • Removed weak algorithms: RSA key exchange, RC4, SHA-1, MD5
  • Encrypted handshake: Certificate encrypted (hidden from observers)
Certificate Verification
Client verifies server cert chain up to trusted CA root. CT (Certificate Transparency) logs prevent mis-issuance. OCSP stapling for revocation.
Follow-ups
• What is perfect forward secrecy and why does ECDHE provide it?
• How does mTLS (mutual TLS) work for service-to-service auth?
• What is certificate pinning and when is it used?

WebSocket Frame
Binary or text frames. Control frames: ping/pong/close. Low overhead: 2-14 byte header vs HTTP's ~500 byte headers per request.
Comparison
  • WebSocket: Full-duplex, persistent, binary/text. Chat, gaming, trading, collaboration.
  • SSE (Server-Sent Events): Server→client only, over HTTP/1.1, auto-reconnect. Dashboards, notifications. Simpler than WS.
  • Long Polling: Client holds HTTP request open until server has data. Fallback. High latency, wasteful.
Scaling WebSockets
Stateful — connection pinned to server. Use:
  • Sticky sessions (HAProxy/Nginx)
  • Message broker for fan-out: Pub/Sub via Redis, Kafka, or NATS
  • Socket.IO: WS with fallback to long-polling

10 CORS — same-origin policy, preflight, headers
corssame-originpreflight
Medium 86%
Same-Origin Policy
Browser blocks cross-origin requests by default. Origin = scheme + host + port. https://api.com:443 ≠ http://api.com:80.
Simple vs Preflight Requests
Simple: GET/POST/HEAD with safe headers → no preflight. Browser sends request with Origin header; server must return Access-Control-Allow-Origin.

Preflight (OPTIONS): Triggered for: non-simple methods (PUT/DELETE/PATCH), custom headers, content-type=application/json.
OPTIONS /api/data HTTP/1.1
Origin: https://app.example.com
Access-Control-Request-Method: DELETE
Access-Control-Request-Headers: Authorization

--- Server response:
Access-Control-Allow-Origin: https://app.example.com
Access-Control-Allow-Methods: GET, POST, DELETE
Access-Control-Allow-Headers: Authorization
Access-Control-Max-Age: 86400  # cache preflight for 1 day
Credentialed Requests
Cookies/auth headers in cross-origin require:
Access-Control-Allow-Credentials: true AND Access-Control-Allow-Origin must be specific (not *).
Follow-ups
• Does CORS prevent all cross-origin attacks? (No — doesn't protect server from CSRF)
• What is CSRF and how is it different from what CORS prevents?
• How does a wildcard origin (*) work with credentials?

11 OAuth 2.0 flows — Authorization Code, Client Credentials, PKCE
oauth2authorization-codepkce
Hard 86%
Authorization Code Flow (Web Apps)
1. User clicks 'Login with Google'
2. App redirects to Google: /auth?client_id=..&redirect_uri=..&scope=email&state=random
3. User logs in on Google, grants consent
4. Google redirects to app with ?code=AUTH_CODE&state=...
5. App server exchanges code for tokens: POST /token {code, client_secret}
6. Gets: access_token (short-lived), refresh_token (long-lived)
7. App uses access_token to call APIs on user's behalf
PKCE (Proof Key for Code Exchange)
For mobile/SPA apps that can't store client_secret securely.
  • App generates code_verifier (random), code_challenge = SHA256(verifier)
  • Sends challenge in auth request, sends verifier in token exchange
  • Server verifies: SHA256(verifier) == challenge → prevents auth code interception
Client Credentials (Machine-to-Machine)
POST /token
client_id=svc1&client_secret=secret&grant_type=client_credentials
→ access_token (no user context)
# Used for: microservice-to-microservice, background jobs
JWT Access Token
Access tokens are often JWTs: header.payload.signature. Resource servers validate signature without calling authorization server. Payload contains: sub (user), iat, exp, scope, aud.

14 CDN architecture — how content is cached and served
cdnedgepop
Medium 84%
CDN Architecture
Points of Presence (PoPs): Edge servers distributed globally (Cloudflare: 300+ PoPs, Akamai: 4000+). User request routed to nearest PoP via Anycast (same IP, BGP routes to nearest datacenter) or GeoDNS.
Cache Flow
User → CDN Edge (PoP)
  → Cache HIT: return immediately (<5ms)
  → Cache MISS: fetch from origin (100-300ms), cache response, serve

Subsequent users at same PoP → cache HIT
Users at different PoP → may still be cache MISS (PoP-local cache)
Cache Control Headers
Cache-Control: max-age=31536000, immutable     # 1 year, static assets
Cache-Control: max-age=60, stale-while-revalidate=30  # 1min fresh, serve stale while revalidating
Cache-Control: no-store                         # never cache (auth pages)
Surrogate-Control: max-age=3600                 # CDN-only hint (Varnish/Fastly)
Vary: Accept-Encoding                           # different cache per encoding
Dynamic Content
Not all content is cacheable. Edge computing (Cloudflare Workers, Lambda@Edge) runs logic at edge. For personalized content: cache fragment (Edge Side Includes) or stream-stitch.
Follow-ups
• How do you purge CDN cache? (cache invalidation API, cache tags)
• What is cache stampede / thundering herd and how to prevent it?
• How does TLS termination at CDN edge work?

17 TCP flow control (receive window) vs congestion control (CWND)
tcpflow-controlcongestion
Hard 82%
Flow Control (Receiver-side)
Prevents sender from overwhelming receiver's buffer.
Receiver advertises receive window (rwnd) in ACK headers. Sender must not have more than rwnd unacknowledged bytes in flight.
Congestion Control (Network-side)
Prevents sender from overwhelming the network (routers/links).
Sender maintains congestion window (cwnd). Effective window = min(cwnd, rwnd).
Congestion Control Phases
  • Slow Start: cwnd=1 MSS → doubles each RTT until ssthresh or packet loss
  • Congestion Avoidance: cwnd grows +1 MSS per RTT (linear)
  • Fast Retransmit: 3 duplicate ACKs → retransmit lost segment immediately (don't wait for timeout)
  • Fast Recovery (CUBIC, BBR): On loss: ssthresh = cwnd/2, cwnd = ssthresh (not back to 1)
BBR (Google)
Model-based congestion control. Estimates bottleneck bandwidth and RTT. Less reactive to loss, better for high-bandwidth long-distance links. Used in YouTube, cloud networking.
Follow-ups

• What is ECN (Explicit Congestion Notification)?
• How does QUIC handle congestion control differently from TCP?

18 What is a CDN and how does it work?
cdnedgeanycast
Medium 80%
CDN Architecture
  • Edge PoPs (Points of Presence): Hundreds of locations near users
  • Anycast routing: Same IP announced from multiple locations, BGP routes to nearest
  • Cache hierarchy: Edge → Regional → Origin
Cache Invalidation
  • TTL-based: Simple. Stale content during TTL window.
  • Purge API: CloudFront invalidation, Fastly instant purge. On deploy.
  • Versioned URLs: /static/app.v5.js — never expires. Best for static assets.
  • Cache-Control: max-age=31536000, immutable for fingerprinted assets
Pull vs Push CDN
  • Pull: CDN fetches from origin on first request (cache miss). Simple. Good for dynamic content.
  • Push: You upload content to CDN proactively. Good for large files, predictable access patterns.
Follow-ups
• How does Cloudflare Workers extend CDN to edge compute?
• How do you handle geo-restricted content on CDN?
• What is the difference between Anycast and unicast routing?
