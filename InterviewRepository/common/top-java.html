1 HashMap vs ConcurrentHashMap — thread safety and internal differences
hashmapconcurrenthashmapthread-safety
Medium 95%
HashMap (Not Thread-Safe)
Array of Node<K,V> buckets. Hash → bucket via (n-1)&hash. Collisions: linked list → red-black tree at TREEIFY_THRESHOLD=8. Resizes (doubles) at 75% load. Multi-threaded writes: race on resize, data loss, infinite loop (Java 7).
ConcurrentHashMap (Thread-Safe)
Java 8+: CAS + synchronized per bucket (not the whole map). Reads are lock-free (volatile). No null keys/values (unlike HashMap). Iteration is weakly consistent — no ConcurrentModificationException.
Code
Map<String,Integer> cmap = new ConcurrentHashMap<>();
cmap.put("TXN-001", 5000);
cmap.putIfAbsent("TXN-001", 3000);         // atomic
cmap.compute("TXN-001", (k,v)-> v+1);      // atomic increment
// Banking: CHM used for dedup cache (idempotency key → status)
Key Differences
  • Null key/val: HashMap ✓, CHM ✗
  • Locking: none vs per-bucket CAS/sync
  • size(): exact vs approximate (sumCount)
  • CHM >> Collections.synchronizedMap() under contention
Follow-ups
• putIfAbsent vs computeIfAbsent — difference?
• Why is CopyOnWriteArrayList useful for rarely-written lists?
• How does CHM handle resize concurrently?

2 JVM memory model: heap, stack, metaspace
jvmmemorygc
Medium 92%
JVM Memory Areas
  • Heap: All objects (new). Divided into Young (Eden + 2 Survivors) + Old/Tenured. GC managed.
  • Stack: Per-thread. Holds stack frames: local variables, operand stack, method calls. Fixed size (typically 512KB-1MB). StackOverflowError if exceeded.
  • Metaspace (Java 8+): Class metadata (class bytecode, method data). Native memory, grows dynamically. Replaced PermGen which had fixed max size.
  • Code Cache: JIT-compiled native code.
  • Direct Memory: Off-heap via NIO ByteBuffer.allocateDirect(). Not GC'd, must be freed explicitly.
Tuning Flags
-Xms512m -Xmx4g       # initial and max heap
-XX:MetaspaceSize=256m # initial metaspace
-XX:MaxMetaspaceSize=512m
-Xss512k               # thread stack size

• What is object header size in JVM? (12-16 bytes: mark word + klass pointer)

3 How to use a POJO as a key in HashMap — hashCode/equals contract
hashmappojohashcode
Medium 92%
The Problem
HashMap uses hashCode() to find the bucket, equals() to match the key. Without overriding both, default Object identity is used — two logically equal POJOs go to different buckets.
Contract
  • If a.equals(b) → a.hashCode()==b.hashCode() (mandatory)
  • Reverse not required (collision allowed)
  • Never mutate fields used in hashCode while object is a map key
Correct Implementation
public final class TradeKey {          // final fields = safe as key
    private final String tradeId;
    private final String bookId;

    @Override public boolean equals(Object o) {
        if (!(o instanceof TradeKey)) return false;
        TradeKey k = (TradeKey) o;
        return Objects.equals(tradeId, k.tradeId)
            && Objects.equals(bookId, k.bookId);
    }
    @Override public int hashCode() {
        return Objects.hash(tradeId, bookId);
    }
}
// Map.get(new TradeKey("TXN-001","BOOK-A")) — finds the entry correctly

• Can an enum be a safe HashMap key? (yes — identity-based equals + stable hashCode)

6 HashMap internals in Java 8+
hashmaptreeifycollision
Medium 90%
HashMap Internals
// Java 8+ structure:
// Node<K,V>[] table  (array of buckets, power of 2 size)
// Each bucket: null | Node (linked list) | TreeNode (red-black tree)

// Hash calculation:
static int hash(Object key) {
    int h;
    return (key == null) ? 0 : (h = key.hashCode()) ^ (h >>> 16);
    // XOR high bits into low bits — better distribution
}
// Bucket index: (n-1) & hash  (n = table length, power of 2)
Thresholds
  • TREEIFY_THRESHOLD = 8: Bucket with >8 nodes → convert to red-black tree (O(log n) per op)
  • UNTREEIFY_THRESHOLD = 6: Tree shrinks back to list on removal
  • LOAD_FACTOR = 0.75: Resize (double) when size/capacity > 0.75
Thread Safety
HashMap is NOT thread-safe. Use ConcurrentHashMap (lock-striping, CAS) or Collections.synchronizedMap() (coarse lock).

• Why XOR high bits into low bits in hash()? (prevents collision when table size is small)

public TradeBookingResult bookTrade(TradeRequest req) {
    ExecutorService pool = Executors.newFixedThreadPool(10);

    CompletableFuture<FxRate> fxFuture =
        CompletableFuture.supplyAsync(() -> fxService.getRate(req.getCurrency()), pool)
            .orTimeout(500, TimeUnit.MILLISECONDS)
            .exceptionally(ex -> FxRate.fallback());

    CompletableFuture<Counterparty> cpFuture =
        CompletableFuture.supplyAsync(() -> cpService.get(req.getCounterpartyId()), pool);

    CompletableFuture<LimitCheck> limitFuture =
        CompletableFuture.supplyAsync(() -> limitService.check(req), pool);

    CompletableFuture.allOf(fxFuture, cpFuture, limitFuture).join();

    if (!limitFuture.join().isApproved())
        throw new LimitBreachException();

    return tradeRepo.save(Trade.builder()
        .amount(req.getAmount().multiply(fxFuture.join().getRate()))
        .counterparty(cpFuture.join())
        .build());
}

10 ThreadPoolExecutor — all 7 parameters explained

Constructor Parameters
new ThreadPoolExecutor(
    int corePoolSize,      // threads always alive
    int maximumPoolSize,   // max threads under load
    long keepAliveTime,    // idle non-core thread timeout
    TimeUnit unit,

Sizing Strategy
  • CPU-bound: core = max = N_CPU + 1
  • I/O-bound: core = N_CPU × (1 + wait/compute). Use virtual threads (Java 21) instead.
  • Queue type: LinkedBlockingQueue (unbounded, dangerous), ArrayBlockingQueue (bounded, triggers max threads), SynchronousQueue (handoff, always spawns threads)
Rejection Policies
  • AbortPolicy: throw RejectedExecutionException (default)
  • CallerRunsPolicy: run task in caller thread (natural backpressure)
  • DiscardPolicy: silently drop task
  • DiscardOldestPolicy: drop oldest queued task
Thread Lifecycle
core threads → fill queue → spawn non-core threads to maxPoolSize → reject

Why JMM Matters in Banking
Without JMM guarantees: Thread A writes trade status=SETTLED, Thread B reads stale PENDING from CPU cache → double settlement!
Happens-Before Rules
  Rule                      | Guarantee
  --------------------------+-----------------------------
  Program order             | Actions in thread are ordered
  Monitor lock (sync block) | unlock HB next lock
  volatile write/read       | write HB subsequent read
  Thread.start()            | start() HB any action in thread
  Thread.join()             | all actions HB join() return
volatile vs synchronized vs AtomicLong
// volatile: visibility ONLY, no atomicity
private volatile boolean running = true;   // safe for simple flag
private volatile long counter = 0;          // NOT safe for i++!

// synchronized: visibility + atomicity
private long counter = 0;
public synchronized void increment() { counter++; }  // safe

// AtomicLong: lock-free CAS — best for high-contention counters
private final AtomicLong tradeCount = new AtomicLong(0);
tradeCount.incrementAndGet();  // CAS at CPU level

// Double-checked locking — MUST use volatile
private static volatile TradeCache instance;
public static TradeCache getInstance() {
    if (instance == null) {
        synchronized (TradeCache.class) {
            if (instance == null)
                instance = new TradeCache();  // volatile ensures write visible
        }
    }
    return instance;
}

HashMap
Array of Node<K,V> buckets. Hash → index via (n-1) & hash. Collision: linked list, then treeify at threshold 8 (TREEIFY_THRESHOLD). Resize (double) at 75% load factor. Java 8: balanced BST (TreeNode) for long chains.

Extends HashMap. Adds doubly-linked list through all entries maintaining insertion order. Can be configured for access order (LRU behaviour) with constructor parameter.

CountDownLatch
One-time gate. Threads await() until count reaches 0 via countDown(). Cannot be reset.
CountDownLatch latch = new CountDownLatch(3);
// 3 workers call latch.countDown() when done
latch.await();  // main thread blocks until all 3 done
CyclicBarrier
Reusable rendezvous point. All N threads call await() and block until all arrive. Then all proceed.
CyclicBarrier barrier = new CyclicBarrier(3, () -> System.out.println("phase done"));
// Each thread calls barrier.await() — blocked until 3 threads reach barrier

Controls access to N permits. acquire() blocks if 0 permits. release() returns one.
Semaphore sem = new Semaphore(5);  // max 5 concurrent threads

try { doWork(); } finally { sem.release(); }

phaser.arriveAndAwaitAdvance() — arrive + wait for next phase.

  • CyclicBarrier: parallel computation phases (map-reduce stages)

  • Phaser: complex multi-phase parallel algorithms

If A happens-before B, A's writes are visible to B.

44 Java GC algorithms — Mark-Sweep, Mark-Compact, Copying, Generational
gc-algorithmsmark-sweepgenerational
Hard 76%
Mark-Sweep
Mark: traverse GC roots, mark all reachable objects. Sweep: scan heap, free unmarked objects. Problem: fragmentation — free spaces scattered.
Mark-Compact
Mark phase same. Compact phase: slide all live objects to one end. No fragmentation. Slower than sweep (extra copy). G1GC uses this for selected regions.
Copying Collection
Divide heap into From/To spaces. Copy live objects to To, flip spaces. No fragmentation, fast allocation (bump pointer). Wastes 50% of heap. Used for young generation.
Generational Hypothesis
Most objects die young. Java heap split:
  • Young (Eden + 2 Survivors): Minor GC — fast, copying collector
  • Old (Tenured): Major/Full GC — mark-compact or concurrent marking
Promotion: object surviving N minor GCs (default 15) moves to Old gen.
G1GC
Divides heap into equal regions (~1-32MB). Marks concurrently. Selects regions with most garbage (Garbage-First) for collection. Pause target: -XX:MaxGCPauseMillis=200.

51 ReentrantReadWriteLock vs StampedLock
rwlockstampedlockoptimistic
Hard 72%
ReentrantReadWriteLock
Multiple concurrent readers OR one exclusive writer. Writer starvation risk if readers never release.
ReadWriteLock rwl = new ReentrantReadWriteLock();
Lock rl = rwl.readLock();
Lock wl = rwl.writeLock();

// Read
rl.lock(); try { return value; } finally { rl.unlock(); }
// Write
wl.lock(); try { value = newVal; } finally { wl.unlock(); }
StampedLock (Java 8)
Better throughput via optimistic reads — no lock acquisition for reads if no writer active.
StampedLock sl = new StampedLock();

// Optimistic read (no blocking):
long stamp = sl.tryOptimisticRead();
int val = value;                      // read without lock
if (!sl.validate(stamp)) {            // check if writer intervened
    stamp = sl.readLock();            // fallback to real read lock
    try { val = value; } finally { sl.unlockRead(stamp); }
}

// Write:
long ws = sl.writeLock();
try { value = newVal; } finally { sl.unlockWrite(ws); }
When to use
  • RRW Lock: read-heavy, need reentrant locking
  • StampedLock: read-heavy, max throughput, no reentrancy needed
  • Avoid StampedLock if writes are frequent (optimistic reads will always fail)
