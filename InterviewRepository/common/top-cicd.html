1 Docker container vs Virtual Machine — key differences?
dockervmcontainer
Easy 93%
Answer
Virtual Machine: Full OS per VM, hardware emulation via hypervisor (Type-1: bare metal, Type-2: hosted). Heavy: ~GBs, slow boot (~minutes), strong isolation.
Docker Container: Shares host OS kernel, isolates via Linux namespaces (PID, NET, MNT, UTS, IPC) + cgroups for resource limits. Lightweight: ~MBs, starts in milliseconds, process-level isolation.
Key Differences
  • Boot time: VM ~1-2 min | Container ~100ms
  • Size: VM ~GBs | Container ~MBs (shared layers)
  • Isolation: VM = full kernel isolation | Container = namespace isolation (kernel shared)
  • Use case: VM for multi-OS, strong isolation | Container for microservices, CI/CD
Follow-ups
• What Linux namespaces does Docker use? (PID, NET, MNT, IPC, UTS, USER)
• How do cgroups limit CPU/memory in containers?
• What is a container runtime? (runc, containerd, CRI-O)

2 Kubernetes architecture — explain all components
kubernetesapi-serveretcd
Hard 92%
Control Plane
  • kube-apiserver: REST API gateway; all kubectl commands go here. Validates, authenticates, stores to etcd.
  • etcd: Distributed KV store (Raft consensus). Single source of truth for all cluster state.
  • kube-scheduler: Watches unscheduled pods, assigns them to nodes based on resources, affinity, taints.
  • kube-controller-manager: Runs controllers (ReplicaSet, Node, Job, Endpoint) in reconciliation loops.
  • cloud-controller-manager: Integrates with cloud provider APIs (LB, volumes, routes).
Worker Nodes
  • kubelet: Agent on each node. Ensures containers in pods are running. Reports to API server.
  • kube-proxy: Manages iptables/IPVS rules for Service networking and load balancing.
  • Container Runtime: containerd or CRI-O. Pulls images, runs containers.
Flow: kubectl apply
kubectl apply → apiserver (auth+validate) → etcd (store)
→ controller-manager (create pods) → scheduler (assign node)
→ kubelet on node (pull image, start container)
Follow-ups
• What happens when the API server goes down?
• How does etcd leader election work?

3 How do Docker image layers work? (Union filesystem)
dockerlayersoverlay2
Medium 90%
Answer
Docker images are built as read-only layers stacked using a Union Filesystem (OverlayFS/AUFS). Each RUN, COPY, ADD instruction in a Dockerfile creates a new layer.

When a container runs, Docker adds a thin read-write layer on top (Copy-on-Write). Writes go to the container layer; reads search layers bottom-up.
Dockerfile Layer Example
FROM ubuntu:22.04          # Layer 1: base OS
RUN apt-get install -y java # Layer 2: java install
COPY app.jar /app/          # Layer 3: app binary
CMD ["java", "-jar", "/app/app.jar"]  # metadata only
Optimization Tips
  • Order layers from least to most frequently changing
  • Combine RUN commands to reduce layer count
  • Use .dockerignore to exclude build artifacts
  • Use multi-stage builds to discard build-time layers
Follow-ups
• What is docker build --cache-from?

4 Pod vs ReplicaSet vs Deployment vs StatefulSet
kubernetespoddeployment
Medium 90%
Pod
Smallest deployable unit. 1+ containers sharing network namespace and volumes. Ephemeral — deleted pods don't restart.
ReplicaSet
Ensures N pod replicas are always running. Uses label selectors. Rarely used directly — Deployments manage them.
Deployment
Manages ReplicaSets for stateless apps. Provides: rolling updates, rollback, pause/resume. kubectl rollout undo deployment/app for rollback.
StatefulSet
For stateful apps (databases, Kafka, ZooKeeper). Provides: stable pod names (pod-0, pod-1), stable DNS, ordered start/stop, per-pod PersistentVolumeClaims.
When to use what
  • Stateless API service → Deployment
  • Database (MySQL, Redis) → StatefulSet
  • One pod per node → DaemonSet
  • One-off batch job → Job/CronJob

6 Kubernetes Services — ClusterIP, NodePort, LoadBalancer, ExternalName
kubernetesserviceclusterip
Medium 88%
ClusterIP (default)
Exposes service on a cluster-internal IP. Only reachable within the cluster. kube-proxy creates iptables rules to load-balance across matching pods. Used for inter-service communication.
NodePort
Exposes service on each node's IP at a static port (30000-32767). nodeIP:nodePort routes to ClusterIP then to pods. OK for dev/testing, not production.
LoadBalancer
Provisions a cloud load balancer (AWS ALB/NLB, GCP LB) and assigns an external IP. Each service gets its own LB — expensive. Use Ingress for shared LB.
Ingress
Not a Service type but routes external HTTP(S) to ClusterIP services. L7 routing by host/path. One LB for many services. Needs an Ingress Controller (nginx, traefik, AWS ALB).

7 ConfigMaps vs Secrets in Kubernetes
kubernetesconfigmapsecrets
Easy 88%
ConfigMap
Stores non-sensitive configuration as key-value pairs. Mounted as environment variables or volume files. Plain text in etcd.
Secret
Stores sensitive data (passwords, tokens, TLS certs). Base64-encoded in etcd (NOT encrypted by default). Enable encryption at rest with EncryptionConfiguration. Types: Opaque, kubernetes.io/tls, kubernetes.io/dockerconfigjson, etc.
Usage
# Mount as env
env:
- name: DB_PASSWORD
  valueFrom:
    secretKeyRef:
      name: db-secret
      key: password

# Mount as volume
volumeMounts:
- name: config
  mountPath: /etc/config
volumes:
- name: config
  configMap:
    name: app-config
Best Practices
  • Use external secret managers: HashiCorp Vault, AWS Secrets Manager with External Secrets Operator
  • Never bake secrets into Docker images
  • RBAC: restrict Secret read access to specific ServiceAccounts

8 Git internals — rebase vs merge, when to use each
gitrebasemerge
Medium 88%
Merge
Creates a merge commit that ties two branches together. Preserves full history including branch structure. Safe for shared branches — never rewrites history.
git checkout main
git merge feature/login
# Creates commit: Merge branch 'feature/login'
Rebase
Replays commits from one branch onto another. Creates linear history. Rewrites commit SHAs — never rebase shared/public branches.
git checkout feature/login
git rebase main
# Moves feature commits on top of latest main
When to use
  • Merge: Merging feature into main (preserves context). Shared branches.
  • Rebase: Keeping feature branch up-to-date with main. Clean PR history. git pull --rebase.
  • Squash merge: Combine all feature commits into 1 clean commit on main.
Interactive Rebase
git rebase -i HEAD~3
# Options: pick, squash, fixup, reword, drop
Follow-ups

• How do you recover from a bad rebase? (git reflog)

9 Explain multi-stage Docker builds and why they matter
dockermulti-stagebuild
Medium 87%
Answer
Multi-stage builds use multiple FROM statements in one Dockerfile. Build artifacts are copied from one stage to another, discarding build-time dependencies from the final image.
Example: Go Application
# Stage 1: Build
FROM golang:1.22 AS builder
WORKDIR /app
COPY . .
RUN CGO_ENABLED=0 go build -o server .

# Stage 2: Minimal runtime (5MB vs 800MB!)
FROM scratch
COPY --from=builder /app/server /server
CMD ["/server"]
Benefits
  • Final image contains only runtime artifacts, no compiler/SDK
  • Security: smaller attack surface
  • Faster pulls and deployments
  • Build cache is still leveraged per stage
Follow-ups
• How do you pass build args between stages?
• What is docker build --target builder for?

10 What is Helm and what problem does it solve?
helmchartrelease
Medium 86%
What is Helm
Helm is the package manager for Kubernetes. It bundles K8s manifests into a Chart (a directory of YAML templates + values.yaml). Manages versioned releases, upgrades, and rollbacks.
Key Concepts
  • Chart: Package of K8s manifests (Deployment, Service, Ingress, etc.)
  • Release: A running instance of a chart in a cluster
  • Values: Configuration injected into templates at render time
  • Repository: Collection of charts (like npm/pip registry)
Common Commands
helm install myapp ./chart -f values.prod.yaml
helm upgrade myapp ./chart --set image.tag=v2.0
helm rollback myapp 1
helm template ./chart  # render YAML without installing
Helm vs Kustomize
  • Helm: Templating + packaging + release management. Better for distributing software.
  • Kustomize: Overlay-based patching, no templating. Better for environment-specific customization.

11 Prometheus + Grafana monitoring stack — how does it work?
prometheusgrafanametrics
Medium 86%
Prometheus
Pull-based metrics collection. Scrapes HTTP /metrics endpoints (Prometheus exposition format) at configurable intervals. Stores as time-series (metric + labels + timestamp + value).

Key components: scrape engine, TSDB (local), PromQL query language, Alertmanager integration.
PromQL Examples
# Request rate per second
rate(http_requests_total[5m])

# 99th percentile latency
histogram_quantile(0.99, rate(http_request_duration_seconds_bucket[5m]))

# CPU usage
100 - (avg by(instance)(rate(node_cpu_seconds_total{mode='idle'}[5m])) * 100)
Grafana
Visualization layer. Connects to Prometheus as a data source. Dashboards with panels (graphs, gauges, heatmaps). Alerting, annotations, templating for dynamic dashboards.
Full Stack: LGTM

12 Kubernetes HPA — Horizontal Pod Autoscaler, how does it work?
kuberneteshpaautoscaling
Medium 85%
How HPA works
HPA watches metrics (CPU, memory, custom) via the Metrics API and adjusts pod replica count.

Control loop (every 15s):
desiredReplicas = ceil(currentReplicas × currentMetric / targetMetric)
e.g., 3 pods at 90% CPU, target 50% → ceil(3 × 90/50) = 6 pods
Setup
kubectl autoscale deployment app \
  --cpu-percent=50 --min=2 --max=20

# Or declarative:
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
spec:
  scaleTargetRef:
    kind: Deployment
    name: app
  minReplicas: 2
  maxReplicas: 20
  metrics:
  - type: Resource
    resource:
      name: cpu
      target:
        type: Utilization
        averageUtilization: 50
VPA vs HPA vs KEDA
  • HPA: scales pod count (horizontal)
  • VPA: adjusts CPU/memory requests per pod (vertical) — requires restart
  • KEDA: event-driven scaling (queue depth, Kafka lag, cron)
Follow-ups
• What happens when HPA and VPA conflict?

13 Explain Kubernetes resource requests and limits — QoS classes
kubernetesresourcesqos
Medium 84%
Requests vs Limits
Requests: Minimum guaranteed resources. Used by scheduler to find a node with enough capacity.
Limits: Maximum allowed. CPU is throttled if exceeded. Memory: container is OOMKilled if exceeded.
QoS Classes
  • Guaranteed: requests == limits for all containers. Highest priority, last to be evicted.
  • Burstable: requests < limits. Medium priority.
  • BestEffort: No requests or limits set. First to be evicted under pressure.
Example
resources:
  requests:
    cpu: "250m"     # 0.25 CPU core
    memory: "256Mi"
  limits:
    cpu: "1000m"    # 1 CPU core
    memory: "512Mi"

GitOps: Git is the single source of truth for infrastructure and application state. All changes happen via PRs. An operator continuously reconciles cluster state with Git state.

15 Docker networking modes explained
dockernetworkingbridge
Medium 82%
Bridge (default)
Docker creates a virtual docker0 bridge. Containers get their own IP on 172.17.0.0/16. Containers communicate by container name (with --network). NAT for outbound traffic.
Host
Container shares the host's network namespace. No isolation, best performance. docker run --network=host nginx — port 80 on container is port 80 on host.
Overlay
Multi-host networking (Docker Swarm / Kubernetes). VXLAN encapsulation for container-to-container traffic across nodes.
None
No network interface. Maximum isolation. Used for batch processing with no network needs.
Kubernetes CNI
K8s uses CNI plugins (Calico, Flannel, Cilium) to implement pod networking. Cilium uses eBPF for high-performance, policy-aware networking.

18 How does Terraform manage infrastructure state?
terraformstateremote-backend
Medium 80%
State File
Terraform tracks real-world resources in a state file (terraform.tfstate). It maps config to actual cloud resources. Without state, Terraform can't know what already exists.
Remote State (production must-have)
# backend.tf
terraform {
  backend "s3" {
    bucket         = "my-tf-state"
    key            = "prod/terraform.tfstate"
    region         = "us-east-1"
    encrypt        = true
    dynamodb_table = "tf-lock"  # distributed locking
  }
}
Core Commands
terraform init    # download providers, init backend
terraform plan    # show what will change (diff)
terraform apply   # apply changes
terraform destroy # tear down resources
terraform import  # import existing resource into state
State Locking
DynamoDB table prevents concurrent state modifications. Always use remote backend with locking in teams.

19 How does distributed tracing work? (OpenTelemetry, Jaeger)
distributed-tracingopentelemetryjaeger
Medium 80%
Core Concepts
  • Trace: End-to-end journey of a request across services
  • Span: Single operation within a trace (has: traceID, spanID, parentSpanID, start/end time, attributes)
  • Context propagation: TraceID passed via HTTP headers (traceparent W3C standard, or X-B3-TraceId Zipkin)
OpenTelemetry
Vendor-neutral CNCF standard for instrumentation. SDK instruments code → exports to backend (Jaeger/Zipkin/Tempo/Datadog).

defer span.End()
