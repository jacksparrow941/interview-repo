1 Process vs Thread vs Goroutine
processthreadgoroutine
Medium 90%
Processes vs Threads
  • Process: Independent address space, separate heap/stack/code/data. Isolated — one process crash doesn't affect others. IPC needed (pipes, sockets, shared memory).
  • Thread: Shares address space (heap, code, global data) with other threads in same process. Has own stack + registers. Cheaper to create/switch than process. Direct memory sharing.
Context Switch Cost
  • Process switch: save/restore full CPU state + page table switch (TLB flush) → ~100μs
  • Thread switch (same process): save/restore registers, stack pointer. No TLB flush → ~1-10μs
  • Goroutine/fiber switch: userspace, ~100ns
Linux Internals
Both processes and threads are task_struct in Linux kernel. Threads created with CLONE_VM flag — share address space. fork() creates new address space.

2 I/O models — blocking, non-blocking, I/O multiplexing, async, signals
io-modelsblockingepoll
Hard 90%
5 I/O Models
  • Blocking I/O: Thread blocks until data ready. Simple. Scales poorly (1 thread/connection).
  • Non-blocking I/O: Returns EAGAIN immediately if no data. Polling loop wastes CPU.
  • I/O Multiplexing (select/poll/epoll): One thread watches many fds. Blocks on select, wakes when any fd ready. Efficient for many connections.
  • Signal-driven I/O (SIGIO): Signal when data ready. Complex, rarely used.
  • Async I/O (AIO, io_uring): Kernel does I/O, notifies completion. True async. io_uring (Linux 5.1+): submission/completion queues in shared memory, no syscall overhead.
epoll vs select vs poll
  • select: fd_set bitmap, max 1024 fds, O(n) scan, copies fd_set each call
  • poll: array of pollfd, no 1024 limit, still O(n) scan
  • epoll: O(1) event notification. Register fds once (epoll_ctl), wait (epoll_wait) returns only ready fds. Kernel red-black tree for O(log n) add/remove. Level-triggered or edge-triggered modes.
io_uring (Modern Linux)
Fully async: app submits I/O requests to SQ ring, kernel processes, posts completions to CQ ring. Zero syscall on fast path. Used in: Tokio (Rust), QEMU, PostgreSQL, Nginx.

3 Virtual memory — paging, page tables, TLB
virtual-memorypagingpage-table
Hard 88%
Virtual Memory
Each process has its own virtual address space (e.g., 0 to 2^48 on 64-bit). OS maps virtual pages → physical frames via page table. Allows: isolation between processes, overcommit memory, memory-mapped files, copy-on-write.
Multi-level Page Tables
64-bit systems use 4-level (x86-64) or 5-level page tables to reduce space. Each level is a 4KB page of 512 8-byte entries. Virtual address split:
[sign ext | L4 (9) | L3 (9) | L2 (9) | L1 (9) | Offset (12)]
TLB (Translation Lookaside Buffer)
Hardware cache for recent virtual→physical translations. TLB hit: 1 cycle. TLB miss: walk page table (several cycles + memory accesses). TLB flushed on context switch (unless ASID used). Huge pages (2MB/1GB) reduce TLB misses.
Page Fault
  • Minor: Page in memory but not mapped (memory-mapped file, copy-on-write) → map it
  • Major: Page not in memory → read from disk (swap). Expensive (~ms)
  • Invalid: Access to unmapped address → SIGSEGV

4 Deadlock — conditions, prevention, avoidance, detection
deadlockcoffmanbanker
Hard 88%
Coffman's Four Necessary Conditions
  • Mutual Exclusion: Resources not sharable
  • Hold and Wait: Process holds resource while waiting for another
  • No Preemption: Resources can't be forcibly taken
  • Circular Wait: T1→waits for T2→waits for T3→waits for T1
Breaking any one prevents deadlock.
Prevention
  • Eliminate Hold and Wait: Request all resources at once before starting
  • Allow Preemption: If waiting, release held resources (costly)
  • Eliminate Circular Wait: Global ordering of resources (always lock in same order)
Avoidance — Banker's Algorithm
Each process declares max resource claim. System checks if granting a request leaves system in safe state (all processes can complete). If unsafe → deny and wait. Used in theory; impractical for dynamic systems.
Detection and Recovery
Allow deadlocks to occur. Periodically run deadlock detector (wait-for graph cycle detection). Recovery: kill one victim process, or preempt + rollback resources.

5 Context switching — what and cost

Medium 86%
Scheduling Algorithms
  • FCFS: Non-preemptive. Convoy effect (short jobs wait behind long ones).
  • SJF: Shortest job first. Optimal average wait time. Requires knowing burst time.
  • Round Robin: Time quantum (10-100ms). Fair. High throughput for interactive tasks.
  • Priority Scheduling: Highest priority runs first. Risk of starvation (aging fixes this).
  • CFS (Linux): Virtual runtime. Always runs goroutine with minimum vruntime. Weighted fair sharing.
  • MLFQ: Multiple queues with decreasing priority + aging. Adapts to CPU vs I/O bound behavior.
Preemptive vs Non-Preemptive
Preemptive: OS can force context switch (timer interrupt). Necessary for interactive systems. Non-preemptive: process runs until done or blocks. Simpler but poor interactivity.

6 Deadlock conditions (Coffman)
deadlockmutual-exclusionhold-wait
Medium 86%
Coffman Conditions for Deadlock
ALL 4 must hold simultaneously for deadlock:
  • Mutual Exclusion: Resource can only be held by one process
  • Hold and Wait: Process holds resources while waiting for more
  • No Preemption: Resources can't be forcibly taken away
  • Circular Wait: Chain of processes each waiting for next in chain
Prevention Strategies
  • Break Hold and Wait: request all resources at once (but reduces concurrency)
  • Break Circular Wait: impose total ordering on lock acquisition (always lock A before B)
  • Allow Preemption: rollback and retry (used in databases)
  • Detection + Recovery: build wait-for graph, detect cycles, kill one process
Banker's Algorithm
Safe state check: simulate allocation, see if all processes can eventually complete. Grant request only if system remains in safe state. O(n²×m) too slow for real OS but used in theory.

7 Context switching — cost, what is saved/restored
context-switchregisterstlb-flush
Medium 86%
What is Context Switch
OS saving state of running process/thread and restoring another's. Triggered by: timer interrupt (preemption), syscall, I/O wait, voluntary yield.
Saved State
  • CPU registers: PC (instruction pointer), SP (stack pointer), general-purpose registers, EFLAGS
  • FPU/SIMD state (optional, lazy)
  • TLB entries (or flush TLB on switch — expensive on older hardware)
  • Process: page table base register (CR3 on x86) → TLB flush → 100s of ns extra
  • Thread (same process): no page table switch → cheaper (~1-10μs vs ~10-100μs)
Cost
Process switch: ~1-100μs depending on TLB state, cache warmth, address space size. Thread switch (same process): ~1-10μs. Goroutine/coroutine switch: ~100ns (no kernel, no TLB flush — all in userspace).
Reducing Context Switches
  • Thread pools (avoid creation overhead)
  • Async I/O / event loops (fewer threads, less switching)
  • CPU affinity (keep thread on same core → warm L1/L2 cache)
  • Lock-free algorithms (avoid blocking)
Follow-ups
• What is ASID (Address Space ID) and how does it reduce TLB flushing?
• How does the Linux scheduler decide when to preempt? (timer interrupt + vruntime)
• What is voluntary vs involuntary context switch? (cs vs nvcswch in /proc/PID/status)

8 Mutex vs Semaphore vs Spinlock
mutexsemaphorespinlock
Medium 84%
Synchronization Primitives
  • Mutex (Mutual Exclusion): Binary lock. Owner must release. Sleeping lock — blocked thread sleeps, woken by OS. Priority inversion risk.
  • Semaphore: Counter (0..N). Binary semaphore ≈ mutex but no ownership. Counting semaphore for resource pools (N available resources).
  • Spinlock: Busy-wait loop checking flag. No context switch. Great for very short critical sections (kernel code). Wastes CPU if held long.
  • Condition Variable: Wait + signal pattern. Used WITH mutex (monitor). Always use predicate loop (spurious wakeups).
Futex (Linux)
Fast Userspace muTEX. Fast path: atomic CAS in userspace (no syscall). Slow path (contended): syscall to sleep. Basis for pthreads mutex and Java's synchronized.

9 Copy-on-Write (COW) in fork() — how it works
copy-on-writeforkpage-table
Medium 84%
fork() without COW
Old approach: fork duplicates entire parent address space immediately. Expensive for large processes — most forked children exec() immediately, wasting the copy.
COW Optimization
After fork(), parent and child share the same physical pages (marked read-only). On first write by either process → page fault → OS copies only that page → independent copy.
fork()
  → Page tables copied (cheap)
  → Physical pages marked read-only + copy-on-write

Child writes to variable x:
  → Page fault (read-only violation)
  → OS copies page → child gets private copy
  → Child's page marked writable
  → Parent still sees original
Where COW is used
  • fork() in Unix/Linux
  • mmap(MAP_PRIVATE): shared initially, COW on write
  • Container images: layers are shared via COW (OverlayFS)
  • Redis persistence: BGSAVE forks → COW allows snapshot without blocking writes

10 Spinlock vs Mutex vs Semaphore — detailed comparison
spinlockmutexsemaphore
Hard 84%
Spinlock
Thread loops (busy-waits) until lock is free. No OS involvement for uncontended case.
Pros: Near-zero overhead for very short critical sections, no context switch.
Cons: Wastes CPU if lock held long, terrible on uniprocessor, can cause priority inversion.
Use when: Critical section <~100ns (kernel code, interrupt handlers, lock-free structures).
Mutex
Thread puts itself to sleep if lock unavailable. OS wakes it when lock released.
Pros: No CPU waste while waiting, works with long critical sections.
Cons: Context switch overhead (~1-10μs), kernel involvement.
Adaptive Mutex (Linux futex): Spin briefly, then sleep. Best of both worlds.
Semaphore
Generalized mutex: can allow N concurrent holders (counting semaphore). Binary semaphore = mutex but can be released by different thread (unlike mutex, which must be released by owner). Use for: resource pools, producer-consumer signaling.
futex (Linux fast userspace mutex)
Check lock in userspace (atomic). Only make syscall when contended (wait/wake). Foundation of pthread_mutex, Java synchronized.

11 Virtual memory and page tables
virtual-memorypagingmmu
Hard 83%
Page Replacement Algorithms
  • OPT (Optimal): Replace page that won't be used for longest time. Theoretical baseline.
  • FIFO: Evict oldest loaded page. Simple. Belady's anomaly (more frames → more faults).
  • LRU: Evict least recently used. Approximates OPT well. Expensive exact tracking.
  • Clock (LRU approximation): Circular list. Reference bit: on access set to 1, on clock hand pass clear to 0, evict when 0. Linux uses clock-PRO.
  • LFU: Evict least frequently used. Doesn't adapt to recent access pattern changes.
Working Set
Set of pages currently needed by process. If working set > available frames → thrashing (process spends more time swapping than executing). OS monitors WSS, suspends processes if needed.

13 Process scheduling — CFS (Completely Fair Scheduler) in Linux
cfsschedulervruntime
Hard 78%
CFS Algorithm
CFS maintains a virtual runtime (vruntime) per process — time the process has run, weighted by priority (nice value). Always picks the process with minimum vruntime (leftmost node in red-black tree).
vruntime Update
vruntime += actual_runtime × (NICE_0_WEIGHT / task_weight)
# Low-priority (high nice) tasks: vruntime increases faster → scheduled less
# High-priority (low nice): vruntime increases slower → scheduled more
Time Slice
No fixed time slice in CFS. Scheduling period (default 6ms) divided proportionally by weights. Minimum granularity: 0.75ms. Prevents starvation.
Priority Inheritance
When high-priority task blocks on mutex held by low-priority task → boost low-priority task's priority temporarily to prevent priority inversion (critical in RT systems).

14 Memory-mapped files (mmap) — mechanics and use cases
mmapmemory-mappedfile-io
Medium 78%
How mmap works
mmap() maps a file or device into virtual address space. OS does NOT read file immediately — uses demand paging. Reading page triggers major page fault → kernel reads from file into physical page → mapped.
mmap vs read()/write()
  • read(): Kernel copies file data → kernel buffer → user buffer. Double copy.
  • mmap(): Maps kernel page cache directly into user address space. Zero copy on access. Better for large files with random access.
Shared Memory via mmap
// Process A:
int fd = open("/tmp/shm", O_CREAT|O_RDWR, 0666);
ftruncate(fd, 4096);
void* ptr = mmap(0, 4096, PROT_READ|PROT_WRITE, MAP_SHARED, fd, 0);

// Process B: same mmap call — both map same physical pages
// Writes by A immediately visible to B
Use Cases
  • Databases: InnoDB buffer pool, SQLite, LMDB use mmap for zero-copy I/O
  • Shared memory IPC: multiple processes sharing data structures
  • Executable loading: kernel mmaps ELF segments — text, data, BSS
  • io_uring: submission/completion queues mapped into user space

15 Linux file system internals — inode, dentry, VFS, page cache
inodedentryvfs
Hard 76%
VFS (Virtual File System)
Abstraction layer. Provides uniform API (open/read/write/close) for all file systems (ext4, XFS, btrfs, tmpfs, NFS, procfs). Drivers implement VFS operations.
Inode
Fixed-size metadata structure for each file:
  • File type, permissions, owner (UID/GID)
  • Size, timestamps (atime/mtime/ctime)
  • Block pointers (direct, indirect, double-indirect)
  • Link count (hard links)
  • NOT: file name (stored in directory entry)
Dentry (Directory Entry)
Cache of name → inode mappings. Path lookup: /home/user/file.txt → traverse dentries: root dentry → home dentry → user dentry → file inode. Dentry cache (dcache) avoids repeated disk lookups.
Page Cache
Buffer for file data. read() → kernel checks page cache first. On miss: read from disk, cache page. write() → write to page cache (writeback=async), or writethrough, or direct I/O (O_DIRECT bypasses cache). free command: 'cached' = page cache using RAM (can be reclaimed).

16 Copy-on-write (CoW)
cowforklazy-copy
Medium 75%
Copy-on-Write — How it works
On fork(), parent and child share the same physical pages. Pages are marked read-only. On first write by either process → page fault → kernel copies the page → each gets their own copy. Non-written pages are shared forever.
Benefits
  • fork() is extremely fast (O(1) instead of O(n) for copying all pages)
  • Shell: fork() then exec() — exec replaces address space, no copy needed at all
  • Redis BGSAVE: fork to get a consistent snapshot. CoW means writes during save only copy modified pages
  • Kubernetes container image layers: read-only base + CoW overlay for each container

18 NUMA (Non-Uniform Memory Access) — impact on performance
numamemory-localitycpu-affinity
Hard 72%
NUMA Architecture
Multi-socket servers: each CPU socket has its own local DRAM. Accessing local memory: fast (~80ns). Accessing remote memory (other socket's DRAM): slow (~150ns, ~2x). OS/hardware provides NUMA node topology.
NUMA Problems
  • Thread on node 0 allocates, migrated to node 1 → remote memory access
  • False sharing: different threads on different NUMA nodes modify same cache line → cache coherence traffic
  • Memory-intensive apps (databases, ML) severely impacted
Mitigation
  • numactl --membind=0 --cpubind=0 ./app — bind to single NUMA node
  • numactl --interleave=all — round-robin allocation across nodes (reduces hot-spots)
  • NUMA-aware memory allocators (jemalloc, tcmalloc have NUMA support)
  • Database NUMA awareness: MySQL/PostgreSQL can bind buffer pool per node
Cache Hierarchy
L1 (4 cycles, 32KB per core) → L2 (12 cycles, 256KB per core) → L3 (30-50 cycles, shared per socket, 32-64MB) → DRAM (~200 cycles) → Remote DRAM (~400 cycles) → NVMe SSD (~100μs) → HDD (~10ms).
