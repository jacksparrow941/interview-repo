1 Race condition — what and how to prevent
race-conditionmutexatomic
Easy 92%
Race Condition
Two or more threads access shared mutable state without synchronization. Result depends on thread scheduling (timing). Non-deterministic bugs.
Examples and Fixes
# Python — unsafe counter (GIL helps here but not in C/Java)
counter = 0
def increment():
    global counter
    counter += 1  # NOT atomic in Java/C: read, add, write — 3 ops

# Java fix:
AtomicInteger counter = new AtomicInteger(0);
counter.incrementAndGet();  // single atomic CAS instruction

# OR use synchronized:
synchronized void increment() { counter++; }

# Go: use atomic
var counter int64
atomic.AddInt64(&counter, 1)
# OR: go run -race ./...  (built-in race detector)
Detection
Go: go run -race. Java: ThreadSanitizer (TSAN) in native, FindBugs for JVM. Helgrind (Valgrind) for C/C++.
Follow-ups
• What is a benign data race and when is it acceptable?
• How does the Go race detector work? (shadow memory — 4 words per memory location tracking last 4 accesses)
• What is the difference between a race condition and a data race?

6 Thread pool sizing — how to determine?
thread-poolcpu-boundio-bound
Medium 80%
Thread Pool Sizing Formula
  • CPU-bound tasks: N_threads = N_CPU (or N+1 to hide memory stall)
  • I/O-bound tasks: N = N_CPU × (1 + wait_time / service_time)
    Example: DB query takes 50ms, processing takes 5ms → ratio = 10 → 10 × N_CPU threads
  • Mixed: Use two pools — CPU pool + IO pool. Don't block CPU pool with IO.
Queue Sizing
  • Bounded queue = backpressure. If queue full → caller blocked or rejected (CallerRunsPolicy).
  • Unbounded queue (LinkedBlockingQueue): can OOM. Never use in production without monitoring.
  • Queue length monitoring: if growing → pool too small or tasks too slow → alert.
Follow-ups
• What is Little's Law and how does it apply to thread pool sizing?
• How do virtual threads (Java 21 Loom) change pool sizing strategy? (pool not needed — 1 VT per request)
• How do you detect thread pool exhaustion in production?

8 Compare-and-swap (CAS) operation
casatomiclock-free
Medium 78%
Compare-And-Swap (CAS)
Atomic hardware instruction: CAS(addr, expected, new) → bool. If *addr == expected, atomically set *addr = new and return true. Else return false.
Lock-free Stack with CAS
class LockFreeStack<T> {
    AtomicReference<Node<T>> top = new AtomicReference<>();
    
    void push(T val) {
        Node<T> newNode = new Node<>(val);
        do {
            newNode.next = top.get();  // read current top
        } while (!top.compareAndSet(newNode.next, newNode));  // retry if top changed
    }
    
    T pop() {
        Node<T> old;
        do {
            old = top.get();
            if (old == null) return null;
        } while (!top.compareAndSet(old, old.next));
        return old.val;
    }
}
CAS vs Mutex
CAS: no sleep, no context switch, no kernel call. But: retry loop wastes CPU under high contention. Best for: low contention, short operations. Use mutex for long critical sections.

9 Java concurrency — synchronized vs ReentrantLock, ExecutorService for trade processing
synchronizedreentrantlockexecutorservice
Hard 78%
synchronized vs ReentrantLock
// synchronized — simple, no tryLock
public synchronized void updatePosition(String book, BigDecimal delta) {
    positions.merge(book, delta, BigDecimal::add);
}

// ReentrantReadWriteLock — multiple readers OR one writer
ReentrantReadWriteLock rwl = new ReentrantReadWriteLock();
public void update(String book, BigDecimal d) {
    rwl.writeLock().lock();
    try { positions.merge(book, d, BigDecimal::add); }
    finally { rwl.writeLock().unlock(); }
}
public BigDecimal get(String book) {
    rwl.readLock().lock();
    try { return positions.getOrDefault(book, ZERO); }
    finally { rwl.readLock().unlock(); }
}
Trade Processing ThreadPool
ExecutorService pool = new ThreadPoolExecutor(
    10, 50, 60L, SECONDS,
    new ArrayBlockingQueue<>(10000),   // bounded = backpressure
    new ThreadFactoryBuilder().setNameFormat("trade-worker-%d").build(),
    new CallerRunsPolicy());            // natural backpressure on caller

pool.submit(() -> tradeService.process(event));
Avoiding Deadlock
  • Always acquire locks in the same order across all threads
  • Use tryLock(timeout) to avoid indefinite blocking
  • Prefer ConcurrentHashMap + atomic ops over coarse synchronized

10 ABA problem in lock-free programming
abacasversion-counter
Hard 72%
ABA Problem
Thread 1 reads value A. Thread 2 changes A→B→A. Thread 1 does CAS: sees A, thinks nothing changed — succeeds. But the state HAS changed (e.g., a node was removed and re-inserted in a lock-free list).
Solution — Tagged Pointers
// 64-bit pointer: high bits = ABA counter (version)
struct TaggedPointer {
    Node* ptr;
    uint64_t tag;  // monotonically increasing
};

// CAS on BOTH ptr and tag:
expected = { nodeA, 5 };
if (CAS(&head, expected, { nodeB, 6 })) { /* won */ }
// Even if ptr went A→B→A, tag goes 5→6→7 — never same tagged value
Alternative: Hazard Pointers
Before accessing a node, register its pointer in per-thread hazard pointer array. Reclaimer checks all hazard pointers before freeing memory. Used in folly::ConcurrentLinkedList.
