1 Smart pointers: unique_ptr, shared_ptr, weak_ptr
smart-pointersraiimemory
Medium 92%
Smart Pointer Types
  • unique_ptr: Exclusive ownership. Non-copyable, move-only. Zero overhead vs raw pointer. Use as default for heap objects.
  • shared_ptr: Shared ownership via reference count. Thread-safe refcount (atomic). Overhead: control block allocation + atomic ops.
  • weak_ptr: Non-owning observer of shared_ptr. Breaks circular references. Must lock() before use — returns shared_ptr (empty if object deleted).
Code Examples
auto up = std::make_unique<Widget>();     // unique_ptr
auto sp = std::make_shared<Widget>();     // shared_ptr (single allocation)
std::weak_ptr<Widget> wp = sp;             // weak_ptr
if (auto spt = wp.lock()) { spt->use(); } // safe access

// Cycle breaking:
struct Node { std::weak_ptr<Node> parent; std::shared_ptr<Node> children; };
Custom Deleter
unique_ptr<FILE, decltype(&fclose)> f(fopen("x","r"), fclose);
Follow-ups
• Why prefer make_shared over shared_ptr(new T)? (single allocation for object+control block)
• What is enable_shared_from_this and when do you need it?
• When would you still use a raw pointer?

2 Implement a thread-safe LRU Cache in C++
lruthread-safeunordered_map
Hard 88%
Design
std::list (doubly-linked list) + std::unordered_map<K, list::iterator>.
Most recently used at front. On access: move node to front. On eviction: remove from back.
Implementation
template<typename K, typename V>
class LRUCache {
    int cap;
    std::list<std::pair<K,V>> lst;
    std::unordered_map<K, decltype(lst.begin())> mp;
    std::mutex mu;
public:
    LRUCache(int cap) : cap(cap) {}

    std::optional<V> get(const K& key) {
        std::lock_guard lock(mu);
        auto it = mp.find(key);
        if (it == mp.end()) return {};
        lst.splice(lst.begin(), lst, it->second);  // move to front
        return it->second->second;
    }

    void put(const K& key, V val) {
        std::lock_guard lock(mu);
        if (mp.count(key)) lst.erase(mp[key]);
        else if ((int)lst.size() == cap) {
            mp.erase(lst.back().first);
            lst.pop_back();
        }
        lst.push_front({key, val});
        mp[key] = lst.begin();
    }
};
Complexity
get/put: O(1) average. Thread-safe with a single mutex. For higher concurrency: use reader-writer lock or shard by key hash.
Follow-ups
• How would you implement LFU instead?
• How would you shard the cache for better concurrency?
• What is RCU (Read-Copy-Update) for lock-free reads?

3 Explain RAII
raiiexceptionsresource
Medium 87%
RAII — Resource Acquisition Is Initialization
Resource lifetime is bound to object lifetime. Acquire in constructor, release in destructor. Guarantees release even on exceptions (stack unwinding calls destructors).
Examples
class FileGuard {
    FILE* f;
public:
    explicit FileGuard(const char* path) : f(fopen(path, "r")) {
        if (!f) throw std::runtime_error("open failed");
    }
    ~FileGuard() { if (f) fclose(f); }  // always runs
    // Delete copy; use move only
    FileGuard(const FileGuard&) = delete;
    FileGuard& operator=(const FileGuard&) = delete;
};

// RAII wrappers: lock_guard, unique_lock, ifstream, unique_ptr, jthread
Why it matters
Without RAII: every error path must manually release resources → leak-prone. With RAII: destructor always called → exception-safe, leak-free.

4 Move semantics and rvalue references
move-semanticsrvalueperformance
Hard 86%
Move Semantics
C++11 introduces rvalue references (T&&). Move constructor/assignment steals resources from temporaries instead of copying. Enables zero-cost transfer of ownership.
Rvalue References
class Buffer {
    int* data; size_t size;
public:
    Buffer(Buffer&& other) noexcept :  // move constructor
        data(other.data), size(other.size) {
        other.data = nullptr; other.size = 0;  // leave source valid but empty
    }
    Buffer& operator=(Buffer&& other) noexcept {
        if (this != &other) {
            delete[] data;          // free own resource
            data = other.data; size = other.size;
            other.data = nullptr; other.size = 0;
        } return *this;
    }
};

void process(Buffer&& b) { Buffer local = std::move(b); } // move, not copy
Buffer create() { Buffer b(1024); return b; }  // NRVO: no copy at all!
std::move vs std::forward
std::move(x): unconditional cast to rvalue. std::forward<T>(x): conditional — preserves lvalue/rvalue category in template (perfect forwarding).

5 How does std::vector grow?
vectoramortizedreallocation
Easy 86%
std::vector Growth
When capacity is exceeded, vector allocates new buffer (typically 2× current capacity), moves all elements, then deallocates old buffer. Amortized O(1) push_back.
Internals
struct vector_internals {
    T* begin;    // pointer to first element
    T* end;      // pointer past last element (size)
    T* cap_end;  // pointer to end of allocation (capacity)
};
// size() = end - begin
// capacity() = cap_end - begin
Important APIs
  • reserve(n): pre-allocate without changing size. Prevents reallocations.
  • shrink_to_fit(): release excess capacity (non-binding request).
  • emplace_back(args): construct in-place, avoids extra copy/move.

T&& in a template (deduced context) is a universal/forwarding reference, not an rvalue reference. With T=int&, T&& collapses to int& (reference collapsing).

8 How does vtable work?
vtablevirtualpolymorphism
Hard 82%
vtable Mechanism
For each class with virtual functions, compiler generates a vtable — a static array of function pointers. Each object has a hidden vptr pointing to its class's vtable (set in constructor).
Virtual Dispatch
class Animal {
public:
    virtual void sound() { printf("..."); }
    virtual ~Animal() {}
};
// vtable_Animal = { &Animal::sound, &Animal::~Animal }

class Dog : public Animal {
    void sound() override { printf("Bark"); }
};
// vtable_Dog = { &Dog::sound, &Dog::~Dog }

Animal* a = new Dog();
a->sound();  // a->vptr -> vtable_Dog[0] = Dog::sound() → "Bark"
Costs
  • Memory: 1 vptr per object (8 bytes on 64-bit)
  • Time: extra pointer indirection per call (cache miss possible)
  • No inlining: compiler can't inline virtual calls (mostly)
  • Final keyword: hints compiler to devirtualize

9 Rule of 0, Rule of 3, Rule of 5 — explain with examples
rule-of-3rule-of-5move
Hard 82%
Rule of 3 (pre-C++11)
If you define any of: destructor, copy constructor, copy assignment, you should define all three. (Managing raw resource → need custom copy + destructor)
Rule of 5 (C++11+)
Add move constructor + move assignment. Without them, moves fall back to copies (expensive).
class Buffer {
    char* data; size_t sz;
public:
    Buffer(size_t n) : data(new char[n]), sz(n) {}
    ~Buffer() { delete[] data; }               // 1: destructor
    Buffer(const Buffer& o)                   // 2: copy ctor
        : data(new char[o.sz]), sz(o.sz) { memcpy(data,o.data,sz); }
    Buffer& operator=(const Buffer& o) {       // 3: copy assign
        if(this==&o) return *this;
        delete[] data; sz=o.sz; data=new char[sz]; memcpy(data,o.data,sz); return *this;
    }
    Buffer(Buffer&& o) noexcept                // 4: move ctor
        : data(o.data), sz(o.sz) { o.data=nullptr; o.sz=0; }
    Buffer& operator=(Buffer&& o) noexcept {   // 5: move assign
        if(this==&o) return *this;
        delete[] data; data=o.data; sz=o.sz; o.data=nullptr; return *this;
    }
};
Rule of 0
Best practice: design classes to own no raw resources. Use RAII wrappers (unique_ptr, vector, string). Then you need ZERO custom special members — compiler generates correct ones.

• What is the copy-and-swap idiom?

10 std::atomic and memory ordering
atomicmemory-orderinglock-free
Hard 80%
std::atomic
Guarantees atomic read-modify-write without undefined behavior. No data races. Hardware CAS instructions.
Memory Ordering
  • relaxed: No ordering guarantees. Only atomicity. Cheapest. Use for counters.
  • acquire: All subsequent reads see writes before the release on same var. (read fence)
  • release: All preceding writes visible to acquire on same var. (write fence)
  • acq_rel: Both acquire + release. Used for RMW operations.
  • seq_cst: Total global order. Strongest guarantee. Default for atomic ops.
Usage
std::atomic<int> counter{0};
counter.fetch_add(1, std::memory_order_relaxed);  // fast counter

std::atomic<bool> ready{false};
// Thread 1:
data = 42;
ready.store(true, std::memory_order_release);
// Thread 2:
while (!ready.load(std::memory_order_acquire));  // guaranteed to see data=42
Follow-ups
• What is a data race vs a race condition?
• When is relaxed ordering safe?
• What is the ABA problem in CAS-based algorithms?

13 std::condition_variable — producer-consumer pattern
condition-variablemutexnotify
Medium 78%
Full Producer-Consumer
#include <mutex>
#include <condition_variable>
#include <queue>

std::mutex mtx;
std::condition_variable cv;
std::queue<int> q;
bool done = false;

void producer() {
    for(int i=0;i<10;i++) {
        std::unique_lock lock(mtx);
        q.push(i);
        cv.notify_one();  // wake one consumer
    }
    { std::lock_guard lock(mtx); done=true; }
    cv.notify_all();
}

void consumer() {
    while(true) {
        std::unique_lock lock(mtx);
        cv.wait(lock, []{ return !q.empty() || done; });  // predicate prevents spurious wakeup
        while(!q.empty()) { process(q.front()); q.pop(); }
        if(done) break;
    }
}
Spurious Wakeups
Always use cv.wait(lock, predicate) — without predicate, spurious wakeups cause bugs. Equivalent to: while(!pred()) cv.wait(lock);
notify_one vs notify_all
notify_one: wake 1 waiter (use for single-consumer or rotating consumers). notify_all: wake all waiters (use for broadcast events like shutdown).

14 unique_lock vs lock_guard vs scoped_lock
lock-guardunique-lockscoped-lock
Medium 76%
lock_guard (C++11)
Simplest RAII wrapper. Locks on construction, unlocks on destruction. Cannot be unlocked/relocked. Cannot be moved. Use when you need a simple lock for a scope.
std::lock_guard<std::mutex> lock(m);
unique_lock (C++11)
More flexible. Can unlock/relock, deferred locking, timed locking. Required for condition_variable.
std::unique_lock lock(m, std::defer_lock);  // don't lock yet
lock.lock();        // lock later
lock.unlock();      // unlock early
bool got = lock.try_lock_for(100ms);  // timed
scoped_lock (C++17)
Locks multiple mutexes atomically without deadlock (uses deadlock-free algorithm). Replaces std::lock(m1,m2) + lock_guard(adopt) pattern.
std::scoped_lock lock(m1, m2, m3); // all or nothing
When to use
  • lock_guard: simple scope lock, no condition_variable
  • unique_lock: condition_variable, deferred/timed locking, early unlock
  • scoped_lock: locking 2+ mutexes, avoiding deadlock
Follow-ups
• How does scoped_lock prevent deadlock? (std::lock uses try-lock backoff)

28 Implement a lock-free stack using CAS
lock-freecasatomic
Hard 72%
Design
Use std::atomic<Node*> for head. CAS in a loop for push/pop.
Implementation
template<typename T>
class LockFreeStack {
    struct Node { T data; Node* next; };
    std::atomic<Node*> head{nullptr};
public:
    void push(T val) {
        Node* n = new Node{std::move(val), nullptr};
        n->next = head.load(std::memory_order_relaxed);
        while (!head.compare_exchange_weak(n->next, n,
               std::memory_order_release, std::memory_order_relaxed));
    }
    std::optional<T> pop() {
        Node* old = head.load(std::memory_order_acquire);
        while (old && !head.compare_exchange_weak(old, old->next,
               std::memory_order_release, std::memory_order_acquire));
        if (!old) return {};
        T val = std::move(old->data);
        // DANGER: delete old  ← ABA problem / use-after-free with concurrent pops
        return val;
    }
};
ABA Problem
After loading old = A, another thread pops A, pushes B, pushes A back. CAS sees A and succeeds but old->next points to stale node. Fix: tagged pointers (version counter) or hazard pointers for safe memory reclamation.

38 What is EBO (Empty Base Optimization)?
eboempty-basesizeof
Hard 64%
The Problem
C++ requires each complete object to have a unique address, so empty classes have size >= 1. But storing an empty allocator/comparator as a member wastes space:
struct Allocator {};  // sizeof = 1
struct MyContainer {
    Allocator alloc;  // 1 byte (but likely padded to 8!)
    size_t size;      // 8 bytes
    // Total: 16 bytes instead of 8
};

Inherit from the empty base instead of storing as member:
struct MyContainer : private Allocator {
    size_t size;  // Allocator takes 0 bytes here!
    // Total: 8 bytes
};
C++20 [[no_unique_address]]

struct MyContainer {
    [[no_unique_address]] Allocator alloc;
    size_t size;  // 8 bytes total if Allocator is empty
};

Processes vs Threads

2 I/O models — blocking, non-blocking, I/O multiplexing, async, signals

5 I/O Models
  • Blocking I/O: Thread blocks until data ready. Simple. Scales poorly (1 thread/connection).
  • Non-blocking I/O: Returns EAGAIN immediately if no data. Polling loop wastes CPU.
  • I/O Multiplexing (select/poll/epoll): One thread watches many fds. Blocks on select, wakes when any fd ready. Efficient for many connections.
  • Signal-driven I/O (SIGIO): Signal when data ready. Complex, rarely used.
  • Async I/O (AIO, io_uring): Kernel does I/O, notifies completion. True async. io_uring (Linux 5.1+): submission/completion queues in shared memory, no syscall overhead.
epoll vs select vs poll
  • select: fd_set bitmap, max 1024 fds, O(n) scan, copies fd_set each call
  • poll: array of pollfd, no 1024 limit, still O(n) scan
  • epoll: O(1) event notification. Register fds once (epoll_ctl), wait (epoll_wait) returns only ready fds. Kernel red-black tree for O(log n) add/remove. Level-triggered or edge-triggered modes.
io_uring (Modern Linux)
Fully async: app submits I/O requests to SQ ring, kernel processes, posts completions to CQ ring. Zero syscall on fast path. Used in: Tokio (Rust), QEMU, PostgreSQL, Nginx.

3 Virtual memory — paging, page tables, TLB
virtual-memorypagingpage-table
Hard 88%
Virtual Memory
Each process has its own virtual address space (e.g., 0 to 2^48 on 64-bit). OS maps virtual pages → physical frames via page table. Allows: isolation between processes, overcommit memory, memory-mapped files, copy-on-write.
Multi-level Page Tables
64-bit systems use 4-level (x86-64) or 5-level page tables to reduce space. Each level is a 4KB page of 512 8-byte entries. Virtual address split:
[sign ext | L4 (9) | L3 (9) | L2 (9) | L1 (9) | Offset (12)]
TLB (Translation Lookaside Buffer)
Hardware cache for recent virtual→physical translations. TLB hit: 1 cycle. TLB miss: walk page table (several cycles + memory accesses). TLB flushed on context switch (unless ASID used). Huge pages (2MB/1GB) reduce TLB misses.
Page Fault
  • Minor: Page in memory but not mapped (memory-mapped file, copy-on-write) → map it
  • Major: Page not in memory → read from disk (swap). Expensive (~ms)
  • Invalid: Access to unmapped address → SIGSEGV

4 Deadlock — conditions, prevention, avoidance, detection
deadlockcoffmanbanker
Hard 88%
Coffman's Four Necessary Conditions
  • Mutual Exclusion: Resources not sharable
  • Hold and Wait: Process holds resource while waiting for another
  • No Preemption: Resources can't be forcibly taken
  • Circular Wait: T1→waits for T2→waits for T3→waits for T1
Breaking any one prevents deadlock.
Prevention
  • Eliminate Hold and Wait: Request all resources at once before starting
  • Allow Preemption: If waiting, release held resources (costly)
  • Eliminate Circular Wait: Global ordering of resources (always lock in same order)
Avoidance — Banker's Algorithm
Each process declares max resource claim. System checks if granting a request leaves system in safe state (all processes can complete). If unsafe → deny and wait. Used in theory; impractical for dynamic systems.
Detection and Recovery
Allow deadlocks to occur. Periodically run deadlock detector (wait-for graph cycle detection). Recovery: kill one victim process, or preempt + rollback resources.

12 Process scheduling — CFS (Completely Fair Scheduler) in Linux

Hard 78%
CFS Algorithm
CFS maintains a virtual runtime (vruntime) per process — time the process has run, weighted by priority (nice value). Always picks the process with minimum vruntime (leftmost node in red-black tree).
vruntime Update
vruntime += actual_runtime × (NICE_0_WEIGHT / task_weight)
# Low-priority (high nice) tasks: vruntime increases faster → scheduled less
# High-priority (low nice): vruntime increases slower → scheduled more
Time Slice
No fixed time slice in CFS. Scheduling period (default 6ms) divided proportionally by weights. Minimum granularity: 0.75ms. Prevents starvation.
Priority Inheritance
When high-priority task blocks on mutex held by low-priority task → boost low-priority task's priority temporarily to prevent priority inversion (critical in RT systems).

Multi-socket servers: each CPU socket has its own local DRAM. Accessing local memory: fast (~80ns). Accessing remote memory (other socket's DRAM): slow (~150ns, ~2x). OS/hardware provides NUMA node topology.
NUMA Problems
  • Thread on node 0 allocates, migrated to node 1 → remote memory access
  • False sharing: different threads on different NUMA nodes modify same cache line → cache coherence traffic
  • Memory-intensive apps (databases, ML) severely impacted
Mitigation
  • numactl --membind=0 --cpubind=0 ./app — bind to single NUMA node
  • numactl --interleave=all — round-robin allocation across nodes (reduces hot-spots)
  • NUMA-aware memory allocators (jemalloc, tcmalloc have NUMA support)
  • Database NUMA awareness: MySQL/PostgreSQL can bind buffer pool per node
Cache Hierarchy
L1 (4 cycles, 32KB per core) → L2 (12 cycles, 256KB per core) → L3 (30-50 cycles, shared per socket, 32-64MB) → DRAM (~200 cycles) → Remote DRAM (~400 cycles) → NVMe SSD (~100μs) → HDD (~10ms).

Race Condition
Two or more threads access shared mutable state without synchronization. Result depends on thread scheduling (timing). Non-deterministic bugs.
Examples and Fixes
# Python — unsafe counter (GIL helps here but not in C/Java)
counter = 0
def increment():
    global counter
    counter += 1  # NOT atomic in Java/C: read, add, write — 3 ops

# Java fix:
AtomicInteger counter = new AtomicInteger(0);
counter.incrementAndGet();  // single atomic CAS instruction

# OR use synchronized:
synchronized void increment() { counter++; }

# Go: use atomic
var counter int64
atomic.AddInt64(&counter, 1)
# OR: go run -race ./...  (built-in race detector)
Detection
Go: go run -race. Java: ThreadSanitizer (TSAN) in native, FindBugs for JVM. Helgrind (Valgrind) for C/C++.

3 Compare-and-swap (CAS) operation
casatomiclock-free
Medium 78%
Compare-And-Swap (CAS)
Atomic hardware instruction: CAS(addr, expected, new) → bool. If *addr == expected, atomically set *addr = new and return true. Else return false.
Lock-free Stack with CAS
class LockFreeStack<T> {
    AtomicReference<Node<T>> top = new AtomicReference<>();
    
    void push(T val) {
        Node<T> newNode = new Node<>(val);
        do {
            newNode.next = top.get();  // read current top
        } while (!top.compareAndSet(newNode.next, newNode));  // retry if top changed
    }
    
    T pop() {
        Node<T> old;
        do {
            old = top.get();
            if (old == null) return null;
        } while (!top.compareAndSet(old, old.next));
        return old.val;
    }
}
CAS vs Mutex
CAS: no sleep, no context switch, no kernel call. But: retry loop wastes CPU under high contention. Best for: low contention, short operations. Use mutex for long critical sections.

4 ABA problem in lock-free programming
abacasversion-counter
Hard 72%
ABA Problem
Thread 1 reads value A. Thread 2 changes A→B→A. Thread 1 does CAS: sees A, thinks nothing changed — succeeds. But the state HAS changed (e.g., a node was removed and re-inserted in a lock-free list).
Solution — Tagged Pointers
// 64-bit pointer: high bits = ABA counter (version)
struct TaggedPointer {
    Node* ptr;
    uint64_t tag;  // monotonically increasing
};

// CAS on BOTH ptr and tag:
expected = { nodeA, 5 };
if (CAS(&head, expected, { nodeB, 6 })) { /* won */ }
// Even if ptr went A→B→A, tag goes 5→6→7 — never same tagged value
Alternative: Hazard Pointers
Before accessing a node, register its pointer in per-thread hazard pointer array. Reclaimer checks all hazard pointers before freeing memory. Used in folly::ConcurrentLinkedList.

1 How does CPU caching work and why does it matter for performance?
cpu-cachecache-linefalse-sharing
Hard 74%
Memory Hierarchy
L1 cache:  ~32KB per core,   ~1ns  latency
L2 cache: ~256KB per core,   ~4ns  latency
L3 cache:   ~8MB shared,     ~40ns latency
RAM:        ~16-64GB,       ~100ns latency
SSD NVMe:              ~100μs latency
HDD:                    ~10ms latency
Cache Lines
Data loaded in 64-byte cache lines. Accessing one byte loads entire 64-byte block. Sequential access (arrays) → excellent cache utilization. Random access (linked lists) → cache miss per node.
False Sharing
# Two threads update different variables in same cache line:
# Thread 1 updates counter_a, Thread 2 updates counter_b
# If they're adjacent in memory → same cache line → cache coherence traffic
# Core 1 invalidates Core 2's cache line on every write → performance degrades!

# Fix: padding
struct PaddedCounter {
    alignas(64) std::atomic<int64_t> value;  // 64-byte aligned
    char padding[64 - sizeof(std::atomic<int64_t>)];  // fill rest of cache line
};
Practical Impact
  • Array of structs vs Struct of arrays (SOA): SOA = better cache usage for column-wise processing
  • Cache-oblivious algorithms (recursive divide) beat sequential for large matrices
  • Go: sync.Mutex padded to avoid false sharing with adjacent data
