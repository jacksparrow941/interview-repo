2 Design a distributed key-value store (like Redis/DynamoDB)
distributed-kvconsistent-hashingreplication
Hard 88%
Architecture
Client → Load Balancer → Coordinator Node
                            ↓ (consistent hash ring)
                        Partition 0 → Replica A, B, C
                        Partition 1 → Replica D, E, F
                        ...
Data Distribution
Consistent hashing: keys mapped to ring. Each node owns a range. Virtual nodes (vnodes): each physical node = 100-200 vnodes for even distribution. Adding/removing node: only adjacent vnodes affected.
Replication
Each key replicated to N nodes (typically N=3, DynamoDB style). Coordinator writes to all N. Quorum: W=2 (write), R=2 (read) → W+R>N = strong consistency. W=1, R=1 → eventual consistency, highest availability.
Conflict Resolution
Vector clocks track causality. On divergent versions (network partition): return both to client (DynamoDB shopping cart), or last-write-wins (LWW) for simpler cases.
Storage Engine
LSM Tree (write-optimized): MemTable → immutable SSTable → compaction. B+Tree (read-optimized): InnoDB, LMDB. LSM preferred for KV stores: fast sequential writes, compaction amortizes cost.

1 Goroutines vs OS threads
goroutinesthreadsgmp
Medium 92%
Goroutines vs OS Threads
  • Goroutine: ~2KB initial stack (grows dynamically to hundreds of MB if needed). M:N threading — N goroutines multiplexed onto M OS threads. Scheduled by Go runtime.
  • OS Thread: ~1MB stack (fixed at creation). 1:1 with kernel thread. Expensive context switch (μs).
  • Can run millions of goroutines. Thousands of OS threads = OOM.
GMP Model (brief)
  • G: Goroutine (the task)
  • M: OS thread (the runner)
  • P: Processor/scheduler context (GOMAXPROCS Ps). Each P has local run queue.
  • When G blocks on syscall → M + G detach from P → P gets another M to continue work
Follow-ups
• What is goroutine stack growth mechanism? (segmented stacks → copying stacks since Go 1.4)
• What is GOMAXPROCS and when would you change it?
• How do goroutines avoid the 10K thread problem?

2 Channels: buffered vs unbuffered
channelsbufferedsynchronous
Medium 90%
Buffered vs Unbuffered Channels
  • Unbuffered make(chan T): Sender blocks until receiver is ready. Receiver blocks until sender sends. Strict synchronization point (rendezvous).
  • Buffered make(chan T, n): Sender blocks only when buffer full. Receiver blocks only when buffer empty. Decouples send and receive timing.
Usage Patterns
// Semaphore (limit concurrency to 5):
sem := make(chan struct{}, 5)
for _, job := range jobs {
    sem <- struct{}{}  // acquire
    go func(j Job) {
        defer func() { <-sem }()  // release
        process(j)
    }(job)
}

// Signal (done channel):
done := make(chan struct{})
go func() { defer close(done); doWork() }()
<-done  // wait for completion
Closing Channels
Only sender should close. Closing a closed channel panics. Reading from closed channel returns zero value + false: v, ok := <-ch; if !ok { // closed }

6 defer, panic, recover — full semantics and patterns
deferpanicrecover
Medium 88%
defer
Deferred call runs when surrounding function returns (normal or panic). Arguments evaluated immediately; call deferred. LIFO order.
func processFile(path string) (err error) {
    f, err := os.Open(path)
    if err != nil { return }
    defer f.Close()           // runs even on early return/panic
    defer func() {            // named return: modify err on cleanup failure
        if cerr := f.Close(); cerr != nil && err == nil {
            err = cerr
        }
    }()
    // ... process f
    return
}
panic / recover
func safeDiv(a, b int) (result int, err error) {
    defer func() {
        if r := recover(); r != nil {     // recover() catches panic
            err = fmt.Errorf("panic: %v", r)
        }
    }()
    return a / b, nil  // panics if b==0
}

// recover() returns nil if no panic, or the panic value
// ONLY works inside a deferred function
Rules
  • recover() only stops a panic if called directly from a deferred function
  • Panic unwinds stack, running deferred functions
  • Use panic for truly unrecoverable states (programming errors), not business logic
  • HTTP handlers should recover panics to avoid crashing the whole server
Follow-ups
• What is the difference between os.Exit and panic?
• Can you defer a method call? (yes)
• What is the defer overhead? (small but measurable in hot loops)

8 goroutine leak — how to detect and prevent
goroutine-leakcontextdone-channel
Medium 86%
What is a goroutine leak
Goroutines that are started but never terminate. They consume memory (~2KB initial stack, can grow), CPU for scheduling, and keep referenced objects alive.
Common Causes
  • Blocked channel read/write with no one to unblock
  • Not passing/checking context.Context
  • Infinite loops without exit condition
  • Forgotten goroutines in tests
Prevention Pattern
func worker(ctx context.Context, jobs <-chan Job) {
    for {
        select {
        case <-ctx.Done():
            return  // clean exit
        case job, ok := <-jobs:
            if !ok { return }  // channel closed
            process(job)
        }
    }
}
Detection with pprof
import _ "net/http/pprof"
// curl http://localhost:6060/debug/pprof/goroutine?debug=2
// Lists all goroutine stacks — look for blocked goroutines

// In tests: goleak

    defer goleak.VerifyNone(t)  // fails if goroutines leak
    ...
}

Interface internals
A Go interface value has two words: (type, pointer). An interface is nil only when both type and pointer are nil.
The Nil Trap
type MyError struct{ msg string }
func (e *MyError) Error() string { return e.msg }

func getError() error {
    var err *MyError = nil
    return err  // TRAP: returns (type=*MyError, ptr=nil) — NOT nil interface!
}

if err := getError(); err != nil {
    fmt.Println("This prints!")  // Bug!
}

// Fix: return nil explicitly
func getError() error {
    var err *MyError
    if conditionFailed { return err }  // still buggy
    return nil  // correct
}
Type Assertions & Switches
var i interface{} = "hello"

// Type assertion
s, ok := i.(string)  // ok=true, s="hello"

// Type switch

}

11 Channel patterns — fan-out, fan-in, pipeline, done channel
channelspipelinefan-out
Hard 84%
Pipeline
func gen(nums ...int) <-chan int {
    out := make(chan int)
    go func() {
        defer close(out)
        for _, n := range nums { out <- n }
    }()
    return out
}
func sq(in <-chan int) <-chan int {
    out := make(chan int)
    go func() { defer close(out); for n := range in { out <- n*n } }()
    return out
}
// Usage: for v := range sq(sq(gen(2,3,4))) { fmt.Println(v) }
Fan-Out
func fanOut(in <-chan int, workers int) []<-chan int {
    outs := make([]<-chan int, workers)
    for i := range outs {
        outs[i] = sq(in)  // each worker reads from same input
    }
    return outs
}
Fan-In (Merge)
func merge(cs ...<-chan int) <-chan int {
    var wg sync.WaitGroup
    out := make(chan int)
    output := func(c <-chan int) {
        defer wg.Done()
        for v := range c { out <- v }
    }
    wg.Add(len(cs))
    for _, c := range cs { go output(c) }
    go func() { wg.Wait(); close(out) }()
    return out
}
Done Channel (Cancellation)
func sq(done <-chan struct{}, in <-chan int) <-chan int {
    out := make(chan int)
    go func() {
        defer close(out)
        for n := range in {
            select {
            case out <- n*n:
            case <-done: return  // cancelled
            }
        }
    }()
    return out
}
// Use context.Context in production instead of done channel

15 Functional options pattern in Go
functional-optionsdesign-patternconfiguration
Medium 80%
Problem
How to provide optional configuration to a constructor without breaking API as options grow? Config structs are verbose; many parameters are messy.
Functional Options Pattern
type Server struct {
    host    string
    port    int
    timeout time.Duration
    maxConn int
}

type Option func(*Server)

func WithPort(p int) Option      { return func(s *Server) { s.port = p } }
func WithTimeout(d time.Duration) Option { return func(s *Server) { s.timeout = d } }
func WithMaxConn(n int) Option   { return func(s *Server) { s.maxConn = n } }

func NewServer(host string, opts ...Option) *Server {
    s := &Server{host: host, port: 8080, timeout: 30*time.Second, maxConn: 100}  // defaults
    for _, opt := range opts { opt(s) }
    return s
}

// Usage (clean, readable, extensible):
srv := NewServer("localhost",
    WithPort(9090),
    WithTimeout(5*time.Second),
)
Advantages
  • Backward compatible — add new options without changing signature
  • Self-documenting call sites
  • Easy to set sensible defaults
  • Options are first-class values — can be composed, stored, passed around

17 sync.Once, sync.Map — when and how to use
sync-oncesync-mapconcurrent
Medium 78%
sync.Once
Guarantees a function runs exactly once, even if called concurrently. Perfect for lazy initialization.
sync.Once Example
var (
    instance *DB
    once     sync.Once
)

func GetDB() *DB {
    once.Do(func() {
        instance = connectDB()  // runs exactly once
    })
    return instance
}
// Thread-safe singleton. Once completes, all goroutines see instance.
sync.Map
Concurrent map without external locking. Optimized for two use cases: (1) write once, read many; (2) different goroutines write different keys.
sync.Map Example
var m sync.Map
m.Store("key", "value")
v, ok := m.Load("key")

m.Range(func(k, v any) bool {
    fmt.Println(k, v)
    return true  // continue iteration

  • sync.Map: better for high-read, diverse-keys workloads

1 JWT — structure, validation, vulnerabilities
jwtrs256alg-none
Medium 90%
JWT Structure
header.payload.signature

Header: {"alg": "RS256", "typ": "JWT"}
Payload: {"sub": "user123", "role": "admin", "exp": 1700000000, "iat": 1699996400}
Signature: RS256(base64url(header)+"."+base64url(payload), privateKey)

Verification: RS256(received_header+"."+payload, publicKey) == received_signature
Critical Vulnerabilities
  • alg:none attack: Attacker sets alg to 'none', removes signature. Old libraries accept it. Fix: whitelist allowed algorithms explicitly — NEVER accept alg from token.

  • Missing expiry check: Always validate exp claim.
  • Sensitive data in payload: JWT is base64 NOT encrypted. Anyone can decode it.
Best Practices
  • Use RS256 (asymmetric): private key signs, public key verifies — microservices can verify without shared secret
  • Short access token TTL (15min) + refresh token (7-30 days in HttpOnly cookie)
  • Store refresh tokens server-side for revocation capability
  • Refresh token rotation: each use issues a new refresh token

1 Design a Sliding Window Rate Limiter (code-level)

Sliding Window Log Algorithm
Store timestamps of each request in a sorted set. On each request: remove old entries, count remaining, allow if below limit.
In-Memory Thread-Safe
class SlidingWindowRateLimiter {
    private final int maxRequests;
    private final long windowMs;
    private final Map<String, Deque<Long>> windows = new ConcurrentHashMap<>();

    boolean allow(String clientId) {
        long now = System.currentTimeMillis();
        long cutoff = now - windowMs;

        Deque<Long> timestamps = windows.computeIfAbsent(clientId, k -> new ArrayDeque<>());

        synchronized (timestamps) {
            // Remove expired
            while (!timestamps.isEmpty() && timestamps.peekFirst() <= cutoff)
                timestamps.pollFirst();
            if (timestamps.size() >= maxRequests) return false;
            timestamps.addLast(now);
            return true;
        }
    }
}

2 Design a Snowflake-style Distributed ID Generator

Hard 88%
Twitter Snowflake Structure (64-bit)
| 1 bit sign | 41 bits timestamp (ms) | 10 bits machine ID | 12 bits sequence |

- Timestamp: ms since custom epoch (Jan 1, 2010)
  → supports 2^41 ms ≈ 69 years
- Machine ID: 10 bits → 1024 machines
- Sequence: 12 bits → 4096 IDs/ms/machine

Total: ~4 million IDs/second per machine, globally unique, sortable!
Implementation
class SnowflakeIdGenerator {
    private final long EPOCH = 1288834974657L;  // Nov 4, 2010
    private final long MACHINE_ID;              // 0-1023
    private long sequence = 0;
    private long lastTs = -1;

    synchronized long nextId() {
        long ts = System.currentTimeMillis();
        if (ts == lastTs) {
            sequence = (sequence + 1) & 0xFFF;  // 12-bit mask
            if (sequence == 0) ts = waitNextMs(lastTs);  // sequence exhausted
        } else { sequence = 0; }
        lastTs = ts;
        return ((ts - EPOCH) << 22) | (MACHINE_ID << 12) | sequence;
    }

    private long waitNextMs(long ts) {
        long now = System.currentTimeMillis();
        while (now <= ts) now = System.currentTimeMillis();
        return now;
    }
}

3 Design a Bloom Filter
bloom-filterprobabilisticbitarray
Hard 82%
What is a Bloom Filter
Space-efficient probabilistic data structure. Answers: 'definitely not in set' OR 'probably in set'. No false negatives, configurable false positive rate.
Implementation
class BloomFilter {
    private final BitSet bits;
    private final int numBits;
    private final int numHashFunctions;

    BloomFilter(int expectedItems, double falsePositiveRate) {
        // Optimal bit count: -n*ln(p) / (ln2)^2
        numBits = (int)(-expectedItems * Math.log(falsePositiveRate) / (Math.log(2)*Math.log(2)));
        // Optimal hash count: (m/n) * ln2
        numHashFunctions = (int)(numBits * 1.0 / expectedItems * Math.log(2));
        bits = new BitSet(numBits);
    }

    void add(String item) {
        for (int i = 0; i < numHashFunctions; i++)
            bits.set(Math.abs(hash(item, i)) % numBits);
    }

    boolean mightContain(String item) {
        for (int i = 0; i < numHashFunctions; i++)
            if (!bits.get(Math.abs(hash(item, i)) % numBits)) return false;  // Definitely not
        return true;  // Probably yes
    }

    private int hash(String s, int seed) {
        return Objects.hash(s, seed);
    }
}

11 TCP flow control (receive window) vs congestion control (CWND)

Hard 82%
Flow Control (Receiver-side)
Prevents sender from overwhelming receiver's buffer.
Receiver advertises receive window (rwnd) in ACK headers. Sender must not have more than rwnd unacknowledged bytes in flight.
Congestion Control (Network-side)
Prevents sender from overwhelming the network (routers/links).
Sender maintains congestion window (cwnd). Effective window = min(cwnd, rwnd).
Congestion Control Phases
  • Slow Start: cwnd=1 MSS → doubles each RTT until ssthresh or packet loss
  • Congestion Avoidance: cwnd grows +1 MSS per RTT (linear)
  • Fast Retransmit: 3 duplicate ACKs → retransmit lost segment immediately (don't wait for timeout)
  • Fast Recovery (CUBIC, BBR): On loss: ssthresh = cwnd/2, cwnd = ssthresh (not back to 1)
BBR (Google)
Model-based congestion control. Estimates bottleneck bandwidth and RTT. Less reactive to loss, better for high-bandwidth long-distance links. Used in YouTube, cloud networking.

Answer
Docker images are built as read-only layers stacked using a Union Filesystem (OverlayFS/AUFS). Each RUN, COPY, ADD instruction in a Dockerfile creates a new layer.

When a container runs, Docker adds a thin read-write layer on top (Copy-on-Write). Writes go to the container layer; reads search layers bottom-up.
Dockerfile Layer Example
FROM ubuntu:22.04          # Layer 1: base OS
RUN apt-get install -y java # Layer 2: java install
COPY app.jar /app/          # Layer 3: app binary
CMD ["java", "-jar", "/app/app.jar"]  # metadata only
Optimization Tips
  • Order layers from least to most frequently changing
  • Combine RUN commands to reduce layer count
  • Use .dockerignore to exclude build artifacts
  • Use multi-stage builds to discard build-time layers

4 ConfigMaps vs Secrets in Kubernetes
kubernetesconfigmapsecrets
Easy 88%
ConfigMap
Stores non-sensitive configuration as key-value pairs. Mounted as environment variables or volume files. Plain text in etcd.
Secret
Stores sensitive data (passwords, tokens, TLS certs). Base64-encoded in etcd (NOT encrypted by default). Enable encryption at rest with EncryptionConfiguration. Types: Opaque, kubernetes.io/tls, kubernetes.io/dockerconfigjson, etc.
Usage
# Mount as env
env:
- name: DB_PASSWORD
  valueFrom:
    secretKeyRef:
      name: db-secret
      key: password

# Mount as volume
volumeMounts:
- name: config
  mountPath: /etc/config
volumes:
- name: config
  configMap:
    name: app-config
Best Practices
  • Use external secret managers: HashiCorp Vault, AWS Secrets Manager with External Secrets Operator
  • Never bake secrets into Docker images
  • RBAC: restrict Secret read access to specific ServiceAccounts

5 Git internals — rebase vs merge, when to use each
gitrebasemerge
Medium 88%
Merge
Creates a merge commit that ties two branches together. Preserves full history including branch structure. Safe for shared branches — never rewrites history.
git checkout main
git merge feature/login
# Creates commit: Merge branch 'feature/login'
Rebase
Replays commits from one branch onto another. Creates linear history. Rewrites commit SHAs — never rebase shared/public branches.
git checkout feature/login
git rebase main
# Moves feature commits on top of latest main
When to use
  • Merge: Merging feature into main (preserves context). Shared branches.
  • Rebase: Keeping feature branch up-to-date with main. Clean PR history. git pull --rebase.
  • Squash merge: Combine all feature commits into 1 clean commit on main.
Interactive Rebase
git rebase -i HEAD~3
# Options: pick, squash, fixup, reword, drop

2 Explain transformer architecture and attention mechanism
transformerattentionself-attention
Hard 82%
Self-Attention Mechanism
Input: sequence of tokens → embeddings (d_model=768 for BERT-base)

For each token, compute:
  Q (query) = embedding × W_Q
  K (key)   = embedding × W_K
  V (value) = embedding × W_V

Attention weights = softmax(Q × K^T / sqrt(d_k))
Output = Attention_weights × V

# Each token attends to all other tokens — captures long-range dependencies
# Multi-head: run h parallel attention heads, concat, project
Transformer Architecture
  • Encoder (BERT): Bidirectional. Sees full context. Used for classification, NER, embeddings.
  • Decoder (GPT): Autoregressive. Each token attends only to previous tokens (causal mask). Used for generation.
  • Encoder-Decoder (T5, BART): Seq2seq tasks: translation, summarization, QA.
Why Transformers replaced RNNs
  • RNN: sequential computation → no parallelism. Gradient vanishing for long sequences.
  • Transformer: parallel over all positions. Self-attention = O(n²d) but parallelizable on GPU.
  • Position encoding: sinusoidal or learned — since attention is permutation-invariant, positional info must be added explicitly.
